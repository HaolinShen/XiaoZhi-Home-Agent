## 零、必须先修正的三处口径（否则面试自曝）

`resume-project-highlights.md` 与 `README.md` 里有三处表述，和 `gap-analysis.md` 的**实测结论**冲突。
面试官顺着问一层就到，必须改口径或先修代码。

### 0.1 不要无条件写「敏感动作执行前需用户确认」

**实测事实**（gap-analysis §1.2/1.3/1.4）：

| 路径 | unlock 的实际审批状态 |
|---|---|
| ReAct 主路 `control_lock(unlock)` | ✅ risk=high，必须批准 |
| **MCP server 入口** `control_lock_mcp(unlock)` | ❌ 零拦截（`src/mcp/server.py:205`，全文 grep `interrupt` 零命中） |
| **Planner 路径** | ❌ risk 硬编码 medium，且 CLI 只渲染**模型自述的 description**——用户看到「准备门口环境」，实际执行 unlock |
| **等效单设备操作**（light+ac+curtain 替代 activate_scene） | ❌ 零审批（审批绑工具名，不绑效果） |

**安全的写法**（把范围限定住，并把洞变成认知）：

> 实现基于 `interrupt()` 的人在回路审批：图内高危动作（门锁解锁）与批量场景执行前中断等待确认，
> 审批状态随 Checkpoint 持久化、进程重启后可恢复；并通过自查识别出该机制的边界——
> 审批实现在编排层，任何绕过编排层的入口（MCP server）自动绕过审批，
> 且审批锚点是「工具名」而非「物理效果」。

这个写法**比原版强**：它同时展示了「实现了 HITL」和「知道 HITL 的架构陷阱」。

### 0.2 不要写「Send 动态并行加速多设备查询」

**实测事实**（gap-analysis §3.2）：`src/agent/parallel.py:55` 的分支只做 `registry.get()` 内存字典查找，
零 IO、零 LLM，fan-out + reducer 的**调度开销大于直接循环**。且 `src/` 除 `src/mcp/` 外**零 `async def`**，
图只用 `invoke`/`stream`，不用 `ainvoke`/`astream`。

被问「并行带来多少加速」时无法回答。**安全写法**：

> 用 LangGraph `Send` 实现动态 fan-out 子图与结果聚合 reducer（多设备查询按设备数动态展开）；
> 已识别当前分支是纯内存查表、并行收益为负，真正需要并行的是外部 MCP 服务发现与调用（当前串行）。

### 0.3 记忆检索的量化指标目前没有实测数据

不要写「token 降低 X%」「命中率 Y%」。没有实验支撑的数字是面试事故。
`docs/resume-memory-system.md` 第三节有补实验的方案，补完再写数字。

**注意别把两个「检索」混成一个**：**说明书**检索在 013 已经有 63 条 golden 评测集和
一整组实测数字（见 Q23–Q25），那些数字可以放心讲；这里说的是**记忆**模块的检索，
它的打分器是手工加权线性排序，至今没有对照实验。被问到时明确区分开，别让面试官
以为你在拿一个模块的数字给另一个模块背书。

## 一、开场必问（准备到能背）

### Q1「介绍一下这个项目」

**不要**按功能列表讲（支持 8 种设备、5 个场景……）。按**问题—设计**讲，30 秒版：

> 这是一个用 LangGraph 做的智能家居 Agent。我更愿意把它描述成「如何把不可靠的 LLM 组件工程化」的练习：
> 规划的成败不由模型自述、由真实设备状态验证；身份不由模型提供、由运行时配置注入，
> 模型在语法上无法伪造；设备的工具面不由九处手写副本维护、由单一能力声明自动派生，
> 一致性靠生成式测试钉住。最近一轮把说明书排障的检索换成了 BM25 加向量的混合检索，
> 并且建了一套 63 条的召回评测集做配置对照——所以这个模块我能给出实测数字。
> 13 轮迭代、约一万八千行代码、264 项测试，每轮迭代都有设计文档。
> 我还做了一轮红队式自查，实测出四个安全与质量缺陷，写在 `gap-analysis.md` 里。

最后一句是**钩子**，主动把面试官引向你准备最充分的战场（§5）。

### Q2「为什么用 LangGraph，不用 LangChain AgentExecutor / 不自己写 while 循环」

答题要点，三个只有 LangGraph 给的东西：

1. **条件边 = 显式状态机**。`planning_status` 驱动 planner→executor→verifier→replan 的流转，
   分支条件是我写的代码，不是模型的自然语言判断。AgentExecutor 只有「调工具 / 结束」二元循环，
   表达不了「验证失败后按错误类型分流到重试或重规划」。
2. **Checkpoint + `interrupt()`**。人在回路审批需要「在图中间暂停、持久化、进程重启后从断点恢复」。
   自己写循环要自己实现状态序列化。
3. **`Send` 动态 fan-out**。运行时才知道要展开几个分支。

**追问「那 LangGraph 的代价是什么」**：State 是全局单点，字段会膨胀（我的 State 有 20+ 字段）；
调试要靠 stream 事件而不是断点；框架版本升级 API 变动大。

### Q3「你的 State 设计成什么样，为什么」

- `messages` 用 `Annotated[list, add_messages]` reducer —— 并行分支写同一字段时才不会互相覆盖，
  这是 fan-in 能工作的前提。
- 业务字段分三类：**本轮可信上下文**（`active_room_id` / `active_device_id`，由 `sync_context` 落定）、
  **状态机字段**（`planning_status` / `problem_type` / 重试计数）、**检索结果**（`memory_context`）。
- **追问「State 太大怎么办」**：诚实答——我的 State 确实膨胀了，20+ 字段里状态机相关的六七个
  其实应该收成一个子对象。这是我知道但没重构的技术债。

## 二、架构决策（区分度最高的一层）

### Q4「Planner 路径和 ReAct 路径怎么选？为什么不全走 Planner」

- 判断在 `should_use_planner()`（`src/agent/heuristics.py`）：**纯正则** —— ≥2 个动作词
  且（≥2 类设备 或 出现连接词）。命中预定义场景关键词一律不走 Planner。
- 为什么不全用 Planner：单步任务（「开灯」）走 Planner 是三次 LLM 调用换一次的效果，
  延迟和成本都翻倍，且 Planner 的结构化输出可能失败。
- **为什么用正则不用 LLM 判断**（这是加分答案）：路由判断在**每一轮请求的关键路径上**，
  用 LLM 等于给每轮加一次调用的延迟和一个失败点；而且正则**可测、确定**，
  264 个测试里这条分支的行为是钉死的。**知道什么时候不该用模型，是 Agent 工程的成熟标志。**

### Q5「Verifier 怎么验证？为什么不让 LLM 判断成功没成功」

- `verify_step()` 读**设备注册中心的真实状态**跟 `expected_state` 比对。
- 为什么不问 LLM：**LLM 会把工具返回的报错文案复述成「已完成」**。这不是假设，
  是 LLM 作为文本续写器的固有行为——它的目标是生成合理文本，不是核对事实。
  真实设备状态是唯一的 ground truth。
- **追问「那 expected_state 从哪来」**：从能力声明 `CAPABILITIES` 派生
  （`expected_state_for_step()`），不是模型给的——否则模型可以「自己定义成功标准」，
  验证就成了同义反复。

### Q6「执行失败怎么处理」（必问，答好了很亮）

按 `problem_type` **分流**，不是无脑重试：

| problem_type | 处理 | 理由 |
|---|---|---|
| `unsupported_action` / `device_not_found` | **跳过重试，直接 replan** | 确定性错误，同样参数重放不可能成功，重试是纯浪费 |
| `tool_error` / `state_mismatch` | 消耗 `max_step_retries` | 可能是瞬时问题 |

replan 时 `planning_failure_feedback` 回喂**合法 action 列表 + 设备清单**，
避免模型在不存在的动作上打转。

**一句话升华**：重试预算是资源，不是仪式。

### Q7「Planner 为什么用 `with_structured_output` 而不是 `bind_tools`」（细节区分度极高）

- Planner 要的是**一份完整计划**（`ExecutionPlan`），不是「调一个工具」。
  `bind_tools` 的语义是让模型选一次工具调用。
- **关键副作用**：走 `with_structured_output` 时，**工具的 docstring 到不了模型面前**。
  所以合法 action 必须由 `planning.py:TOOL_ACTIONS` 显式拼进 prompt。
  我踩过这个坑——漏喂词表时，Planner 生成的第一版计划**稳定失败且不报错**。
- 能讲清这一点 = 你真的理解两条工具调用链路的差异，而不是照抄教程。

### Q8「意图路由为什么要确定性兜底」（有具体案例，务必讲）

`classify_intent()` 在确定性信号命中 `automation_management` 时**直接返回，不问 LLM**。

**真实 bug 案例**：「明天早上 6 点回家前把空调打开」——模型会把它分类成预定义的
**「回家模式」场景**，于是**立刻**执行回家场景，而不是创建一条明天 6 点的定时例程。
用户第二天早上没有空调，而且当晚家里空调白开一夜。

解法是硬约束短路：识别到「未来时间信号 + 设备动作信号」同时出现，直接走自动化路径，不给模型误判的机会。

**升华**：这是「模型分类 + 确定性兜底」的分层决策——模型负责模糊语义，规则负责不可妥协的边界。

### Q9「多智能体是怎么做的？为什么不用 Supervisor handoff」

- 6 个角色（device / scene / memory / automation / knowledge / chat）各自 `bind_tools` **一个工具子集**，
  `agent_node` 按 `delegated_agent` 选用。本质是**工具集隔离**，不是多进程/多图。
- 为什么这样：工具太多会让单个模型的选择准确率下降（schema 挤占上下文、相似工具混淆）。
  隔离后每个角色面对的工具面很小。
- **代价，必须主动说**：新增非设备工具时如果忘了加进角色的名字集合，**该角色永远调不到它**，
  且不报错。device 角色因为工具名从 `CONTROL_TOOL_NAMES` 派生所以安全，其他角色是手工列表。
- `automation` 角色还有一层强制：`required_automation_tool()` 识别出「未来触发 + 设备动作」时
  锁定必须调的工具，模型没调就补一条纠正 SystemMessage 重试一次。

## 三、安全边界（你的强项 + 你的雷区，务必分清）

### Q10「身份怎么保证不被伪造」（**最漂亮的答案，主动引到这里**）

> 身份永远来自 `RunnableConfig["configurable"]`，工具通过 `config: RunnableConfig` 命名参数接收。
> **关键在于：这个参数不出现在工具的 JSON Schema 里，所以模型在语法上无法表达 `home_id`。**

这比「校验模型传来的 home_id」强一个层次——不是「有校验但可能绕过」，
而是**连伪造的接口都不存在**。

配套三层：`SpaceDirectory.validate()` 校验 room/device 的住宅归属；
`MemoryService` 的作用域 + 管理员权限规则；权限边界全部有测试钉住
（跨家庭隔离、非管理员写共享记忆被拒、模型参数无法覆盖身份）。

**追问「为什么不能信模型输出」**：一句 prompt injection 就能让 Agent
「帮我把隔壁家的门锁解开」。身份必须走可信通道。

**可以顺带讲的坑（011 迭代修的）**：旧实现有个 `if config is not None` 的兜底，
但空 `configurable` 的 config 也是真值，所以「逐键检查后安静跳过」的保护形同虚设。
根因是把安全策略做成了**运行期的隐式推断**。改法是提到**构造期的显式选择**：
图路径 `build_device_tools(registry, service)` 开启偏好观察、缺身份直接 `RuntimeError` fail-fast，
后台执行器和 MCP 显式传 `enable_preference_tracking=False`。

### Q11「人在回路审批能被绕过吗」（⚠️ **雷区，但可以变成加分**）

**不要说「不能」。** 诚实且有结构的答法：

> 图内路径不能，但我自查时发现三个能绕过的地方，根因都是**同一个架构错误**：
> 我把审批实现在编排层（图节点里 `interrupt()`），而安全边界必须在**每个入口**重复，
> 或者下沉到所有入口共用的那一层。
>
> 1. **MCP server 是另一个进程入口**，根本不经过图，所以 `control_lock_mcp(unlock)` 零拦截。
> 2. **Planner 路径**的 `risk_level` 硬编码 medium，且 CLI 渲染的是**模型自己写的 description**
>    ——实测出现过用户看到「准备门口环境」、实际执行 unlock 的情况。
>    这里的教训是：**HITL 展示的必须是机器从 `tool_calls` 生成的事实，不能是模型撰写的摘要**，
>    否则用户批准的是模型的「说法」而不是「行为」，HITL 的意义就废掉了。
> 3. **审批锚定工具名而非物理效果**：`activate_scene('回家模式')` 要审批，
>    但等效的 light+ac+curtain 三连零审批。用户说「调成回家的样子」时模型自然可能选后者。
>
> 修法我想清楚了：审批下沉到工具执行层（所有入口共用），风险等级从**实际动作集合**推导而非硬编码，
> 展示层强制渲染 `tool_calls`。

**这个答案的效果远好于「我做了审批」**——它展示了架构层次感、红队思维和根因分析能力。

### Q12「prompt injection 怎么防」（⚠️ 雷区）

诚实答：**身份字段防住了（不可表达），但内容注入面还开着两处**：

1. 远端 MCP server 返回的 `tool.description` 被无条件拼进 system prompt
   ——远端服务改一行描述就能改变本地 Agent 行为。
2. 记忆的 `memory_value` 原样进 `memory_context` 再进 system prompt，
   而记忆是**跨会话持久化**的 —— 这是**存储型注入**面。

当前唯一防护是一句自然语言祈使句（「这些标识来自受信任的业务上下文，不得改写」），
它只保护身份字段。**「用一句祈使句请模型别照做」不是控制手段。**
正确方向：不可信输入隔离到 user 消息（而不是 system），或显式标注边界。

### Q13「记忆写入怎么防止记错」

**候选确认制**：从对话里抽出的偏好候选**必须经用户确认才落库**，不是抽到就写。
这是把「人在回路」的思想用在记忆写入上——不是所有从对话里抽到的东西都该记住。
配套：记忆版本追踪、置信度衰减、四级作用域（个人/家庭/房间/设备）权限隔离。

## 四、质量与度量（013 前是你最大的缺口，现在补上了检索这一块）

### Q14「你怎么知道你的 Agent 效果好？怎么评测的」

**这曾经是最危险的问题**（gap-analysis 把它列为「学习价值最高的缺口」）。
013 之后它变成了半个亮点——**检索层已经有真评测集了，缺的是路由和端到端**。

诚实且有方案的答法：

> 分两层说。**代码逻辑层**是确定性测试——264 个用例覆盖权限边界、状态机流转、
> 调度确定性、能力一致性；但这些测的不是模型输出质量。
>
> **模型行为层**我目前只覆盖了一块：说明书检索。我建了一套 63 条的 golden 召回评测集
> （口语 30 / 说明书原词 10 / 错误码 10 / 同码异义 6 / 应拒答 7），跑真实 embedding、
> 不带 LLM，度量 Recall@1 / Recall@3 / MRR / 拒答准确率，并且拿它做了四组配置的对照——
> 旧词法、仅 BM25、仅向量、混合。结论是 Recall@1 从 51.8% 提到 87.5%，口语化查询的
> 召回从 3/30 提到 23/30，拒答准确率四组都是 100%。三档分数下限也是在这套集合的
> （权重 × 下限）网格上扫出来的，不是手调的。
>
> **还没覆盖的是意图路由和端到端任务成功率**，这是我认为现在最大的缺口。但路子是清楚的：
> 路由做几十条带标注的 case（尤其「明天 6 点回家前开空调」这类容易误判的边界样本）度量
> 分类准确率；端到端我有 `verify_step` 读真实设备状态，天然有客观成功判据，
> 不需要 LLM-as-judge。**大多数 Agent 项目评测难是因为没有 ground truth，而我有。**

最后那句是**把缺口转成亮点**的关键；中间那段是证明「我不是只会说该怎么评测，我真跑过」。

**如果面试官接着问「那你评测里发现过什么问题吗」——直接切到 Q26**，那是这一轮最好的故事。

### Q15「不调真实 LLM 怎么测？测试怎么写的」（强项）

- `patch("src.agent.graph.build_llm", return_value=FakeLLM())`，FakeLLM 实现
  `bind_tools` / `invoke`，走 Planner 的再实现 `with_structured_output`。
- settings 用 `types.SimpleNamespace` 手搓，绕开 `Settings` 的 API Key 校验
  → **全离线、无 API Key 可跑**。
- **调度测试的确定性**（这条很亮）：`RoutineScheduler.tick(now=...)` 支持**注入虚拟时间**，
  所以定时逻辑测试**不睡眠、完全确定**。很多人做定时任务测试靠 `sleep`，又慢又 flaky。
- 测的是**权限边界、数据库状态、设备真实副作用、Checkpoint 恢复、事件顺序**，
  **不是返回文本**——文本断言在 LLM 项目里必然 flaky。

**可以讲的踩坑**：Windows 上 `TemporaryDirectory.cleanup()` 遇到未关闭的 SQLite 连接会抛
`PermissionError [WinError 32]`，断言通过也判失败。而且 unittest 先跑完整个 `tearDown()`
才轮到 `doCleanups()`，所以 cleanup 注册顺序有坑——正确做法是在 `setUp` 里
`addCleanup(temp_dir.cleanup)`，靠 LIFO 保证它最后执行。

### Q16「LLM 调用失败了怎么办」（⚠️ 弱项）

诚实：**当前韧性不足** —— 有 3 处裸 `invoke`，结构化输出没有兜底
（`with_structured_output` 失败会直接抛）。只依赖 `ChatOpenAI(max_retries=2)` 的传输层重试。

有意思的是我**刻意没接** `src/middleware/interceptors.py` 里的 RetryInterceptor，理由写在文件头：
无条件 `except Exception` 会吞掉 `GraphInterrupt` 从而**破坏审批语义**；
叠加在已有 `max_retries` 上会放大无效 API Key 这类确定性错误的等待。
**保留代码 + 诚实说明为何不启用**，比删掉它更有价值。

### Q17「上下文超长怎么办」

- 三道闸门：消息数 / token / 字符上限 + 滚动摘要 + 工具结果裁剪。
- **主动说出洞**（gap §3.1）：`max_tokens=2400` 只约束**消息历史**，
  而 system prompt 本身约 2200 token、全部工具的 JSON Schema、`memory_context`
  都不在预算内。日志打 `estimated_tokens=42` 时真实请求可能是几十倍。
  **预算必须对完整请求体计数，而且要用真实 tokenizer 而非字符近似。**
- 修过的一个真 bug（gap §1.1）：裁剪会切断「`tool_calls` ↔ `ToolMessage`」的配对，
  30.8% 的裁剪产生非法消息序列 → 已加边界对齐，降到 0%。
  **教训：长度闸门不认识消息协议不变量，必须单独兜住。**

## 六、后端向 + 检索向的问题（Q20–Q22 非 LLM 岗会问；**Q23–Q26 是 LLM / 算法岗的主战场**）

### Q20「设备能力单一数据源那套，本质是什么模式」

**SSOT / schema-as-code**。原先新增一种设备要手工同步 **9 处**
（工具 if/elif、Planner 词表、`Literal` 枚举、MCP 工具……），其中两处是无法反射检查的副本，
漏改表现为「Planner 第一版计划**稳定失败且不报错**」。

收敛后 **1 处声明 + 2 处手工**：`CAPABILITIES` 是唯一数据源，
工具 Schema / 规划词表 / `PlanStep` 枚举 / `registry.find` 关键词 / 模拟器实例 /
场景集合 / 自动化工具名 / MCP 工具全部**自动派生**。
一致性由**生成式断言**（声明 ↔ 工具实现双向反射）兜底 → **漏改在测试期失败，而非运行期静默**。

- 可类比：数据库 migration、OpenAPI 生成客户端、protobuf。
- **追问「为什么不用装饰器自动注册」**：显式声明表比隐式注册**可审计、可 diff、可生成文档**；
  隐式注册的失败模式是「忘了 import 所以没注册」，更难查。
- 一句话升华：**一致性靠测试钉住，不靠 code review 的记性。**

### Q21「自动化子系统为什么不放在图里」

- 图是**对话路径**，生命周期是一次请求；例程要**跨进程持久化**、按时间触发。
  硬塞进图里会让「图」同时承担编排和调度两个职责。
- `AutomationRuntime` 组装 store / executor / scheduler / arrivals，由 `main.py` 起后台线程。
- 落 `data/automation.db`。任务按 `dedupe_key` 去重——**用 UNIQUE 索引，不是「先查再插」**，
  避开 TOCTOU 竞态（这个细节值得主动说）。
- 车辆 ETA 更新只移动**尚未执行**的任务。
- 安全下限延伸到后台：创建例程一律人工审批，自动化动作**不含门锁解锁**。

### Q22「传感器为什么是只读的？这个约束怎么保证」

传感器故意没有 `control_*` 工具，且 `PlanStep.tool_name` 的 `Literal` 不含 `read_sensor`，
`get_device_list_prompt()` 把传感器单列成只读组，场景批量操作**不能遍历所有设备**去关。

**踩过的坑**：早期场景「离家模式」遍历全部设备关闭，把人体存在传感器也关了，
表现是「Agent 说家里没人」——从现象很难联想到根因。
**教训：一个约束由多处协同保证时，任何一处遗漏都是静默失败。**

另一条：`registry.tick_environment()` 只应由 `read_sensor` 调用，
别处调用会让同一轮对话里的读数随调用次数漂移。

### Q23「RAG 是怎么做的」（013 后已经可以当强项讲）

**分三段讲：检索前、检索、检索后。**

**检索前**是**实体消解**（用户措辞 → 设备实例 → 型号，结果四态、仅唯一命中放行检索，
其余三态直接拒答、绝不退化成全库检索）。**型号的唯一数据源是设备自己的 `model` 字段**，
知识模块里不放型号映射表；设备没填 `model` 是合法的，表示「没登记说明书」，检索会拒答
而不是猜。

**检索**是 **BM25 词法通道 + 向量语义通道、加权 RRF 融合名次**（生产权重 0.5/0.5，
分词用 jieba）。关键是**错误码和型号不参与打分，走硬过滤**——理由见 Q24。
语料是 `docs/knowledge/` 下 **39 份说明书、124 个可检索小节、13 个型号，覆盖全部
10 种设备类型**。

**检索后**：排查项按「系统可自证 / 需人工」分流，可自证项直接读设备与传感器真实状态核对
（三值判定，读不到传感器就退回人工、绝不默认通过），**目前 12 条自证检查**覆盖空调、灯、
窗帘、电视、加湿器、热水器、水壶、门锁和两类传感器。答案正文由 LLM 写，但**引用块和
自动核对块由代码拼接、不经模型改写**——强制引用是结构保证，不是提示词约定。而且引用未
声明的检查 id 会让 `KnowledgeBase` 在**构造期**直接抛 `ValueError`，不容忍降级成「需人工
确认」——否则拼错一个 id 就让一条本该自动核对的检查项无声消失。

**加分句**：整条链路 `llm=None` 时仍可用（重写走确定性词表），所以单元测试不需要 API Key；
真实 embedding 只在召回评测和端到端手跑时用。

**要主动说的边界**：只核对排名第一的小节；拒答阈值的假阳性余量只有 4%（见 Q24）。
013 之前那句「检索是词法 bigram、没有语义泛化」**已经作废，别再说了**。

### Q24「纯向量指标更好，你为什么还留着 BM25」（最能体现判断力的一问）

先把数字亮出来，**承认对方是对的**：

> 诚实说，纯向量在两个指标上确实更好——Recall@3 是 94.6% 对混合的 89.3%，
> MRR 是 0.908 对 0.881。我仍然选了混合，三条理由，第三条才是决定性的。
>
> 一，把 BM25 权重清零等于把词法通道整个关掉，**embedding 服务一挂就全部拒答**；
> 混合配置下 BM25 还兜着，离线 Recall@1 也有 58.9%。
> 二，用户直接引用说明书原词时 BM25 更强，10/10 对 9/10。
> 三，**「这份说明书没讲这件事」这句话只有词法通道说得出来。** 我统计了 63 条用例的
> 余弦分布：正例中位 0.653，而「同一型号的其它症状小节」这类困难负例中位 0.568——
> 两个分布大幅重叠。也就是说**向量靠绝对余弦分不开「对的症状」和「同一台电器的另一个
> 症状」**，因为它们语义上真的很近。而「卧室空调有点响」查那台空调时，「响」和「噪音」
> 在它说明书全文里根本不存在，**BM25 返回 0**——这是唯一能触发拒答的信号。
> **拒答闸门的可靠性来自 BM25，不是来自阈值调得准。**

**顺带把错误码那条一起讲掉**（面试官几乎必接着问「那错误码怎么办」）：
错误码类四组配置都是 10/10，因为它走**硬过滤**——查询里的码必须出现在该小节，
向量根本碰不到它。理由是**E4 的语义近邻天然就是 E5、E7**，而它们讲的是完全不同的故障。
一旦把错误码降级成「相似度的一部分」，用户问 E4 会拿到 E7 的处理步骤，
**而且读起来完全通顺、完全权威**——这是最坏的一类错误。型号过滤同理。

**薄弱点主动交**：拒答用例里最高的假阳性是 0.336，阈值是 0.35，只有 4% 余量，
根因就是上面那个余弦分布重叠。

### Q25「两路结果怎么融合的？为什么不直接加权平均分数」

> 用 RRF（Reciprocal Rank Fusion），`Σ w/(k+rank)`，k 取 60。但**我只用它排名次，
> 不用它守门**——这是这块设计里我最想讲的一点。
>
> 因为 RRF 是**纯名次的**：某个通道里名次第一的条目，必然拿到该通道能给的最高分，
> **跟它到底像不像毫无关系**。一个语料里根本没有对应章节的查询，它的第一名照样是满分
> RRF。所以**拿 RRF 去套拒答阈值，拒答分支永远走不到**。
>
> 我的做法是两套分数：`rrf` 只决定名次——好处是**对量纲免疫**，BM25 是无上界的正数
> （实测真实命中一路到 30 多）、余弦是 0 到 1 且带 0.3~0.4 的基线偏移，直接加权平均
> 得先解决归一化，而 RRF 只看排序；
> 另外算一个 [0,1] 的绝对置信度，**只决定放不放行**，三档分数下限（带错误码 0 /
> 首轮 0.35 / 重写后 0.42）套在它上面。
>
> 一句话：**排序问题和守门问题需要不同性质的分数，硬用一个会让其中一个失效。**

### Q26「讲一个你踩过的坑 / 你怎么保证质量」（013 的最佳弹药）

这个故事同时回答两个问题，**优先用它**，因为它的结论有普适性。

> 013 我把验证分成三层：**单元测试**（确定性、无 API Key、向量通道注入 stub）、
> **召回评测**（真实 embedding、无 LLM、只测首轮检索）、**端到端手动跑**
> （真实 embedding + 真实 LLM + 完整主图）。**最严重的一个 bug 只有第三层抓得到。**
>
> 漏洞在查询重写的 prompt：我写的是「请判断最可能属于哪一个小节」——**强制单选**。
> 正确答案根本不在清单里时，模型必然挑一个最像的；而我的校验只检查「这个标题真实存在」，
> **存在不等于相关**。于是「卧室空调有点响」——那台空调的说明书压根没有噪音章节——
> 拿到了「蒸发器结霜」的内容，还挂上了三条引用。最讽刺的是**模型自己在答案正文里都写了
> 「说明书片段中未提及空调异响的相关信息」，系统却仍然以权威格式把引用递了出去。**
>
> 前两层为什么测不到：单元测试全部传 `llm=None`，走的是确定性词表重写；
> 召回评测刻意只测首轮检索，不带 LLM。**两层各自都是绿的，组合起来的那条真实路径没人测。**
>
> 修法是给模型一个明确的出口——「没有任何小节相符就只输出『无』，不要勉强挑一个」，
> 并且模型说「无」时**连词表兜底都不走**，因为词表只看用户措辞，不知道这个型号到底
> 有没有对应章节。
>
> 结论我写进迭代文档了：**「测试全绿」和「功能正确」之间的差距，取决于测试有没有覆盖到
> 配置的真实组合。**

**为什么这个故事好**：它不是「我忘了写校验」，是「我写了校验但校验的是错的东西」；
而且根因是**分层测试的盲区结构**，不是一次疏忽。面试官能从里面看出你会设计验证策略。
