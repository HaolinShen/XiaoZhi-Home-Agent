# 智能家居 Agent 长期记忆系统——简历说明

## 一、项目定位

本项目实现了一个面向智能家居 Agent 的工程化长期记忆系统，基于 LangGraph、SQLite 和结构化记忆模型，支持个人、家庭、房间、设备多级记忆隔离，并将短期会话记忆与跨会话长期记忆分离管理。

当前适合在简历中描述为：

> 设计并实现面向智能家居 Agent 的分层长期记忆系统，基于 LangGraph 和 SQLite 支持个人/家庭/房间/设备级记忆隔离；实现自然语言偏好候选抽取、用户确认写入、冲突合并、置信度衰减、Top-K 混合检索及记忆版本追踪，并通过自动化测试验证核心流程和权限边界。

不建议表述为“已经达到先进智能体记忆系统水平”，更准确的定位是“面向智能家居 Agent 的工程化长期记忆系统”。

## 二、简历项目描述候选

### 精简版

负责智能家居 Agent 长期记忆模块设计与实现：支持用户、家庭、房间、设备多级作用域和权限隔离；实现自然语言偏好候选抽取、用户确认后写入、记忆冲突合并、置信度衰减、Top-K 混合检索和版本历史追踪；使用 SQLite 持久化，并通过自动化测试覆盖跨家庭隔离、权限校验、候选生命周期和长对话上下文治理。

### 技术亮点版

- 设计结构化长期记忆模型，支持 `user/home/room/device` 多级作用域，基于可信 `RunnableConfig` 校验 `home_id`、`user_id`、空间和管理员权限，避免跨家庭和越权访问。
- 实现自然语言记忆候选抽取器，区分稳定偏好与临时表达；候选必须经过用户确认后才能转化为长期记忆，降低误记忆风险。
- 实现结合词项相关性、置信度、重要性、更新时间和访问次数的可解释 Top-K 混合检索，并记录记忆访问统计。
- 增加记忆版本与有效时间区间，支持用户偏好变更、历史追踪、过期和删除时的生命周期管理。
- 使用 SQLite Repository 持久化记忆、候选、冲突和版本数据，并支持旧数据库自动迁移。

## 三、需要补充的量化实验

简历和面试中尽量不要只写“支持检索”或“支持压缩”，应补充可复现实验数据。建议建立一组固定测试集，记录以下指标。

### 1. 检索与上下文效率

对比“全量记忆注入”和“Top-K 混合检索”：

- 平均注入记忆条数。
- Prompt token 数量减少比例。
- 相关记忆 Top-K 命中率。
- 无关记忆注入率。
- 单次检索耗时。

建议记录格式：

| 指标 | 全量注入 | Top-K 混合检索 | 目标结论 |
|---|---:|---:|---|
| 平均注入条数 | 待测 | 待测 | 控制上下文规模 |
| Prompt token | 待测 | 待测 | 降低模型输入成本 |
| 相关记忆命中率 | 待测 | 待测 | 保持任务相关性 |
| 无关记忆注入率 | 待测 | 待测 | 减少上下文噪声 |
| 平均检索耗时 | 待测 | 待测 | 满足交互延迟要求 |

### 2. 候选抽取质量

构造稳定偏好、临时指令、敏感推断、冲突偏好四类样本，人工标注期望结果，统计：

- 候选抽取准确率。
- 候选召回率。
- 临时表达误抽取率。
- 未确认候选自动写入率，目标应为 0。
- 用户拒绝候选比例。

### 3. 长对话治理效果

对不同轮数的会话记录：

- 压缩前消息数和 token 数。
- 压缩后消息数和 token 数。
- 摘要保留关键信息比例。
- 工具结果裁剪比例。
- Checkpoint 数据增长情况。

### 4. 安全边界验证

至少保留以下自动化测试结果：

- 不同 `home_id` 的数据隔离。
- 不同用户的个人记忆隔离。
- 非管理员写入家庭共享记忆被拒绝。
- 错误房间或设备归属被拒绝。
- 模型参数无法覆盖可信请求身份。

## 四、系统架构图

建议在简历项目介绍或面试材料中配一张如下架构图：

```text
┌──────────────────────┐
│      用户自然语言     │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│ 可信请求上下文校验     │
│ home/user/room/device │
└──────────┬───────────┘
           │
     ┌─────┴─────┐
     ▼           ▼
┌───────────┐  ┌────────────────┐
│候选抽取器  │  │混合记忆检索器   │
│只生成候选  │  │Top-K 注入 Agent │
└─────┬─────┘  └───────┬────────┘
      │                │
      ▼                ▼
┌───────────┐  ┌────────────────┐
│待确认候选  │  │LangGraph Agent │
│确认/拒绝   │  │设备工具调用     │
└─────┬─────┘  └───────┬────────┘
      │                │
      └────────┬───────┘
               ▼
┌────────────────────────────┐
│ MemoryService               │
│ 权限/冲突/置信度/生命周期    │
└──────────────┬─────────────┘
               ▼
┌────────────────────────────┐
│ SQLite Repository           │
│ memories                    │
│ preference_candidates       │
│ memory_versions             │
│ memory_conflicts            │
└────────────────────────────┘
```

### 架构图讲解顺序

1. 请求首先经过可信身份和空间上下文校验。
2. 自然语言抽取器只产生候选，不直接写入长期记忆。
3. 当前问题通过混合检索召回最相关的 Top-K 记忆，注入 LangGraph Agent。
4. Agent 根据当前指令调用设备工具或记忆管理工具。
5. MemoryService 统一处理权限、冲突、置信度、版本和生命周期。
6. SQLite Repository 负责持久化和跨版本数据库迁移。

## 五、面试中需要解释的关键取舍

### 为什么没有直接引入向量数据库？

当前记忆规模较小，结构化过滤和可解释排序已经足够；先不增加 Embedding、向量数据库和额外运维依赖。系统保留了向量检索评估接口，达到规模阈值后可以在混合排序前增加向量召回层。

### 为什么候选必须确认后才能写入？

设备控制和自然语言中的一次性表达不一定代表稳定偏好。先生成候选、再由用户确认，可以降低误记忆、敏感推断和错误个性化的风险。

### 如何防止不同家庭之间的记忆泄漏？

所有 Repository 查询都限定 `home_id`；个人记忆还限定 `user_id`；房间和设备通过 `SpaceDirectory` 校验归属；共享范围写入要求管理员权限。

### 记忆冲突时为什么保留版本？

用户偏好可能随时间变化，直接覆盖会丢失历史。版本和有效时间可以回答“当前偏好是什么”和“过去曾经是什么”，也便于回滚和审计。

### Top-K 的排序依据是什么？

当前使用可解释的加权评分：词项相关性、置信度、重要性、更新时间和访问次数。这样可以控制上下文规模，也便于通过实验调整权重。

### 如何证明记忆系统真的有效？

通过固定样本集对比全量注入和 Top-K 检索，统计命中率、无关记忆注入率、Prompt token、检索延迟、候选抽取准确率和权限测试结果。
