## 二、这个项目真正的主线：一套"不信任 LLM 输出"的完整谱系

我通读代码后的核心判断：**这个项目最值钱的不是任何单个模块，而是一条贯穿始终、
且在每个交接面上手法都不同的主线**——LLM 的每一个输出都被当作不可信输入，
系统在每一处都做了收窄。

大多数候选人的 Agent 项目只有一处防护（通常是"加了个校验"）。这个项目有七处，
**而且七处的收窄手法各不相同**——这才是难以伪造的深度信号：

| # | 不可信的东西 | 收窄手法 | 代码位置 |
|---|---|---|---|
| 1 | 身份（`home_id`/`user_id`） | **从 schema 里删除**——用 `config: RunnableConfig` 命名参数接收，该参数不进 JSON Schema，模型在语法上无法表达 | `tools/*.py` 的 `_identity()` |
| 2 | 工具名 | **枚举**——`PlanStep.tool_name` 是 `Literal[tuple(...)]`，进 structured output 的 JSON Schema enum，在**生成时**就被约束 | `planning.py:81` |
| 3 | 计划规模 | **有界性**——`steps` 限定 `min_length=2, max_length=8`，pydantic 拒绝 + `planner_node` 再截断一次 | `planning.py:90`, `graph.py:404` |
| 4 | 步骤编号 | **忽略并重算**——`normalize_step_ids` 无条件重排，不用模型给的 `step_id` | `planning.py:92` |
| 5 | 参数值 | **显式失败**——`brightness="很亮"` 抛 `InvalidPlanArgument` → 变 `preparation_error` → 直接 replan | `capabilities.py:123` |
| 6 | 执行结果 | **外部 ground truth 复核**——`verify_step` 读注册中心真实设备状态比对 `expected_state` | `planning.py:197` |
| 7 | 最终叙述 | **把叙述权收回**——`planning_finalize_node` / `clarification_node` 返回硬编码文案 | `graph.py:596,620` |

第 5 和第 7 是我认为**最被低估**的两个，也是最好的面试弹药：

**第 5 的三选一**（`capabilities.py:123` 的注释原文思路）：模型写出 `brightness="很亮"` 时
有三条路——裸 `int()` 抛 ValueError **掀翻整张图**；静默套默认值把"调到很亮"**悄悄执行成
"调到 50%"再报告成功**；或者显式失败并把合法区间回喂给模型。项目选了第三条。
**能说出"静默降级是三个选项里最坏的那个"，比说"我做了参数校验"高一个层次。**

**第 7 的叙述权**：绝大多数 Agent 项目让模型总结执行结果，于是失败被复述成"已完成"。
这个项目把"最终告诉用户什么"从模型手里拿走了——`planning_finalize_node` 按
`planning_status` 和成功计数拼出确定性文案。**它的效果是：系统不可能对用户谎报成功。**

## 三、六个可辩护的技术点

每个点给出：写什么、为什么稀缺、追问会到哪里、答到什么深度算够。

### 3.1 面向 LLM 的错误消息设计 ★ 我认为这是全项目最独特的一点

**没人这么写简历，但这是"真做过 Agent"和"跟着教程搭过 Agent"的分水岭。**

代码事实：
- `_unsupported_action()`（`planning.py:162`）把**合法值列表**拼进错误消息
- `verifier_node`（`graph.py:581`）在 `device_not_found` 时追加**完整设备清单** +
  "device_name 必须与设备名称逐字一致（不要添加'的''那台'等修饰）"
- 注释写明动机：否则"模型只能凭常识反推正确写法，弱一点的模型可能改成
  close/disable 又错一轮，白白耗掉重新规划额度"

**洞察一句话**：在 Agent 系统里，错误消息不是给人看的日志，**是给模型看的 prompt**；
错误消息的信息量直接决定自愈的收敛速度。

**简历写法**：
> 将失败反馈设计为面向模型的输入而非日志：动作不合法时回喂合法值列表、
> 设备名解析失败时回喂完整设备清单与命名约束，使重规划在一轮内收敛，
> 而不是让模型凭常识反复试错耗尽重试额度。

**追问路径**：「为什么不直接把工具 docstring 给它？」→ 因为 Planner 走
`with_structured_output(ExecutionPlan)` 而不是 `bind_tools`，**工具 docstring 一个字都到不了
模型面前**，合法值必须显式拼进 prompt（`planning.py:42-46` 的注释就是这个坑的记录）。
这一层答出来，面试官会知道你理解两条工具调用链路的本质差异。

### 3.2 Planner–Executor–Verifier 是显式状态机，且 Planner 输入有界

**写法**：
> 以 `planning_status` 字段驱动全部条件边，实现 Planner→审批→Executor→Verifier→
> 重试/重规划/终止的显式状态机；Verifier 读设备注册中心真实状态与 `expected_state` 比对，
> 失败按 `problem_type` 分流——`unsupported_action`/`device_not_found` 是确定性错误，
> 跳过重试直接重规划；`tool_error`/`state_mismatch` 才消耗重试额度。

**我发现的、值得额外讲的一点**：Planner 分支**不经过** `compact_context`
（`task_router → planner` 是直连边）。`planner_node` 也确实不读 `state["messages"]`，
只读 `planning_goal` + 设备清单 + 记忆 + 失败反馈。所以：

> **Planner 是无状态的一次性调用，输入完全有界且可复现。** 它不吃对话历史，
> 因此不会被历史里的噪声或早先的失败措辞污染，同一个目标 + 同一份设备清单
> 必然得到同分布的计划。

这是个干净的设计决策，也是"为什么这条路径可测"的根本原因。

**追问路径**：
- 「为什么不让 LLM 判断成败」→ LLM 的目标是生成合理文本，不是核对事实；
  它会把工具返回的报错文案复述成"已完成"。真实设备状态是唯一 ground truth。
- 「`expected_state` 从哪来」→ 从能力声明派生（`expected_state_for_step()`），
  **不是模型给的**——否则模型可以自己定义成功标准，验证就成了同义反复。
- 「为什么确定性错误不重试」→ 同样参数原样重放不可能成功。**重试预算是资源，不是仪式。**

### 3.3 意图路由：知道什么时候不该用模型

**写法**：
> 意图路由采用「模型结构化分类 + 确定性短路 + 异常兜底」三层：`classify_intent()`
> 在确定性信号命中自动化管理时直接返回，不询问模型；LLM 调用异常时降级到关键词
> 分类器，保证路由永不阻塞主流程。

**必讲的真实 bug**（这是整份材料里最好的故事）：
> 「明天早上 6 点回家前把空调打开」——模型会抓住"回家"把它分类成预定义**回家模式场景**，
> 于是**当晚立刻**执行回家场景。用户第二天早上没有空调，而且空调白开了一夜。
> 解法是硬约束：识别到「未来时间信号 + 设备动作信号」同时出现就直接走自动化分支，
> 不给模型误判的机会。

**升华**：模型负责模糊语义，规则负责不可妥协的边界。**知道什么时候不该调用模型，
是 Agent 工程的成熟标志**——路由在每轮请求的关键路径上，用 LLM 等于给每轮加一次
延迟和一个失败点，而正则可测、确定，行为被测试钉死。

**同一思路的第二个证据**（`heuristics.py:135` 的注释）：`required_automation_tool()`
的**默认值必须是"不强制"**。查询类请求（"当前有多少个定时任务"）如果被误判成创建请求，
Agent 会被反复要求为一个问句创建例程，两轮失败后只能对用户报错，
而它本该去调 `list_automation_routines`。**强制机制的默认值必须是不强制**——
这是"fail-open vs fail-closed 该选哪个"的一次具体判断。

### 3.4 设备能力单一数据源 + 结构反射式一致性测试

**这一条对后端/基础架构面试官最有效，非 AI 岗要放第一位。**

**写法**：
> 将设备能力收敛为单一声明数据源：原先新增一种设备需手工同步 9 处
> （工具 if/elif、Planner 词表、Pydantic `Literal`、registry 关键词、模拟器实例、
> 场景类型集合、自动化工具名、MCP 工具），其中两处无法反射检查，漏改的表现是
> "Planner 首版计划稳定失败且不报错"；收敛后新增设备只需 1 处声明，
> 其余全部自动派生，并以结构反射断言（用 `typing.get_args` 反射 pydantic `Literal`
> 与声明表比对）保证漏改在测试期失败而非运行期静默。

**为什么"结构反射断言"值得单独说**（`tests/test_capabilities.py:56`）：
它断言的是**派生关系**，不是具体值——所以**新增设备时不需要改测试，测试自动覆盖新设备**。
这类测试在秋招里极少见到，绝大多数人写的是"assert 灯的动作等于 on/off"这种硬编码。

**追问路径**：
- 「本质是什么模式」→ SSOT / schema-as-code。可类比 DB migration、OpenAPI 生成客户端、protobuf。
- 「为什么不用装饰器自动注册」→ 显式声明表**可审计、可 diff、可生成文档**；
  隐式注册的失败模式是"忘了 import 所以没注册"，更难查。
- 「一致性凭什么保证」→ 不靠 code review 的记性，靠测试钉住。

### 3.5 把时钟作为参数：确定性的调度测试

**这条是通用后端能力，对任何岗位都成立。**

`RoutineScheduler.tick(now=...)`（`automation/scheduler.py:79`）接受注入时间，
后台线程只是 `while not stop.wait(poll): self.tick()`。业务逻辑与时钟完全解耦。

**写法**：
> 事件驱动自动化子系统运行在对话图之外：SQLite 持久化例程由后台调度线程执行，
> 动作同样经真实设备状态验证；调度器把当前时间作为参数注入，
> 使全部定时逻辑测试零 sleep、完全确定。

**同一子系统里另外两个值得说的细节**：
- `dedupe_key` 去重用 **UNIQUE 索引**而不是"先查再插"，避开 TOCTOU 竞态；
- `set_alarm` 的 `due_at = now` 而非 `anchor_at`——**闹钟必须在创建例程时就设好，
  不是到点才设**。这是个真实的业务语义洞察，不是代码技巧。

**追问路径**：「为什么不放在图里」→ 图的生命周期是一次请求，例程要跨进程持久化并按
时间触发；塞进图里等于让图同时承担编排和调度两个职责。**知道框架的边界在哪。**

### 3.6 可信身份边界

**写法**：
> 身份仅来自 `RunnableConfig["configurable"]`，工具通过 `config` 命名参数反解——
> 该参数不出现在工具 JSON Schema 中，**模型在语法上无法表达 `home_id`**；
> 配合住宅归属校验与管理员权限规则，跨家庭隔离、非管理员写共享记忆被拒、
> 模型参数无法覆盖身份三类边界均有测试钉住。

**关键在措辞**：不是"我校验了模型传来的 home_id"，而是"**连伪造的接口都不存在**"。
这两句话在面试官耳朵里是两个水平。

**可顺带讲的坑**（011 迭代）：旧实现有 `if config is not None` 的兜底，
但空 `configurable` 的 config 也是真值，于是"逐键检查后安静跳过"的保护形同虚设。
根因是把安全策略做成了**运行期的隐式推断**。改法是提升到**构造期的显式选择**：
图路径开启偏好观察、缺身份直接 `RuntimeError` fail-fast，后台执行器与 MCP
显式传 `enable_preference_tracking=False`。

## 四、三个不要写的词 + 一个已经可以写的词

我读代码后认为这几个词不能当免检标签用，**不是因为实现差，而是因为词选大了**。
改口径后它们仍然是有效的设计，只是不再是雷。**但表里第三行已经变了性质**：
013 之后「混合检索」是真的，**可以写、也可以主动讲**——雷从「这个词」挪到了
「这个词用在哪个模块上」。

| 别写 | 代码实际是什么 | 改成 |
|---|---|---|
| **多智能体协作** | 6 次 `bind_tools` 不同子集 + 一个 dict 查表选 LLM；`supervisor_finalize` 只记状态然后 END。**没有 handoff、没有 agent 间通信、没有 supervisor 决策循环** | 「按意图隔离工具集与角色提示词，降低单模型的工具选择错误率」——诚实且仍是有效设计 |
| **Send 动态并行加速** | `query_device` 分支只做 `registry.get()` 内存字典查找，零 IO；`parallel_query_node` 用 `subgraph.invoke()` 同步驱动；全项目除 `src/mcp/` 零 `async def` | 「用 `Send` 实现按目标数动态 fan-out 的子图与聚合 reducer」——只讲机制，不提性能 |
| ~~**Agentic RAG**~~ **013 后这行反过来了：可以写，而且是加分项** | BM25 词法通道 + 向量语义通道、加权 RRF 融合名次（生产 0.5/0.5，jieba 分词），错误码与型号走硬过滤不参与打分；检索前实体消解四态（仅唯一命中放行）、检查项按可自证/需人工分流读真实状态三值核对、引用与核对块由代码拼接；语料 39 份说明书 / 124 小节 / 13 型号 / 10 种设备，12 条自证检查；**63 条 golden 召回评测集**做过四组配置对照 | 「说明书故障排查的混合检索链路：BM25 与向量双通道加权 RRF 融合，错误码与型号走硬过滤不参与打分；63 条 golden 召回集实测 Recall@1 51.8% → 87.5%、口语化查询召回 3/30 → 23/30、拒答准确率 100%」——**这条现在是全项目唯一带实测指标的模块，别再说"检索是词法 bigram、没有语义泛化"了，那句已作废** |
| **「记忆」的混合检索 / 语义检索** | 注意范围：说明书检索确实是混合的（上一行），但**记忆**模块的 `_retrieval_score` 仍是手工加权线性打分：relevance(0.45，子串命中率) + confidence(0.20) + importance(0.20) + recency(0.10, exp 90 天衰减) + frequency(0.05, log1p)，没有向量 | 记忆那边说「多因子可解释加权排序」——**"可解释"是真优点**：每一项权重都能说出理由，零成本、确定、可测。**两个模块别混着说**，被追问「你的记忆也是向量检索吗」要立刻答「不是，那边是加权排序」 |

还有一条不是措辞问题而是数据问题：**记忆检索的 token 降幅 / 命中率目前没有实测数据，
不要写数字。** 没有实验支撑的量化指标是面试事故。（说明书检索不受这条限制——013 的
63 条 golden 评测集就是为了让那些数字能写出来。**两个模块的数据成熟度不一样，别互相借。**）

**顺带一个诚实回答的准备**：车辆 / 音响是模拟器闭环，未接真实厂商 API。
被问就直说"本地模拟后端闭环，接口按 Backend 抽象隔离，替换真实 API 不动上层"——
这本身是面向接口编程的正面例子。

## 五、简历怎么写

### 5.1 主线句（放在项目名下面第一行）

> 用 LangGraph 构建的智能家居 Agent。核心是一套「把 LLM 当不可信组件」的工程实践：
> 模型的身份、工具名、计划规模、参数、执行结果、最终叙述在七个交接面上分别被收窄，
> 264 项离线测试钉住权限边界与状态机行为。

### 5.2 AI 应用 / Agent 岗版本（5 条）

```
智能家居 AI Agent（Python / LangGraph / Pydantic / SQLite / MCP，个人项目，13 轮迭代）
• 设计 Planner–Executor–Verifier 显式状态机：planning_status 驱动全部条件边，

• 建立可信身份边界：身份仅来自运行时配置，经 config 命名参数注入且不进工具

• 构建说明书排障的混合检索链路：BM25 词法与向量语义双通道加权 RRF 融合，错误码与

  51.8% → 87.5%、口语化查询召回 3/30 → 23/30、拒答准确率 100%
• 收敛设备能力为单一声明数据源（新增设备 9 处手工同步 → 1 处），工具 Schema /
  规划词表 / Literal 枚举 / MCP 工具全部自动派生，以结构反射断言使漏改在测试期失败
```

**投 LLM / 算法岗时第四条不能砍**——它是这份简历里唯一带实测指标的条目，
其余四条讲的都是"设计得对"，只有它能讲"我量过、而且量完改了决策"。

### 5.3 后端 / 基础架构岗版本（换序 + 换重点）

```
智能家居 AI Agent（Python / LangGraph / SQLite / MCP，个人项目，13 轮迭代）
• 消除跨模块手写副本：设备能力收敛为单一声明数据源，9 处派生点（工具 Schema、
  Pydantic Literal、关键词表、MCP 工具等）全部自动生成，并以 typing 反射断言
  校验派生关系，使漏改在测试期失败而非运行期静默

  UNIQUE 索引去重避开 TOCTOU；调度器将当前时间作为参数注入，定时逻辑测试零 sleep
• 设计显式状态机替代隐式流程：单一状态字段驱动全部条件边，执行结果由外部真实状态
  复核而非组件自述，失败按错误类型分流（确定性错误不消耗重试额度）
• 建立请求身份的可信边界：身份仅来自运行时配置且不进入不可信组件的输入 schema，
```

注意后端版本里**一个 LLM 词都没有**，但描述的是同一份代码。这不是包装，
是同一个设计的另一个正确抽象层——面试官问起来你能双向映射。

### 5.4 30 秒开场自述

> 这是一个用 LangGraph 做的智能家居 Agent，一万八千行代码、264 个测试、13 轮迭代。
> 我更愿意把它描述成"如何把不可靠的 LLM 组件工程化"：模型说执行成功了不算，
> 要读设备真实状态复核；模型给的身份不接受，身份从运行时配置注入而且不进工具 schema，
> 模型连伪造的语法都没有；模型参数写错了不静默套默认值，显式失败并把合法值回喂给它重写。
> 最近一轮做的是说明书排障的检索升级——换成 BM25 加向量的混合检索，并且建了一套 63 条的
> golden 召回评测集做配置对照，Recall@1 从 51.8% 到 87.5%；有意思的是评测跑完我反而
> **没有**选指标最好的那个配置，这个取舍我可以细讲。
> 我还自己做了一轮红队审查，实测出四个安全缺陷，都定位到了根因——最典型的是审批实现在
> 编排层，所以 MCP 那个入口天然绕过它。

最后两句各是一个钩子：一个引向 §6.4 第三题（那是你少有的"有数据支撑的取舍"），
一个引向 §6.4 第一题（那是你准备最充分的战场）。

### 6.2 LLM 应用 / Agent 面试官

| 问题 | 答到哪里算够 |
|---|---|
| 为什么用 LangGraph 不用 AgentExecutor / 自己写循环 | 三个只有它给的东西：条件边=显式状态机（AgentExecutor 只有"调工具/结束"二元循环，表达不了按错误类型分流）、Checkpoint + `interrupt()`（审批要能中途暂停并持久化）、`Send` 动态 fan-out。代价：State 全局单点会膨胀、调试靠事件流不靠断点 |
| Planner 和 ReAct 怎么选 | `should_use_planner()` 纯正则：≥2 动作词 且（≥2 设备类 或 有连接词）；命中预定义场景关键词一律不走。为什么不用 LLM 判断：在关键路径上、加延迟加失败点、且正则可测确定 |
| Planner 为什么用 `with_structured_output` 不用 `bind_tools` | 要的是一份完整计划不是一次工具调用；**副作用**是工具 docstring 到不了模型面前，所以合法 action 必须显式拼进 prompt——这是首版计划反复失败的根因 |
| 幻觉 / 模型胡说怎么处理 | 展开 §2 那张七行表。重点讲第 7 行：最终叙述是硬编码的，**系统不可能对用户谎报成功** |
| 说明书 RAG 的检索怎么做的 | BM25 词法 + 向量语义双通道，加权 RRF 融合名次（生产 0.5/0.5，k=60，jieba 分词）；**错误码与型号走硬过滤、不参与打分**（E4 的语义近邻天然是 E5/E7，降级成相似度就会把 E7 的步骤当权威答案递出去）；**RRF 只排名次不守门**（名次第一必拿满分，跟像不像无关，所以另算一个 [0,1] 绝对置信度专门管拒答）。有 63 条 golden 召回集，Recall@1 51.8% → 87.5%、口语召回 3/30 → 23/30、拒答 100% |
| 为什么不直接用纯向量 | ⚠️ **这题必须诚实答，见 §6.4 第三题**——纯向量指标其实更好 |
| 你怎么知道效果好？怎么评测 | ⚠️ **最危险的问题**，见 §6.4 |
| 不调真实 LLM 怎么测 | `patch build_llm` 换 FakeLLM（实现 `bind_tools`/`invoke`/`with_structured_output`）；settings 用 `SimpleNamespace` 绕开 API Key 校验；断言权限边界、DB 状态、设备副作用、事件顺序，**不断言返回文本**（文本断言在 LLM 项目里必然 flaky） |
| 上下文超长怎么办 | 三道闸门（消息数/token/字符）+ 滚动摘要 + 工具结果裁剪。**主动说洞**：`max_tokens` 只约束消息历史，system prompt（约 2200 token）、工具 JSON Schema、memory_context 都不在预算内，日志报 42 token 时真实请求可能是几十倍。**预算要对完整请求体计数，且要用真实 tokenizer** |
| 修过什么真 bug | 两个都值得讲。①裁剪切断 `tool_calls ↔ ToolMessage` 配对，30.8% 的裁剪产生非法消息序列 → 加边界对齐降到 0%。**长度闸门不认识消息协议不变量，必须单独兜住**。②013 的查询重写 prompt 写成"请判断最可能属于哪一个小节"，**强制单选**——正确答案不在清单里时模型必然挑一个最像的，而校验只检查"标题真实存在"，**存在不等于相关**。于是"卧室空调有点响"（那台空调说明书没有噪音章节）拿到了「蒸发器结霜」的内容还挂了三条引用，**模型自己在正文里都写了"说明书片段中未提及空调异响"，系统仍以权威格式把引用递出去**。单元测试全传 `llm=None`（走确定性词表）、召回评测刻意只测首轮检索，**两层都是绿的，组合起来那条真实路径没人测**——只有第三层端到端手跑抓得到。修法是给模型一个明确出口（不相符就只输出「无」），且模型说"无"时**连词表兜底都不走**。结论：**"测试全绿"和"功能正确"的差距，取决于测试有没有覆盖到配置的真实组合** |
| LLM 调用失败怎么办 | **诚实**：韧性不足，有裸 `invoke`、结构化输出无兜底；只有路由层有 try/except 降级到关键词分类器。有意思的是 `middleware/interceptors.py` 里的 RetryInterceptor **刻意没接**，理由写在文件头：无条件 `except Exception` 会吞掉 `GraphInterrupt` 从而破坏审批语义 |
| 成本怎么控制 | `UsageTracer` 挂在 `build_llm` 的 callbacks 上，随 `bind_tools`/`with_structured_output` 传播，所以路由/Planner/ReAct 每次调用的 token 与延迟都落 `channel=llm_usage` 日志；路由与澄清走确定性路径不消耗调用 |

### 6.4 三个必须提前写好逐字稿的问题

这三题决定面试印象的上限，**不能临场组织语言**。

**Q：你的人在回路审批能被绕过吗？**

不要说"不能"。答：

> 图内路径不能，但我自查时发现三处能绕过，**根因是同一个架构错误**：
> 我把审批实现在编排层（图节点里 `interrupt()`），而安全边界必须在**每个入口**重复，
> 或者下沉到所有入口共用的那一层。
>
> 一，MCP server 是**另一个进程入口**，根本不经过图，所以 `control_lock_mcp(unlock)` 零拦截；
> 二，Planner 路径的 `risk_level` 硬编码 medium，而且 CLI 渲染的是**模型自己写的
> step description**——实测出现过用户看到"准备门口环境"、实际执行 unlock。
> 这里的教训是 **HITL 展示的必须是机器从 tool_calls 生成的事实，不能是模型撰写的摘要**，
> 否则用户批准的是模型的"说法"而不是"行为"，HITL 的意义就废掉了；
> 三，审批锚定的是**工具名**不是**物理效果**：`activate_scene('回家模式')` 要审批，
> 但等效的 light + ac + curtain 三连零审批——用户说"调成回家的样子"时模型自然可能选后者。
>
> 修法我想清楚了：审批下沉到工具执行层，风险等级从实际动作集合推导而非硬编码，
> 展示层强制渲染 `tool_calls`。

（补充一个可以主动加的正面细节：ReAct 主路的审批文案**已经是**机器生成的——
`build_approval_request` 从 `args` 里取设备名、场景名、自动化时间和 action 列表拼装，
并把**全部** tool_calls 附在 payload 里。所以问题只在 Planner 路径没走这个函数。
能精确区分"哪条路径对、哪条路径错"，比笼统认错更有说服力。）

**Q：你怎么知道你的 Agent 效果好？**

> 分两层。**代码逻辑层**是确定性测试——264 个用例覆盖权限边界、状态机流转、
> 调度确定性、能力派生一致性；但这些测的不是模型输出质量。
>
> **模型行为层**我目前只覆盖了一块，就是说明书检索：63 条 golden 召回集
> （口语 30 / 说明书原词 10 / 错误码 10 / 同码异义 6 / 应拒答 7），跑真实 embedding、
> 不带 LLM，度量 Recall@1 / Recall@3 / MRR / 拒答准确率，拿它做过四组配置对照。
> 三档分数下限也是在这套集合的（权重 × 下限）网格上扫出来的，不是手调的。
>
> **意图路由和端到端任务成功率还没做**，这是现在最大的缺口。但路子清楚，而且我这个项目
> 有个别人没有的优势：**我有客观 ground truth**。`verify_step` 读的是设备真实状态，
> 所以端到端任务成功率可以机器判定，不需要 LLM-as-judge，也不需要人标。
>
> 大多数 Agent 项目评测难，是因为没有 ground truth。我的架构恰好把这件事变简单了，
> 而且检索那块我已经证明这套方法在这个项目里跑得通了。

最后一段是整个面试里最能体现"你理解自己系统的性质"的话。

**Q：你为什么不直接用纯向量？**（**主动暴露局限，比被问出来强得多**）

这题的价值不在答案，在于**你敢先把对自己不利的数字说出来**。

> 诚实说，纯向量在两个指标上确实比我最终用的混合配置更好：Recall@3 是 94.6% 对 89.3%，
> MRR 是 0.908 对 0.881。我仍然选了混合，三条理由，第三条才是决定性的。
>
> 一，把 BM25 权重清零等于把词法通道整个关掉，**embedding 服务一挂就全部拒答**；
> 混合配置下 BM25 还兜着，离线 Recall@1 也有 58.9%。
> 二，用户直接引用说明书原词时 BM25 更强，10/10 对 9/10。
> 三，**"这份说明书没讲这件事"这句话只有词法通道说得出来。** 我统计了 63 条用例的
> 余弦分布：正例中位 0.653，而"同一型号的其它症状小节"这类困难负例中位 0.568——
> 两个分布大幅重叠。也就是说**向量靠绝对余弦分不开"对的症状"和"同一台电器的另一个
> 症状"**，因为它们语义上真的很近。而"卧室空调有点响"查那台空调时，"响"和"噪音"
> 在它说明书全文里根本不存在，**BM25 返回 0**——这是唯一能触发拒答的信号。
> **拒答闸门的可靠性来自 BM25，不是来自阈值调得准。**
>
> 顺着说个我自己也不满意的地方：拒答用例里最高的假阳性是 0.336，阈值是 0.35，
> **只有 4% 余量**，根因就是上面那个余弦分布重叠。这也是我下一步要动的地方——
> 靠一个绝对分数区分"同一台电器的另一个症状"本来就不牢，更该做的是让通道之间互相校验。

**为什么这题一定要主动讲**：候选人讲评测时最常见的破功方式是"我做了 A/B，A 更好，
所以我用了 A"——这只证明你会看表。而"B 的指标更好，我选了 A，因为指标没覆盖到的那个
风险更贵"证明的是**你知道指标的边界在哪**，这是完全不同层次的信号。
