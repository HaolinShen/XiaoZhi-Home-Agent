# 简历三点：怎么讲成一个系统，而不是三个功能

> 依据你给的三点构想（范式分派 / 说明书排障 RAG / 自动化编排）重新组织。
> 目标是**故事的说服力**：每一点讲成「问题—为什么难—我的设计」，而不是功能罗列。

---

## 零、先解决一个结构问题：三点必须有关系

三条并列 bullet，面试官读到的是三个功能，会挑一个追问然后走。
三条有内在关系，面试官读到的是一个系统，会想听你把它讲完。

我给的关系是这样的：**三点是同一个能力在三个不同时间维度上的展开。**

| | ① 范式分派 | ② 说明书排障 | ③ 自动化编排 |
|---|---|---|---|
| 回答的问题 | 怎么**做** | 为什么**不工作** | **什么时候**做 |
| 时间 | 此刻 | 此刻 | 未来 |
| 用户在场 | 在 | 在 | **不在** |
| 主要挑战 | 可靠性 / 成本 | 不许胡说 | 幂等 / 时序 |

它们共享**同一个事实来源：设备的真实状态**。

- ① 用它**验证执行结果**（Verifier 读注册中心真实状态，不采信模型自述）
- ② 用它**自动核对说明书里的检查项**（说明书说"确认设置温度低于室温"，系统直接读来核）
- ③ 用它**验证后台动作**（没人在场，只能靠真实状态确认烧水器真的开了）

还有第二层贯穿关系：**人在回路的密度，随"人是否在场"收紧。**

- ① 对话中的不可逆动作（解锁）→ 必须审批
- ② 排障只给建议 + 说明书出处，物理操作交给人 → 不代替人动手
- ③ 后台执行没人可问 → 动作集直接不含不可逆操作（自动化不能解锁门锁）

**一句话主线（放在项目名下面）：**

> 一个把设备真实状态作为唯一事实来源的家居智能体：控制路径按任务性质分派四种范式并以真实状态验证，
> 故障路径以厂商说明书为权威文本做可溯源排障，未来路径由目标时间倒推的持久化任务编排承担；
> 三条路径的人在回路强度随用户在场程度收紧。

有了这句，三条 bullet 就不是清单了。

## 一、第一点：四种范式的分派

### 故事怎么讲

不要说"我实现了 ReAct 和 Plan-Execute-Verify"——这是在报菜名。要讲**为什么一个系统需要四种**。

> 家居请求的分布极不均匀，用一种范式覆盖全部，必然在某一端付出代价。
>
> "把客厅灯打开"是单步确定任务。"把家里调成适合看电影的样子"是多步跨设备任务。
> "回家模式"是业务上**已经定义好的固定序列**。"解锁大门"是不可逆的物理动作。
>
> 全走 ReAct：多步任务会在中途丢失整体目标，而且无法回答"整件事成了吗"——
> 它只知道每次工具调用返回了什么，不知道计划完成度。
> 全走 Planner：单步任务要付三次 LLM 调用的延迟和成本，还多一个结构化输出失败点。
> 固定流程走 LLM 规划：等于让模型**重新发明一个业务上已经确定的答案**，而且每次结果可能不同。
>
> 所以我按任务性质分派：

| 任务性质 | 范式 | 关键设计 |
|---|---|---|
| 单步 / 需要边看边定 | **ReAct** | 工具结果回喂，模型下一步再定 |
| 多步跨设备 | **Plan–Execute–Verify** | 先出完整计划、逐步执行、**每步按真实设备状态验证** |
| 预定义场景（回家/离家/观影/睡眠） | **固定流程** | 序列写死在业务层，**规划阶段零 LLM 参与** |
| 不可逆物理动作（解锁） | **人在回路** | 不是第四条路，是**横切**在前三条之上 |

### 三个把这一点讲高级的关键句

**1. HITL 是横切关注点，不是第四种范式。**

前三条回答"怎么决定做什么"，HITL 回答"做之前要不要问人"。它跟范式是正交的两个维度。
能主动做这个区分，展现的是架构层次感——很多人会把它们并列成四个 feature。

**2. 分派本身用确定性规则，不用 LLM。**

> 分派在**每一轮请求的关键路径上**。用 LLM 判断等于给每轮加一次调用的延迟和一个失败点，
> 而且分派规则的行为会变得不可测。我用的是确定性判断：动作词数量、涉及的设备类别数、
> 是否出现连接词，命中预定义场景关键词则优先走固定流程。规则可测，行为被测试钉死。

**升华句：知道什么时候不该调用模型，是 Agent 工程的成熟标志。**

**3. Verifier 不问模型，读真实状态。**

> LLM 的目标是生成合理文本，不是核对事实——它会把工具返回的报错文案复述成"已完成"。
> 所以验证读设备注册中心的真实状态，跟期望状态比对。而**期望状态是从设备能力声明派生的，
> 不是模型给的**——否则模型可以自己定义成功标准，验证就成了同义反复。

### 必讲的两个具体案例

**案例 A（分派为什么不能全交给模型）**：

> "明天早上 6 点回家前把空调打开"——模型会抓住"回家"两个字，把它归到预定义的**回家模式**，
> 于是**当晚立刻**执行回家场景。用户第二天早上没有空调，而且空调白开了一夜。
> 这是范式分派错误的典型形态：它把一个**未来时刻的自动化任务**误判成**此刻的固定流程**。
> 解法是硬约束——识别到「未来时间信号 + 设备动作信号」同时出现就直接走自动化，不给模型误判机会。

这个案例极好用，因为它同时证明了第一点和第三点的边界。

**案例 B（HITL 的展示层陷阱，讲出来直接高一档）**：

> 审批弹给用户看的文案，必须是**机器从 tool_calls 里的参数生成的事实**，
> 不能是模型自己写的摘要。否则会出现用户看到"准备门口环境"、实际执行的是解锁的情况——
> **用户批准的是模型的"说法"，不是它的"行为"，HITL 的意义就废掉了。**

### 失败处理（问到必答，答好很亮）

> 验证失败不无脑重试，按错误类型分流：
> - 动作不支持 / 设备不存在 → **确定性错误，跳过重试直接重新规划**。同样参数原样重放不可能成功。
> - 工具异常 / 状态不匹配 → 才消耗重试额度，可能是瞬时问题。
>
> 重规划时把**合法动作列表和设备清单回喂给模型**，让它知道哪些词是可用的，
> 而不是凭常识再猜一轮。

**升华句：重试预算是资源，不是仪式。**

### 简历文字

```
• 按任务性质分派四种智能体范式而非套用单一 ReAct 循环：单步指令走 ReAct、多步跨设备走
  Plan–Execute–Verify、预定义场景走零 LLM 参与的固定流程，不可逆物理动作横切人在回路审批；
  分派由确定性规则完成不引入额外 LLM 调用，Verifier 以设备真实状态而非模型自述判定成败，
  失败按错误类型分流（确定性错误跳过重试直接重规划并回喂合法动作词表）
```

## 二、第二点：说明书 RAG 与故障排查

### 故事怎么讲

这一点的关键是**先说清为什么这个场景非 RAG 不可**，再说设计。

> 家电排障是 RAG 最站得住的场景之一，原因是**错误答案的代价不对称**。
>
> 用户问"空调显示 E4 是什么意思"，如果让模型凭常识猜：不同厂商、不同型号的同一个错误码
> 含义可能完全不同。猜错的后果不是"回答不够好"，而是用户白等一天、或者去拆一个不该拆的部件。
> 说明书是**厂商权威文本**，这个问题**有确定答案**，不该让模型自由发挥。
>
> 所以这个模块的设计目标不是"让回答更流畅"，而是**在有权威答案的领域里禁止模型即兴创作**。

由此推出三条设计约束——**这三条是这一点的骨架，比"我用了向量数据库"值钱得多**：

**1. 强制引用**：每个结论必须能溯源到说明书的具体段落，**不能溯源就不输出**。

**2. 拒答纪律**：检索不到就明确说"说明书里没有这条，我不能可靠确认"，而不是让模型硬答。

> 大多数 RAG 系统的失败模式恰恰是：检索质量差的时候，模型仍然自信地答。
> 拒答是**要专门设计**的，因为它逆着模型的默认行为。

**3. 检索前必须做实体消解**：用户措辞 → 设备实例 → 型号 → 文档集合。

> 用户说"客厅那个空调滴滴响"。系统必须先把这句话解析到**具体设备实例**，
> 再拿到**型号**，才能确定查哪一份说明书。
> **查错型号的说明书比不查更危险**——它会给出一个看起来权威、实际不适用的答案。
> 这是通用文档问答没有的环节：它把知识库和设备注册中心连起来了。

### 高潮：说明书 + 实时设备状态

**这是这一点最值钱的设计，一定要讲。** 它把这个模块从"文档问答"抬升到"诊断"。

> 说明书给的排查项，往往分成两类：一类是**系统自己能核对的**，一类是**必须人动手的**。
> 纯 RAG 只能把两类一起念给用户；这个 Agent 能读设备真实状态，所以能把第一类**自动核对掉**。
>
> 举个具体的：用户说"客厅空调开着但一点都不凉"。
>
> 1. 实体消解 → 客厅那台，型号 SmartCool-AC2024
> 2. 混合检索首轮直接命中"制冷效果不佳"章节（置信度 0.83），拿到 **5 条排查项**。
>    这一步值得展开一句：这句口语和说明书用词**一个共同的字都没有**，
>    所以纯词法通道下它首轮什么都查不到、要靠查询重写才能救回来；
>    是语义通道让它首轮就命中的（余弦 0.673）
> 3. 其中 **3 条系统直接读设备真实状态核对**：
>    - ✗ 空调当前是关机状态 —— 后续检查项都无从谈起
>    - ✓ 设定温度 26°C 低于实测室温 27°C（客厅温湿度传感器）
>    - ✓ 当前运行模式为制冷
> 4. 另 **2 条是物理检查**（滤网积尘、室外机遮挡），给出说明书原文 + 出处，交用户确认
>
> **说明书能回答的它回答，设备状态能自证的它自证，剩下必须人动手的才交给人，
> 并且明确告诉用户哪一部分是哪一种。**

最后那句是这一点的收尾句，建议背下来。

两个能顶住细问的实现细节，问到了再展开：

- **三值而不是布尔。** 核对结果是 `problem` / `ok` / `unknown`。`unknown` 是必需的第三态——
  "这个房间没有温湿度传感器所以读不到室温"跟"室温确实高于设定温度"是两件事，
  前者必须退回给人确认，把它当成"核对通过"是最危险的做法。
- **标注写在说明书行内，不在索引里。** 每条排查项末尾挂一个 Markdown 注释
  （`<!--check:device_is_on-->` / `<!--manual-->`），渲染时不可见，说明书在任何阅读器里
  仍然是一份说明书；解析时剥离，正文一个字不改。写在索引里就要靠"第几节第几条"定位，
  说明书改一行顺序全部标注错位，**而且错位是静默的**。
  语料引用一个不存在的检查 id 时，知识库构造直接抛异常——不容忍降级成"需人工确认"，
  否则拼错一个 id 就让一条本该自动核对的检查项无声消失。

### 面试追问

**"为什么不 fine-tune / 不靠模型常识？"**
> 说明书会随固件更新、型号数量多且各不相同、内容是厂商权威文本。
> 这三个特征指向检索而不是参数记忆：内容更新只需换文档，不需要重训；
> 而且检索能给出**出处**，参数记忆给不了。

**"检索用什么做的？向量吗？"**
> 现在是**混合检索**：BM25 词法通道 + 向量语义通道，用 RRF 融合名次。
> 但这个答案值钱的地方不是"我用了向量"，而是**我先做了判断，然后把它建出来、量出来了**。
>
> 当初的判断是：**型号 + 错误码是强关键词，词法在这类查询上比向量更准**——"E4"的
> 向量邻居可能是"E5"，而词法匹配不会。向量真正值钱的地方是症状的**同义表述**
> （"不凉快"/"制冷差"/"温度下不来"）。所以合理的形态是**词法负责型号与错误码的精确命中，
> 向量负责症状的语义召回**。
>
> 建完之后 63 条评测用例把这个判断逐条证实了：
> 错误码类**所有配置都是 10/10**——因为错误码走的是**硬过滤**（查询里的码必须出现在
> 那一小节），向量根本碰不到它。而"说明书原词"类上 BM25 是 10/10、纯向量 9/10，
> 词法不是摆设。真正的提升全在口语类：**3/30 → 23/30**，Recall@1 从 51.8% 到 87.5%。
>
> 错误码为什么必须是硬过滤而不是打分项，这一点我想强调：一旦把它降级成"相似度的一部分"，
> 用户问 E4 就会拿到 E7 的处理步骤，**而且读起来完全通顺、完全权威**。
> 用户没有任何线索能判断这段话答的不是他问的那个码。

这个答案比"我用了 FAISS"强得多，因为它证明你知道**为什么**用，而不是跟风用。

**"你上了向量，那纯向量是不是更好？"（这条我会主动说，因为答案是"是"）**
> **是的，纯向量的 Recall@3（94.6% vs 89.3%）和 MRR（0.908 vs 0.881）都比混合更好。**
> 我仍然选了混合，三条理由，第三条是我真正学到的东西：
>
> 一，把 BM25 权重清零等于关掉整个词法通道，**embedding 服务一挂就全部拒答**；
> 混合配置下还有 BM25 兜着，离线 Recall@1 还有 58.9%。
>
> 二，"查询就用说明书原词"这一类上 BM25 更强（10/10 vs 9/10）。
>
> 三，也是最关键的：**"这份说明书没讲这件事"只有词法通道说得出来。**
> 我统计了 63 条用例的余弦分布——正例中位 0.653，而"同一型号的**其它**症状小节"
> 这类困难负例中位 0.568，**两个分布大幅重叠**。也就是说向量靠绝对余弦
> **分不开「对的症状」和「同一台电器的另一个症状」**，因为它们语义上真的很近。
> 而"卧室空调有点响"查那台空调时，"响/噪音"在它的说明书全文里不存在，
> **BM25 返回 0**——这是唯一能触发拒答的信号。
> **拒答闸门的可靠性来自 BM25 通道，不是来自阈值调得准。**

**"融合用的什么方法？"**
> RRF（Reciprocal Rank Fusion），但**只用它排名次，不用它守门**——这是我踩明白的一点。
>
> RRF 是 `Σ w/(k+rank)`，纯名次。好处很实在：对量纲免疫。BM25 无上界、余弦在 [0,1]，
> 直接加权求和得先把两者拉到同一尺度，RRF 不用。
>
> 但它有个性质会**直接毁掉拒答纪律**：名次第一的必然拿到该通道的最高分，
> **跟它到底像不像毫无关系**。一个语料里根本没有对应章节的查询，它的第一名照样是满分 RRF。
> 所以拿 RRF 去套拒答阈值，拒答分支**永远走不到**。
>
> 我的做法是两套分数各管一件事：`rrf` 只决定名次，另一个锁在 [0,1] 的绝对置信度
> 只决定放不放行。**先按置信度筛掉不够格的，再按 RRF 排名次。**
>
> 还有一个更细的坑值得讲：**RRF 会奖励"在两个通道都出现"，而 BM25 的"出现"极其廉价**
> ——任何一个词有一点重叠就有名次。于是一个只靠通用词沾边的小节，会因为
> "BM25 排第一 + 向量排第五"击败"BM25 没排上 + 向量排第一"的正确答案。
> 这个 bug 让混合检索一度**比单通道更差**（85.7% vs 91.1%）。给弱通道降权没用，
> 因为问题不在票数权重，在**噪声本来就不该有投票权**——修法是让噪声在**进入名次之前**
> 就归零，不只是在合成置信度时归零。改完才回到持平。

**"口语症状召回不到怎么办？"（这条是上一问的自然追问，答好非常亮）**
> 这是词法检索的固有短板，我实测过："空调开着但一点都不凉"去查说明书，
> 全部小节都只有 0.11 分，而且**第一名是错的**（一个故障码章节靠文档名字母序赢了）。
> 原因不是权重没调好，是**真的几乎没有字面重叠**——"一点都不凉"和"制冷效果不佳"
> 一个共同的字都没有。
>
> 后来我把这个判断也量了：**换成 BM25（有 IDF、有 TF、有长度归一）之后，
> 口语类召回从 3/30 只升到 7/30。** 也就是说 IDF、BM25 在这里确实救不回来——
> 这不是打分函数的问题，是词汇表根本不重叠。**只有语义通道能跨过去**
> （同一句话余弦 0.673，首轮置信度 0.832，直接命中）。
>
> 在没有语义通道之前，我的兜底是**查询重写**，两条路：有 LLM 时把**该型号说明书里
> 真实存在的小节标题清单**给模型，让它在里面挑，而不是让它自由发挥关键词——
> 模型给的标题必须能在清单里对上，否则视为无效重写、退回词表。没有 LLM 时走确定性症状词表，
> 所以测试不需要 API Key。
>
> **有了语义通道之后，这套重写的定位变了**：它从"语义泛化的唯一手段"降级成
> "没配 embedding 时的离线兜底"。上面那句"不凉"现在首轮就命中了，根本走不到重写。
>
> 还有个细节我要主动更正，因为它是个好例子。我原来的说法是"重写必须是**替换式**而不是
> 追加式，因为分数分母是查询词总数，留着原话会让永远匹配不上的词稀释分数"——
> 同一句话实测替换式 0.73、追加式 0.39。**这个理由在换成 BM25 之后就不成立了**：
> BM25 是对查询词求和，匹配不上的词贡献 0，不存在稀释。
> 现在仍然用替换式，但理由换了：重写后的查询要和"重写后"那一档阈值配套，
> 而那一档是按"纯说明书用词"的分数分布标定的，追加式会让分数落在两档之间、
> 阈值失去稳定含义。
>
> 我愿意讲这一段，是因为**换掉打分函数会让一批旧结论悄悄失效**，
> 而"这条结论当初成立的前提是什么"往往比结论本身更值得记住。

**"检索阈值怎么定的？"（如果对方在意工程细节，这条最能证明你真跑过数据）**
> 我踩了个坑，值得讲：原来是一个硬编码阈值卡所有情况，结果它同时犯了两种错。
>
> 一开始我把阈值提高来滤掉噪声，结果**错杀**了一条正确答案：
> "空调显示 E4 是什么意思"命中的那一节只有 0.111 分——因为"是什么意思"这几个字
> 永远匹配不上说明书，只是把分母撑大了。
>
> 根因是**我把三种不同的检索机制混用了一个阈值**：
>
> 1. **查询带错误码**时，检索已经把不含该码的小节全部滤掉了，活下来的必然就是讲这个码的
>    那一节，相似度分数毫无意义。这一档下限取 **0**，而且**这一档刻意不做成可配置项**
>    ——它不是一个可调参数，是"精确键命中不该被模糊阈值否决"这条规则本身。
> 2. **原始口语**这一档滤掉靠"空调""是不是"这类通用词凑出来的命中。
> 3. **重写之后**要**更严**。不是"重写更可信"，恰恰相反：重写后的查询是纯说明书
>    用词、没有一个虚词，真命中的分数天然更高。
>
> 第 3 档是被一个真实 bug 逼出来的：用户说"卧室空调有点响"，重写成"噪音异常"后去查，
> 而**那台空调的型号说明书根本没有噪音章节**——它却靠"异常"这个在每份故障码文档里
> 都出现的词命中了"排水异常"，刚好过了原来的阈值。
> 系统于是拿一段讲排水泵的内容回答了噪音问题，格式权威、内容不相干。
> 这句话的正确输出是**拒答**：这个型号的说明书里没有讲噪音的章节。
>
> 顺着同一条逻辑还得出一条规则：**带错误码的查询永不重写**。错误码是精确键，
> 语料里没有 E9，换任何说法也变不出 E9，重写只会把用户引到某个"看起来相关"的小节。
>
> 换成混合检索之后这三档的**结构没变，数字全换了量纲**（现在是 0 / 0.35 / 0.42，
> 套在一个 [0,1] 的绝对置信度上）。这次我做对了一件事：**它们不是手调的。**
> 我建了 63 条 golden 用例，用一个 `--sweep` 入口在（向量权重 × 下限）网格上扫。
> 关键的一格是 **0.35**——向量权重取 0.5 到 1.0 的**任何**值，拒答准确率都在
> 0.30 → 0.35 这一步从 85.7% 跳到 100%。**所以它不是拟合某一条用例。**
> 代价是 Recall@1 从 89.3% 降到 87.5%，这个方向的取舍是刻意的：查到错章节比查不到更危险。
>
> 我也会主动说这里的**薄弱点**：拒答用例里最高的假阳性是 0.336，离 0.35 只有 4% 余量。
> 为什么这么薄，前面那个余弦分布给了答案——正例和"同一台电器的另一个症状"重叠太多，
> **绝对置信度本质上分不开这两者**。所以这道闸门真正靠的是 BM25 返回 0，
> 不是阈值卡得准。知道一个机制的可靠性来自哪里，比知道它的参数值重要。

**"讲一个你踩过的坑。"／"你怎么保证质量？"（这条我最想讲）**
> 讲一个**测试全绿但功能是错的**例子，它彻底改变了我对"验证"的理解。
>
> 我这次的验证分三层：单元测试（确定性、不需要 API Key，向量通道注入一个 stub）、
> 召回评测（真实 embedding、不带 LLM、只测首轮检索）、端到端手动跑（真实 embedding +
> 真实模型 + 完整主图）。**最严重的一个 bug 只有第三层抓得到。**
>
> 那个 bug 在查询重写上。我的 prompt 写的是"请判断最可能属于哪一个小节"——**强制单选。**
> 当正确答案根本不在清单里时，模型必然挑一个最像的；而我的校验只检查
> "这个标题真实存在"，**存在不等于相关**。于是"卧室空调有点响"（那台空调的说明书
> 没有噪音章节）拿到了"蒸发器结霜"的内容，还挂上了三条引用。
>
> 最讽刺的是：**模型自己在答案正文里写着"说明书片段中未提及空调异响的相关信息"，
> 系统却仍然以权威格式把三条引用递了出去。**
>
> 前两层为什么测不到它：单元测试全部传 `llm=None`（走的是确定性词表重写那条路），
> 而召回评测刻意只测首轮检索，压根不跑重写。**两道防线都是真的在测东西，
> 只是没有一道覆盖到"真实模型被迫在不相关的选项里单选"这个配置组合。**
>
> 修法很小：给模型一个明确的出口——"如果没有任何小节相符，只输出「无」，
> 不要勉强挑一个最接近的"。并且模型说"无"时**连词表兜底都不走**，
> 因为词表只看用户措辞，它不知道这个型号到底有没有对应章节。
>
> 我从这件事拿到的结论是：**"测试全绿"和"功能正确"之间的差距，
> 取决于测试有没有覆盖到配置的真实组合。** 一个只在"接了真模型"时才出现的缺陷，
> 无论加多少个用 FakeLLM 的用例都测不出来。

**"多份说明书内容冲突怎么办？"**

> 实体消解在检索之前——先定到唯一型号，再检索该型号的文档集合，冲突在源头就被排除。
>
> 这一点在我的语料里是**刻意做出来的**：家里两台空调是不同型号，
> 而两份说明书的 **E4 含义完全不同**（一份是室内外机通信异常，一份是排水泵异常，
> 处理步骤毫无交集）。所以用户只说"空调显示 E4"时，系统**必须反问是哪一台**，
> 挑一台猜就会给出一段格式权威但完全不适用的答案。
>
> 为什么要刻意这么设计：如果两台同型号，"型号过滤"这条约束在演示和测试里都不可见，
> 等于摆设。有了这个差异，它才是一条能被验证的约束——我有一条用例专门断言
> 同一个 E4 在两台设备上答出的内容互不包含对方的关键词。

**"实体消解具体怎么做的？"**

> 结果是**四态**而不是"型号或 None"：定位到唯一设备叫 `resolved`；对上多台叫 `ambiguous`；
> 定位到设备但它没登记型号叫 `no_model`；连是哪台都没解析出来叫 `unknown`。
> **后三种一律不进检索**，代码里没有"兜底成不带型号搜全库"这个分支。
>
> 配套做了一件小事但我觉得挺关键：检索函数的 `model` 参数是**关键字必填**的。
> 全库检索仍然做得到，但必须由调用方显式写出来——**不能是漏传参数的副产品**。
>
> 消解顺序是 显式设备名 > 类型关键词 > 可信上下文。用户明确说了"卧室空调"就不能被
> App 当前所在房间覆盖；用户只说"空调"时，才用可信空间（来自请求上下文、不是模型生成的
> 房间/设备 ID）去消解多候选。这里复用的是整个项目的可信身份边界。

**"怎么保证不胡说？"**

> 三层：强制引用（不能溯源不输出）、拒答纪律（检索不到就说不知道）、
> 以及能自证的检查项走真实设备状态而不走模型推断。
>
> 强制引用是**结构保证而不是提示词请求**：模型只负责写处理建议，
> 并且被明确要求不要复述核对结果和来源；来源块和核对结果块都是**代码拼的**。
> 模型无论怎么发挥，来源都在，且指向真实被检索到的小节。
> 模型不可用或调用失败时退回原文片段拼接——信息量下降，但引用和核对结论一个不少。

## 三、第三点：自动化编排

### 故事怎么讲

你举的"起床前烧热水 + 准时唤醒"这个例子选得非常好，因为它天然包含**倒推**。
一定要把这层挑明——这是整点的核心洞察。

> 用户说的是"我明天 7 点起床"。落地的是五个动作、三个不同时刻：

| 时刻 | 偏移 | 动作 | 为什么是这个值 |
|---|---|---|---|
| 6:30 | **-30** | 卫生间电热水器 → 45°C | 洗澡水，水箱加热要半小时 |
| 6:50 | **-10** | 厨房烧水壶 → 80°C | 冲牛奶，壶小烧得快；80°C 而非 100°C 是因为用途是冲奶 |
| 7:00 | 0 | 闹钟 + 卧室窗帘打开 + 卧室灯 40% | 唤醒动作本体 |

> **一句话意图产生了一组不同时刻、不同参数的任务——所以自动化不是定时器，
> 是从目标时间倒推的任务图。**

**"两种热水"这个细节一定要讲**：洗澡水和饮用水是**两台设备、两个提前量、两个目标温度**。
偏移承载的是**物理准备时间**的差异，参数承载的是**用途**的差异。
如果做成"起床时把水烧上"，用户 7 点起床得等到 7:30 才能洗澡——
**这个例程的全部价值就在提前量里**，而提前量必须来自对设备物理特性的建模。

由此推出的设计（每一条都是真实的系统设计问题，后端面试官很吃这套）：

**1. 锚点 + 偏移，而不是五个独立定时器。**
> 例程锚定在**目标时刻**（7:00 起床），每个动作带自己的偏移（-30 热水器 / -10 烧水壶 / 0 唤醒组）。
> 用户改成 6:30 起床，整组任务一起平移。
> 如果做成五个独立定时器，改一次时间要改五处，**迟早漂移**——这是数据冗余的经典后果。

**2. 默认提前量是「规划建议」，不是隐藏的执行规则。**

> 系统内置一张默认提前量表（热水器 30 / 空调 20 / 烧水壶 10 / 窗帘 2 / 灯 0 分钟），
> 但它的定位是**喂给规划环节的建议值**——用户明确说了"提前一小时"就用用户的。
>
> 这个区分很重要：如果默认值在执行时才悄悄生效，它就成了**暗箱**——
> 用户看到的计划是一套，实际执行是另一套。**默认值必须在生成计划时就展开成显式参数，
> 让用户在审批时看到的就是最终会执行的东西。**

**3. 有些动作必须在创建时就落地，不能等到点。**
> 闹钟就是典型：你要在**创建例程的那一刻**把闹钟设进去，
> 而不是 7 点到了再去"设一个 7 点的闹钟"——那时候人已经该被叫醒了。
> 所以闹钟这个动作的到期时间是**创建时刻**，不是锚点时刻。

这个细节很小，但极有说服力，因为它证明你想过语义而不是套模板。**建议一定讲。**

**4. 定时任务的失败成本极高，所以所有检查都前移到创建时刻。**

这是我认为第三点里最值钱的一条，它有一个统一的理由：

> 一条例程创建于晚上、触发于凌晨六点半。**它失败的时候没有人在场处理，
> 也没有人可以反问。** 所以任何能在创建时发现的问题，绝不能留到触发时。
>
> 创建路径上因此有三道防御，全部在写库之前：
>
> 1. **归一化模型输出**。真实模型会输出 Home Assistant 风格的 `turn_on`/`turn_off`
>    （训练数据里 HA 太多）、会给设备 ID 而不是设备名、还会把 JSON 数组**双重字符串化**。
>    这些都做归一，但**解码次数有上限**（最多两次）——畸形输入要确定性失败，不能让解析循环下去。
> 2. **可执行性预检**。用跟正式执行完全相同的那套校验，检查设备是否存在、动作是否支持、
>    参数是否在合法区间。**创建时就报错让用户改，而不是半夜静默失败。**
> 3. **schema 层硬拒绝**。定时解锁门锁在 Pydantic 校验器里直接拒掉，
>    不是靠文档约定、也不是靠 prompt 叮嘱模型别这么干。

**升华句：交互式请求可以失败后追问，定时任务不行——没有人在的时候，
系统的容错窗口是零，所以校验必须前移。**

**5. 触发源不只有时间。**
> 车辆 ETA 是事件触发：你在回家路上，系统按预计到达时间提前开空调。
> 但 ETA 会变（堵车），更新时**只能移动尚未执行的任务**——已经执行的不能撤回，
> 空调已经开了就是开了。**幂等性在这里的具体形态是：调度可以改，执行不可回滚。**
>
> 顺带一个可讲的对比：车辆例程的热水器提前量是 **-15 分钟**，起床例程是 **-30 分钟**，
> 同一台设备、两个值。**理由是触发源的确定性不同**：固定时间是确定的，可以放心提前；
> ETA 是预测，提前量越大，预测偏差造成的浪费越大。
> **提前量不只取决于设备的物理特性，还取决于触发时刻本身有多可信。**

**6. 去重要在存储层做。**

> 同一个例程、同一次触发、同一个动作只能执行一次。用**唯一约束**保证，
> 而不是"先查再插"——后者在并发下有 TOCTOU 窗口。

**7. 跑在对话图之外。**

> 对话图的生命周期是**一次请求**；例程要跨进程持久化、按时间自己醒来。
> 塞进图里等于让图同时承担编排和调度两个职责。
> 所以是独立的持久化调度子系统，SQLite 落库 + 后台调度线程。
> **知道框架的边界在哪，比多用框架的功能更重要。**

**8. 动作集随执行上下文收紧——而且是在 schema 层强制的。**
> 后台执行时没有人可以审批：定时任务触发的时候用户可能在睡觉。
> 所以自动化能开空调、能烧水，**不含门锁解锁**这类不可逆动作；创建例程本身则一律走人工审批。
>
> 关键是**这条约束的实现位置**：定时解锁在 Pydantic 校验器里直接拒绝，
> 车辆例程的元数据里另有一个显式标记——**不是写在文档里的约定，也不是 prompt 里的叮嘱**。
> 安全约束写在 prompt 里等于没写，写在 schema 里才是真的关上了。
>
> **安全边界随执行上下文收紧**，这跟第一点的 HITL 是同一个原则的两个位置。

**9. 时间作为参数注入，所以调度逻辑完全可测。**
> 调度器的 tick 接受一个"当前时间"参数，后台线程只是按固定间隔调用它。
> 业务逻辑跟真实时钟解耦，**定时测试零 sleep、完全确定**。
> 很多人的定时任务测试靠 sleep，又慢又 flaky。

### 面试追问

**"任务执行失败了怎么办？没人在场。"**
> 后台动作同样按真实设备状态验证。但这里没有人在回路可以求助，
> 所以策略是**明确记录并在下次对话时主动告知用户**，而不是静默重试掩盖。
> 静默重试在物理世界里很危险——你不知道第一次到底有没有生效。

**"为什么不用 cron / APScheduler？"**

> 单个任务用 cron 就够。这里的复杂度不在"到点执行"，
> 在**一组任务共享一个可变锚点**、ETA 事件会重排未执行任务、以及去重与执行验证。
> 这些是业务语义，不是调度器的职责。

### 换一版写法（建议用这版）

```
智能家居 AI Agent | Python · LangGraph · Pydantic · SQLite · MCP（个人项目，13 轮迭代）

• 四条执行路径按任务性质分派：单步指令走 ReAct，多步跨设备走 Planner–Executor–Verifier，
```

**改了什么**（以后你自己改别处也照这几条）：

- **删掉四处"不是 X 而是 Y"。** 原稿里"而非套用单一 ReAct""而非模型自述""而非默认通过""而非提示词约定"连着出现四次，同一修辞用四遍是最明显的机器味。改成直接陈述——"不采信模型自述""不经模型改写"，语义一样，不摆对比架势。
- **删掉名词化。** "使强制溯源成为结构保证""以设备真实状态为唯一事实来源"这类"使……成为""以……为"是公文句式。换成"来源清单与核对结果由代码拼接，不经模型改写"。
- **删掉自我评价。** "把文档问答变成可执行诊断"是替面试官下结论。把三条自证项列出来，结论他自己会得出。
- **换成真标识符。** `expected_state` / `problem_type` / `dedupe_key` / `model` 字段——写得出字段名的人显然真写过这份代码，比"确定性错误跳过重试"这种抽象转述可信。
- **长分号句拆开。** 原稿一个 bullet 是一句话套五个分号，读到末尾已经忘了主语。

**分寸在哪：目标是技术书面语，两头都不要。** 往上过头是公文腔（使……成为、旨在、从而实现），往下过头是口语（核掉、拒掉、碰不到、一次模型都不调）。判断方法很简单：**这句话能不能出现在一份正经的设计文档里**——能，就对了；像在跟同事口头解释，就收一收。

空间不够时按这个顺序删：第三条的 ETA 重排与去重 → 第一条的失败分流细节 → 第二条的 E4 例子（这个例子最好留着，面试官最容易顺着它追问）。

**30 秒口述版：**

> 一个智能家居 Agent。我把它拆成三条路径：**怎么做、为什么不工作、什么时候做**。
>
> "怎么做"是控制路径——我没有套单一的 ReAct 循环，而是按任务性质分派四种范式，
> 因为单步指令和多步跨设备任务的可靠性—成本曲线完全不同，而预定义场景根本不该让模型规划。
> 多步任务的成败不由模型自述，读设备真实状态验证。
>
> "为什么不工作"是排障路径——存厂商说明书做检索，因为错误码这种东西**有确定答案，不该猜**。
> 而且检索前必须先定到具体设备和型号：我家两台空调型号不同，同一个 E4 一个是通信异常、
> 一个是排水泵异常，定不下来就反问，绝不挑一台猜。
> 有意思的是说明书给的检查项里有一部分系统自己能核对——"制冷效果不佳"那节五条里有三条
> （是否开机、设定温度是否低于室温、模式是否为制冷）我直接读设备和传感器的真实状态核掉，
> 剩下两条物理检查才交给用户，并且明确告诉他哪部分是哪种。
>
> "什么时候做"是自动化路径——"明早 7 点起床"要倒推成一组任务：6:30 烧洗澡水（水箱慢，
> 要半小时）、6:50 烧饮用水（壶小，十分钟）、7:00 闹钟加窗帘加灯。
> 所以它不是定时器，是锚点加偏移的任务图，锚点一改整组平移，**提前量来自对设备物理特性的建模**。
> 而且这条路径没有人在场，所以所有校验都前移到创建时刻——半夜静默失败是没法补救的。
>
> 三条路径共用同一个事实来源：设备真实状态。而人在回路的强度随用户是否在场收紧——
> 对话里的解锁要审批，后台自动化直接不含不可逆动作。
