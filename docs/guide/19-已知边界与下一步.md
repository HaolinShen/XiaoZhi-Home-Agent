# 第 19 章 已知边界与下一步

这一章把项目还没修的洞逐条摊开，给出严重度、根因和修法方向，最后排一张按「学习收益 / 工作量」排序的练习清单。

## 19.1 为什么要有这一章

前面十八章讲的都是「这里做对了什么」。这一章讲反面。

一个教学项目的价值恰恰在于**边界是可见的**。你用过的任何商业产品，它的文档都不会告诉你「我们的鉴权只在编排层做，绕过编排层的入口没有保护」——不是因为它没这个问题，而是因为公开写出来等于发漏洞公告。于是你从产品文档里学不到最重要的那件事：**怎么识别自己系统的洞**。

这章的材料来自 `docs/gap-analysis.md`：一份从学习者视角做的现状盘点，每条结论标注了证据强度（【实测】= 跑过脚本，【审查】= 读代码推断）。本章写作时逐条回到代码里复核过一遍，哪些还在、哪些已经修掉，19.5 和文末的核对结论都是复核后的结果。

先把语气定准。这个项目：

- 设备全部跑在**模拟器**上（`src/devices/simulator.py`），没有一行代码连真实硬件；
- 只有一个本地 CLI 用户，没有多租户、没有公网入口；
- 全套测试当前 **264 passed, 383 subtests passed**，机制层面（权限边界、数据库状态、设备真实副作用、Checkpoint 恢复、事件顺序）覆盖得相当扎实。

所以下面这些洞**不是「这个项目很危险」**，也**不是「小瑕疵」**。准确的说法是：在这个跑模拟器的教学场景里它们不造成损害，但**任何一条在接真实门锁之前都必须补上**。你要学的就是把这两句话分清楚。

## 19.2 安全与人在回路的洞

三条都跟同一件事有关：第 7 章那套人在回路（HITL）审批，覆盖范围比它看起来的小。按严重度排。

### 洞一：MCP 入口零审批暴露 `unlock`（`gap-analysis.md` 1.2，严重度：高）

**现象。** 图内 `control_lock(action="unlock")` 是全项目唯一 `risk_level="high"` 的动作，必须人工按 y 才执行（`src/agent/approval.py:23-32` 判定，`:97` 定级）。而 `src/mcp/server.py:205-213` 的 `control_lock_mcp` 是同一个工具的薄包装，没有任何拦截：

```python
@mcp.tool()
async def control_lock_mcp(device_name: str, action: str) -> str:
    """控制智能门锁上锁与解锁（解锁属于敏感动作）。
    :param action: lock(上锁), unlock(解锁)
    """
    return built["control_lock"].invoke({...})
```

docstring 第 209 行还**主动把 `unlock` 文档化给了外部客户端**。实测走这条路（`built["control_lock"].invoke(...)`，与 MCP 包装内部做的事逐字一致）：

```
MCP 薄包装 unlock -> ✅ 玄关门锁已解锁。
执行后: {'device_id': 'entryway_lock', 'name': '玄关门锁', ..., 'locked': False}
```

零提示、零暂停，锁真的开了。对 `src/mcp/server.py` 全文 grep `interrupt` / `approval` / `home_id` / `user_id`：**零命中**。`activate_scene_mcp`（`:248-253`）同理。

**根因不是漏写，是架构层次。** 审批实现在编排层——图节点里调 `interrupt()`（第 7 章）。MCP server 是**另一个进程入口**，它拿到的是 `build_all_tools()` 返回的工具对象，根本不经过图：

```
CLI ────→ build_graph() ──→ agent  ──→ [build_approval_request] ──→ tools
                        └─→ planner ──→ [plan_approval_payload]  ──→ executor
                            └────────── 审批只装在这一层 ──────────┘

Claude Desktop ──→ src/mcp/server.py ──→ built["control_lock"].invoke(...)   ← 绕开
后台调度线程   ──→ RoutineExecutor    ──→ self.tools[name].invoke(...)        ← 绕开
```

**怎么修。** 两个方向，第二个更值得学：

1. **每个入口各自重复一遍。** 在 `control_lock_mcp` 里判 `action == "unlock"` 就拒绝（MCP 协议没有 `interrupt` 这种带外交互，拒绝比征求同意现实）。三十行能完事，但这是第三份手写副本了——见下一条。
2. **把风险声明下沉到所有入口共用的那一层。** `src/devices/capabilities.py:84-93` 的 `ActionSpec` 现在有 `name` / `signature` / `doc` / `expected` / `handler` / `precheck` / `preference` 七个字段，**没有 `risk`**。加上它，让审批判定从声明派生（第 3 章讲过这套单一数据源的收益）。这样新增一个敏感动作时，所有入口自动跟上。

> **概念**：安全边界必须在**每个入口**重复，或者下沉到所有入口共用的那一层。「在编排器里做鉴权」是分布式系统里的经典反模式。

### 洞二：审批绑定「工具名」而非「效果」（`gap-analysis.md` 1.3，严重度：高）

**现象。** `src/agent/approval.py:78-81` 的 `risky_calls` 按**工具名**过滤：

```python
risky_calls = [
    call for call in tool_calls
    if call.get("name") == "activate_scene" or _is_unlock_call(call) or _is_automation_call(call)
]
```

于是效果等价的两种做法，审批状态完全不同。实测：

```
activate_scene('回家模式')                    -> medium（需要审批）
control_light + control_ac + control_curtain -> None（零审批直接执行）
control_lock unlock                          -> high
```

第二行改的设备和第一行几乎一样，一次确认都没有。

**根因。** 审批锚定的是「模型挑了哪个工具」，不是「产生了什么物理效果」。而**挑哪个工具是模型的自由**——这就是关键：**这不需要恶意提示词**。用户说「帮我把客厅调成回家的样子」，模型**自然可能**拆成三个单设备调用；说「启用回家模式」，才会走 `activate_scene`。同一个意图、同一个结果，审批凭措辞时有时无。

（一处澄清：`control_lock(action='lock')` 不需审批是**正确的刻意设计**——上锁是收拢安全边界，注释写在 `approval.py:23-28`。这条不算缺陷。）

顺着这条往下看会发现更有意思的事：「unlock 是敏感动作」这一条规则，在项目里被**三个入口各自实现了一遍，而且做法都不同**：

| 入口 | 位置 | 做法 |
|---|---|---|
| 图 / ReAct | `approval.py:23-32` `_is_unlock_call` | `interrupt()` 征求同意 |
| 后台自动化 | `automation/planning.py:62-66` `reject_scheduled_unlock` | pydantic 校验器直接**禁止**（定时解锁一律拒绝） |
| MCP server | — | **无** |
| Planner 路径 | — | 见洞三（能规划，但审批文案里看不见） |

三份实现、三种语义、一处遗漏。这正是洞一说的「下沉到共用那一层」要解决的问题：规则应该在 `ActionSpec` 上声明一次，各入口读它。

**怎么修。** 把审批的判定输入从「工具名」换成「动作对物理世界的影响面」。可行的最小版本：给每个 `ActionSpec` 标 `risk`，再在 `build_approval_request` 里对**一批** `tool_calls` 做聚合判断——比如「一次调用里跨 ≥3 类设备」本身就构成一个需要确认的效果，无论模型用的是场景工具还是单设备工具。

### 洞三：Planner 路径的审批文案是模型自己写的（`gap-analysis.md` 1.4，严重度：高）

**现象。** 三处叠加造成的：

- `src/agent/graph.py:441-451` 的 `plan_approval_node` 只调 `plan_approval_payload`，**从不调用 `build_approval_request`**（后者只出现在 ReAct 路径的 `graph.py:773`）；
- `src/agent/planning.py:148-159` 的 `plan_approval_payload` 里，`risk_level` **硬编码 `"medium"`**（`:156`），跟计划里有没有 `unlock` 无关；`question` 由模型自己写的 `step["description"]` 拼成（`:151`、`:155`）；返回的 payload **根本没有 `tool_calls` 键**；
- `src/main.py:255-266` 的 `_ask_for_approval` 只渲染 `payload.get("question")`（`:259`），从不展示底层动作。

`control_lock` 在 `PLANNING_TOOL_NAMES` 里（第 5 章：这个元组从能力声明派生），所以 Planner 可以正常规划解锁。实测把一份含 unlock 的计划喂给 `plan_approval_payload`：

```
control_lock 可被 Planner 规划: True
risk_level = medium
payload 有没有 tool_calls 键 -> False

--- CLI 展示给用户的全部内容 ---
已生成 2 步执行计划，是否开始执行？
1. 打开客厅灯
2. 准备门口环境          ← 模型措辞里一个"解锁"都没有

--- 实际会执行 ---
control_light({'device_name': '客厅灯', 'action': 'turn_on'})
control_lock({'device_name': '玄关门锁', 'action': 'unlock'})
```

**根因。** 给人看的东西不是事实，是模型的作文。第 6 章反复讲「不要相信模型说它做完了，去查真实设备状态」——这里犯的是同一个错误的另一半：**审批环节把「模型说它要做什么」当成了「它实际会做什么」**。而这两者之间隔着一整个 `arguments` 字典，模型完全有余地写一句无害的 `description`。

这是 HITL 最危险的失效模式：**它看起来在工作**。用户看到了确认框，按了 y，全程有仪式感——但他批准的是模型的**说法**，不是模型的**行为**。这恰好废掉了人在回路的全部意义。相比之下，「审批根本没弹出来」（洞一、洞二）反而更容易被发现。

**怎么修。** 让 payload 从 `plan["steps"]` 的 `tool_name` + `arguments` **机器生成**动作明细，风险等级同样从实际动作推导（含 unlock → high），`_ask_for_approval` 展示这份明细而不是 `question` 一行。配套测试要钉住的不是文案，而是不变量：「含 unlock 的计划必须 `risk_level == "high"`」「展示文本必须包含 `unlock` 字面量」。

> **概念**：HITL 的展示内容必须是**机器从 `tool_calls` 生成的事实**，不能是模型撰写的摘要。风险等级同理，必须从实际动作推导。

## 19.3 两个学科级缺口

上面三条是「实现里少了一段」。下面两条不一样——它们缺的是整个学科，补它们学到的东西跨项目通用。

### 19.3.1 没有评测体系（`gap-analysis.md` 2.1，学习价值最高）

> **2026-08-31 更新**：013 迭代补上了**四维中的一维**（RAG 召回质量）。下面的盘点原文保留，
> 因为**四分之三仍然是这个状态**，而且它描述的「零评测」是理解这一节为什么重要的起点。

**现状盘点。**

- `src/evaluation/trajectory.py` 全文 **18 行**，一个纯函数 `evaluate_rag_trajectory`；
- 唯一调用点是 `tests/test_phase_twelve.py:80`，喂给它的是**手写字面量 dict**，不是 `graph.invoke()` 的真实输出；
- ~~全仓库 `.jsonl` / `.yaml` / `.csv` 数据集数量为 **0**~~ → 013 起有一份 `evals/knowledge_recall.json`，**63 条 golden 用例**；
- ~~没有 `evals/`、没有 eval 命令~~ → 都有了（`python -m src.evaluation.recall`，`--offline` 无 Key 可跑、`--sweep` 扫参标阈值）；**仍然没有 `.github/`（CI 不存在）**；
- 全部测试用 FakeLLM（第 17 章）——**没有一项在衡量真实模型行为**（那个评测 runner 也一样：它测检索，不测 LLM）。

~~四个关键维度全缺测量~~ —— 013 之后是**一有三缺**：

| 维度 | 状态 |
|---|---|
| RAG 召回质量 | **013 已补**：Recall@1 51.8% → 87.5%，口语查询 3/30 → 23/30，拒答准确率全程 100% |
| 路由准确率 | 仍缺 |
| Planner 计划质量 | 仍缺 |
| 端到端任务成功率 | 仍缺 |

**补掉的恰好是最容易的那一维**，这一点要说清楚，否则这节的教学价值会被误读：检索是纯函数，
`source#section` 是能逐字比对的标签，golden 用例写起来是机械劳动。剩下三维都要先回答一个真问题——
**「正确答案不唯一」时怎么打分**：一个多步计划有几种合法写法？端到端「成功」怎么定义？
013 一个都没回答。所以这一条依然是全书学习价值最高的缺口。

**为什么这是「学科级」而不是「还缺个功能」。** Agent 工程与传统软件最本质的区别，是被测系统**非确定性**。现有 264 项测试钉住的是机制正确性，这部分做得比多数教学项目都好。但假设你改了 `intent_router_prompt` 里的一行措辞，意图分类准确率从 92% 掉到 71%——**当前测试全绿，没有任何信号**。你会在几周后从用户抱怨里发现它。

同一类盲区在这个项目里已经真实咬过两次（都不是模型行为问题，而是「测试钉住了数据结构，没钉住真实执行路径」）：

1. `UsageTracer._log` 的格式串引用了一个从未被赋值的 `model` 键。真实 CLI 每轮打三行 `Error in UsageTracer.on_llm_end callback: KeyError('model')`，token 日志一条都不落盘。原有两条用例都注入了自定义 sink，**那条唯一有 bug 的路径从未被执行过**。更糟的是异常被 LangChain 回调管理器吞成一行 stderr，业务照常跑完——**度量静默归零比没有度量更糟**。
2. 第 12 章那个切断工具调用配对的 bug，靠一份把错误行为编码成预期的 fixture 活了很久。

两条都在说同一句话：**测试通过 ≠ 那条路径被执行过**。

**一条可执行的补法**，分两档，第一档不需要 API Key：

**离线档。** 攒一个 golden 数据集，一行一条：`{"query": "...", "expected_intent": "...", "expected_planner": true/false, "expected_source": "..."}`。放 `evals/routing.jsonl` 之类的位置。然后写一个 runner 遍历它，对三块**纯函数**打分——这三块本来就不需要模型：

| 被测对象 | 位置 | 断言什么 |
|---|---|---|
| 意图分类的确定性兜底 | `heuristics.py` 的 `ROUTING_*` 词表 + `routing.py:60-78` `classify_intent_fallback` | 预测 intent == 期望 intent 的比例 |
| 是否走 Planner 的正则 | `heuristics.py:56` `should_use_planner` | 混淆矩阵（假阳性最要命：把单设备请求送进 Planner） |
| ~~RAG 词法检索~~ **013 已做** | `evals/knowledge_recall.json` + `src/evaluation/recall.py` | 期望的 `source#section` 是否进了 top_k（Recall@1 / @3 / MRR / 拒答准确率） |

输出一张分维度的分数表，**跑法跟测试一样一条命令**：

```bash
# 013 已经落地的那一维，可以直接跑
PYTHONIOENCODING=utf-8 "F:/Software/Anaconda/envs/langgraph/python.exe" -m src.evaluation.recall --offline
```

> **上面表格的第三行现在是可照抄的样板。** 前两行还没人做，但骨架已经有了：
> 数据集是纯声明的 JSON、runner 遍历它、输出一张分维度分数表、`--offline` 保证无 Key 可跑。
> 从 013 顺手抄走两条纪律会省很多事：① **阈值要扫参扫出来，不是手调的**
> （`--sweep` 在网格上跑全部用例，证明 0.35 这一格对权重不敏感，所以不是拟合某一条用例）；
> ② **数据集里必须有你真实踩过的坑**——013 刻意在语料里留了两处缺口（客厅灯不登记 `model`、
> FrostLine 的症状手册没有噪音章节）当**被测行为**，守住的正是拒答那条路。

关键纪律有两条：① 断言的是**聚合分数有没有跌破阈值**（比如路由准确率 ≥ 0.85），不是逐条精确匹配——非确定性系统不该要求满分；② 数据集里必须有你**真实踩过的坑**，比如「明天 6 点回家前开空调」不能被判成预定义回家模式（第 9 章那条硬约束）。

**真实模型档。** 同一份数据集打真实端点，产出可对比的分数。这一档必须能在无 Key 时跳过，否则 CI 跑不了。

项目自己也意识到了——`docs/iterations/011-engineering-hardening.md` 结尾写「结构收口后，拟真语料回归集才有稳定的底座」。**底座已经有了，回归集建了四分之一。**

### 19.3.2 LLM 被当成「总会成功返回合法结果」的依赖（`gap-analysis.md` 2.2）

四个 LLM 调用点，只有一个有防护：

| 调用点 | 位置 | 防护 |
|---|---|---|
| 意图分类 | `routing.py:89-95` | ✅ `try/except` + 关键词兜底 |
| ReAct 主调用 | `graph.py:691` | ❌ 裸 `invoke` |
| 自动化纠正重试 | `graph.py:719` | ❌ 裸 `invoke` |
| Planner 结构化输出 | `graph.py:400` | ❌ 裸 `invoke` |

全库 `with_fallbacks` / `include_raw`：**零命中**。

具体会怎么坏？LLM 有两类失败，都没处理：

- **网络类**：超时、限流（429）、端点 5xx。裸 `invoke` 让异常一路冒到 `src/main.py:421-423`，那里 `console.print(f"出现错误: {e}")` 把原始英文异常打给用户。
- **生成类**：返回空内容、结构化输出违约。Planner 这处尤其值得看——`ExecutionPlan` 的约束很紧（`steps` 有 `min_length=2`，`tool_name` 是从能力声明派生的 `Literal`），schema 违约直接 `ValidationError` 冒泡。而 `planning.py:40-51` 的注释详细记录了「模型会写 Home Assistant 风格的 `turn_on`，这是规划第一版反复失败的根因」，解法是把合法值写进 prompt——**纯 prompt 约束，零运行时兜底**。prompt 是概率性的，约束不是。

**怎么修。** `routing.py` 已经示范了正确形状，把同一模式推广到另外三处。但有个坑必须先知道：`src/middleware/interceptors.py:6-21` 已经写清了「无条件 `except Exception` 会吞掉 `GraphInterrupt`，破坏审批语义」——用户还没回答，同一个节点就又跑了一遍。所以 `except` 必须按异常类型判断，至少排除 `GraphInterrupt` 和 `KeyboardInterrupt`。

（那个模块本身也是个教学样本：**保留代码 + 诚实说明为何未启用**，比直接删掉更有价值。）

> **概念**：LLM 是网络依赖 + 概率性生成器，两种失败都要处理。

## 19.4 次要但值得知道

五条，每条两三句（例外是 ④——它已经被修掉了，改成讲修完之后**换来的**那批边界，所以长一些）。严重度都不高，但都指着一个值得记住的概念。

**① 上下文预算算错了对象**（`gap-analysis.md` 3.1）。`graph.py:292` 把 `max_tokens=2400` 传给裁剪器，它只约束**消息历史**。实测同口径（`(字符数+1)//2`）估算，真实请求体里还有：system prompt 3708 字符 ≈ 1854 token，21 个工具的 JSON Schema 15645 字符 ≈ 7823 token——**后者单项就是整个预算的三倍多，而两项都不在预算内**。于是 `graph.py:299-300` 打出「上下文规模 | messages=12 | estimated_tokens=42」时，真实请求可能是它的几十倍。护栏给的是虚假安全感。**预算必须对完整请求体计数，而且该用真实 tokenizer 而非字符数近似。** 参见第 12 章。

**② `Send` 动态并行没有并行任何东西**（3.2）。`parallel.py:52-53` 的 `fan_out` 扇出 N 个分支，但每个 `query_device`（`:55-61`）只做一次 `registry.get()` 内存字典查找——零 IO、零 LLM。fan-out + reducer 的调度开销**大于**直接循环。它演示了 `Send` 的**机制**，没演示 `Send` 解决的**问题**。而真正该并行的地方反而是串行的：`mcp/client.py:186-190` 在 `for` 循环里逐个发现服务，`:157` / `:181` 每次工具调用都重开会话（stdio 下等于每次拉起一个新子进程）；整个 `src/` 除 `src/mcp/` 外**零 `async def`**。**并行的收益来自 IO 等待的重叠。** 参见第 10 章。

**③ Prompt injection 面**（3.3）。两处不可信输入无隔离地进入 system prompt：`graph.py:190-198` 把远端 MCP server 返回的 `tool.description` 无条件拼进去（远端改一行描述就能改变本地 Agent 行为）；`graph.py:250-263` 把记忆的 `memory_value` 原样格式化进 `memory_context`，再由 `:677` 拼进 system prompt——记忆是**跨会话持久化**的，所以这是存储型注入面。当前唯一防护是 `graph.py:680` 那句自然语言祈使句「这些标识来自受信任的业务上下文，不得根据用户文本改写」，它保护的是身份字段，不覆盖记忆内容和远端描述。**不可信输入要么隔离到 user 消息里，要么显式标注边界；「请模型别照做」不是控制手段。** 参见第 8、12、16 章。

**④ RAG 已经不是「词法检索 + 粘贴」了，但换来了一批新边界**（3.4）。这一条**过时过两轮**，原文说的是「`rag.py` 全路径一次 LLM 都没调、`graph.py` 为 knowledge 角色准备的专用 LLM 永远用不到、语料是 4 个文件共 1550 字节」——现在三句全不成立。012 接入了 LLM 综合（负责查询重写与答案正文，而「自动核对结果」块和「来源」块由**代码拼接**、不经模型改写），013 又上了 **BM25 + 向量双通道混合检索**和一份**召回评测集**。实测收益是硬的：口语查询召回 **3/30 → 23/30**，Recall@1 **51.8% → 87.5%**，语料 5 份 → **39 份 / 124 个 chunk / 13 个型号**（覆盖全部 10 种设备类型），自证检查 3 条 → **12 条**（不再只有空调），而拒答准确率**全程 100%**。所以这一条不再是「它教的是检索，不是 RAG 的 G」——完整设计与全部实测数字见 `docs/iterations/013-hybrid-retrieval.md`，讲透在第 13 章。

**013 留下的四条新边界**，都是量出来的，比上面那条旧账更值得记住：

1. **绝对置信度分不开「对的症状」和「同一台电器的另一个症状」。** 在 63 条用例上统计 `text-embedding-v4` 的余弦：正例中位 **0.653**，困难负例（同型号的**其它**症状小节）中位 **0.568**，两条分布**大幅重叠**。代价直接落在拒答闸门的余量上——最高的假阳性是 **0.336**（「卧室空调有点响」命中 FrostLine 的「制冷效果不佳」），离阈值 0.35 **只有 4% 余量**。**这道闸门的可靠性其实来自词法通道，不是来自阈值调得准**：「响 / 噪音」在 FrostLine 全文一个都没有，BM25 直接返回 0——「这份说明书没讲这件事」只有 BM25 说得出来。**所以不许为了召回率把 `RAG_BM25_WEIGHT` 清零**，尽管纯向量的 Recall@3（94.6% vs 89.3%）和 MRR（0.908 vs 0.881）确实更好：那条路会让 embedding 一挂就**全部**拒答。
2. **确定性的代价真实发生了，只是发生在生产侧。** 第 13 章当初把「换个 embedding 版本，测试断言可能全变」列为上向量检索最贵的一项。测试侧用 stub 躲掉了（语义通道是**显式注入的依赖**，所以仍然离线、确定性、不要 Key），**生产侧躲不掉**：余弦的两个刻度（噪声基线 0.42 / 强命中 0.70）是对 `text-embedding-v4` 实测标定的，**换模型必须重测**。这不是消灭了那个问题，是把它从测试挪到了部署。
3. **召回评测只测首轮检索。** 不测端到端任务成功率、不测真实 LLM 的综合质量、也不测查询重写（刻意的：要回答的问题是「语义通道能不能替掉那张人工症状词表」，把重写也跑上等于让词表替检索背书）。所以 87.5% 是**检索层**的数字，不能当成「说明书问答答对率」念。
4. **BM25 的噪声基线依赖语料规模。** 3.5 这个数由 IDF 和平均文档长度决定，两者都是语料级统计量，**换语料必须 `--sweep` 重标**。已经踩过一次：拿三个 chunk 的合成语料写测试，所有 BM25 分数都远低于 3.5，测出来的是「基线没标定」而不是被测的机制。

（还有个残留：`_SYMPTOM_LEXICON` 那五条空调正则**还在**，定位从「语义泛化的唯一手段」降级成「没配 embedding 时的确定性兜底」。要不要给另外十二个型号补词表，取决于离线配置是不是一个需要认真支持的场景——013 没有下这个判断。）

## 19.5 已经修掉的（同样重要）

看修好的东西和看没修的一样有教学价值，因为你能看到「修法」长什么样。

### 修掉的一：对话裁剪切断「工具调用 ↔ 工具结果」的配对

**原来的 bug。** 一次工具调用在历史里是**一对**消息：带 `tool_calls` 的 `AIMessage`（问题）+ 带同一 `tool_call_id` 的 `ToolMessage`（答案）。OpenAI 兼容协议**强制**要求配对——请求体里出现了答案却找不到问题，服务端直接 400。而裁剪窗口的起点 `keep_from` 由「消息条数」和「估算字符长度」算出，这两个量跟配对关系毫无关系，刀口落在哪纯属巧合。加上 `RemoveMessage` 会把窗口外的消息**从 SQLite 物理删除**，父消息不是「这轮没带上」而是没了。

实测口径（穷举 243 段对话、4455 个裁剪点）：**真正发生裁剪的调用里，30.8% 产出孤儿**；会话维度 85.2% 至少踩一次。症状是「长对话偶尔莫名报一次错，重问一遍就好」——因为下一轮孤儿把自己挤出窗口，**问题自愈**，是最难查的那类间歇性故障。

**修法。** 不去改那两道闸门（它们永远不会知道配对关系），而是在它们算完之后**加一道对齐**（`src/memory/summarizer.py:33-57` `_align_window_start`，调用点 `:82`），守住一条不变量：**窗口首条不能是 `ToolMessage`**。策略是「优先前进，前进不通才后退」——默认向后跳过孤儿结果（窗口只会变小，预算天然仍满足）；只有当 `keep_from` 之后全是 `ToolMessage`、前进会清空窗口时才后退去带上父消息，**刻意接受那点预算超支**（超预算最坏是账单大一点，非法请求体是必然 400）。

同时修了 token 估算：`_billable_chars`（`:15-30`）把 `tool_calls` 的工具名和参数字符数也计入——带 `tool_calls` 的 `AIMessage` 其 `content` 通常是空串，原来整个调用载荷被 `max(1, ...)` 兜底成 1 token，预算护栏恰好在最需要它的地方（工具密集的长对话）失效。

**从中学到什么。** 三点：

1. **协议不变量要有专门一步兜住。** 不要指望按长度算出来的东西顺便满足按结构定义的约束。
2. **规整的语料会系统性地掩盖 bug。** 第一次写复现脚本用「每轮固定 1 次工具调用」的 FakeLLM，修复前后都是 0 孤儿，一度以为复现不了——那种对话每轮恰好 4 条消息，历史长度永远是 4 的倍数，`keep_from` 必然落在 `HumanMessage` 上。把每轮次数改成 0/1/2 混合、破坏长度周期性，立刻稳定复现。**手写测试 fixture 天然是规整的**，这正是这个 bug 能活下来的原因。
3. **bug 能长期存活，往往是因为有测试在保护它。** 修完之后一条旧用例失败了，根因不是新代码有问题，而是那个 fixture 用了一条**没有父消息的裸 `ToolMessage`**——现实中不会出现的形状，把错误行为编码成了预期。一份不合法的 fixture 让绿灯变成了噪音。

回归用例在 `tests/test_phase_three.py:175-275`（`ToolCallPairingTests`），四条断言的都是协议不变量本身而不是返回文本，其中 `test_no_orphan_across_generated_corpus` 还加了 `assertGreater(checked, 1000)`，防止语料被改小后静默失效。

### 修掉的二：`UsageTracer` 的 `KeyError('model')`

`_log` 的 loguru 格式串引用了一个从未被赋值的 `model` 键。现在 `telemetry.py:63-78` 的 `_extract_model` **永远返回一个字符串**（取不到就 `"unknown"`），docstring 里就地记下了为什么必须这样：格式串在 `logger.info()` 里就地做 `str.format`，缺键当场抛 `KeyError`，而这个异常被 LangChain 回调管理器吞成一行 stderr，业务照常跑完、token 日志一条都不落盘。

补的守卫用例（`tests/test_telemetry.py:89` `test_default_sink_actually_writes_a_log_line`）有个细节值得抄：它刻意用**默认 sink + 真实 loguru**，不能 patch 成 `MagicMock`——Mock 的 `.info()` 接受任何参数，而 `KeyError` 恰恰发生在 loguru 内部的 `str.format` 里。**Mock 掉的正是出 bug 的那一步。**

> 这两条都属于 19.3.1 说的那类问题：不是模型答错，而是真实链路上有一段从没被执行过。所以它们不只是「修好了两个 bug」，更是评测体系为什么值得建的两个具体证据。

## 19.7 读完这本教程你应该带走什么

八条跨项目通用的原则。都不是这个项目的细节，换个语言、换个框架也成立。

**① 不要相信模型的自述。** 模型说「已完成」不算完成，去查系统里的真实状态。这个项目的 `verify_step` 读注册中心而不是读模型的话，是整个 Planner 分支最有价值的一行设计。→ 第 6 章

**② 给人看的东西必须是机器事实。** 「人在回路」批准的必须是模型的**行为**（从 `tool_calls` 生成），不能是模型的**说法**（模型写的摘要）。否则你有全部的仪式感，零保护。→ 第 7 章、19.2

**③ 安全边界必须在每个入口重复，或者下沉到所有入口共用的那一层。** 「在编排器里做鉴权」是经典反模式——第二个进程入口一出现，全部保护自动失效。→ 第 16 章、19.2

**④ 让越权在语法上不可表达，胜过校验越权。** 身份走 `RunnableConfig`、不出现在工具的 JSON Schema 里，模型**物理上无法**伪造 `home_id`。这比「校验模型传来的 home_id」强一个层次：前者不需要正确性证明。→ 第 8 章

**⑤ 单一数据源胜过多处同步。** 新增一种设备从「改 9 处」收敛到「改 1 处声明 + 2 处手工」，一致性由生成式断言兜底。多处手写副本的失败模式是**静默漂移**，不是报错。→ 第 3 章

**⑥ 协议不变量要有专门一步兜住。** 别指望按长度算出来的东西顺便满足按结构定义的约束。裁剪窗口那道对齐就是这一步。→ 第 12 章、19.5

**⑦ 知道什么时候不该用 LLM。** 能用 20 行正则确定回答的，别问模型——更快、更便宜、可测，而且不会因为模型换版本就变行为。`classify_intent()` 在确定性信号命中时直接返回兜底结果、根本不问模型，是这个项目最成熟的一处判断。→ 第 9 章

**⑧ 测试通过 ≠ 那条路径被执行过。** 这是非确定性系统里最容易骗自己的一句话。Mock 掉的往往正是会出 bug 的那一步；规整的 fixture 天然掩盖依赖不规则输入才暴露的问题。→ 第 17 章、19.3.1
