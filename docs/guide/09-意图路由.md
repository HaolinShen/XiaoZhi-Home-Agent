# 第 9 章 意图路由：什么时候不该用 LLM

这一章讲一件反直觉的事：在一个以大模型为核心的系统里，**最关键的几个判断恰恰不能交给大模型**。

## 9.1 要解决什么问题

到第 8 章为止，我们搭出来的东西是这样的：用户说一句话 → 送给 LLM → LLM 挑工具 → 执行 → 验证。每一步都在问模型。

这套流程有两个你迟早会撞上的问题。

**问题一：LLM 不是免费的。** 一次调用要付三样东西：延迟（一次 HTTP 往返，几百毫秒到几秒）、token（prompt 里的设备清单、历史消息、工具 Schema，全都按字数计费）、以及**一定概率的胡说**——最后这样最贵。

**问题二：LLM 不是确定的（deterministic，同样输入总给同样输出）。** 同一句话问两次，可能得到两个答案。对聊天来说这叫「有活力」，对「要不要现在解锁大门」来说这叫「不可接受」。

下面是这个项目真实踩过的一次误判。用户说：

> 我今天下午 5 点打球回到家，帮我提前准备洗澡水，同时提前打开客厅空调降温

人一眼就懂：这是**定时任务**，5 点前把热水器和空调准备好。但模型看到「回到家」三个字，联想到系统里预定义的「回家模式」场景，于是给出了：

```
intent = scene_control    confidence = 0.96    reason = "看到了回家关键词"
```

`confidence 0.96`。它非常自信。后果是**现在**（不是 5 点）立刻启用回家模式——热水器现在烧，空调现在开，到 5 点人回家时水凉了、屋子的冷气也散了。而且用户完全不知道自己的定时请求被吃掉了，因为 Agent 回复的是「已为您启用回家模式」，听起来像办成了。

你的第一反应大概是改 prompt：在分类器提示里加一句「注意区分定时任务和即时场景」。这个项目试过，**它不可靠**，9.3 会讲清为什么。

这一章的核心主张只有一句：

> **能用 20 行正则确定回答的问题，不要问模型。**

这句话有个可量化的版本。把确定性分类器跑 1000 次实测一下：

```bash
cd "G:/大厂学习/minimind/langgraph" && PYTHONIOENCODING=utf-8 "F:/Software/Anaconda/envs/langgraph/python.exe" -c "
import time
from src.agent.routing import classify_intent_fallback
t0 = time.perf_counter()
for _ in range(1000):
    classify_intent_fallback('明天早上6点回家前打开空调')
elapsed = (time.perf_counter() - t0) * 1000
print('1000 次确定性分类: %.1f ms，单次 %.4f ms' % (elapsed, elapsed / 1000))
"
# 1000 次确定性分类: 2.9 ms，单次 0.0029 ms
```

单次 **0.0029 毫秒、零 token**。同样这一次判断交给模型，你要付出几百毫秒、几百个 token，外加一次它可能答错的机会。差了五个数量级，换来的还是更差的答案。

## 9.2 代码怎么写的

### 9.2.1 全景：`task_router` 分出五条互斥的路

图的入口是三段固定前置处理，然后由 `task_router` 一次性决定这轮走哪条路：

```
sync_context → memory_reasoner → task_router ─┬→ planner ⇄ plan_approval ⇄ executor ⇄ verifier → planning_finalize
                                              │      （第 5、6、7 章：多动作自定义请求）
                                              ├→ compact_context → agent ⇄ (approval) ⇄ tools → END
                                              │      （ReAct 主路：默认路径）
                                              ├→ device_query_subgraph → END
                                              │      （第 10 章：多目标并行查询）
                                              ├→ knowledge_rag → END
                                              │      （第 13 章：本地知识检索）
                                              └→ clarification → END
                                                     （信息不足，直接反问）
```

**五条路互斥**，一轮只走一条。分派逻辑是 `route_task`（`src/agent/graph.py:825-834`），一个只读状态的纯函数：

```python
def route_task(state: AgentState) -> Literal[...]:
    if state.get("intent_route") == "clarification":
        return "clarification"
    if state.get("intent_route") == "parallel_query":
        return "device_query_subgraph"
    if state.get("intent_route") == "knowledge_rag":
        return "knowledge_rag"
    return "planner" if state.get("planning_active") else "compact_context"
```

（省略的 `Literal[...]` 是五个目标节点名。）注意它**没有调用任何模型**，只读 `intent_route` 和 `planning_active` 两个字段。真正的判断在上一个节点里已经做完并写进了状态。这是 LangGraph 里一个值得抄的模式：**条件边只查状态，不做决策**。决策留在节点里，因为节点的输出会进 Checkpoint，可复现、可追溯；条件边函数的中间变量不会。

条件边的注册在 `graph.py:836-846`，三条查询/反问路径直接连 `END`（`graph.py:847-849`）——**它们不经过 ReAct，一次模型调用都不做**。

### 9.2.2 `task_router` 节点：三次判断，零次或一次模型调用

节点本体是 `task_router_node`（`graph.py:311-388`）。它做三件事：

**第一件：拿到意图**（`graph.py:318-324`）。它先读 `settings.routing.enabled`，再二选一：

```python
intent = (
    classify_intent(llm, latest_text)
    if routing_enabled
    else classify_intent_fallback(latest_text)
)
```

`routing.enabled`（`src/config.py:82-87`，默认 `True`）关掉时，**整个路由环节一次模型都不调**，只跑确定性分类器。这是个有用的开关：调试图结构时把它关掉，路由行为完全可复现。

**第二件：判断要不要 Planner**（`graph.py:326-328`）。`use_planner = planning_enabled and should_use_planner(latest_text)`，然后 `intent_route` 初值取 `"planner"` 或 `"react"`。`should_use_planner()` 是纯正则，见 9.2.5。

**第三件：在 `use_planner` 为假的前提下，依次检查三条特殊路径**（`graph.py:329-345`）：

| 顺序 | 条件 | 路由到 |
|---|---|---|
| 1 | `intent == "device_knowledge"` 且 `rag.enabled` | `knowledge_rag` |
| 2 | `intent == "device_query"` 且 `should_use_parallel_query(text, registry)` | `parallel_query` |
| 3 | `intent == "clarification"` 或 `confidence < threshold` 或 记忆推理判定需要澄清 | `clarification` |

三个判断都带 `not use_planner` 前缀——**Planner 一旦选定，后面的特殊路径不再抢**。而 `clarification` 放在最后检查，所以它的优先级最高（后写的赋值覆盖前面的）。这个顺序是刻意的：**宁可反问，不要走错路**。

第 3 条里的第三个来源值得注意：`state.get("memory_decision", {}).get("needs_clarification", False)`（`graph.py:343`）。上游 `memory_reasoner` 节点如果发现长期记忆里有互相冲突的偏好，也能把这一轮拽到反问分支。**澄清的触发权不属于路由器一个人。**

### 9.2.3 `classify_intent()` 的分层结构

分类的全部逻辑在 `src/agent/routing.py`，不到 100 行。八种意图定义在 `routing.py:24-33`（`Intent` 是一个 `Literal`），结果结构是 `IntentResult`（`routing.py:36-39`，带 `intent` / `confidence` / `reason`）。

核心是 `classify_intent()`（`routing.py:81-95`）：

```python
def classify_intent(llm, text: str) -> IntentResult:
    """Use structured LLM output when available; never let routing break the agent."""
    fallback = classify_intent_fallback(text)
    # Explicit future times and automation phrases are deterministic business
    # signals. Do not let a model over-weight words such as "回家" and route a
    # fixed-time routine into the predefined scene branch.
    if fallback.intent == "automation_management":
        return fallback
    try:
        structured = llm.with_structured_output(IntentResult)
        result = structured.invoke(intent_router_prompt(text))
        result = result if isinstance(result, IntentResult) else IntentResult.model_validate(result)
        return result
    except Exception:
        return fallback
```

十几行里有三层，边界要看清：

**第一层 · 确定性信号（`routing.py:83-88`）。** 先无条件跑一遍 `classify_intent_fallback`。如果它判定是 `automation_management`，**直接返回，模型根本不被调用**。这是全章最重要的一行，9.3 决策一专门讲。

**第二层 · LLM 结构化分类（`routing.py:89-93`）。** 用 `llm.with_structured_output(IntentResult)` ——让模型直接吐一个符合 pydantic 模型的对象，而不是让它自由写字再去解析。prompt 在 `intent_router_prompt()`（`routing.py:42-57`），里面逐条描述八种意图，并写明「confidence 低于 0.6 时优先选择 clarification」（`routing.py:54`）。注意这里用的是 `with_structured_output` 而**不是** `bind_tools`——分类器不该有能力去动设备，它只该回一个标签。

**第三层 · fallback 兜底（`routing.py:94-95`）。** `except Exception` 抓一切：模型超时、返回不合 Schema、API key 过期、网络断。任何一种情况下路由都不抛异常，而是退回确定性结果。docstring 那句 `never let routing break the agent` 就是这个意思——**分类失败不该让整个 Agent 挂掉，最多让它路由得笨一点**。

这里有个设计上的巧劲：**第一层和第三层是同一个函数**。`classify_intent_fallback` 在第 83 行就被算出来了（不管后面走哪条路），它同时充当「LLM 之前的守卫」和「LLM 之后的安全网」。一份 20 行的正则，两个用途，不存在「守卫和兜底逐渐失去同步」的可能。

### 9.2.4 确定性分类器：顺序就是优先级

`classify_intent_fallback`（`routing.py:60-78`）是一串有序的 `if`，词表都在 `heuristics.py`：

| 顺序 | 判据 | 意图 | confidence |
|---|---|---|---|
| 0 | 空字符串 | `clarification` | 0.1 |
| 1 | `has_future_time()` 或 `ROUTING_AUTOMATION_WORDS` | `automation_management` | 0.9 |
| 2 | `ROUTING_MEMORY_WORDS` | `memory_management` | 0.92 |
| 3 | `ROUTING_KNOWLEDGE_WORDS` | `device_knowledge` | 0.9 |
| 4 | `ROUTING_SCENE_WORDS` | `scene_control` | 0.88 |
| 5 | `ROUTING_QUERY_WORDS` | `device_query` | 0.86 |
| 6 | `ROUTING_CONTROL_WORDS` | `device_control` | 0.82 |
| 7 | 长度 < 2 | `clarification` | 0.2 |
| 8 | 兜底 | `general_chat` | 0.75 |

**自动化在最前面，场景在它后面。** 这个顺序是 9.1 那个 bug 的直接修复：「明天 6 点回家前打开空调」同时含未来时间信号（第 1 条）和场景词「回家」（第 4 条），谁在前面谁赢。

「未来时间」的判据是 `ROUTING_FUTURE_TIME_PATTERN`（`heuristics.py:90-93`），语义是**必须先有一个日期词（今天/明天/后天/周 X/星期 X），再在 10 个字之内出现一个时段词或钟点（上午/下午/晚上/早上/凌晨/`\d{1,2}\s*[点时]`）**。它故意不匹配裸的「6 点」——这个选择有代价，9.5 坑二会讲。

顺便注意那些 confidence 数值（0.82 ~ 0.92）**全都高于默认阈值 0.6**，只有两个 `clarification` 分支是 0.1 / 0.2。也就是说关掉 `routing.enabled` 时，「置信度不足 → 反问」这条规则几乎只对空输入生效。想让它对「帮我调一下」这种含糊请求生效，你必须打开 LLM 分类层。

### 9.2.5 `should_use_planner()`：一个纯正则的开关

判定在 `heuristics.py:56-71`：

```python
def should_use_planner(text: str) -> bool:
    """Conservatively route explicit custom multi-action requests to Planner."""
    normalized = text.strip()
    if not normalized:
        return False

    # Predefined scene requests remain on the existing ReAct + scene approval path.
    if any(marker in normalized for marker in PLANNER_SCENE_MARKERS):
        return False

    action_count = sum(len(re.findall(pattern, normalized)) for pattern in PLANNER_ACTION_PATTERNS)
    device_kinds = sum(
        1 for keyword in PLANNER_DEVICE_KINDS if keyword in normalized
    )
    connectors = any(connector in normalized for connector in PLANNER_CONNECTORS)
    return action_count >= 2 and (device_kinds >= 2 or connectors)
```

规则一句话：**≥2 个动作词 且（≥2 类设备 或 出现连接词）**。逐条看每个条件为什么在那里。

**为什么先排除预定义场景（`heuristics.py:63-64`）？** 场景（`PLANNER_SCENE_MARKERS`，`heuristics.py:44-47`）已经有自己的批量执行实现和审批级别（第 7 章）。让 Planner 去拆解「回家模式」，等于把一套测试过的原子操作换成模型现场编的步骤清单，没有收益只有风险。

**为什么要求 `action_count >= 2`（`heuristics.py:66`）？** Planner 是为「多步计划」存在的。单动作请求走 ReAct 又快又准——一次模型调用、一次工具调用、结束。走 Planner 要多付「出计划 + 审批 + 逐步执行 + 逐步验证」四道工序。注意这里用的是 `re.findall` 数**总出现次数**而不是数「命中了几种模式」，所以「打开空调然后调到 26 度」（「打开」+「调到」）算 2，「打开 A 再打开 B」也算 2。

**为什么 `device_kinds >= 2` 或 `connectors` 是「或」（`heuristics.py:67-71`）？** 这两个条件各覆盖一半的真实句式：「打开客厅灯并且打开电视」两边都命中；「把空调调到 26 度，窗帘拉上」用逗号而非连接词，靠 `device_kinds` 命中；「打开空调然后调到 26 度」**只有一类设备**，靠「然后」命中。如果改成「与」，第三种句式就会被漏掉；而如果两个条件都不要（光看动作数），「打开灯」+「打开灯」这种重复表达也会被误送去 Planner。

`PLANNER_ACTION_PATTERNS`（`heuristics.py:49`）在共享的 `ACTION_CORE`（`heuristics.py:34`，`打开/开启/关闭/关掉/调到`）之上加了「设为/调成/拉开/拉上/静音/切换」——**都是用户对设备的直接命令**，没有一个是模糊的意图线索。这跟路由那张表的扩展方向正好相反（`ROUTING_CONTROL_WORDS` 加的是「设置/调高/调低」这类更宽的线索，`heuristics.py:86` 的注释解释了原因）。

### 9.2.6 `clarification`：宁可反问，不要猜一个设备

反问分支的实现短到令人怀疑（`graph.py:620-621`）：

```python
def clarification_node(state: AgentState) -> dict:
    return {"messages": [AIMessage(content="为了安全执行，请补充具体的设备、房间或要执行的动作。")], "planning_active": False}
```

一句硬编码文案，然后直接 `END`（`graph.py:847`）。它的价值不在写了什么，在**没做什么**：没调模型、没调工具、没猜设备。当用户说「帮我调一下」时，模型完全有能力编出一个看起来合理的动作——比如「已把客厅空调调到 26 度」。**这比报错糟糕得多**，因为用户会以为系统听懂了。

`tests/test_phase_eight.py:51-67` 把这一点钉成了断言：测试塞进去的假 LLM，它的 `invoke` 方法**直接 `raise AssertionError("clarification branch must not invoke ReAct")`**。只要反问分支哪天不小心开始调模型，测试立刻红。用「不该被调用的东西一被调用就炸」来表达约束，比检查返回文本可靠得多。

### 9.2.7 三个判定住在同一个文件里

`should_use_planner`、`classify_intent_fallback` 的词表、`required_automation_tool` 现在都在 `src/agent/heuristics.py`。模块 docstring（`heuristics.py:9-15`）说明了为什么要合并：

> 这三处以前各自维护一份关键词表（"打开""关闭"至少出现三次），语义上重叠、改一处容易漏另一处。

合并的方式不是「合成一张大表」，而是**共享真正相同的基表（`ACTION_CORE`），各自做有语义的扩展，每个扩展注明为什么与别处不同**。三个判定的目标确实不同（意图线索 / 精确动作 / 定时语义动作），强行统一成一张表只会让每次改动都产生三处副作用。`tests/test_heuristics.py:101-118` 用两组断言钉住这个结构：一组验证 `ACTION_CORE` 的每个词同时出现在三张表里，另一组验证各表的独有词**不该**出现在别处。

旧的 import 路径没有断：`src/agent/planning.py:13` 保留了 `from .heuristics import should_use_planner  # noqa: F401` 作为再导出（`planning.py:15-17` 说明新代码请直接 import `heuristics`）。

## 9.3 关键设计决策

### 决策一：确定性信号命中 `automation_management` 时，不问 LLM

这是全章唯一一处「无条件否决模型」的地方（`routing.py:87-88`）。

被否决的方案是改 prompt。事实上 `intent_router_prompt` 里**已经写了**一句相当具体的说明（`routing.py:49-50`）：

> `automation_management`：创建、查看或取消任何未来时间/提前执行的自动化，包括固定时间回家准备、定时起床、闹钟和车辆回家联动

「固定时间回家准备」几个字就是冲着这个 bug 写的。然而它治不好，原因有三层：

**第一层，prompt 是概率性的。** 加一句说明只是移动了分布，没有消除尾部。0.1% 的误判率对聊天无所谓，对「立刻烧一整箱热水」很要命——而且这个尾部你测不出来，测 100 句全对，上线第 300 句翻车。

**第二层，误判源于真实的语言歧义。** 「回家」在这句话里既是场景名的一部分，又是时间锚点的一部分。模型不是没读懂说明，它是在两个都合理的解释里选错了一个。你没法用更多措辞消掉一个本来就存在的歧义。

**第三层——决定性的一层——这个判断根本不需要理解语言。** 句子里有「今天下午 5 点」，有「提前」。这两个信号用正则就能抓，抓到了就是定时任务，**没有第二种解释**。既然存在一个 100% 准确、0.003 毫秒、零 token 的判据，为什么要去优化一个 99.9% 准确的判据？

所以正确的修法是**前置拦截**：在模型有机会发表意见之前就把这条路封掉。注意代码注释（`routing.py:84-86`）的措辞是 `Do not let a model over-weight words such as "回家"` —— 承认模型会犯这个错，然后不给它犯错的机会。代价要说清楚：**只要确定性分类器把某句话判成 `automation_management`，模型就再也没有纠正的机会**，假阳性会被永久固化（9.5 坑三）。这是拿「消除一类灾难性假阴性」换「引入一类可控假阳性」，因为定时任务的假阳性后果是「多存了一条例程，用户能看见能删」，而假阴性后果是「该定时的事情立刻执行了，用户看不见」。

`tests/test_phase_eight.py:95-111` 是这个决策的守卫用例：它塞进一个**故意答错**的假路由器（返回 `scene_control`，`confidence=0.96`，`reason="看到了回家关键词"`），然后断言 `classify_intent` 的结果仍然是 `automation_management`。这是我见过的最干脆的测试写法之一——**不是测「模型答对时能用」，而是测「模型答错时不生效」**。

### 决策二：路由只选路，不选工具

`task_router` 只往状态里写 `intent` / `intent_confidence` / `intent_reason` / `intent_route`（`graph.py:346-351`）。它不决定调哪个工具，也不生成任何面向用户的文字。

这个边界让路由错误的后果是可恢复的。走进 ReAct 的请求，Agent 仍然可以自己选任何工具；走进 Planner 的请求，Planner 仍然要出计划、过审批。**路由选错只是让请求走了条不太合适的路，不会让它执行错误的动作。** 反过来，如果路由器同时决定「意图是 X 所以调工具 Y」，一次分类错误就变成一次错误执行。

`routing.py` 的模块 docstring 用一句话说了这件事：`The router is deliberately small: it selects a business path, while the specialised Agent/Planner nodes still decide the concrete tool calls.`（`routing.py:3-4`）

### 决策三：路由结果全部进状态，供事后追溯

`intent_reason` 这个字段没有任何运行时作用——没有任何条件边读它。它存在只为了一件事：出问题时你能看见**为什么**这么路由。`graph.py:359-367` 的 `emit_progress("supervisor_routing", ...)` 把请求前 80 字、意图、置信度、路由目标一起吐进 trace 通道，加 `--trace` 跑 CLI 就能看到。**排查「Agent 为什么不理我」这类问题，第一步永远是看这条事件**（第 15 章讲完整链路）。

## 9.5 踩坑与局限

### 坑一：场景排除是子串匹配，注释想避免的情况仍然会发生

`heuristics.py:40-43` 的注释是这么写的：

> 这里匹配的是**整句惯用表达**（"我要出门"），routing 匹配的是**子串线索**（"离家"），宽窄不同是有意的——Planner 的排除必须精确，误伤一句"我要出门前关灯"就会把两个动作的请求送去走场景分支。

但实现用的是 `marker in normalized`（`heuristics.py:63`），**这本身就是子串匹配**。所以实验一里 `'我要出门前关灯和关空调' -> False`：注释点名要避免的那句话，现在仍然会被误伤。

这不是笔误，是「意图（整句惯用表达）」和「实现（子串包含）」之间的一道缝。要真正实现注释描述的语义，需要锚定句子边界或做长度比例判断。**目前没有测试覆盖这个 case**（`tests/test_heuristics.py:30-33` 测的都是纯场景句），所以它是一个已知未修的假阴性。

### 坑二：两套「未来时间」正则的严格程度不一致，后果是用户可见的

`heuristics.py` 里有两个时间正则，宽窄不同：`ROUTING_FUTURE_TIME_PATTERN`（`heuristics.py:90-93`）**要求**日期词前缀，而 `required_automation_tool` 用的 `AUTOMATION_TIME_PATTERN`（`heuristics.py:126-132`）**不要求**——裸的 `\d{1,2}\s*[点时]` 就算命中。实测这个差异会让两个判定对同一句话给出矛盾的结论：

```
6点打开空调           future_time=False fallback=device_control         required_tool=create_scheduled_routine
晚上6点打开空调         future_time=False fallback=device_control         required_tool=create_scheduled_routine
明天6点打开空调         future_time=True  fallback=automation_management  required_tool=create_scheduled_routine
半小时后打开空调         future_time=False fallback=device_control         required_tool=None
```

看第一行：`required_automation_tool` 认为这是创建定时例程的请求，但路由认为这是**立刻控制设备**。而 `required_automation_tool` 的强制机制被 `graph.py:695-701` 门控在 `state.get("intent") == "automation_management"` 之内——**路由已经判成 `device_control`，强制机制根本没机会介入。** 于是用户说「6 点打开空调」，空调现在就开了。这正是 9.1 那个 bug 的变体，只是这次漏的不是模型，是正则（第四行的「半小时后」同理：`AUTOMATION_TIME_PATTERN` 要求数字，「半」不是数字）。

**教训不是「正则不好」，而是「同一个概念不要写两遍」。** 把设备能力收敛成单一数据源那套思路（第 3 章）在这里还没做完。

### 坑三：确定性短路是单向的，模型无法纠正假阳性

决策一让 `automation_management` 的判定不可被模型推翻。这是有意的，但它意味着**假阳性没有第二道防线**。

举个例子：「明天早上的天气怎么样」含日期词「明天」和时段词「早上」→ `has_future_time` 命中 → 直接判 `automation_management`，模型不会被问。用户问的是天气，系统在准备创建例程。

同时注意实验三第二行揭示的不对称：第二层的 LLM 结果**完全没有后置校验**。模型说 `scene_control` 就是 `scene_control`，哪怕句子里一个场景词都没有。所以整套机制的形状是：

```
确定性说 automation      → 锁定，模型无权发言
确定性说其他任何东西      → 模型说什么算什么，确定性无权发言
```

两边都是「一方独裁」，中间没有交叉验证。**这是当前实现最明显的结构性不足。** 一个可能的改进方向是让确定性结果参与置信度调整（模型结论与确定性结论冲突时降低 confidence，从而更容易掉进 `clarification`），但那需要一批真实误判样本来标定，目前没有。

顺带一个小浪费：短路只认 `automation_management`（`routing.py:87`），所以一个空白输入仍会走完「fallback 算出 `clarification` → 不是 automation → 调模型 → 模型也说 clarification」这条链。把 `clarification` 也加进短路条件是一行代码的事，目前没做。

### 坑四：两张场景词表不同源

Planner 的排除表 `PLANNER_SCENE_MARKERS`（`heuristics.py:44-47`）和路由的 `ROUTING_SCENE_WORDS`（`heuristics.py:84`）是**两张独立的表**。实验二第三行的意外就来自这里：「我回来了」在 `PLANNER_SCENE_MARKERS` 里（Planner 认为它是场景请求，不接），却**不在** `ROUTING_SCENE_WORDS` 里（那张表只有「回家」），于是路由判成 `general_chat`。这句话走进 ReAct 主路被当成闲聊，能不能触发回家模式全看模型愿不愿意调 `activate_scene`。

宽窄不同**有一部分是刻意的**（Planner 的排除要精确、路由的线索要宽），但「我回来了」显然不在设计意图里——它落进了两张表都不管的缝隙。

### 坑五：关键词表的维护成本是真实的，而且会随时间上升

这一章展示的所有正确性都建立在「词表覆盖了用户实际说法」之上。这有两重成本：

1. **新增设备类型要记得加词。** `PLANNER_DEVICE_KINDS`（`heuristics.py:51`）是八个硬编码字符串。第 3 章讲的「新增设备只改一处声明」在这里**不成立**——这张表没有从 `capabilities.py` 派生，加了新设备如果忘了加词，Planner 就永远不会为它计数。
2. **用户的说法会漂移。** 你的词表覆盖「打开」，用户说「给我把灯弄亮点」。这类长尾正是 LLM 该做的事——所以这一章的主张是「**该确定的地方确定**」，不是「不要用 LLM」。

正因为这些成本，`tests/test_heuristics.py` 的表驱动用例不是可选的。它的价值在于**让词表改动的副作用立刻可见**：你为了修一个假阴性往表里加词，如果这个词同时破坏了另一个判定，测试当场告诉你，而不是等某个用户的空调半夜自己开了。

---

**这一章的局限**：路由把请求分给了五条路，但每条路内部仍然是**串行**的。用户问「客厅和卧室的灯都开着吗」时，`device_query` 分支要一个一个设备去查，延迟随设备数线性增长。而这些查询之间毫无依赖——它们本该同时发生。
