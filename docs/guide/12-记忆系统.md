# 第 12 章 记忆：Checkpoint 与长期记忆

这一章讲两种完全不同的"记忆"，以及为什么把它们混为一谈，会让你写出一个"用户说过的话第二天就蒸发"的 Agent。

## 12.1 要解决什么问题

先看两个失败场景。它们看起来是同一个毛病，其实是两件事。

**场景一：话说到一半，进程没了。** 你说"把客厅灯打开、空调调到 26 度、窗帘关上"，Agent 报出一个 3 步计划等你确认 —— 这时候你按了 Ctrl+C，或者服务器重启了。重启后你希望它还记得那个待批准的计划。这是第 7 章审批能活过进程重启的前提。

**场景二：关掉终端再打开，Agent 把你说过的一切忘得一干二净。**

```
（周一）你：记住我怕冷，空调不要低于 24 度
        Agent：好的，已经记下了。
（周二，重开一个终端）
        你：把卧室空调打开
        Agent：好的，已设为 22 度。      ← ？？？
```

第二个才是真正让人恼火的那个。而新手最常见的处理方式是：**"那我把 checkpointer 换成 SQLite 不就行了？"** 不行 —— 这是本章第一要务要掰清楚的事。

### 两种记忆，一张对照表

| | Checkpoint（检查点，短期记忆） | 长期记忆（本项目自建） |
|---|---|---|
| 一句话 | 一个 `thread_id` 内的**完整状态快照**，进程重启后能原地续上 | 跨会话、跨线程的**事实库** |
| 谁提供 | LangGraph 内置（`langgraph-checkpoint-sqlite`） | 本项目自己建的 SQLite 表 + Service |
| 存什么 | 整个 `AgentState`：消息列表、`planning_status`、待批准的计划…… | 结构化事实：`ac.temperature = {"min": 24}` |
| 隔离键 | `thread_id`（= `session_id`） | `home_id` + `user_id`（+ `room_id`/`device_id`） |
| 生命周期 | 一次会话，默认 7 天后被清理 | 长期，直到用户删除 |
| 落地位置 | `data/checkpoints.db` | `data/memories.db` |
| 解决什么 | "这轮中断了能续上"、"审批暂停能活过重启" | "主人怕冷，空调不低于 24 度" |
| 代码入口 | `src/memory/store.py:create_checkpointer` | `src/memory/repository.py` + `service.py` |

**为什么 checkpoint 顶不了长期记忆？** 因为有三套机制各自独立地在销毁它：

1. **它按 `thread_id` 隔离。** 新会话就是新 `thread_id`，读到一片空白 —— 这正是隔离想要的效果（手机和音箱同时说话不能串线），但也意味着"上周说过的话"天生不在这条线上。
2. **裁剪会真的删数据。** `compact_context` 节点发出 `RemoveMessage`，旧消息从 SQLite 里被物理删除（12.2.5 详讲）。你指望"反正历史都存着"，其实存不住。
3. **过期清理会整条删。** `SessionManager.cleanup_expired()`（`src/agent/session.py:52`）默认 7 天（`session_ttl_hours=168`，`src/config.py:68`）没动静的 thread 直接 `delete_thread`。

结论是硬的：**checkpointer 让"一次对话"变得可靠，长期记忆让"这个人"变得可知。两件事，两套存储，两种生命周期。**

## 12.2 代码怎么写的

图的入口三段前置处理里，两段跟记忆有关；第三段裁剪在 ReAct 循环内部：

```
sync_context ──→ memory_reasoner ──→ task_router ──┬→ planner ⇄ executor ⇄ verifier
（检索长期记忆）   （判断哪条适用）                  ├→ compact_context ──→ agent ──┬→ END
                                                   │        ↑                      └→ tools ─┐
                                                   │        └─────────────────────────────────┘
                                                   └→ clarification
```

`src/memory/` 下六个文件分工明确：`store.py` 只管 checkpointer（跟长期记忆无关）；`models.py` 是长期记忆的模型和枚举；`repository.py` 是 SQLite 读写，**每条查询都带 `home_id`**；`service.py` 管作用域、权限、冲突与检索排序；`extractor.py` 从自然语言里抽候选、**从不写库**；`summarizer.py` 是三个纯函数（估算 token、算保留窗口、生成状态更新）。

### 12.2.1 Checkpoint：`thread_id` 是唯一的钥匙

装配只有两行（`src/agent/graph.py:927-928`）：

```python
checkpointer = create_checkpointer(settings.memory.db_path)
graph = workflow.compile(checkpointer=checkpointer)
```

`create_checkpointer`（`src/memory/store.py:37`）的分支很直白：`db_path` 非空 → `SqliteSaver`；空或 `None` → `MemorySaver`（进程内，重启丢）。还有第三种情况值得注意：配了路径但 `langgraph-checkpoint-sqlite` 没装，它**直接 `RuntimeError`**，不悄悄退回内存。刻意的 —— "你以为持久化了，其实没有"是最难发现的一类故障，宁可启动时就炸。

钥匙从哪来？呼应第 8 章：`AgentContext.to_config()`（`src/agent/context.py:42`）把 `session_id` 原样填进 `configurable["thread_id"]`。一句话：**`session_id` 就是 `thread_id`**。所以"换一个会话"和"换一条 checkpoint 线"是同一件事 —— CLI 的 `/reset` 就是这么实现的，它**不删任何数据**，只是生成一个新 `session_id`（`src/main.py:375-386`），旧线还躺在 SQLite 里等 TTL 收走。

要真删得显式调用：`SessionManager.end()`（`session.py:45`）走 `checkpointer.delete_thread`，而且 checkpointer 不支持这个方法时**报错而不是假装成功**。

顺带说一句 checkpoint 长什么样：它落地成 LangGraph 的两张通用表（`checkpoints` / `writes`），业务数据全在 `checkpoint` 这个不透明的序列化 blob 里。你没法拿它"查一下所有说过怕冷的用户" —— 这就是下一节必须自己建表的原因。**不是 checkpointer 不够持久，是它的数据形状不支持按业务维度查询。**

### 12.2.2 长期记忆：一张表 + 一个作用域四元组

`MemoryScope` 四个值（`models.py:16`）：`home` / `room` / `device` / `user`。`MemoryType` 四个值（`models.py:23`）：`preference` / `alias` / `routine` / `constraint`。

主表 `memories` 的核心是这条唯一索引（`repository.py:56-60`）：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS uq_memories_business_key
    ON memories(
        home_id, COALESCE(user_id, ''), COALESCE(room_id, ''),
        COALESCE(device_id, ''), scope, memory_type, memory_key
    );
```

它定义了"什么算同一条记忆"。用户第二次说"我喜欢冷白光"不会插入第二行，而是走 `upsert`（`repository.py:149`）更新原行、`version + 1`，并把上一版写进 `memory_versions` 表封上 `valid_to`。

**可见性由一条 SQL 决定**（`list_accessible`，`repository.py:376`）：

```sql
WHERE home_id=? AND status='active'
  AND (user_id IS NULL OR user_id=?)
  AND (room_id IS NULL OR room_id=?)
  AND (device_id IS NULL OR device_id=?)
```

`user_id IS NULL` 就是"家庭共享"，所以家规人人可见、个人偏好只有主人可见 —— **不靠代码里的 if，靠 NULL 的语义**。

规则在 `service.py`。`save()`（`service.py:25`）的顺序值得记：先 `spaces.validate(context)` 校验 `room_id` / `device_id` 属于这个住宅（第 8 章），再规范化作用域（`home` 不许带 room/device，`device` 会自动反查所属房间），共享作用域（home/room/device）**必须管理员**否则 `MemoryPermissionError`，最后同业务键已存在就递归合并、值真的不同还要往 `memory_conflicts` 表记一条审计。

**作用域和权限这层不在这章重复讲** —— 它是第 8 章可信身份边界的直接延伸：身份来自 `RunnableConfig`，工具用 `_context()`（`src/tools/memory.py:22`）反解，`is_admin` 只从 `configurable` 读，模型填不了。

检索是**词法打分**（`_retrieval_score`，`service.py:166`）：`0.45 × 词命中率 + 0.20 × 置信度 + 0.20 × 重要性 + 0.10 × 新鲜度 + 0.05 × 使用频度`，其中新鲜度是 `exp(-age_days/90)`。没有 embedding，没有向量库。中文查询靠 `_query_terms()`（`service.py:277`）里一张手写别名表命中英文 `memory_key`：`"空调": {"ac", "temperature", "mode", "fan"}` 等 9 组。命中后 `record_accesses()` 加访问计数，于是频度项形成正反馈：**常用的记忆越来越容易被检索到**。

### 12.2.3 长期记忆的两条写入路径

| | 路径 A：模型显式调工具 | 路径 B：偏好观察被动抽取 |
|---|---|---|
| 触发 | 用户说"记住我喜欢暖光" | 用户重复做同一操作 / 说出稳定表达 |
| 入口 | `save_personal_memory` / `save_home_rule`（`tools/memory.py:68`、`:89`） | `make_preference_recorder`（`tools/memory.py:39`）、`extract_memory_candidates`（`extractor.py:18`） |
| 直接写库？ | **是**，立刻 `service.save()` | **绝对不是** |
| 产物 | `memories` 表一行 | `preference_candidates` 表一行，`status='pending'` |

路径 B 又分两支。

**B1：数动作。** 设备工具每次成功执行都调一次闭包里的 `recorder`（第 4 章讲过它的构造），最终落到 `service.record_operation()`（`service.py:59`）。它先在 `preference_observations` 表累加计数，**只有累计到 3 次（`minimum_repetitions=3`）才生成候选**，而且置信度是 `min(0.95, 0.5 + 0.1 * count)` —— 上限锁在 0.95，观察出来的偏好永远不会自称"百分之百确定"。

**B2：读原话。** `sync_context` 每轮先调一次 `extract_candidates_from_text`（`graph.py:252`）。抽取器（`extractor.py`）是纯正则，两道闸门串起来：命中 `_TEMPORARY_MARKERS`（今天/这次/现在/有点/暂时/刚才）直接返回空；没命中 `_STABLE_MARKERS`（我喜欢/我偏好/我习惯/我通常/我一般/以后都/以后请）也返回空。**临时标记优先否决** —— "今天有点冷，空调调到 28 度"一个候选都不产出。

两支汇合到同一个确认流程：候选只能由用户通过 `confirm_preference_candidate` 工具转正（`service.confirm_candidate`，`service.py:96`），转正时才写 `memories` 表。

> 这个设计的分量：**系统可以观察你，但不能替你决定你是什么样的人。**

### 12.2.4 `memory_reasoner`：一个只做判断的节点

`sync_context` 已经把 Top-K 记忆检索出来放进 `memory_context` 了。为什么还要单独一个节点（`graph.py:268`）？

因为"检索到"不等于"该用"。这个节点调 `reason_about_memories()`（`src/agent/reasoning.py:17`）产出一个可检查的结构体 `MemoryDecision`（`reasoning.py:7`）：`applicable_memory_ids` / `ignored_memory_ids` / `constraints` / `preferences` / `conflicts` / `needs_clarification` / `reason`。规则是**确定性的**，一共两条：

1. **用户本轮出现"这次 / 临时 / 不要按"这类覆盖标记 → 忽略 `preference` 类记忆，但 `constraint` 照旧生效。** 这是 001 方案那条优先级链的落地：`安全与权限规则 > 用户当前明确指令 > 个人偏好 > 家庭默认偏好`。
2. **同一个 `memory_key` 出现两个不同值 → `conflicts` 非空 → `needs_clarification = True`。**

第 2 条会跨节点生效：`task_router`（`graph.py:341-345`）在判断要不要走反问时，把 `state["memory_decision"]["needs_clarification"]` 和"意图分类为 clarification"、"置信度低于阈值"并列成三个条件之一。**记忆自相矛盾时，Agent 走反问路径，而不是随便挑一条执行。**

为什么值得单独一个节点，而不是塞进 `sync_context`、或者写进 prompt 让模型自己判断？**可审计**：决策是 `state["memory_decision"]` 里一个字典，事后能从 checkpoint 里读出来，写进 prompt 就只剩模型的自述。**可测试**：纯函数，不需要 LLM，`tests/test_phase_eleven.py` 直接断言 `applicable_memory_ids` 含哪条 id。**能驱动路由**：结论是一个布尔值，条件边能直接用，模型的自然语言判断做不到。

节点最后把决策格式化进 `memory_context`，由 `agent_node` 塞进 system prompt（`graph.py:677-678`）。

### 12.2.5 `compact_context`：裁剪不是"少发几条"，是真删

大模型是无状态的。所谓"多轮对话"，全靠客户端每轮把整段历史重新发一遍。历史越长请求体越大 —— 直到撑爆上下文窗口或者账单失控。而本项目的历史还**落盘**，同一个 session 一直累积，进程重启也不清空。所以必须裁。

`compact_context_node`（`graph.py:286`）把当前全部消息交给 `build_compaction_update`（`summarizer.py:95`），一次裁剪做四件事：

**① 过长的工具结果就地截断。** 超过 `tool_result_max_chars`（默认 1200）的 `ToolMessage` 砍掉尾部加省略标记。只瘦身，不删条。

**② 算保留窗口起点 `keep_from`**（`summarizer.py:77-79`）。两道闸门串联：

```python
keep_from = max(0, len(messages) - max_messages)
while keep_from < len(messages) - 1 and estimate_tokens(messages[keep_from:]) > max_tokens:
    keep_from += 1
```

先按**条数**（默认 12）定位，再按**估算 token**（默认 2400）一格格往后推。

**③ 对齐窗口边界**（`summarizer.py:82`）。这一行是 12.3 决策一的全部主角，先记住它存在。

**④ 窗口外的消息压成摘要，并对它们逐条生成 `RemoveMessage(id=...)`。**

这一步有两个容易被忽略的性质。

**性质一：所谓"摘要"没有调用 LLM。** 它就是 `role: 内容前 240 字` 的字符串拼接，再和已有摘要合并、整体保尾部 1800 字符。被裁掉的信息不是消失，而是**降级**成 system prompt 里的一段粗文本。

**性质二：`RemoveMessage` 是真删。** `state.py:29` 声明 `messages: Annotated[list, add_messages]`，`add_messages` 这个 reducer 把 `RemoveMessage(id=...)` 解释成删除指令，写回 SQLite 时那几行就没了，**下一轮读不回来**。这是刻意的（控制存储无限增长），但也意味着切错的后果不可逆。

还有一个位置问题：`compact_context` 有三个入口，其中两个是 `tools → compact_context`（`graph.py:922`）和 `reject_tools → compact_context`（`graph.py:923`）。也就是说**每次工具执行完都会立刻走一遍裁剪，然后才把消息发给模型** —— 裁剪运行的时刻，正好是历史尾部刚被追加了新 `ToolMessage` 的时刻。记住这点，下一节的 bug 就不是"边角情况"，而是主路径上的高频事件。

### 12.2.6 时间旅行：为什么只在有 checkpointer 时成立

`src/agent/time_travel.py` 一共 28 行，两个函数：`list_state_history`（`:6`）遍历 `graph.get_state_history(config)`，列出每个快照的 `checkpoint_id` / `created_at` / `next`（下一个要执行的节点）/ 状态键 —— CLI 的 `/history` 就是它（`src/main.py:150`）；`fork_from_checkpoint`（`:22`）找到指定快照，用 `graph.update_state(snapshot.config, updates)` 在它上面**分叉**出一条新线。

两个都是薄封装，能力全在 checkpointer 里。**没有 checkpointer，`get_state_history` 无从可读、`update_state` 无处可写，时间旅行整个概念不成立。** 这也是第 7 章审批中断能活过重启的原因：`interrupt()` 挂起时的完整状态就是一个 checkpoint，恢复不过是从那格继续往下走。用 `MemorySaver` 时这些函数照样能用，只是"历史"随进程一起消失。

## 12.3 关键设计决策

### 决策一：协议不变量必须由专门一步兜住（一个真实的 bug）

**前提：一次工具调用在历史里是一对消息，不是一条。** 先是一条 `AIMessage` 带 `tool_calls`（"我要调 `control_light`"，每个调用有唯一 id，比如 `c1`），紧跟一条 `ToolMessage` 带同一个 `tool_call_id=c1`（"c1 的结果：客厅灯已打开"）。一问一答。

而 OpenAI 兼容协议对这个配对是**强制**的：`tool` 角色的消息必须紧跟在带对应 `tool_calls` 的助手消息之后。请求体里出现了答案却找不到问题，服务端不会宽容忽略，而是**直接 400 拒绝整个请求**。

**根因：`keep_from` 由条数和字符长度算出，这两个量跟配对关系毫无关系。**

回看 12.2.5 第 ② 步。`max(0, len(messages) - max_messages)` 是数出来的，token 循环推到哪格取决于每条消息有多长。**没有任何一处知道"哪条消息是哪条的答案"。刀口落在哪，纯属巧合。**

假设某会话已存 13 条，本轮用户又问一句变成 14 条（`AI*` = 带 `tool_calls`）：

```
索引  消息                        说明
 0   Human   "客厅灯开一下"
 1   AI*c1   tool_calls=[c1]       ← 问题
 2   Tool c1 "客厅灯已打开"          ← 答案（绑定 c1）
 3   AI      "已经打开了"
 ...
13   Human   "现在几度"              ← 本轮新追加

keep_from = max(0, 14 - 12) = 2
recent = messages[2:]   → 窗口首条是索引 2 的 Tool c1
old    = messages[:2]   → 索引 1（正是它的父消息 AI*c1）被 RemoveMessage 从 SQLite 删掉
```

发出去的请求体第一条（System 之后）就是一个孤儿 `ToolMessage` → 400。

**这个 bug 的三个性质，每一个都让它更难查。**

1. **它是间歇性的。** 换成 13 条或 15 条，`keep_from` 变成 1 或 3，落在合法位置，这轮完全正常。同一份代码、同一个用户，只因历史条数的巧合而时好时坏 —— **不是调 `context_max_messages` 能避开的**。
2. **它会自愈。** 下一轮追加新 `Human` 后 `keep_from` 前移一格，孤儿把自己挤出窗口并删除。于是症状是"长对话偶尔莫名报一次错，重问一遍就好了"。
3. **报错文案把人带偏。** CLI 把原始英文异常直接打给用户：`messages with role 'tool' must be a response to a preceding message with 'tool_calls'`。看到这句，第一反应通常是怀疑 API Key 或网络。

实测数字（穷举语料，见 `docs/gap-analysis.md` §1.1）：**每 3 次真正发生的裁剪就有 1 次切断配对**（474 / 1541 = 30.8%）；会话维度 207 / 243 = 85.2% 至少踩一次。

**修法：不改那两道闸门，在它们算完之后加一道对齐**（`summarizer.py:82`）：

```python
# 条数与 token 两道闸门都算完之后再对齐边界：这两道闸门只看长度，
# 不认识 tool_calls ↔ ToolMessage 的配对，必须由对齐兜住协议不变量。
keep_from = _align_window_start(messages, keep_from)
```

`_align_window_start`（`summarizer.py:33`）只守一条不变量：**窗口首条不能是 `ToolMessage`**。策略是"优先前进，前进不通才后退"：

```python
index = keep_from
while index < len(messages) and isinstance(messages[index], ToolMessage):
    index += 1                      # 向后跳过孤儿结果
if index >= len(messages):          # 前进会把窗口清空，才退回去
    index = keep_from
    while index > 0 and isinstance(messages[index], ToolMessage):
        index -= 1                  # 退到带 tool_calls 的父消息
return index
```

两个方向的取舍不是随手写的：**默认前进**（丢掉孤儿结果），窗口只会变小，两道预算闸门天然仍满足、不用重算，而且丢掉的那次工具结果，它的请求已经被切走了，模型看着它也无从解释；**只在前进会清空窗口时后退**（超小预算 + 一轮多次工具调用），此时略微超出 `max_tokens` —— **刻意接受**：超预算最坏是账单大一点，发出非法请求体是必然 400。

**顺带修掉的第二处：token 估算把工具调用当成了 1 token。** `estimate_tokens` 原来只数 `content`，而带 `tool_calls` 的 `AIMessage` 其 `content` 通常是空串 —— 工具名和参数都在 `tool_calls` 字段里，于是整个调用载荷被 `max(1, ...)` 兜底成 1。现在 `_billable_chars`（`summarizer.py:15`）把工具名和参数的字符数也算进去。这两处必须一起改：只修对齐不修估算，token 闸门在工具密集的长对话里几乎不生效（正是最需要它的场景）；只修估算不修对齐，`keep_from` 被推得更远，切错刀口的概率反而更高。

**通用教训，比这十几行补丁值钱得多：**

> **凡是"按长度切"的逻辑，都不认识"按语义配对"的约束。** 长度闸门（条数、token、字节）永远不会知道哪两条消息是绑定的。指望调参数避开是徒劳的 —— 参数只改变踩中的概率，不改变可能性。协议不变量必须由**专门一步**兜住，而且这一步的断言要写成"不变量本身"（`assertNotIsInstance(recent[0], ToolMessage)`），不是"返回文本长这样"。

还有一条附加教训，藏在这个 bug 为什么能活这么久里：最早的复现脚本用"每轮固定 1 次工具调用"的 FakeLLM，修复前后都是 0 孤儿 —— 那种对话每轮恰好 4 条，历史长度永远是 4 的倍数，`keep_from` 必然落在 `Human` 上。**规整的语料会系统性地掩盖这个 bug，而手写测试 fixture 天然是规整的。** 更糟的是旧用例的 fixture 是一条没有父消息的裸 `ToolMessage`，等于把错误行为编码成了预期，修复后它反而失败了（`tests/test_phase_three.py:34-36` 有注释就地记着这件事）。

> **bug 能长期存活，往往是因为有测试在保护它。**

### 决策二：候选永不自动入库

12.2.3 的两条被动路径都停在 `preference_candidates` 表。这是 001 方案的硬要求，代价是用户必须主动确认，收益是"系统不会替你决定你是谁"。

想想反面：如果 3 次重复操作就自动写进长期记忆，一个来家里住三天的客人就能把你的偏好改掉，而你完全不知道 —— 而且长期记忆**跨会话持久**，错误会一直复现。

### 决策三：检索先用词法打分，向量检索留一个"评估开关"

`evaluate_vector_retrieval()`（`service.py:131`）只干一件事：数活跃记忆条数，超过 `threshold=500` 就返回 `recommend_vector_retrieval: True`。不引入 embedding 依赖的理由很实在：这个规模下词法 + 结构化过滤够用，而且**确定性可测**（测试不需要跑模型）。方案文档把它写成了"评估"而不是"实现"。第 13 章的 RAG 是同一个取舍。

### 决策四：删除是软删除，修改留版本

`repository.delete()`（`repository.py:434`）不 `DELETE`，只把 `status` 改成 `'deleted'` 并给版本封上 `valid_to`；`update_value()` 走 `upsert` 生成新版本。为什么？**偏好会变，而"什么时候变的"本身是有用信息。** `list_memory_versions` 工具能把一条记忆的完整版本区间读出来。代价是表只增不减（见 12.5）。

### 实验 A：亲眼看两种记忆的区别

import tempfile, pathlib
from types import SimpleNamespace
from unittest.mock import patch
from loguru import logger; logger.remove()
from langchain_core.messages import AIMessage, HumanMessage
from src.agent.context import AgentContext, DeviceLocation, SpaceDirectory
from src.agent.graph import build_graph
from src.agent.time_travel import list_state_history
from src.devices import DeviceRegistry, SimulatorBackend
from src.memory import MemoryScope, MemoryType, MemoryWrite, close_checkpointer

tmp = tempfile.TemporaryDirectory(); root = pathlib.Path(tmp.name)

    turn(g1, ctx, '打开客厅灯'); turn(g1, ctx, '刚才我说了什么')
    print('session-1 累计消息 =', len(g1.get_state(ctx.to_config()).values['messages']))
    print('checkpoint 历史条目 =', len(list_state_history(g1, ctx.to_config(), limit=20)))
    close_checkpointer(g1.checkpointer); g1.memory_repository.close()   # 必须关，见 12.5

    g2 = build_graph(registry, settings, spaces)                        # ← 模拟进程重启

实测输出（最后一行是新会话 system prompt 里被注入的长期记忆）：

```
session-1 累计消息 = 4
checkpoint 历史条目 = 14
重启后 session-1 消息 = 4
新 session-2 消息     = 0
- [user/preference] ac.temperature: {'min': 24} (confidence=1.00, importance=0.50)
```

三行结论，正好对上 12.1 那张表：`重启后 session-1 消息 = 4` —— **checkpoint 活过了"进程重启"**（换了一个 `build_graph` 出来的图对象，读的是同一个 `thread_id`）；`新 session-2 消息 = 0` —— **换会话就一片空白**，checkpoint 不跨线；最后一行 —— **长期记忆跨会话生效**，`session-2` 的 prompt 里带上了 `min: 24`。

另外注意 `checkpoint 历史条目 = 14`：两轮对话产生了 14 个状态快照。checkpoint 存的不是"消息"，是**每个节点执行前后的完整状态**，所以条目数远多于消息数 —— 这也是 12.2.6 时间旅行的物质基础。

## 12.5 踩坑与局限

### 坑一：Windows 上 `TemporaryDirectory.cleanup()` 抛 `PermissionError`

这个坑的症状极具误导性：**测试断言全部通过，用例照样判失败**。

```python
import tempfile, pathlib
from src.memory import MemoryRepository
tmp = tempfile.TemporaryDirectory()
repo = MemoryRepository(str(pathlib.Path(tmp.name) / 'm.db'))
tmp.cleanup()          # 忘了 repo.close()
```

实测报错（traceback 最后一行）：

```
PermissionError: [WinError 32] 另一个程序正在使用此文件，进程无法访问。: 'C:\\Users\\ASUS\\AppData\\Local\\Temp\\tmpxyxsvnk6\\m.db'
```

Windows 不允许删除被打开的文件（Linux 允许，所以这个坑只在 Windows 显形）。凡在临时目录里建过 `MemoryRepository`、`AutomationStore`，或者调过 `build_graph()`，都要在目录删除前 `close()`。`build_graph()` 尤其容易漏：**它内部会创建 `MemoryRepository`**（`graph.py:146`），并通过 `graph.memory_repository` 暴露（`graph.py:931`）。CLI 退出时靠 `_release_runtime_resources()`（`src/main.py:306`）关它，测试里得自己关。

**更阴的是顺序陷阱。** 直觉写法是把 `self.temp_dir.cleanup()` 放进 `tearDown()` —— 但 unittest **先跑完整个 `tearDown()`，才轮到 `doCleanups()`**。于是它会早于测试方法内 `addCleanup(repo.close)` 注册的关闭动作执行：你明明注册了 close，它却在删目录之后才跑。正确做法是在 `setUp` 里注册（`tests/test_automation_routines.py:50` 附近的注释就地记着这个坑）：

```python
def setUp(self):
    self.temp_dir = tempfile.TemporaryDirectory()
    self.addCleanup(self.temp_dir.cleanup)     # ✓ 最先注册
```

`doCleanups` 是 **LIFO** —— 最先注册的最后执行，于是目录删除永远排在所有 `close()` 之后。

### 坑二：`store.py` 的模块 docstring 在撒谎

`src/memory/store.py` 顶部的 docstring 至今写着"长期记忆（用户偏好学习）**规划中**"、"当前实现：短期记忆（LangGraph Checkpoint）"、"规划中：向量数据库 + 用户画像"。**这段话早就过时了** —— 长期记忆已经完整实现（五张表），只是没用向量数据库。文件名也和方案文档不一致（`docs/iterations/001-memory-system-mvp.md` 里这个模块叫 `checkpoint.py`）。

写进来不是为了吐槽，而是提醒：**注释和文档会漂移，代码不会。** 判断"这个项目有没有长期记忆"，去看 `src/memory/` 下有几个文件、`build_graph` 里 `enable_long_term` 分支干了什么，别信任何一段自述。

### 坑三：token 预算约束的不是完整请求体

`context_max_tokens = 2400` 只约束**消息历史**。而实际请求体里还有 system prompt 本身（同口径估算约 2200 token，**单它就接近整个预算**）、全部工具的 JSON Schema（21+ 个），以及拼在 prompt 里的 `memory_context` + `conversation_summary`。所以日志打出 `上下文规模 | messages=12 | estimated_tokens=42` 时，真实请求可能是它的几十倍。修完决策一那处 `tool_calls` 漏算后倍数变小了，但性质不变：**护栏给的是偏乐观的估算**（见 `docs/gap-analysis.md` §3.1）。而且 `estimate_tokens` 是 `(字符数+1)//2`，不是真 tokenizer。

### 坑四：抽取器是正则，它"看懂"的比你想的少

实验 C 里 `我喜欢卧室的灯用暖白光` 抽出来的值是 `{'color': '暖白'}` 而不是 `暖白光` —— 因为 `extractor.py` 里 `(暖白|暖黄|暖光|冷白光|白光)` 是有序分支，`暖白` 先匹配上就不再往后试。这类"差不多对"的结果会原样进候选表、确认后进长期记忆、再拼进 system prompt。它不会报错，只会让偏好慢慢变得不精确。同理，`_STABLE_MARKERS` 之外的表达（"我一直都是……"）一条也抽不到。**这个取舍是有意的**（宁可漏，不可错），但你得知道漏在哪。

**这一章的局限**：

1. **SQLite 单机 + 零锁。** `MemoryRepository` 用 `check_same_thread=False`（`repository.py:22`）打开连接，全项目 3 处这么干，而后台调度线程和主对话流程会并发访问共享状态。单机演示没问题，多进程部署要换存储 + 加事务边界（`docs/gap-analysis.md` §3.5 自陈为已知局限）。
2. **检索是词法的。** 说"我怕冷"检索不到 `ac.temperature`，因为别名表里没这一对。语义检索是第 13 章的话题 —— 但第 13 章会告诉你，那边也没上向量库，理由和这里一样。
3. **`decay_stale_confidence()` / `evaluate_vector_retrieval()` / `clear_personal()` 没有生产调用方**，只有测试在跑。置信度衰减不会自动发生，规模阈值不会自动提醒 —— 都是"接口备好了，触发点还没接"。
4. **候选表可能悄悄堆积。** 用户只能通过 `list_preference_candidates` 工具（也就是"问一句"）看到待确认候选，CLI 没有对应命令。你可能观察了一个月，用户一条都没见过。
5. **`memories` / `memory_versions` 只增不减。** 软删除 + 版本留档意味着没有归档策略，长期运行会一直长。
6. **记忆内容是存储型 prompt injection 面。** `memory_value` 原样格式化进 `memory_context` 再拼进 system prompt（`graph.py:677`）。当前唯一防护是 prompt 里一句自然语言祈使句，它保护的是身份字段，不覆盖记忆内容。

**下一章的问题**：这一章的记忆全都是"关于**你**的事实" —— 存进 `MemoryRepository` 必须带 `home_id` / `user_id`，作用域和权限都围绕"谁的"展开。可是用户问"客厅空调显示 E3 是什么意思"，这条信息**不属于任何用户**，它属于那台空调的说明书，不该走记忆系统。那它走哪？更要紧的是：说明书里根本没写的时候，怎么让 Agent 闭嘴，而不是编一段听起来很专业的话？
