# 第 17 章 怎么验证你的改动

前面十六章讲的是这个系统怎么搭起来的。这一章讲你动手改完之后，怎么知道自己没改坏。

## 17.1 要解决什么问题

假设你读完第 3 章，觉得家里该有台香薰机，于是往 `CAPABILITIES` 里加了一条声明。你启动 CLI，说"打开香薰机"，Agent 回你：

```
好的，已经为您打开了客厅香薰机。
```

看起来成功了。但设备真的开了吗？

这个项目早期真的踩过这个坑，形态是：**Planner 生成的第一版计划稳定失败，而且不报错。** 原因是 action 词表有九份手写副本，你只改了其中八份 —— 喂给 Planner 的合法值列表说支持 `mist_on`，工具实现的 `if/elif` 里没有这一支，于是每次执行都返回"不支持的操作"，Verifier 判失败，replan，再失败。日志里没有一行 `ERROR`，只有一堆看着很正常的重试。

再假设一个更隐蔽的：你改了一行代码，跑测试，全绿，提交。三天后发现偏好库里少了一半数据 —— 因为那行代码让一个 `if` 恒为真，守卫失效了，而没有任何测试断言过"守卫真的拦住了东西"。

所以"验证改动"要回答两个不同的问题：

1. **功能对不对** —— 设备状态真的变了吗？数据库里真的写进去了吗？
2. **不变量还在不在** —— 那些散落在九个文件里的、必须同步的约定，有没有被你悄悄破坏？

这一章讲这个项目怎么用一套 `unittest` 同时回答这两个问题。以及为什么它**不**去断言 Agent 说了什么话。

## 17.2 代码怎么写的

### 17.2.1 第一原则：断言副作用，不断言措辞

`CLAUDE.md` 里有一句话，是整个测试体系的地基：

> 测试验证的是权限边界、数据库状态、设备真实副作用、Checkpoint 恢复和事件顺序，**不是返回文本**。

为什么？因为 LLM 的输出不是函数。同样的 prompt 问两次，一次说"已为您打开客厅灯"，一次说"客厅灯已开启 ✅"。你写 `assertIn("已打开", reply)`，第二次就红了 —— 而系统一点问题都没有。反过来更糟：模型可以在**什么都没做**的情况下说"已经打开了"（这就是第 6 章要有 Verifier 的原因）。**断言措辞既会误报，也会漏报。**

于是每一类测试都把断言点从"模型说了什么"下移到"世界变成了什么样"：

| 要验证的东西 | 断言的对象 | 实例 |
|---|---|---|
| 设备真实副作用 | `registry.get(...)` 的字段 | `test_phase_seven.py:370-371`：`assertFalse(...living_room_light.power)` |
| 数据库状态 | 仓库/服务的查询结果 | `test_phase_five.py:105`：`len(graph.memory_service.list_candidates(context)) == 1` |
| 权限边界 | 抛不抛异常 | `test_phase_two.py:158-168`：非管理员写家庭共享记忆 → `MemoryPermissionError` |
| Checkpoint 恢复 | 重建图之后能不能续上 | `test_phase_seven.py:353-372` |
| 事件顺序 | 事件流的序列 | `test_planning_progress.py:170`：批准后每步必须先 executor 再 verifier |
| 状态机走位 | `planning_status` / `intent_route` 字段 | `test_phase_eight.py:91-93` |

拿 Checkpoint 那条看一眼，它是这套哲学最漂亮的例子（`test_phase_seven.py:353-372`）：

```python
first_graph, _ = self._build([plan()])
interrupted = self._start(first_graph)
self.assertEqual(interrupted["__interrupt__"][0].value["kind"], "plan_approval")
close_checkpointer(first_graph.checkpointer)

second_graph, _ = self._build([plan()])            # 换了一张图，模拟进程重启
completed = second_graph.invoke(
    Command(resume={"approved": True}), self.context.to_config()
)
self.assertEqual(completed["planning_status"], "completed")
self.assertFalse(self.registry.get("living_room_light").power)
self.assertTrue(self.registry.get("bedroom_ac").power)
```

从头到尾没有一个自然语言断言。它检查的是：图被销毁重建之后，从 SQLite 里恢复出来的暂停点还能不能被 `Command(resume=...)` 续上，而且**续上之后灯真的关了、空调真的开了**。

### 17.2.2 怎么在没有 API Key 的情况下跑整张图

测试要跑 `build_graph()`，但 `build_graph` 第一步就是 `build_llm(settings)`，而 `Settings`（`src/config.py:243-247`）在初始化时校验 API Key，空值或占位符直接 `raise ValueError`。

两个替换手法，配合起来就绕开了整条依赖：

**手法一：`types.SimpleNamespace` 手搓 settings。** 不实例化 `Settings`，只造一个"长得像 settings 的东西"。`test_phase_eight.py:24-32` 是最完整的样本：

```python
self.settings = SimpleNamespace(
    memory=SimpleNamespace(
        enable_long_term=False, long_term_db_path=str(Path(self.temp_dir.name) / "memory.db"),
        db_path="", context_max_messages=12, context_max_tokens=2400,
        tool_result_max_chars=1200, summary_max_chars=1800, retrieval_top_k=6,
    ),
    planning=SimpleNamespace(enabled=True, max_steps=8, max_step_retries=1, max_replans=1),
    routing=SimpleNamespace(enabled=False, confidence_threshold=0.6),
)
```

只需要提供**你走的那条路径会读到的字段**。跑记忆的用例不需要 `routing`（`test_phase_three.py:74-82` 的 settings 只有 `memory` 一层，甚至没有 `long_term_db_path`）。缺字段的表现是 `AttributeError`，一眼就知道该补什么。

注意 `long_term_db_path` / `db_path` 都指向 `TemporaryDirectory` —— **测试从不碰仓库里的 `data/`**。

**手法二：`patch("src.agent.graph.build_llm", return_value=FakeLLM())`。** 打桩点是 `graph` 模块里的名字，不是 `llm` 模块里的定义处 —— 因为 `graph.py` 已经 `from ... import build_llm` 把名字绑到自己模块了。

一个最小可用的 FakeLLM 只要两个方法（从 `test_phase_five.py:83-89` 提炼），就够跑通 ReAct 主路：

```python
class FakeLLM:
    def bind_tools(self, tools):
        return self                              # 必须返回一个还能 .invoke 的对象

    def invoke(self, messages):
        return AIMessage(content="好的")
```

要走 Planner 或结构化路由分支，再加第三个 —— 它们用的是 `llm.with_structured_output(Schema)` 而不是 `bind_tools`（第 5 章讲过为什么），所以要返回一个能吐出 pydantic 对象的替身（`test_phase_eight.py:70-79`）：

```python
class FakeStructured:
    def invoke(self, prompt):
        return IntentResult(intent="memory_management", confidence=0.97, reason="...")

class FakeLLM:                                   # 三件套版本
    def bind_tools(self, tools): return self
    def with_structured_output(self, schema): return FakeStructured()
    def invoke(self, messages): return AIMessage(content="已识别为记忆管理请求。")
```

`test_phase_seven.py:38-52` 的 `PlanningFakeLLM` 多了一个狠招，值得抄：

```python
def invoke(self, messages):
    raise AssertionError("complex planning branch should not invoke the ReAct agent")
```

**把"不该走的路"做成断言。** 如果哪天路由改错、复杂请求被塞进了 ReAct 主路，测试不是"结果不对"，而是直接指着鼻子告诉你走错了分支。这比事后猜为什么状态不对省一小时。

### 17.2.3 生成式断言：让"漏改一处"在测试期爆炸

这是本章最值钱的一节。

第 3 章讲过设备能力收敛成了单一数据源（`src/devices/capabilities.py:1-23` 的模块注释里写着为什么）。但"收敛"只是把手写副本删了，它不能保证以后没人再加回来，也不能保证派生链条上每一环都真的接通了。

保证这件事的是 `tests/test_capabilities.py`。它的手法不是"写 20 个用例覆盖 8 种设备"，而是：**遍历声明表，对每条声明反射检查它的每个派生物。**

看最直白的一个（`test_capabilities.py:42-51`）：

```python
def test_control_tool_names_derive_from_capabilities(self):
    tools = {
        tool.name: tool
        for tool in build_device_tools(self.registry, enable_preference_tracking=False)
    }
    for cap in CAPABILITIES:
        with self.subTest(tool=cap.tool_name):
            self.assertIn(cap.tool_name, tools)
            self.assertNotIn("read_sensor", CONTROL_TOOL_NAMES)
```

注意这里没有任何字面量设备名。`for cap in CAPABILITIES` 意味着**你新加的第九种设备自动被这个用例覆盖**，你不需要为它写测试。`with self.subTest(...)` 让失败信息里带上是哪个工具挂的，而不是笼统一句"断言失败"。

同一份文件还钉住了另外六条派生链：

| 用例 | 钉住什么 | 行 |
|---|---|---|
| `test_planner_specs_and_literal_derive_from_capabilities` | `PlanStep.tool_name` 的 `Literal` ≡ `PLANNING_TOOL_NAMES` ≡ `DEVICE_ACTION_SPECS` 的键集 | `:53-63` |
| `test_automation_tool_names_derive_from_planning_tool_names` | `AutomationToolName` = 控制工具 + `set_alarm` | `:65-72` |
| `test_registry_keywords_derive_from_capabilities` | 每种设备类型都有 `find()` 关键词，且模拟器里真有这台设备 | `:74-84` |
| `test_simulator_defaults_derive_from_capabilities` | 声明的每台默认设备都真的注册进了模拟器 | `:86-94` |
| `test_tool_schema_exposes_declared_params_and_rejects_foreign_actions` | 声明的参数都进了 JSON Schema，`config` 绝不进 | `:96-111` |
| `test_mcp_server_reuses_the_same_tool_implementations` | MCP 工具与图内工具行为逐字一致 | `:129-141` |

`Literal` 那条特别值得停一下。`PlanStep.tool_name` 用 `Literal[tuple(PLANNING_TOOL_NAMES)]` 派生，所以理论上永远同步。那为什么还要测？因为 `assertEqual(set(get_args(...)), set(CAPABILITIES_BY_TOOL))` 也在防**未来某个人手写覆盖它**。`test_phase_seven.py:150-152` 的注释把这层意思写明了：「顺手确认它们没有被手写覆盖过」。

派生链的最后一环在 `test_phase_seven.py:172-205`，它做的是**双向反射**：

```python
for tool_name, spec in DEVICE_ACTION_SPECS.items():
    tool = tools_by_name[tool_name]
    device_name = self._sample_device_name(spec.device_type)
    for action in spec.actions:
        result = str(tool.invoke({"device_name": device_name, "action": action}))
        self.assertNotIn("不支持的操作", result)        # 正向：声明有的，实现必须认
    for foreign_action in ("turn_on", "turn_off", "toggle", "enable"):
        self.assertNotIn(foreign_action, spec.actions)  # 反向：实现不认的，声明里不能有
        result = str(tool.invoke({"device_name": device_name, "action": foreign_action}))
        self.assertIn("不支持的操作", result)
```

正向方向复现的正是 17.1 那个"Planner 稳定失败且不报错"的 bug —— 现在它会在测试期变成一条明确的失败信息。反向方向防的是另一件事：其他平台习惯写 `turn_on`，如果哪天有人"顺手兼容一下"，声明表就悄悄多了一个只有一半链路支持的 action。

连取样设备名都是反射的 —— `_sample_device_name()`（`test_phase_seven.py:129-137`）从模拟器里现取一台该类型的设备，docstring 写着「故意不写死映射表：新增设备类型时这些一致性用例应该自动覆盖到，而不是又多一处需要手工同步的清单」。

**一个用例里出现字面量清单，就是一处新的同步点。** 这是这套测试的自觉。

## 17.3 关键设计决策

### 决策一：不建 LLM 输出的评测集，把预算花在生成式断言上

被否决的方案是"造一批 prompt，跑真实模型，断言回答质量"。三条否决理由：**要钱要网络要 Key**（现在任何人 clone 下来就能跑）；**不稳定**（模型换版本就得重标，红了你不知道是代码坏了还是模型变了，这种测试很快会被 `@skip`）；**边际成本**（生成式断言新加设备自动覆盖，成本零；评测集是线性的）。

代价是诚实的：**LLM 行为层面的回归靠人肉。** 详见 17.5。

### 决策二：调度用虚拟时间，不用 `sleep`

自动化子系统是个后台调度器，测它最直觉的写法是 `time.sleep(2)` 等任务触发。这个项目没有 —— `RoutineScheduler.tick(now=...)` 接受注入的时间：

```python
wake_at = datetime(2026, 8, 16, 6, 0, tzinfo=UTC)
created_at = wake_at - timedelta(hours=8)
self.scheduler.schedule(routine, anchor_at=wake_at, trigger_key="wake-1", now=created_at)

self.scheduler.tick(created_at)                          # 立刻：闹钟应该已布好
self.scheduler.tick(wake_at - timedelta(minutes=30))     # 提前 30 分：热水器
self.scheduler.tick(wake_at - timedelta(minutes=10))     # 提前 10 分：烧水壶
self.scheduler.tick(wake_at)                             # 到点：窗帘 + 灯
```

（`test_automation_routines.py:63-88`，每次 `tick` 之后都去 `registry` 查真实设备状态。）

好处不只是快。是**确定性**：不管测试跑在多慢的机器上，第三次 `tick` 之前烧水壶一定还没开。用 `sleep` 的测试在 CI 上会随机红。

### 决策三：`ruff` / `mypy` 渐进式，配置先行

`pyproject.toml:53-77` 有配置，但环境里**默认没装**（`pyproject.toml:32` 的注释：「安装需用户明确许可，配置先行」）：

```bash
pip install -e ".[dev]"
ruff check src tests
mypy src
```

配置是刻意保守的：`ruff` 选了 `E/F/W/I/UP` 但 `ignore = ["E501"]`（行宽交给 `line-length`，不制造噪声）；`mypy` **不开 `strict`**、`exclude = ["tests/"]`，注释写着「先不加 strict，避免一次性淹没在存量标注缺口里」。

为什么值得装？因为有一类同步点**只有 mypy 看得见**。比如 `src/models.py:583-594` 的 `AnyDevice` 联合类型 —— 它只出现在类型注解里（`grep AnyDevice src/` 全是 `-> Optional[AnyDevice]` 这种），运行期完全是装饰品。你新加一种设备忘了往 `AnyDevice` 里加，**264 个测试全会绿**，只有 `mypy` 会说话。

### 实验 D（贯穿式）：亲手给家里加一台香薰机

这个练习把第 3、4、5、17 章串起来。目标：加一种 `DeviceType.DIFFUSER`（香薰机，动作 `on` / `off` / `set_level`），全程**让测试当导航**。

规则：**每改一步就跑一次 `tests/test_capabilities.py`，读它报什么错，再决定下一步改哪。** 不要先照着清单一次改完 —— 那样你学不到派生链条长什么样。

```bash
PYTHONIOENCODING=utf-8 "F:/Software/Anaconda/envs/langgraph/python.exe" -m pytest -q tests/test_capabilities.py
# 基线：10 passed, 8 subtests passed in 1.37s
```

**第 1 步（故意先做错的那一步）：** 只在 `src/devices/capabilities.py:400` 的 `CAPABILITIES` 元组里加一条 `DeviceCapability`，`device_type=DeviceType.DIFFUSER`，`default_devices` 先写 `()`。

跑测试 → **收集阶段就炸**：`AttributeError: type object 'DeviceType' has no attribute 'DIFFUSER'`。教训：能力声明依赖 `models.py` 的枚举，单一数据源不等于单一文件。

**第 2 步：** 补 `src/models.py`（这是两处手工里的第一处，内部有三件事）：

- `DeviceType` 枚举（`:25`，执行器成员在 `:52-59`）加 `DIFFUSER = "diffuser"`
- 新增 `class DiffuserAromaDevice(BaseDevice)`，字段范围用 `Field(..., ge=..., le=...)` 约束。照 `KettleDevice`（`:434-447`）抄：`target_temp: int = Field(default=100, ge=40, le=100, ...)` 再配一个 `@field_validator` 做 clamp
- `AnyDevice` 联合（`:583-594`）加上新类

跑测试 → 现在过了收集，但红在：

```
AssertionError: () is not true : DeviceType.DIFFUSER 缺少类型关键词
```

（形状和实验 B 一模一样。）

**第 3 步：** 补 `src/devices/capabilities.py:779` 的 `TYPE_KEYWORDS`，加 `DeviceType.DIFFUSER: ("香薰机", "香薰", "扩香")`。

跑测试 → 还是红，但换了一条：`test_registry_keywords_derive_from_capabilities` 的 `assertTrue(self.registry.get_by_type(cap.device_type))` 失败 —— 因为你第 1 步把 `default_devices` 写成了空元组，模拟器里没有这台设备，关键词匹配无从验证。

**第 4 步：** 把 `default_devices` 填上，例如
`((DiffuserAromaDevice, {"device_id": "living_room_diffuser", "name": "客厅香薰机", "location": "客厅", ...}),)`。模拟器会自动注册（`src/devices/simulator.py:233-245` 直接遍历 `CAPABILITIES`），你不用碰 `simulator.py`。

跑测试 → `tests/test_capabilities.py` **应该全绿了，subtest 数从 8 涨到 9**（多的那个就是你的新设备）。

**第 5 步：** 跑 `tests/test_phase_seven.py`。这里会触发 17.2.3 那个双向反射：它拿你声明的每个 action **真的调一次工具**。如果你的 `handler` / `expected` 写得对不上（比如 `set_level` 的 handler 忘了处理 `level` 参数），这里会红，信息是「`control_diffuser` 声明支持 `'set_level'`，但实现拒绝了它」。

**第 6 步：** 跑全量。测试方法数还是 264（你没新增用例），subtest 数会上涨 —— 涨的那些就是生成式断言自动帮你覆盖的部分。

**第 7 步（第二处手工）：** 想清楚新设备有没有**对外敏感动作**。香薰机没有 —— 它开着最多费点精油，不像门锁 `unlock` 会把家门打开，所以 `src/agent/approval.py` 不用改。如果你加的是"车库门"这类设备，就要照 `_is_unlock_call`（`approval.py:23-32`）加一条判定，并且**自己补一条用例**（照 `test_new_devices.py:90` 的 `test_unlock_requires_approval_but_lock_does_not` 抄）—— 审批判定是手工的，没有生成式断言会替你兜。

## 17.5 踩坑与局限

### 坑一：`TemporaryDirectory.cleanup()` 撞上没关的 SQLite 连接

Windows 上文件被占用时删不掉。SQLite 连接不关，`.db` 文件就被占用，`cleanup()` 抛 `PermissionError: [WinError 32]`，**测试本体断言全过也会判失败**（实验 C 已经看到了）。

所以凡是在临时目录里建过这些东西的，都要在目录删除前 `close()`：

- `AutomationStore`
- `MemoryRepository`
- `build_graph()` —— 注意这条：它内部会建 `MemoryRepository`（`src/agent/graph.py:146`），并通过 `graph.memory_repository` 暴露出来（`:931`）。所以是 `graph.memory_repository.close()`（`test_phase_five.py:106`）。`enable_long_term=False` 时它是 `None`，需要判空（`test_phase_eleven.py:49-50`）。
- SQLite Checkpointer —— 用 `close_checkpointer(graph.checkpointer)`（`test_phase_seven.py:362`）。

### 坑二（真正的杀手）：`tearDown` 早于 `doCleanups`

知道要 `close()` 还不够。**顺序也会错，而且错法很反直觉。**

unittest 的执行顺序是：`setUp` → 测试方法 → **整个 `tearDown` 跑完** → 才轮到 `doCleanups()`。而 `doCleanups` 是 **LIFO**（后注册先执行）。

把 `temp_dir.cleanup()` 写进 `tearDown`，它就会早于测试方法里 `addCleanup(repo.close)` 注册的关闭动作：

```
❌ cleanup() 写在 tearDown 里              ✅ cleanup() 在 setUp 里 addCleanup
──────────────────────────────           ────────────────────────────────────
setUp()                                  setUp()
  store = AutomationStore(...)             addCleanup(temp_dir.cleanup)   ← 注册 #1
                                           store = AutomationStore(...)
test_xxx()                               test_xxx()
  repo = MemoryRepository(...)              repo = MemoryRepository(...)
  addCleanup(repo.close)                    addCleanup(repo.close)        ← 注册 #2
tearDown()                               tearDown()
  store.close()                             store.close()
  temp_dir.cleanup()  💥 repo 还开着      doCleanups()  ← LIFO
doCleanups()                               repo.close()        （#2 先跑）
  repo.close()  ← 太晚了，目录已经删过了     temp_dir.cleanup()  （#1 后跑）✅
```

正确做法是**在 `setUp` 里 `self.addCleanup(self.temp_dir.cleanup)`** —— 最先注册，LIFO 保证它最后执行，一定排在所有 `close()` 之后。

实例在 `tests/test_automation_routines.py:36-42`，注释就是这段推导：

```python
def setUp(self):
    self.temp_dir = tempfile.TemporaryDirectory()
    # 目录删除必须排在所有 SQLite 连接关闭之后，否则 Windows 会抛
    # PermissionError: [WinError 32]，测试断言全过也判失败。
    # unittest 先跑完整个 tearDown 才轮到 doCleanups，所以放在 tearDown 里
    # 会早于测试方法内 addCleanup 注册的 close；而 doCleanups 是 LIFO，
    # 在 setUp 最先注册就能保证它最后执行。
    self.addCleanup(self.temp_dir.cleanup)
```

同一个类里 `tearDown`（`:53-56`）只做 `scheduler.stop()` 和 `store.close()`，测试方法内新建的 `MemoryRepository` 用 `self.addCleanup(repository.close)`（`:108-109`）。**这套组合是这个项目里唯一正确的写法，照抄别自创。**

（注意 `test_phase_seven.py:108-109` 的 `tearDown` 里还留着 `self.temp_dir.cleanup()`。它没炸，是因为那些用例都在方法末尾显式 `close_checkpointer(...)` 了。这是"能用但脆"的写法 —— 你在它里面加一个忘记关连接的用例，就会红。）

### 坑三：不要硬编码未来日期

`AutomationRuntime.schedule_wake()`（`src/automation/runtime.py:41-45`）和 `create_scheduled_routine()`（`:54-66`）都会校验目标时间晚于当前时间：

```python
if wake_at <= datetime.now(timezone.utc):
    raise ValueError("起床时间必须晚于当前时间")
```

写死 `datetime(2026, 12, 1, ...)`，用例今天绿、明年永久红。要用相对锚点（`test_automation_routines.py:235`、`:340`、`:409` 等）：

```python
wake_at = datetime.now(UTC) + timedelta(hours=8)
```

**反过来说：`scheduler.schedule(..., now=...)` + `scheduler.tick(虚拟时间)` 这条路径不做该校验**，所以 `test_automation_routines.py:63` 那个 `datetime(2026, 8, 16, 6, 0)` 是安全且刻意的 —— 固定日期让调度断言完全确定（那个日期今天已经是过去了，测试照样绿）。**区分标准是"走不走 runtime 的校验"，不是"日期在过去还是未来"。**

### 坑四：「1 处声明 + 2 处手工」还漏了两个手工点

`CLAUDE.md` 说新增设备只要改 `capabilities.py` 一处声明，加 `models.py` 和 `approval.py` 两处手工。实测下来还有两个地方是手写字面量，**而且没有生成式断言兜着**：

1. **`src/devices/simulator.py:112-123` 的 `type_order`** —— `get_status_summary()` 用一张手写的「`DeviceType` → emoji 标签」清单来排版设备状态报告。新设备不加进去，`get_device_status` 工具的输出里**根本看不到它**，而 264 个测试全绿。只有 `test_humidifier.py:45` 这种针对单个设备的手写断言（`assertIn("💧 加湿器", ...)`）能发现，新设备没人替你写。
2. **`src/tools/scenes.py:38` 的 `_SLEEP_POWER_OFF`** —— 睡眠模式只关灯/电视/加湿器，是手写 frozenset。这个更像刻意的业务选择（热水器、烧水壶睡眠时不强制关），但你新加设备时**必须自己想一遍"睡眠模式该不该关它"**，因为离家模式的 `SCENE_EXIT_TYPES`（`capabilities.py:806-809`）是派生的、会自动包含它，睡眠模式不会。顺带 `SCENE_META`（`scenes.py:46` 起）的场景描述文案里也逐字列了设备清单，那也是手写的。

补一条生成式断言就能堵住第 1 个（遍历 `CAPABILITIES`，断言每种类型都出现在 `get_status_summary()` 里）—— 这是个适合练手的小 PR。

### 坑五：两个跑测试的小陷阱

`-k` 是**子串**匹配（匹配测试 ID，不是正则全匹配，也不区分类名/方法名）。想精确到一个用例用完整路径：

```bash
... -m pytest -q "tests/test_phase_seven.py::PhaseSevenPlannerExecutorVerifierTests::test_sqlite_checkpoint_resumes_approved_plan_after_graph_rebuild"
```

另外仓库里**没有 `conftest.py`**，`pytest` 靠 rootdir 推断把仓库根加进 `sys.path`。所以**必须在仓库根目录跑**，`cd tests && pytest` 会 `ModuleNotFoundError: No module named 'src'`。

**这一章的局限**（三条都是真的短板，不粉饰）：

1. **没有 LLM 行为层面的回归集。** 所有 264 个测试都用 FakeLLM，验证的是"给定模型输出，系统怎么处理"。至于"真实模型面对这个 prompt 会不会输出正确的 tool_call"，唯一的验证手段是人肉跑 `python -m src.main --trace` 挨个试。你改了 prompt、改了工具 docstring、改了 `TOOL_ACTIONS` 喂给 Planner 的文本 —— 测试全绿也不代表模型的表现没变差。`test_phase_twelve.py:74` 有个 `test_trajectory_evaluator_reports_retrieval_and_citation_metrics`，是评测器本身的单测，不是评测集。
   > **013 起有了半步进展**，但要说清它是半步：`evals/knowledge_recall.json`（63 条 golden 用例）+ `src/evaluation/recall.py` 是这个仓库第一个真正的评测集，跑法是 `python -m src.evaluation.recall`（`--offline` 无 Key 可跑、`--sweep` 扫参标阈值）。它测的是**说明书检索的召回**——Recall@1 / Recall@3 / MRR / 拒答准确率，**不是 LLM 行为**。所以这一条局限依然成立：路由准确率、Planner 计划质量、端到端任务成功率三维仍然一个数字都没有。它的价值在于给另外三维留了个可照抄的骨架，见 `docs/gap-analysis.md` 的 2.1。
2. **没有 CI 配置。** 仓库里没有 `.github/workflows/`。谁也不会替你跑测试，靠自觉。
3. **覆盖率没测过。** 没装 `pytest-cov`，没有基线数字。哪些分支从来没被执行过，目前是未知的 —— 尤其是错误路径（precheck 拒绝、`InvalidPlanArgument`、replan 耗尽）里有几条只有一个用例路过。
