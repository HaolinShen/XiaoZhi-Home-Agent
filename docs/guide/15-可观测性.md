# 第 15 章 可观测性：出了问题怎么看见

这一章讲怎么让 Agent 的每一步都留下可查的痕迹 —— 事件、token、延迟，三种数据、四条通道。

## 15.1 要解决什么问题

上一章那个后台调度线程，凌晨 3 点醒过来，执行了一个例程，然后又睡回去了。第二天早上你发现空调没开。**现在你怎么查？**

进程还在跑，没崩，没报错。任务确实到期了、确实被取走了。至于它有没有真的调工具、工具返回了什么、Verifier 比对时期望值和实测值差在哪 —— 你手上什么都没有。你唯一能做的是加几行 `print`，然后等到明天凌晨 3 点。

这不是自动化独有的问题，它只是把问题放大了。更普遍的版本是：**Agent 说「已完成」的时候，你凭什么信它？** 这个项目开发过程中撞过四种「它说完成了但其实没有」：

1. **模型自述成功。** 它调了 `control_light`，工具返回一句失败提示，模型照样回「已经为你打开客厅灯」。工具返回值只是一段文本，模型有权把它总结成任何话。
2. **悄悄少调一个工具。** 用户说「关灯并把空调调到 26 度」，模型只调了关灯，回复却写「都办好了」。少调的那一个不会报错 —— **没发生的事不会抛异常。**
3. **重试三次全失败，最终回话很自信。** 第 6 章的 Verifier 会拦住失败，但拦住之后的重试、replan 全在图内部循环，用户看到的只有最后那句话。
4. **度量本身静默失效。** 这条最阴险，15.5 坑一会完整还原：token 日志的格式串引用了一个不存在的键，异常被 LangChain 的回调管理器吞成一行 stderr，业务照常跑完，**token 日志一条都不落盘**。

### 为什么 `print` 在这里不够用

`print` 调试的隐含前提是「有一个人正坐在终端前面，而且他知道该看哪里」。Agent 系统把这两个前提都打破了：

| `print` 的前提 | 为什么不成立 |
| --- | --- |
| 有人在看终端 | 后台调度线程在凌晨跑，没人在看 |
| 输出是给人读的 | 一次多步任务刷几十行，人读不过来，机器又解析不了自由文本 |
| 出错的地方就是该看的地方 | 症状（「空调没开」）和根因（Planner 把设备名写错了）隔着四个节点 |
| 信息量固定 | 用户要看「正在执行第 2 步」，开发者要看「路由置信度 0.83」，一份输出满足不了两种人 |

还有一个更麻烦的：**图有两种消费方式，它们看到的东西不一样。** 这是本章所有设计的起点。

## 15.2 代码怎么写的

三种可观测数据，落到四条日志通道：

```
                ┌──────────── emit_progress() ─────────────┐
 图节点 ────────┤  (a) stream custom 通道 → PlanProgressView → 终端
 （16 处调用）  │  (b) loguru channel=graph_progress (DEBUG) ──→ 日志
                └──────────────────────────────────────────┘
 build_llm() → ChatOpenAI(callbacks=[UsageTracer()])
                └→ channel=llm_usage (INFO)      ── token + 延迟
 @traced_node("verifier")
                └→ channel=node_latency (DEBUG)  ── 节点耗时
```

### 15.2.1 双写：因为有两条路径根本没人在听 stream

`emit_progress()`（`src/agent/observability.py:48-66`）整个函数只有十行，但每一行都在回答一个具体的事故：

```python
def emit_progress(event: str, **payload) -> None:
    try:
        writer = get_stream_writer()
    except Exception:
        writer = None
    if writer is not None:
        writer({"event": event, **payload})
    logger.bind(channel="graph_progress").debug(
        "{event} | {payload}",
        event=event,
        payload=json.dumps(payload, ensure_ascii=False, default=str),
    )
```

**为什么要写两遍？** 因为 LangGraph 的 `custom` 通道有一个非常安静的失败模式。

`get_stream_writer()` 拿到的写入器，只有在 `graph.stream(...)` 下才是真的。用 `graph.invoke()` 时，LangGraph 给你一个**空写入器** —— 调用它不报错、不警告，事件直接进垃圾桶。`docs/iterations/009-runtime-planning-visibility.md:17-20` 把根因写得很直白：

> `graph.invoke()` 会给一个空写入器，事件被静默丢弃，不报错也不警告。CLI 一直用 `invoke`，所以 007 加的那批 `custom` 事件从来没有到过终端。

也就是说：007 那一轮辛辛苦苦埋的进度事件，在 009 之前**一个都没到过任何地方**。代码里到处是 `emit_progress`，运行时一片死寂。项目里有三种调用路径：

| 路径 | 谁在消费 stream | 只写 stream 的后果 |
| --- | --- | --- |
| CLI 交互（`graph.stream`） | `PlanProgressView` | 正常 |
| `graph.invoke()`（测试、任何库调用方） | 没有人 | **全部丢失** |
| 后台自动化执行器（直接 `tool.invoke`） | 连图上下文都没有 | `get_stream_writer()` 直接抛 `RuntimeError` |

所以那个 `try/except`（`:56-59`）不是防御性编程的习惯动作，它是第三条路径的必需品。函数注释（`:52-53`）说得很清楚：

> 所以流式通道必须容错，日志侧才是所有路径都能依赖的痕迹。

**双写的全部理由：stream 是给人看的实时通道，能不能送到取决于调用方；日志是给事后查的落盘通道，任何路径都保证有。** 两者不是冗余，是覆盖不同的时间和不同的读者。顺带一个可抄走的细节：`json.dumps(payload, ..., default=str)`（`:65`）—— payload 里有嵌套 dict（`expected_state` / `actual_state`）和非 JSON 类型，`default=str` 兜底，注释原话「度量日志绝不该把业务打断」。

### 15.2.2 从零讲清 `stream_mode`

上一节反复提到 `stream` 和 `invoke` 的区别，现在把这个 API 完整讲一遍。它是 LangGraph 里最容易懵的部分。

先说两者的关系：`graph.invoke(input, config)` 跑完整个图、返回最终状态（**一个返回值**）；`graph.stream(input, config, stream_mode=...)` 跑图的同时不断往外吐东西、你用 `for` 循环接（**一个生成器**）。`stream_mode` 决定「吐出来的是什么」，当前版本（langgraph 1.2.10）支持这些取值：

| `stream_mode` | 每次 yield 什么 | 什么时候用 |
| --- | --- | --- |
| `"values"` | 每一步之后的**完整状态** | 想看状态整体怎么演化；数据量大（消息列表会重复吐很多遍） |
| `"updates"` | 每个节点返回的**状态增量**（`{节点名: 它返回的 dict}`） | 想知道「哪个节点改了什么」；也是 **`interrupt` 的到达通道** |
| `"messages"` | LLM 的 token 流（`(token, metadata)`） | 做打字机效果 |
| `"custom"` | 你自己用 `get_stream_writer()` 写进去的任意 dict | **自定义进度事件 —— 本章的主角** |
| `"debug"` / `"checkpoints"` / `"tasks"` | LangGraph 内部的调度细节 | 排查图本身的执行顺序 |

关键点一：**`custom` 通道里的东西完全是你自己写进去的。** LangGraph 不生产它，只负责传递。`emit_progress` 里那个 `writer({"event": event, **payload})` 就是这个通道的唯一入口。

关键点二：`stream_mode` 可以传一个**列表**。这时候 yield 出来的不再是裸 chunk，而是 `(mode, chunk)` 二元组 —— 你得自己按 mode 分流。本项目 CLI 就是这么用的（`src/main.py:280-282`，在 `_stream_segment()` 里）：

```python
for mode, chunk in graph.stream(
    payload, config, stream_mode=["custom", "updates"]
):
    if mode == "custom":
        view.handle(chunk)
    elif mode == "updates":
        interrupts = chunk.get("__interrupt__") if isinstance(chunk, dict) else None
        if interrupts:
            pending = interrupts[0].value
```

**为什么必须两个一起要？** 因为它们各自承担一件不可替代的事：`custom` 送进度事件，渲染 Planner / Executor / Verifier 的过程；`updates` 送 `{"__interrupt__": (Interrupt(...),)}`，第 7 章的人在回路审批全靠它 —— 审批中断不会出现在 `custom` 里，它是 LangGraph 自己的机制。去掉 `updates`，审批就永远等不到用户回答；去掉 `custom`，进度就退回 009 之前那两行光秃秃的话。`_stream_segment` 的注释（`main.py:272-274`）把这层因果也记下来了：

> 用 stream 而不是 invoke 是关键：只有 stream 才会把节点里 `emit_progress` 发出的 custom 事件交给调用方。

顺带一个连锁改动：既然进度已经边跑边打印了，最终状态就不必依赖返回值。`_invoke_with_approval()`（`main.py:292-304`）最后一行改成从 Checkpoint 读：`graph.get_state(config).values`。

### 15.2.3 事件分两级：`PLANNING_EVENTS` 和 `TRACE_EVENTS`

图里有 16 处 `emit_progress` 调用。全部默认显示的话，一次简单的「开灯」也会刷出路由置信度、记忆决策、上下文同步一堆东西 —— 用户看不懂，真正重要的那行还会被埋掉。所以 `observability.py` 把事件名分成两张词表（完整清单在 15.4 实验 A 里打出来）：

- **`PLANNING_EVENTS`（`:24-34`，9 个）—— 默认显示。** 注释里的理由是「它们正是『规划与执行分开』的证据」：`plan_generated`、`step_started`、`step_verified`、`step_retry` 这些。用户需要知道「正在执行第 2 步」「这一步没通过，在重试」—— 这些不是调试信息，是**任务状态**。
- **`TRACE_EVENTS`（`:37-45`，7 个）—— 要 `--trace` 才显示。** `supervisor_routing`、`memory_reasoned`、`context_synced` 这些是「Agent 为什么做了这个选择」的证据：路由分到了哪个意图、置信度多少、哪几条长期记忆被判为适用。用户不关心，改代码的人非常关心。

**不分级会怎样？** 只有两个结局，都不能接受：全显示 → 刷屏，重要信息被淹没，用户开始无视终端输出；全不显示 → 用户看着光标闪三十秒，不知道 Agent 死了还是在思考。分级把这个二选一变成了一个命令行开关。

渲染层的分流只有五行（`src/progress_view.py:68-75`）：

```python
def handle(self, event: dict[str, Any]) -> None:
    name = event.get("event", "")
    if name in PLANNING_EVENTS:
        self._planning_seen = True
        getattr(self, f"_on_{name}")(event)
    elif name in TRACE_EVENTS and self.show_trace:
        self._on_trace(name, event)
```

注意 docstring 那句「未知事件一律忽略」。这是刻意的向前兼容：以后图里加新事件，旧版 CLI 不会因为找不到 `_on_xxx` 方法而崩掉。而 `getattr(self, f"_on_{name}")` 这种按名字派发有个风险 —— 词表里写了名字但忘了写渲染方法，运行时才炸。`tests/test_planning_progress.py:349` 的 `test_every_declared_planning_event_has_a_renderer` 就是钉这个的。

### 15.2.4 `UsageTracer`：钩子必须挂在构造 LLM 的那一层

token 和延迟由 `UsageTracer`（`src/agent/telemetry.py`，一个 `BaseCallbackHandler`）采集。它挂载的位置只有一行（`src/agent/graph.py:105`）：`ChatOpenAI(..., callbacks=[UsageTracer()])`。`graph.py:96-97` 的注释解释了为什么这一行就够了：

> callbacks 会随 `bind_tools` / `with_structured_output` 一路传播，所以路由、Planner、ReAct Agent 的每一次 LLM 调用都会被记录。

这句话是本节的全部要点。展开讲：这个项目里 LLM 被调用的地方非常分散 —— 意图路由调一次，记忆推理调一次，Planner 用 `with_structured_output` 调，ReAct Agent 用 `bind_tools` 调，多智能体那 6 个角色各 `bind_tools` 一个子集，知识 RAG 还要调。**如果让每个调用点自己统计 token，那就是十几处需要手写的埋点，而十几处埋点意味着必然漏**：新加一个节点忘了埋，这个节点的 token 就永远不计入；`with_structured_output` 返回的是一个**新的 Runnable**，你以为埋在 `llm` 上就够了，结果漏掉整条 Planner 链路。

而挂在 `build_llm` 上只有一处。**因为 LangChain 的 callbacks 会跟着 Runnable 的组合传播** —— `llm.bind_tools(...)` 返回的新对象继承同一批回调。这是「唯一入口」型设计：想统计所有 LLM 调用，就把钩子挂在**唯一能构造 LLM 的地方**，而不是所有使用 LLM 的地方。（和第 4 章 `build_all_tools` 是同一个思路。）

`UsageTracer` 本身很简单：`on_llm_start` 按 `run_id` 记下 `time.monotonic()` 起点；`on_llm_end` 算延迟、提取用量、组装 record、追加进 `self.records`、再交给 sink。值得单独说的是**用量提取的容错**：`_extract_usage()`（`telemetry.py:34-60`）要兼容 openai 兼容接口的两代字段名 —— 新的 `usage_metadata` 用 `input_tokens` / `output_tokens`，旧的 `token_usage` 用 `prompt_tokens` / `completion_tokens`。`_normalize_usage()` 用 `or` 把两代合成统一的 `input/output/total`，`total` 缺失时用加法补，提取不到就返回三个 `None` —— 注释原话「绝不让度量本身把业务链路打断」。

**这个「提取不到就填 None」的宽松策略是对的**，因为中转网关、各厂商兼容层返回的字段名五花八门：度量少一条可以接受，度量抛异常把对话搞崩不可以接受。（这份宽松有个例外：模型名必须永远是字符串。为什么，见 15.5 坑一。）

### 15.2.5 `traced_node`：回答「到底哪一步慢」

`UsageTracer` 只能覆盖有 LLM 调用的节点。但慢的地方常常没有 LLM —— Verifier 要去查真实设备状态，`sync_context` 要检索长期记忆（可能是一次向量检索）。所以有第二层：`traced_node(name)` 装饰器（`telemetry.py`）。实现是最朴素的那种 —— `time.monotonic()` 夹一层 `try/finally`，`finally` 里写一行 `channel=node_latency` 的 DEBUG 日志。两个细节：

1. **`finally` 而不是正常返回后计时。** 节点抛异常时也要留下耗时 —— 「跑了 30 秒然后炸了」和「立刻炸了」是完全不同的两种故障。
2. **`functools.wraps` + `*args, **kwargs` 透传。** 图节点签名有两种（`(state)` 和 `(state, config)`），装饰器不能假设是哪种。`tests/test_telemetry.py` 的 `test_decorator_preserves_signature_and_records_latency` 钉住了 `__name__` 不被改写 —— LangGraph 用函数名做节点名，改写了图就连不起来。

当前被装饰的是 5 个节点（`src/agent/graph.py` 的 `:267` `memory_reasoner`、`:311` `task_router`、`:390` `planner`、`:506` `verifier`、`:654` `agent`）。有了这条日志，「到底哪一步慢」就从猜变成了查：把 `node_latency` 的行按 `node=` 分组，看 `latency_ms` 分布。如果 `task_router` 稳定占 800ms，那就是路由那次 LLM 调用的钱和时间 —— 这时候第 9 章那个「确定性信号直接返回、不问 LLM」的优化才有数据支撑。

### 15.2.6 `progress_view.py`：把事件变成人能看的东西

`src/progress_view.py` 是纯表现层。模块注释（`:1-18`）自己声明了分层原则：

> - 事件由 `src/agent/observability.py` 定义并发出（不依赖任何终端库）
> - 渲染只在这里做（依赖 rich，属于表现层）
> - 图和工具层不知道有终端存在

这个边界是有代价换来的：图里不能直接 `console.print`，得走事件；渲染层拿到的是 dict，得自己容错。换来的是图能在没有终端的地方跑（后台执行器、MCP 服务器、测试），而且渲染逻辑能用 `Console(file=StringIO())` 单测（见实验 C）。`PlanProgressView` 每个事件一个 `_on_*` 方法，三个有代表性的：

- `_on_plan_generated`（`:97-122`）把计划渲染成一张 rich 表格，标题写着「**此刻尚未触碰任何设备**」。这行字不是装饰，是「Planner 只写不做」的现场证明。
- `_on_step_verified`（`:154-171`）成功时打一行 `期望 X ≡ 实测 Y`，失败时打四行（`problem_type` + 期望 + 实测 + 原因）。**期望和实测并排显示**，让人一眼看出「是设备没听话，还是计划本身写错了」。
- `_on_planning_finished`（`:190-201`）里有段注释（`:196-197`）记的是一个措辞坑：「total 是"尝试次数"而不是"步数"：失败重试和被放弃的旧版本计划都记在里面，所以这里写成 通过 X 次 / 共 Y 次尝试，避免看成 X/Y 步。」

另外两处：`format_arguments()`（`:33-43`）按 `_MAX_VALUE_CHARS = 40`（`:30`）截断长值，把「日志会爆炸」挡在源头；`_on_trace()`（`:205-209`）是所有 `TRACE_EVENTS` 共用的极简渲染 —— 一行灰字列出 payload 键值，诊断信息不值得为每种事件写专用渲染器。

### 15.2.7 `middleware/interceptors.py` 是教学演示，不在生产路径上

`src/middleware/interceptors.py` 里有 `LoggingInterceptor`（`:45`）、`RetryInterceptor`（`:102`）和 `apply_all_middleware()`（`:174`），看起来像一个完整的中间件栈。**它没有在跑。** 文件顶部的警告（`:6-8`）是原话：

> ⚠️ 本模块是装饰器模式的教学演示，**未接入任何运行路径**。全库没有一处 import 它，删掉也不会影响功能。

为什么留着又不接？注释给了三个具体理由（`:9-18`）：

1. `RetryInterceptor` 无条件重试**所有** `Exception`（见 `:143` 那个裸 `except Exception`）。而 LangGraph 的 `interrupt()` 是靠**抛 `GraphInterrupt`** 实现人工审批的 —— 被它捕获重试，审批语义直接破坏：用户还没回答，同一个节点又跑了一遍。
2. LLM 层重试已经由 `ChatOpenAI(max_retries=2)` 做了，而且只重试可重试的错误码。叠加之后，「API Key 无效」这类确定性错误会被放大到十几次请求。
3. `LoggingInterceptor` 想解决的可观测性问题，现在由 `emit_progress()` 的结构化事件承担，后者还能按两张词表分级投递。

**所以：读这个文件是为了理解装饰器模式和「横切关注点」这个概念，不要以为它在生产路径上。** 它同时也是个好例子 —— 一段看起来很正确的通用重试逻辑，放进有 `interrupt` 语义的框架里就是错的。`try/except Exception` 写多了的人都该看一眼第 1 条。

## 15.3 关键设计决策

### 决策一：事件载荷按职责边界切分，而不是按方便切分

最省事的做法是每个事件都把当前状态整个塞进去。项目没这么做。`009` 文档 2.1 节写明了切法：`step_executed`（`graph.py:485-493`）**只报告 `tool_result`**（工具说了什么），不含任何结论；`success` / `problem_type` / `expected_state` / `actual_state` **只出现在 `step_verified`**（`graph.py:517-527`）里。

理由：让终端上的分工是**数据结构的形状**，而不是解说词。如果 `step_executed` 里也有 `success`，那 Executor 就等于在自己判自己的成败 —— 这恰恰是第 6 章要拆掉的东西。**可观测性的数据形状泄露了架构，就等于在鼓励别人破坏架构。** `tests/test_planning_progress.py:170` 的 `test_approved_run_emits_executor_then_verifier_for_each_step` 直接断言 `step_executed` **不含** `success` —— 这条边界是被测试钉住的。

### 决策二：`--trace` 和 `--debug` 是两个正交开关

这两个 flag 很容易被当成一回事，但控制的是完全不同的东西：

| flag | 位置 | 改变什么 |
| --- | --- | --- |
| `--trace` | `main.py:453-457` → `main.py:575` | 只改 `PlanProgressView(console, show_trace=trace)`，即**终端上 `TRACE_EVENTS` 显不显示** |
| `--debug` | `main.py:483-484` | 把 `settings.log_level` 改成 `DEBUG`，即**日志侧 DEBUG 级通道显不显示** |

而各通道的级别是（`log_level` 默认 `INFO`，见 `src/config.py:186-189`）：`llm_usage` 是 INFO，**默认可见**；`graph_progress` 和 `node_latency` 是 DEBUG，需要 `--debug`。

**所以：想看 token 花销，什么都不用加；想看结构化的进度事件日志，要 `--debug` 而不是 `--trace`。** 这个组合我第一次找的时候绕了一圈 —— 加了 `--trace` 却在日志里找不到 `graph_progress`，以为双写没生效。为什么级别这么定？`llm_usage` 一次对话也就十几行，而且直接对应钱，值得默认可见；另两条一次多步任务能出几十行，默认打开就是噪音。

### 决策三：进度事件是流水，Checkpoint 才是账本

被否决的方案是「把进度事件也存进状态里，方便事后查」。没这么做，因为状态里已经有更权威的记录了：`plan` / `planning_results` / `last_verification` 全在 Checkpoint 里。进度事件只负责**实时**，事后复盘走另一条路 —— `/plan` 命令（`main.py:166-171`）从 Checkpoint 把同一份轨迹重新取出来渲染：

> 进度事件是"流过去就没了"，这个命令从 checkpoint 里把同一份轨迹再取出来，用于事后复盘：哪一步重试过、Verifier 比对的期望值和实测值分别是什么。

**同一份事实，两种读法：流式的给当下，Checkpoint 的给事后。** 一份数据存两遍才是真正的隐患。

## 15.5 踩坑与局限

### 坑一：度量静默失效比没有度量更糟

这是本章最值得记住的坑，`telemetry.py` 里 `_extract_model()` 的 docstring 完整记录了它：

> `_log` 的格式串直接 `**record` 展开，loguru 在 `logger.info()` 里就地做 `str.format`，缺键会当场抛 `KeyError`。而这个异常会被 LangChain 的回调管理器吞成一行 stderr 提示（`Error in UsageTracer.on_llm_end callback: KeyError('model')`），业务链路照常跑完，token 日志却一条都不落盘 —— 度量静默失效比没有度量更糟。

根因链完整还原：

```
_log 的格式串写了 "model={model}"，但 record 字典里从来没被赋过 model 键
  → loguru 在 logger.info() 内部做 str.format(**record) → KeyError('model')
  → LangChain 回调管理器捕获所有回调异常（回调不该影响业务）→ 只打一行 stderr
  → 对话正常完成，用户毫无感觉
  → llm_usage 通道一行日志都没有，而你以为它在工作
```

**为什么「以为在工作」比「知道没有」更糟？** 因为你会基于「token 日志是空的」得出「这个路径没调 LLM」的错误结论，然后往错的方向查一整天。修法是让 `_extract_model()` **永远返回一个字符串**，取不到就 `"unknown"`。

这个坑对测试的要求特别有启发。`tests/test_telemetry.py` 的 `test_default_sink_actually_writes_a_log_line` docstring 说了两个「不能」：不能注入自定义 sink（另两个用例都注入了，于是 `_log` 这条唯一有 bug 的路径从未被覆盖）；也不能 patch 成 MagicMock（Mock 的 `.info()` 接受任何参数，而 `KeyError` 恰恰发生在 loguru 内部的 `str.format` 里）。所以这个用例真的装了个真 sink（`logger.add(lines.append, ..., filter=...)`），再断言 `lines` 里有一行且含 `model=deepseek-chat`。**「为了可测而注入的假依赖，会把唯一有 bug 的真依赖路径整条绕过去」** —— 这个教训不限于可观测性。

### 坑二：`--trace` 不会让结构化日志出现

见 15.3 决策二。`--trace` 只管终端渲染的事件分级，`graph_progress` / `node_latency` 是 DEBUG 级，要 `--debug`。两个都想要就都加上。

### 坑三：`traced_node` 的覆盖面比 telemetry.py 的注释暗示的窄

`telemetry.py` 模块注释举例说 `traced_node` 覆盖「没有 LLM 调用的节点（如 verifier / sync_context）」。实际上截至当前代码，被装饰的只有 5 个：`memory_reasoner`、`task_router`、`planner`、`verifier`、`agent`。

**`sync_context_node`（`graph.py:213`）和 `executor_node`（`graph.py:453`）都没有被装饰。** 后者尤其值得补 —— Executor 是真正调工具、真正碰设备的那一步，它的耗时最该被看见。你要给这个项目提第一个 PR，加两个装饰器是个很小的切口。

### 坑四：观测代码把业务搞崩

`emit_progress` 里的 `try/except` + `default=str`、`_extract_usage` 的「提取不到返回空 dict」、`traced_node` 的 `finally`、`handle()` 的「未知事件一律忽略」—— 这四处都是同一条纪律的实例：**观测层永远不能成为故障源。** 它可以少记一条，不可以抛一个异常上去。但这条纪律和「fail-fast」（第 4 章 `make_preference_recorder` 缺身份直接 `raise`）并不矛盾，因为两者性质不同：偏好记录**是业务**（丢了就是数据丢失），token 日志**是元数据**（丢了只是看不见）。分清哪个是哪个，才知道该 fail-fast 还是该兜底。

---

**这一章的局限**（诚实列，都是真的缺）：

1. **没有贯穿一次请求的 `trace_id`。** 日志里有 `run_id`（LangChain 给每次 LLM 调用的），但没有一个 ID 能把「同一次用户请求」的 `graph_progress` + `llm_usage` + `node_latency` 串起来。并发两个会话时日志会交错，你没法可靠地分开。`session_id` / `thread_id` 明明已经在 `RunnableConfig` 里了，只是没有 `logger.bind` 进去。
2. **没有采样。** 所有事件全量落盘。开发期没问题，量大了就是磁盘和 I/O 问题。
3. **没有成本汇总。** `UsageTracer.records` 只在**单个 tracer 实例**的内存里，而 `build_llm` 每次调用都 `UsageTracer()` 一个新的。没有跨请求聚合，没有「今天花了多少钱」这种视图 —— token 数有了，单价和汇总都没有。
4. **结构化日志目前只能 grep。** 通道名（`channel=llm_usage`）是为机器解析准备的，但没有任何东西在消费它。想看趋势只能 `grep llm_usage app.log | ...` 手工统计。

想往前走一步，两个方向：

- **接 LangSmith / Langfuse。** 最省事的路，因为 `UsageTracer` 已经是标准的 `BaseCallbackHandler`。`telemetry.py` 模块注释自己就写了「后续要接 Langfuse 等可视化时只需换 sink，数据来源不变」。LangSmith 更进一步 —— 设几个环境变量就能自动追踪整条 LangChain / LangGraph 调用链，`trace_id` 的问题它顺手就解决了。
- **接 OpenTelemetry。** 如果这个 Agent 要和别的服务放在同一套监控里，OTel 是通用语言：把 `traced_node` 换成 OTel span，把 `graph_progress` 事件挂成 span event，`trace_id` 自然贯通。代价是要引入一套不小的依赖和一个 collector。

不管走哪条，本章的三层结构（事件 / token / 节点延迟）和四条通道都不用改 —— **换的是 sink，不是埋点。** 这是把观测数据统一走 `logger.bind(channel=...)` 换来的最大好处。

**下一章的问题**：到这里，这个 Agent 自己能看、能查、能验证了。但它的工具箱只有它自己能用 —— Claude Desktop、Cursor、别的 Agent 想调你的 `control_light` 怎么办？总不能让每个客户端都 import 你的 Python 包。
