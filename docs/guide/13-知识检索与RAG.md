# 第 13 章 知识检索与拒答纪律

这一章讲 Agent 怎么回答"说明书里写了什么"，以及**答不上来的时候怎么闭嘴**。

## 13.1 要解决什么问题

上一章的记忆系统解决的是"关于**你**的事实"：你喜欢 25 度、你家周五晚上看电影、你不许小孩碰门锁。这些事实的共同点是**有主人**——存进 `MemoryRepository` 时必须带上 `home_id` / `user_id`，作用域和权限都围绕"谁的"展开。

现在来一个问题：**"客厅空调显示 E3 是什么意思？"**

这条信息**不属于任何用户**。它属于那台空调的说明书。你不会把它写进"张三的偏好"里，因为换成李四家的同款空调，答案一字不差。所以它不该走记忆系统。那它走哪？

**先看不做任何处理会发生什么。** 直接把这句话丢给大模型，它会给你一段非常流畅的回答：

> E3 通常表示空调的室外机通信故障或制冷剂压力异常，建议检查……

听起来很专业。问题是——**这可能是编的**。模型不知道你家这台"SmartCool AC2024"的错误码表，它只是把训练数据里见过的几十个品牌的错误码混在一起给了个"平均答案"，甚至可能把美的的 E3 说成格力的 E3。两个原因让它必然不知道：**训练数据有截止时间**（之后出的新型号它一无所知），**它从来没看过你家的说明书**（定制固件、物业贴的维护单，都不在任何公开语料里）。

而这类幻觉在家居场景特别危险，因为**用户会照做**。模型编一句"滤芯建议每 3 个月更换一次"，用户就真的三个月才换一次；编一句"E3 可以自行拆机检查"，用户就真的去拆带电设备了。

这一章要做的就是：**在让模型开口之前，先去一个我们自己控制的文档库里查一遍。查到了就照文档答并给出来源；查不到就说不知道。** 而且比这个多一步——说明书里的排查清单，有一部分系统**自己就能核对**，这一章会把文档问答做成可执行诊断。

## 13.2 代码怎么写的

### 13.2.1 先讲清 RAG 是什么

**RAG = Retrieval-Augmented Generation，检索增强生成。** 拆开看就三步，一点也不玄：

1. **Retrieval（检索）**：拿用户的问题去文档库里搜，找出最相关的几段文字。
2. **Augmented（增强）**：把搜到的原文塞进给模型的 prompt 里，相当于当场给它发一份开卷考试的参考资料。
3. **Generation（生成）**：模型只依据这份资料作答。

一句话总结：**RAG 不是让模型变聪明，是让它别凭记忆答题。**

```
用户问题
   │
   ▼
┌──────────┐  实体消解：这句话说的是哪台设备、哪份说明书？
│ identify │──── 解析不出唯一设备 ──► 反问 / 拒答
└──────────┘
   │ 唯一设备 + 型号
   ▼
┌──────────┐   在该型号的文档库里搜
│ retrieve │────────────────────────► 命中若干段原文（chunk）
└──────────┘
   │                                          │
   │ 低分 / 零命中                            │ 高分命中
   ▼                                          ▼
┌──────────┐ 改写成说明书用词后重搜      ┌───────────┐
│ rewrite  │ ─── 还不行 ──► 拒答        │ self_check│ 读设备真实状态核对检查项
└──────────┘                            └───────────┘
                                             │
                                             ▼
                                   模型写建议 + 代码拼引用与核对结论
```

注意两条失败分支。**很多 RAG 教程只画命中的那条**，于是你学到的是"怎么检索"，而不是"检索失败怎么办"。而失败分支恰恰是生产系统里出事最多的地方。

### 13.2.2 知识库：从 Markdown 文件到可检索的 chunk

语料是 `docs/knowledge/` 下的普通 Markdown 文件，加一份目录 `catalog.json`（每篇一条，共 39 篇）：

```json
{"id": "smartcool-ac2024-errors", "title": "SmartCool AC2024 故障代码",
 "model": "SmartCool-AC2024", "file": "smartcool-ac2024-errors.md"}
```

`model` 字段是**型号标签**，型号过滤全靠它。39 篇文档覆盖 **13 个型号、全部 10 种设备类型**，每个型号固定三份：**故障代码 / 常见症状排查 / 保养与清洁**。013 之前只有 5 篇覆盖 3 个型号——那个规模测不出检索质量，因为几乎每个查询的候选集都只有十来段，随便打分都不太会错。

型号里**两台空调刻意是不同型号**（`SmartCool-AC2024` / `FrostLine-AC310`），而且两份说明书里 **E4 的含义完全不同**——一个是室内外机通信异常，一个是排水泵异常。这不是随手写的语料，是一块试金石：型号过滤要是失效，问"空调显示 E4"就会拿到另一台空调的答案，而且测试能立刻抓住（13.4 实验一）。

还有**两处刻意保留的语料缺口**，它们不是"还没补"，而是**被测行为**：

- **客厅灯不登记 `model`。** 守住 `no_model` 那条拒答路径——没登记说明书就说没有，不拿别的灯的手册凑（13.4 实验一第 4 条）。
- **`FrostLine-AC310` 的症状手册只有「制冷效果不佳 / 排水不畅 / 蒸发器结霜」三节，没有噪音章节。** 守住"本型号说明书查不到就必须拒答"。这条缺口后来变成了整章最有价值的一个实测发现（13.3 决策三）。

`KnowledgeBase._load()`（`src/knowledge/base.py:114`）在构造时把全部文档读进内存，对每篇按 `## ` 二级标题切段（`_split_markdown()`，`base.py:199`——只认二级标题，`###` 会被当成正文吞进上一节），然后对每段调 `_extract_checklist()`（`base.py:216`）做一件事：**剥行内标注、抽排查清单**。

排查清单的条目长这样（`docs/knowledge/smartcool-ac2024-symptoms.md`）：

```markdown
1. 确认空调处于开机状态，待机或定时未启动时不会送出冷风。<!--check:device_is_on-->
2. 确认设置温度低于当前室温，温差过小时压缩机不会持续运行。<!--check:ac_target_temp_below_room-->
3. 确认运行模式为制冷，送风或除湿模式不会降低室温。<!--check:ac_mode_is_cool-->
4. 检查进风口滤网是否积尘，滤网堵塞会显著降低风量。<!--manual-->
5. 检查室外机出风口是否被杂物或墙面遮挡，散热受阻会明显削弱制冷能力。<!--manual-->
```

标注为什么写在正文行内、用 Markdown 注释，而不是在 `catalog.json` 里另开一张"第几节第几条归谁核对"的表？三条理由，每条都是教训式的：

- **同位。** 标注跟着它描述的那一行走。写在索引里，说明书改一行顺序全部标注错位，**而且错位是静默的**。
- **不可见。** 注释渲染时不显示，说明书在任何阅读器里仍然是一份说明书。不存在"为了代码好解析而篡改厂商文本"的问题。
- **不污染检索。** 标注被剥离后**既不进给用户看的正文，也不进检索词表**。如果不剥，`ac_target_temp_below_room` 会被切成 latin token 参与打分——搜"target"就能搜出空调说明书。

`_load()` 里有两道**构造期校验**，都是"宁可启动失败"：

- `_validate_check_ids()`（`base.py:239`）：**语料引用了一个 `SELF_CHECKS` 里不存在的 check id，`KnowledgeBase` 构造直接抛 `ValueError`。** 不容忍"未知 id 降级成需人工确认"——那会让一条本该自动核对的检查项无声消失，功能变弱但不报错，是最难定位的那类缺陷。
- **`catalog.json` 登记了却不存在的 `.md` 文件，抛 `FileNotFoundError`**（`base.py:123`）。012 时代这里是一句静默 `continue`：那份说明书永远检索不到，而**什么都不报**。改名文件忘了改 catalog，表现是"这个型号怎么老是拒答"，根因藏在一行 `if not path.exists(): continue` 里。

全部加载完是 **124 个 chunk**，分布很均匀（每个型号 7~10 节，`VisionTV-V1` 最少 7、`GlowSoft-L90` 等十个型号各 10）。以 `SmartCool-AC2024` 为例（`source | section | 字数 | 清单条目数`）：

```
smartcool-ac2024-errors.md       | E3         |  71 | 0
smartcool-ac2024-errors.md       | E4         | 173 | 0
smartcool-ac2024-errors.md       | 安全提醒    |  56 | 0
smartcool-ac2024-symptoms.md     | 制冷效果不佳 | 155 | 5
smartcool-ac2024-symptoms.md     | 噪音异常    | 198 | 0
smartcool-ac2024-symptoms.md     | 有异味      | 184 | 0
smartcool-ac2024-maintenance.md  | 清洗周期    |  53 | 0
smartcool-ac2024-maintenance.md  | 清洁步骤    |  55 | 0
```

124 个 chunk 里带排查清单的有 **25 个**，一共 **47 条可自证 + 56 条需人工**。其余小节清单为空——**识别范围由语料显式声明**，代码不去猜"长得像清单的行"。

### 13.2.3 分词：先让"词"真的是词

检索的第一步是把中文切成 token。这一步在 013 之前是整条链路里最弱的一环，而且它的弱**会伪装成"检索算法不行"**，所以单独讲。

012 的做法（`_terms()`）是**字符 bigram**：把所有汉字抽出来拼成一串，再滑窗取相邻两字。"空调滤芯" → `{空调, 调滤, 滤芯}`。好处是零依赖，坏处有三处，前两处会**掩盖失败**，第三处直接堵住了后面要用的 BM25：

- **伪词会意外匹配。** "客厅空调显示"切出「厅空」「调显」这种不存在的词。它们在查询侧和文档侧规则一致，所以偶尔真能对上——于是一次本该暴露的召回失败被掩盖成"分数低但有命中"。
- **跨边界。** 非汉字字符（空格、标点、错误码）被整体删掉之后才拼接，"显示 E3 是什么"会切出跨过 E3 的「示是」。
- **丢词频。** 旧实现返回 `set`，一个词出现 10 次和 1 次同权。**BM25 需要的 TF 在建集合那一步就已经没了**，所以旧打分只可能是"覆盖率"，不可能是 BM25。

013 换成 jieba 词典分词（`src/knowledge/tokenizer.py:85`），返回 `list` 而不是 `set`（把词频交给 BM25）。三个具体决定：

**一、错误码先整体摘出来，再从原文里挖掉。** 两步都是必要的：不先摘，`E3` 会被切成「e」和「3」，而单字母在下面会被丢掉——结果是**错误码在检索里彻底消失**，偏偏它是这套语料里最精确的键。不挖掉，同一个码会被计两次（摘一次、jieba 又切一次），TF 凭空翻倍。

**二、修掉一个真实缺陷：错误码正则的边界。** 旧实现用 `\b`：

```python
# 旧：Unicode 模式下汉字也算 \w，所以 "示" 与 "E" 之间没有 \b
re.compile(r"\b(?:[a-z]\d+|\d{3,})\b")     # "显示E3是什么" → 匹配不到 E3

# 新：ASCII 前后向断言，汉字和标点都算边界
CODE_PATTERN = re.compile(r"(?<![a-z0-9])(?:[a-z]\d+|\d{3,})(?![a-z0-9])")
```

**旧实现只在用户恰好打了空格时才认得出错误码。** 不打空格，"显示E3是什么"就静默走成一句普通口语查询——错误码硬门槛不生效、"带错误码永不重写"也不生效，而日志里什么都看不出来。这个正则现在是**唯一数据源**（`tokenizer.py:61`），型号硬过滤和"带错误码永不重写"都用它；012 时代它在两个文件里各写了一遍，靠一句注释"保持一致"约束。

**三、关掉 jieba 的 HMM 新词发现（`HMM=False`）。** 这一条是实测逼出来的，而且代价算得很清楚：

```
默认开着 HMM：jieba.cut_for_search("卧室灯不太亮了") → 卧室 / 灯不太亮 / 了
```

「灯不太亮」是 HMM 凭概率粘出来的词，**任何说明书里都不存在**。后果是召回**归零**：BM25 只剩「卧室」可用，而「卧室」恰好出现在讲清洁周期那节（"普通卧室环境建议…"）、不出现在正确的「亮度明显偏低」里——BM25 因此给**错误**小节 4.84 分、给正确小节 0 分。关掉后切成 `卧室/灯/不/太/亮/了`，「亮」能对上「亮度」。

代价是文档侧的技术词会被拆散（换能片 → 换/能/片，热释电 → 热/释/电）。这个代价可以接受，因为它是**对称**的：用户问「换能片」时查询也这样拆，仍然匹配得上，只是单字 IDF 低、信号弱一些——**损失的是精度**。而 HMM 粘连损失的是**召回**，直接归零。**非对称粘连严格劣于对称拆分。**

查询侧和文档侧**都**用 `cut_for_search`（搜索引擎模式，长词再切出短词："排水泵" → 排水 / 水泵 / 排水泵），这也是刻意的对称：文档切成「排水」「泵」而查询切成「排水泵」的话，这一项完全对不上，而且失败得很安静。

还留了一张很短的停用词表（`tokenizer.py:71`）。这里要说清它为什么**还需要**存在：BM25 里对不上的查询词贡献 0 分，本来不该有影响——问题出在**对得上**的那些。"是""在""有"这类词在说明书里真的会出现（"E3 表示……"），IDF 只能把它们压低、压不到 0，于是每个小节都拿到一份均匀的噪声底分。而这个模块的下游是**绝对分数守门**（13.2.6 的三档下限），抬高噪声底分等于让垃圾看起来也有分。所以只删"出现与否都不携带检索信号"的功能词，语义词一律留给 IDF。

### 13.2.4 检索：混合检索，两套分数各管一件事

`KnowledgeBase.search()`（`base.py:137`）现在只做**硬过滤**，打分整个委托给 `HybridRetriever`（`src/knowledge/retrieval.py`）。分层的界线是：`base.py` 认识"说明书""型号"这些概念，`retrieval.py` 只认下标和文本。

**先讲硬过滤：型号相等、错误码 issubset 是准入条件，不是打分项。**

```python
candidates = [
    index
    for index, chunk in enumerate(self.chunks)
    if not (model and chunk.model != model)                          # 硬过滤一
    and (not query_codes or query_codes.issubset(self._codes[index])) # 硬过滤二
]
scored = self.retriever.score(query, candidates)
```

`model` 是**关键字必填**参数，签名里没有默认值：

```python
def search(self, query: str, *, model: str | None, top_k: int = 3) -> list[KnowledgeHit]:
```

`model=None` 依然能搜全库，但必须由调用方显式写出来。全库检索从此**不可能是漏传参数的副产品**——而"不带型号过滤搜全库"恰恰是这个模块最该防住的失败模式（13.2.5 讲为什么）。

**加了向量通道之后，这两道硬过滤比以前更重要，不是更不重要。** 向量检索在这里尤其危险：**E4 的语义近邻天然是 E5、E7**——它们讲的是完全不同的故障，但在任何 embedding 空间里都离得很近。一旦把错误码从硬过滤降级成"相似度的一部分"，用户问 E4 就会拿到 E7 的处理步骤，**而且读起来完全通顺**。所以这两道门在候选集阶段就生效，绝不能变成融合公式里的一个权重。

**两套分数：`rrf` 定名次，`confidence` 定放行。**

这是整个 013 最要紧的一个设计，值得慢慢读。

012 的拒答纪律依赖一个**绝对**判断：所有候选都不够好时必须说"查不到"，而不是把最不差的那个递出去。它靠分数下限实现，成立的前提是**分数带量纲**——0.11 是噪声、0.75 是真命中。

而 RRF（Reciprocal Rank Fusion，倒数排名融合）是**纯名次**的：`Σ w/(k + rank)`，k 取 60（Cormack 2009 的原始取值，也是业界默认）。**名次第一的文档必然拿到该通道的最高分，跟它到底像不像毫无关系。** 一个语料里根本没有对应章节的查询，它的第一名照样是满分 RRF。

**所以如果直接拿 RRF 分去套三档下限，拒答纪律会当场失效：每个查询都会有一个"高分"命中，拒答分支永远走不到。** 这不是理论担忧，它是设计这一层时必须先解决的问题。

结论是两套分数各管一件事，不能混：

| 分数 | 管什么 | 取值 | 为什么是它 |
|---|---|---|---|
| `rrf` | **只定名次** | 无上界、只可比大小 | 名次融合对**量纲免疫**：BM25 无上界、余弦在 [0,1]，直接加权求和得先把两者拉到同一尺度，而 RRF 不用标定 |
| `confidence` | **只定放不放行** | 锁死 [0,1] | 三档下限套在它身上（13.2.6）。它必须是绝对的，否则"查不到"这句话就说不出口 |

分工落到代码里是两处：`base.search()` 按 `rrf` 排序并截到 `top_k`（排序键末两级是 `document_id` / `section` 稳定 tiebreak——RRF 是 `1/(k+rank)` 的和，取值离散，同分概率比连续分数高得多，没有确定性 tiebreak 会让测试随机失败，`base.py:167`）；**够不够格放行则由 `rag.py` 的 `retrieve` 节点拿三档下限卡 `confidence`**。名次和放行是两个独立的判断，一条命中可以"排第一但不够格"——13.4 实验七里就有一条专门钉住这件事的用例。

**`confidence` 怎么合成：只对"有确凿证据"的通道求平均。**

`_confidence()`（`retrieval.py:285`）的规则一句话说完：**只对有确凿证据的通道求加权平均，弱通道不参与，而不是当 0 分参与平均。**

这条规则是实测逼出来的，代价很具体。先看**固定权重求平均**（0.5/0.5）为什么不行：

```
查询「洗澡水不够热」，正确答案是 AquaWarm-W80 说明书的对应小节
  BM25   0.00    （一个词都对不上）
  余弦   0.623   （语义完全对上）
  固定 0.5/0.5 平均 → 0.362
  而"离线时靠通用词凑出来的错误命中"是 0.331
```

**只差 9%，阈值根本没有可用的落点。** 更本质的问题是：固定权重让"只有一个通道确信"的命中**上限变成 0.5**，而那恰恰是混合检索存在的理由——如果两个通道必须同时确信才算高分，那就没必要要第二个通道。按"有证据的通道"平均之后，这一条是 **0.725**，而噪声因为两个通道都低于各自基线，得到的是 **0**。

反过来也要防住：**不能用 max 或 soft-OR。** 那会让单通道的噪声直接成为置信度——两个弱信号本该互相否证，soft-OR 却把它们相加。

所以**关键不在"用哪种合成函数"，而在于每个通道各自先有噪声基线**：弱信号必须先归零，再谈合成。这也顺带取消了"语义通道不可用时把权重收拢到词法通道"的特例——**通道缺席和通道弱本来就该走同一条路**。

**两个通道各自的归一化，都是实测标定的。**

**BM25 无上界。** 不能用"除以本次查询的最高分"来归一——那样第一名恒为 1.0，又变回名次分，绝对性再次丢失（和 RRF 不能守门是同一个理由）。用饱和函数 `(x - floor) / (x - floor + 6.0)`，噪声基线 `floor = 3.5`：

```
靠"异常""检查""卧室"这类通用词凑出来的噪声命中   BM25 ≤ 2.96
真实词法命中                                    BM25 ≥ 4.26（一路到 30.6）
```

3.5 正好落在这条缝里。**低于基线的 BM25 分一律记 0**，不折算成 0.27 那样的小正数——理由就是上一段：两个弱信号必须得到 0，不能靠累加凑出个中间值。

**这个基线依赖语料规模，换语料必须重标**（`retrieval.py:57` 的注释里记着这个坑：拿三个 chunk 的合成语料写测试，所有 BM25 分数都远低于 3.5，于是什么都进不了名次——测出来的是"基线没标定"而不是被测的机制）。重标方法是 `python -m src.evaluation.recall --sweep`。

**余弦有基线偏移。** `text-embedding-v4` 上两段完全无关的中文也有 0.31~0.42 的余弦（向量空间各向异性），直接当置信度用会让垃圾看起来有四成把握。所以减掉基线、再按"多高算强命中"拉回 [0,1]：

```
_V4_BASELINE_SIMILARITY = 0.42   # 取六组无关对余弦的**上界**
_V4_STRONG_SIMILARITY   = 0.70   # 取六组相关对余弦的中位数
```

基线取无关对的上界而不是中位数，是刻意的：宁可把边缘的相关对压成 0，也不让无关对拿到正分——下游是绝对分数守门，假阳性会直接变成"拿着别人家的章节权威作答"。只减基线不除强命中也不够：`(0.60-0.42)/(1-0.42)` 只有 0.31，而 0.60 在实测里已经是确凿的相关命中了。

**两个刻度挂在 provider 上**（`embeddings.py:66`），不写死在检索层。**换 embedding 模型必须重测这两个数，不能沿用。**

**名次也要过噪声基线。**

最后一处修正是评测逼出来的，很反直觉：**进名次的门槛也得是"有证据"，不能是"分数大于 0"。**

RRF 会**奖励"在两个通道都出现"**，而 BM25 的"出现"极其廉价——任何一个词有一点重叠就有正分、就有名次。于是一个只靠通用词沾上边的小节会赢：

```
噪声小节   BM25 排第 1 + 向量排第 5 → 0.2/(60+1) + 0.8/(60+5) = 0.0156
正确答案   BM25 没排上 + 向量排第 1 →              0.8/(60+1) = 0.0131
```

**给弱通道降权解决不了这个问题**（上面那组数就是权重 0.2 时算的），因为问题不在票数权重，而在**噪声本来就不该有投票权**。所以 `score()` 里进 `_ranks()` 的候选先过各自通道的基线：BM25 要高过 3.5，余弦要高过该模型的基线（`retrieval.py:225-245`）。

顺带一个实现上的纪律：权重为 0 表示"这个通道完全不参与"，**名次和置信度都不参与**，不是只把置信度权重清零。只清置信度会留下一个隐蔽的错——RRF 名次仍然算进去，于是"纯向量检索"的排序里还混着 BM25 的意见，**消融实验测出来的就不是纯向量**。

**降级必须可见。**

`ApiEmbeddings` 调用失败**不在 provider 里兜底**。它只负责"要么给出向量，要么抛"；降级成纯词法检索是检索层的决定，而且必须留痕：

- 构造期建索引失败 → `logger.error` + 整条通道关掉（`retrieval.py:170`）；
- 单次查询向量失败 → `logger.warning`，**只影响这一次**，不关掉整个通道（`retrieval.py:319`）；
- 未配置模型 → `NullEmbeddings`，`build_embeddings()` 打一条 INFO 明说"检索退化为纯 BM25，同义不同字的口语症状会召不回来，这是配置结果而不是故障"；
- 任何一种情况，RAG 轨迹里的 `dense` 字段都是 `false`（`rag.py:179`）。

`NullEmbeddings.embed_documents()` 刻意**直接抛**而不返回零向量：零向量会安静地参与融合、贡献 0 分，看起来一切正常，只有召回质量偷偷退化。检索层应该先看 `provider.semantic` 再决定要不要调，真调到这里就是检索层的 bug，应该炸出来。

### 13.2.5 实体消解：检索之前，先定到"哪一台"

这是 012 迭代新加的一层，也是整个模块的入口闸门。**为什么必须在检索之前、而且必须能拒答？**

说明书检索有一个普通文档问答没有的性质：**查到错型号的说明书比查不到更危险。** "E4 是排水泵异常，请检查排水管是否弯折"读起来完全权威、格式专业、步骤具体——用户没有任何线索能判断这段话属于另一台空调。查不到只是没帮上忙，查错型号是拿着别人家的答案指挥用户拆机。

旧实现里型号是从问题里**猜**的：一张三条目的硬编码表，`if "空调" in query: return None, "SmartCool-AC2024"`。当时看不出问题，因为两台空调恰好同型号；一旦不同，"空调显示 E4"就会被安静地按客厅那台的说明书回答。

现在 `resolve_device()`（`src/knowledge/resolution.py:66`）把「用户措辞 → 设备实例 → 型号」做成显式的四态：

| 状态 | 含义 | 后续 |
|---|---|---|
| `resolved` | 唯一一台设备且登记了型号 | 进检索 |
| `ambiguous` | 条件对上多台（两台空调型号还不同） | 反问是哪一台 |
| `no_model` | 定位到设备但它没登记型号 | 说清"没有这份资料" |
| `unknown` | 连是哪台都没解析出来 | 反问 |

**后三种一律不进检索。** 子图的条件边 `after_identify`（`rag.py:146`）只在 `resolved` 时放行，图里不存在"兜底成全库搜"的分支。

型号从哪来？**`BaseDevice.model` 字段，设备注册中心是唯一数据源。** 知识模块里不放任何型号映射表——放第二份就要两处同步，漏改的那处不报错，只会让检索按旧型号查（和 011 收敛 `CAPABILITIES` 是同一个原则）。灯、窗帘不填 `model` 是合法的，表示"没登记说明书"，检索拒答而不是猜。

消解的候选顺序是 **显式设备名 > 类型关键词 > 可信上下文**（`resolution.py:112`）：

- **设备名匹配**（`:133`）：剥掉"的/那/台"虚词后做子串匹配，取最长命中——设备名里同时有"空调"和"客厅空调"时，"客厅空调坏了"取后者。
- **类型关键词匹配**（`:151`）：用 `capabilities.TYPE_KEYWORDS`。命中多类时按两条确定性语言习惯择一：**更长的关键词更具体**（"温湿度传感器"不该被"温度"拉走）、**出现更早的通常是句子主语**（"空调设置温度"里问的是空调不是温度传感器）。两条都平手才算真歧义。
- **可信上下文**：用户一个字没提设备（"这个 E3 是什么意思"，从某台设备的面板发起），才用 `active_device_id`；多候选时用 `active_room_id` 缩窄——**且只在缩窄后恰好剩一台时采纳**，剩零台说明用户问的不是本房间的设备，缩窄反而会把正确候选删光。

用户明确说了"卧室空调"，就不能被 App 当前所在房间覆盖掉；可信空间（`sync_context` 从 `RunnableConfig` 落定的 `active_room_id` / `active_device_id`）只用来消歧，不推翻显式点名。这复用的是第 3 章的可信身份边界：房间与设备来自请求上下文，**不是模型生成的**。

### 13.2.6 子图：六个节点，LLM 只出现在两个地方

`build_knowledge_rag_subgraph()`（`rag.py:105`）的签名——`registry` 是**必需**参数，`llm` 可传可不传，两档分数下限可配：

```python
build_knowledge_rag_subgraph(knowledge, registry, *, llm=None, top_k=3, max_rewrites=1,
                             min_score=DEFAULT_MIN_SCORE,
                             rewritten_min_score=DEFAULT_REWRITTEN_MIN_SCORE)
```

没有注册中心就没有型号，也就没有型号过滤——那正是这个子图最该防住的失败模式，所以 `registry` 不给默认值。`llm=None` 时整条链路仍然可用（重写走词表、作答走片段拼接），所以**测试不需要 API Key**。

```
identify ──(resolved)──► retrieve ──┬─(有命中)──────► self_check ──► answer ──► END
    │                               │
    └─(其余三态)──► refuse ──► END   ├─(无命中 & 无错误码 & 还没改写过)► rewrite ─┐
                                    │                                       │
                                    └─(其余)────────► refuse ──► END ◄────────┘
                                                （rewrite 回到 retrieve 再搜一次）
```

| 节点 | 位置 | 做什么 |
|---|---|---|
| `identify` | `rag.py:122` | 实体消解，四态写进状态 |
| `retrieve` | `rag.py:152` | 硬过滤 + 混合检索，三档分数下限过滤 |
| `rewrite` | `rag.py:197` | 口语症状 → 说明书用词（两层） |
| `self_check` | `rag.py:209` | 检查项分流：可自证的核掉，其余交人工 |
| `answer` | `rag.py:240` | 模型写建议 + 代码拼引用与核对块 |
| `refuse` | `rag.py:278` | 按失败原因输出拒答文案 |

**三档分数下限**卡的是 13.2.4 那个 [0,1] 的 `confidence`，不是 RRF（理由见 13.2.4：RRF 是纯名次的，拿它守门等于门不存在）。下限取决于查询处在哪种检索机制里（`rag.py:152-168`）：

1. **查询带错误码 → 下限 0。** 错误码硬过滤已经把不含该码的小节全部滤掉，活下来的必然就是讲这个码的那一节，相似度分数毫无意义——"空调显示 E4 是什么意思"里"是什么意思"永远匹配不上说明书，只会摊低分数。拿模糊阈值卡精确命中，会把对的答案判成"查不到"。
2. **原始口语 → 0.35**（`DEFAULT_MIN_SCORE`）。**这个数是扫参扫出来的，不是手调的**：向量权重取 0.5~1.0 的**任何**值，拒答准确率都在 0.30 → 0.35 这一步从 85.7% 跳到 100%。所以它不是拟合了某一条用例，而是一条稳定的分界。代价写在明处：Recall@1 从 89.3%（下限取 0.20）降到 87.5%。
3. **重写之后 → 0.42**（`DEFAULT_REWRITTEN_MIN_SCORE`）。不是"重写更可信"，恰恰相反：重写后的查询是**纯说明书用词**，真命中的分数明显更高（实测离线 0.60~0.82、混合 0.52~0.86），而"该型号根本没有这一章"的通用词误命中是 0.000（离线）/ 0.005（混合）。0.42 比首轮那档高 20%，又比最弱的真命中（混合下"排水 排水泵 冷凝水"命中「排水不畅」的 0.517）低 19%，两边都留余量。

**前两档 013 起移进了 `RAGConfig`**（`RAG_MIN_SCORE` / `RAG_REWRITTEN_MIN_SCORE`），因为它们是**按语料实测标定**的量，换语料或换 embedding 模型就要重标（`--sweep`），适合作为配置暴露。但**第三档"带错误码时为 0"刻意不可配置**——那不是一个可调参数，而是"精确键命中不该被模糊阈值否决"这条规则本身。`RAGConfig` 的默认值必须和 `rag.py` 的两个常量一致：两处不一致会让"测试跑的"和"生产跑的"是两套阈值，而测试全绿。

**带错误码的查询永不重写**（`after_retrieve`，`rag.py:185`）。错误码是精确键：语料里没有 E9，换任何说法也变不出 E9 来，重写只会把用户引到某个"看起来相关"的小节。

**重写分两层**（`_rewrite_query`，`rag.py:351`）：

- **有 LLM**：把**该型号说明书真实存在的小节标题清单**给模型，让它在里面挑一个，后面可以跟几个关键词——不是让它自由发挥。模型给的标题必须能在清单里对上（`rag.py:401`），否则视为无效、退回词表。这层校验是必要的：一个凭空编出来的小节名会让重写后的检索比重写前更差，而且失败得很安静。
- **无 LLM**：确定性症状词表 `_SYMPTOM_LEXICON`（`rag.py:76`）——`不凉|不制冷|制冷效果 → "制冷效果不佳 制冷 室温"`，诸如此类。

**013 之后这张词表的地位变了**：它不再是语义泛化的唯一手段，而是"没配 embedding 时"的确定性兜底。启用远程 embedding 后，"不凉" → 「制冷效果不佳」这一跳由向量通道直接完成（实测余弦 0.673），**根本走不到重写这一步**。词表留着有两个用处：离线可用，以及给 LLM 重写一个可校验的对照答案。

重写是**替换式**而不是追加式，但**理由换了**。012 给的理由是"分数分母是查询词总数，留着原话会稀释分数"——换成 BM25 之后这个理由**不再成立**：BM25 对查询词求和，匹配不上的词贡献 0，不存在稀释。现在的理由是：重写后的查询要和 `rewritten_min_score` 那一档阈值配套，而那一档是按"纯说明书用词"的分数分布标定的，**追加式会让分数落在两档之间，阈值就没有稳定含义了**。（一个旧理由失效时把它替换掉、而不是留着继续引用，是这份文档能被信任的前提。）

### 13.2.7 自证核对：把文档问答做成可执行诊断

这是这一章的高潮。`self_check` 节点（`rag.py:209`）把排名第一的小节的清单分成两摞：

- **可自证的**（`<!--check:xxx-->`）：调 `run_self_check()`（`src/knowledge/selfcheck.py:396`）真的去核对；
- **需人工的**（`<!--manual-->`）：原样交回用户，附说明书出处。

核对读的是**注册中心的真实设备状态**，不问模型——和 Planner 路径的 `verifier` 是同一个原则：模型会把"设定了 26 度"复述成"温度设置正常"，只有实测值能反驳它。

判定结果是**三值**而不是布尔（`selfcheck.py:39`）：`problem` / `ok` / `unknown`。`unknown` 是必需的第三态——"这个房间没有温湿度传感器所以读不到室温"跟"室温确实高于设定温度"是两件事，前者必须退回给人确认，后者才是定位到了根因。把读不到当成"核对通过"是最危险的做法。

检查函数能看到的全部世界是一个 `CheckContext`（`selfcheck.py:42`）：这台设备、本房间的温湿度读数、读数来自哪台传感器。**刻意不传 `registry`**——检查函数不该有能力遍历全屋设备，更不该调 `registry.tick_environment()`（环境推演只允许 `read_sensor` 触发，别处调用会让同一轮对话里的室温随调用次数漂移，诊断结论再也复现不了）。`self_check` 组装 `CheckContext` 时用的是 `get()` / `get_by_type()` 稳定快照读（`rag.py:417`）。

**013 把检查项从 3 条扩到 12 条**，声明在 `SELF_CHECKS`（`selfcheck.py:327`）。这不只是"多了几条"——012 时代那 3 条**全是空调的**，所以"可执行诊断"实际只对一种设备成立，其余设备的排查清单全部落到人工。现在覆盖到了每一种设备类型：

| 检查 id | 设备 | 读的是什么 |
|---|---|---|
| `device_is_on` | 通用 | 电源状态 |
| `ac_mode_is_cool` / `ac_target_temp_below_room` / `ac_fan_speed_not_lowest` | 空调 | 运行模式 / 设定温度 vs 实测室温 / 风速档位 |
| `light_brightness_not_zero` | 灯 | 亮度是否被调到 0 |
| `curtain_not_fully_closed` | 窗帘 | 开合度 |
| `tv_is_not_muted` | 电视 | 静音状态 |
| `humidifier_tank_has_water` / `humidifier_target_above_room` | 加湿器 | 水箱 / 目标湿度 vs 实测湿度 |
| `water_heater_target_is_high_enough` | 热水器 | 设定水温 |
| `kettle_target_is_boiling` | 电水壶 | 目标温度是否到沸点 |
| `device_battery_not_low` | 传感器 / 门锁 | 电量 |

新增的每一条都遵守同一条纪律：**挂错设备类型必须返回 `unknown`，绝不能假通过。** `_unsupported()`（`selfcheck.py:84`）负责这件事，`tests/test_knowledge_rag.py` 的 `NewDeviceSelfCheckTests` 逐条钉住它——因为"某检查项在一台不该核对的设备上安静地返回 ok"是这套机制唯一能造成实质伤害的失败方式。

语料与代码之间的引用关系现在是**双向校验**的：

- **正向**（012 就有）：语料引用了未声明的 id → `KnowledgeBase` 构造抛 `ValueError`（13.2.2）。
- **反向**（013 新增）：`SELF_CHECKS` 里声明了 id 但**没有任何语料引用它** → 测试失败（`CorpusConsistencyTests`）。012 时代这个方向是空的，一条声明了却没人用的检查项会静默成为死代码：写了、测了、永远不会被触发。**现在 12 条全部被语料引用过。**

### 13.2.8 答案：模型组织语言，代码陈述事实

`answer` 节点（`rag.py:240`）的输出由四块拼成：

```
<模型写的处理建议>                 ← LLM 综合或片段拼接
自动核对结果（已读取设备真实状态）：   ← 代码渲染，不经模型
需你确认（系统读不到，得人到现场）：   ← 代码渲染，说明书原文逐字
来源：                             ← 代码拼接
```

prompt 里明确要求模型**不要罗列检查清单、不要复述核对结果、不要写来源**——那两块由系统另行附上。这样"引用"是**结构保证而不是提示词请求**：模型无论怎么发挥，来源块都在，且指向真实被检索到的小节。模型只拿到"片段 + 已核对出的异常"，写一段不超过四句的处理建议。

`llm=None` 或调用抛异常时退回片段原文拼接（`_synthesize`，`rag.py:470`）——信息量下降，但引用与核对结论一个不少。注意 `except Exception` 前面显式重抛了 `GraphInterrupt`：人工审批靠抛它实现，无条件吞掉等于用户还没回答就重跑节点（第 6 章和 `middleware/interceptors.py` 早已记下这个坑）。

### 13.2.9 主图怎么接进来

`build_graph` 在构造期建好知识库和子图（`src/agent/graph.py:210`），路由条件在 `task_router`（`graph.py:362-366`）——三个条件必须同时成立：**不走 Planner**、`intent.intent == "device_knowledge"`、`rag_config.enabled` 为真。

构造期还有一件 013 新增的事：**embedding provider 在这里被选定并注入**。`build_embeddings()` 按 `RAG_EMBEDDING_MODEL_ID` / 地址 / Key 是否齐全决定给 `ApiEmbeddings` 还是 `NullEmbeddings`，两种都打 INFO 日志。地址与 Key 留空时回落到 LLM 的那一份——多数部署里 embedding 和对话模型在同一个 OpenAI 兼容端点上，不该逼用户填两遍。

`knowledge_rag_node`（`graph.py:669`）是薄薄一层适配：调子图，把结果写回主状态的四个字段（`src/agent/state.py`：`rag_status` / `rag_citations` / `rag_trajectory` / `rag_device_model`），然后直连 `END`。注意它把 `active_room_id` / `active_device_id` 一起传进子图——用户只说"空调显示 E4"时要靠它们消歧，而这两个值来自可信上下文，不是模型生成的。

**这条路径不经过 `agent` 节点，也就不碰任何设备控制工具。** 问"E3 是什么意思"绝不会顺手把空调关了。`tests/test_phase_twelve.py` 用一个"传消息列表就抛 `AssertionError`"的假 LLM 钉死了这一点（假 LLM 允许被 RAG 综合以纯字符串 prompt 调用，两者靠入参类型区分）。

`device_knowledge` 意图从哪来？两条路：LLM 结构化路由（`src/agent/routing.py`），或关键词兜底（`heuristics.py:83`）。兜底的词表只有 7 个：`故障 / 错误代码 / 说明书 / 怎么清洗 / 怎么维护 / 支持什么 / 是什么意思`。

## 13.3 关键设计决策

### 决策一：Agentic 到哪一档

"Agentic RAG" 和"一次性检索"的区别，落在三个问题上：

| 问题 | 一次性检索（naive RAG） | Agentic RAG | 本项目 |
|---|---|---|---|
| 要不要检索？ | 每次都检索 | Agent 自己判断 | **路由器判断**（`intent == device_knowledge`） |
| 检索几次？ | 恰好一次 | 不够就再来 | **最多两次**（`max_rewrites=1`） |
| 检索到的够不够？ | 不判断，全塞给模型 | Agent 评估相关性 | **三档分数下限**（错误码 0 / 首轮 0.35 / 重写后 0.42） |
| 检索词不合适怎么办？ | 没有这个概念 | 改写重试 | **两层改写**（LLM 挑小节标题 / 症状词表） |

三个判断里，"要不要检索"是确定性规则，"够不够"和"怎么改"在有 LLM 时交给模型（但改写结果必须对上真实存在的小节标题）、没有 LLM 时退回词表。骨架是 `after_retrieve`（`rag.py:185`）这个条件边——`rewrite → retrieve` 这条回边让图里出现了**环**，这就是"Agentic"在拓扑上的样子。

### 决策二：012 说"这不是向量检索"，013 上了向量——那当初的判断错了吗？

这一节在 012 版的教程里叫「这仍然不是向量检索（请读完这一节）」，写着：

> **`src/knowledge/` 里没有 embedding，没有向量数据库，没有余弦相似度。** 全部检索能力就是"bigram 集合求交集除以问题词数"。依赖只有标准库的 `re` 和 `json`。

013 之后这段话**每一个分句都不成立了**。但正确的读法**不是**"之前说的都不对"——那样你只学到"结论会变"，学不到任何可迁移的东西。正确的读法是：**当初列的代价清单是对的，现在逐条对账，看每一笔到底付了没有。**

先复述当初判断的两个前提，它们仍然成立：

1. **领域词固定。** 错误码、型号、滤网这些词在文档里一字不差地存在，词法命中就是精确命中——"E4"的向量邻居可能是"E5"，词法匹配不会。这一条不但没过时，013 把它升级成了**硬过滤在两个通道之前**（13.2.4）。
2. **可解释 + 确定性对测试至关重要。** 这一条决定了 013 的整个架构形态：provider 是**注入**的，不是模块级单例。

**只有一个前提被规模推翻了**："库很小，5 份文档 12 个 chunk，遍历是精确的"。语料扩到 39 份 124 chunk 之后，"遍历"还是精确的，但**遍历的对象错了**——精确遍历一堆对不上的词，得到的是精确的零分。口语类查询在纯词法通道上的 Recall@1 是 **3/30**。这不是规模问题，是**语义鸿沟**问题，规模只是让它无处躲藏。

**逐条对账：当初列的代价，013 付了哪些。**

| 当初列的代价 | 013 的实际结果 |
|---|---|
| embedding 模型（API 或本地 `sentence-transformers`）：API 每次检索一次网络调用 + 费用；本地几百 MB 模型 + torch 依赖 | **部分规避。** 走 API 不走本地（不引入 torch）；向量按 `sha256(文本)` **落盘缓存**（`data/embeddings/<模型名>.json`），改一个字的说明书只重算那一节，不是每次检索都联网。查询侧同样缓存，重复问句零调用 |
| 向量库（Chroma / FAISS / pgvector）：新增持久化组件，索引要跟文档同步更新 | **规避了。** 124 个 chunk 用一个 numpy 矩阵装得下，`self._matrix @ query`一次矩阵乘法就是全库检索。**这个规模不需要向量库**，装一个反而多一处要同步的持久化状态 |
| 切块策略调优：chunk 太大噪声多，太小丢上下文 | **没花代价。** 切块沿用 012 的"按 `## ` 二级标题"，一节就是一个 chunk。说明书天然按症状/错误码分节，**语料结构本身就是切块策略**——这是选 Markdown 而不是 PDF 的红利 |
| 相似度阈值重新标定：余弦的 0.7 和词法的 0.15 完全不是一回事 | **付了，而且比预想的重。** 不只是"换个数字"：得先把余弦从模型自己的区间拉回 [0,1]（减基线 0.42、除强命中刻度 0.70），再把 BM25 从无上界压成饱和分，才谈得上"阈值"。这一整套标定就是 13.2.4 那一节的内容，也是 `evals/` 存在的直接原因 |
| **确定性丢失**：换个 embedding 版本，测试断言可能全变。这是最贵的一项 | **这一笔真实发生了，只是被切成了两半。** 见下 |

**那笔"最贵的代价"，实际付了一半。**

**测试侧规避了。** `tests/test_knowledge_rag.py` 的向量通道用一个 `StubEmbeddings`：按主题词返回**设计好的单位向量**。它不是在模拟语义，而是**构造出想验证的局面**——"BM25 给 0 分但语义命中"、"名次第一但置信度不够格"、"语义通道缺席"这些局面，靠真模型反而不可控。所以测试**仍然不需要 API Key，仍然逐位确定**。

**离线可用性也规避了。** `NullEmbeddings` 让"没配 embedding"成为一条一等公民路径：检索退化为纯 BM25，`Recall@1` 还有 58.9%，而且这件事写在 INFO 日志和 RAG 轨迹的 `dense: false` 里，不是静默退化。

**但生产侧确实付了：**

- 生产检索**依赖一个外部 embedding 服务**。它挂了就只剩词法通道——不是崩，但召回质量掉一个档，这是新引入的运行时依赖。
- **换 embedding 模型必须重测余弦刻度。** `_V4_BASELINE_SIMILARITY = 0.42` / `_V4_STRONG_SIMILARITY = 0.70` 是在 `text-embedding-v4` 上实测的，**换模型直接沿用会让阈值失去含义**。这就是当初那句"换个 embedding 版本，测试断言可能全变"的真实形态：断言没变（Stub 顶住了），**但生产的判定标准变了，而且不会报错**。所以两个刻度挂在 provider 上而不是写死在检索层——换模型时你至少会看到自己在改哪个对象。
- 新增三个依赖：`rank-bm25`、`jieba`、`numpy`（numpy 以前是传递依赖，013 顺手把它显式写进 `pyproject.toml`——传递依赖哪天被上游去掉就变成运行期 ImportError）。

**还有一笔当初没预见到的代价：一个"看起来免费"的第二通道是陷阱。** 013 最初想留 `HashingEmbeddings`（词特征哈希当向量）做离线兜底，好处是离线、确定、让混合检索永远双通道。**实测把它否决了**：

```
查询「客厅空调开着但一点都不凉」（正确答案是「制冷效果不佳」）
  哈希向量给**错误的**「噪音异常」余弦 0.243，排第一
  BM25       给「噪音异常」0 分
六组"口语 → 说明书书面语"的相关对，哈希向量有四组余弦恰好 0.000
```

根因：**它没有 IDF，按"共享了几个常见词"排序。** 那个 0.243 就是靠一个「空调」凑出来的。而 IDF 压制通用词恰恰是 BM25 已经做好的事——**把这条通道放回来等于从旁路重新引入 BM25 刚干掉的噪声，而且绕过了 IDF，BM25 那边的修正管不到它。** 它还破坏阈值标定：真命中与噪声命中的 `confidence` 一度只差 0.007（0.129 vs 0.122），三档下限没有任何可用落点。

结论：**双通道要靠真模型换来，不能靠一个假的第二通道凑出来。** 宁可诚实退化成单通道**并且说出来**（`NullEmbeddings` + INFO 日志 + 轨迹里的 `dense: false`）。

**当初那句加粗警告，现在交代。** 原文末尾写着：

> **但不要为了上向量库把拒答纪律弄丢。**

**交代：拒答准确率全程 7/7，四种配置一个不漏。** 而且实测给了一个当初写这句话时想不到的答案——**拒答闸门的可靠性恰恰来自被保留下来的那条 BM25 通道，不是来自阈值调得准**（详见决策三）。这句警告不但没有被打破，它反而变成了"不能为了召回率把 `bm25_weight` 清零"的技术理由。

保住它靠的是两条结构性安排，都在 13.2.4：**RRF 只定名次、`confidence` 只定放行**（拿 RRF 守门会让拒答分支永远走不到）；**硬过滤在两个通道之前**（否则 E4 的语义近邻 E7 会被当成答案递出去，而且读起来完全通顺）。

### 决策三：为什么选混合，而不是数字更好的纯向量

这一节要诚实写一个**对我们不利**的结果。

四种配置的评测（63 条 golden 用例，详见决策五）里，**纯向量的 Recall@3 和 MRR 比混合更好**：

```
仅向量    Recall@1 87.5%   Recall@3 94.6%   MRR 0.908   口语 24/30   literal  9/10
混合      Recall@1 87.5%   Recall@3 89.3%   MRR 0.881   口语 23/30   literal 10/10
```

生产配置仍然选混合（`bm25_weight=0.5` / `dense_weight=0.5`），三条理由，最后一条最重要：

**一、`bm25_weight=0` 会让词法通道完全关闭，embedding 一挂就全部拒答。** 权重为 0 意味着这个通道**名次和置信度都不参与**（13.2.4 里那条"权重为 0 就完全不参与"的纪律）。于是纯向量配置下语义通道是唯一通道：它不可用时 `_dense_scores()` 返回全零且 `dense_live=False`，两个通道都拿不到名次，`score()` 把每个候选都跳过——候选集为空、`hit_count` 为 0、**每条查询都走 `refuse`**。混合配置下 BM25 还兜着：离线 Recall@1 58.9%，答得不如双通道好，但**答得出来**。用 2.7pp 的 MRR 换一条"外部服务挂了还能工作"的路径，这笔账很清楚。

**二、`literal` 类上 BM25 更强**（10/10 vs 9/10）。用户直接用说明书原词提问（"排水泵异常怎么处理"）时，词法匹配就是精确匹配，而向量会把它和语义邻近的小节混起来。这类查询在真实使用里占比不低——用户看过一次说明书之后就会这么问。

**三、"这份说明书没讲这件事"只有词法通道说得出来。** 这条是实测逼出来的，也是整章最反直觉的发现。

拒答用例里最高的假阳性是 **0.336**（"卧室空调有点响"命中 FrostLine 的「制冷效果不佳」），离 0.35 的下限只有 **4% 余量**。为什么这么薄？在 63 条用例上统计 `text-embedding-v4` 的余弦分布，答案很清楚：

| | n | min | p05 | 中位 | max |
|---|---|---|---|---|---|
| 正例 | 61 | 0.403 | 0.511 | **0.653** | 0.864 |
| 困难负例（同型号的**其它**症状小节） | 74 | 0.302 | 0.425 | **0.568** | 0.734 |
| 容易负例 | 398 | 0.263 | 0.350 | 0.488 | 0.706 |

**正例与困难负例大幅重叠，中位只差 0.085。** 把基线从 0.42 提到 0.55 也只挡掉 35% 的困难负例，同时丢掉 15% 的正例。

所以要说得很直白：**向量通道靠绝对余弦无法区分「对的症状小节」和「同一台电器的另一个症状小节」**——它们在语义上真的很近，模型没有说错，是这个任务要求的分辨率超出了绝对余弦能给的。

那"卧室空调有点响"为什么最终被正确拒答了？因为**词法通道返回 0**："响""噪音"这两个词在 FrostLine 全文根本不存在（那份症状手册只有制冷效果不佳 / 排水不畅 / 蒸发器结霜，13.2.2 那处刻意的语料缺口）。BM25 没有名次、没有强度，向量那 0.568 的相关性只能自己撑，撑不过 0.35。

**这道闸门的可靠性来自 BM25，不是来自阈值调得准。** 把词法通道去掉，换来的 2.7pp MRR 会拿"偶尔权威地答错型号里的另一个故障"来付账——而这正是这一章从第一页起就在防的事。

### 决策四：拒答纪律——查不到就说不知道

落实在**五道锁**上，一道比一道靠前：

**锁一：消解不出唯一设备，就不检索。** `after_identify`（`rag.py:146`）只在 `resolved` 时放行。两台空调型号不同，只说"空调"就反问是哪一台；解析到没登记型号的设备就说清"没有这份资料"。四种拒答各说各的原因，但都带同一句"我不能可靠确认"。

**锁二：错误码必须精确匹配**（`base.py:152` 的硬过滤二）。问 E9 时 E3 的文档被直接跳过，宁可无话可说，也不拿邻居的答案凑数。带错误码的查询还**永不重写**——重写只会把精确键引到"看起来相关"的小节。**加了向量通道之后这道锁更关键**：E4 的语义近邻就是 E5、E7，硬过滤是唯一挡住它们的东西。

**锁三：低分命中不算命中**，且下限分三档（13.2.6），卡的是绝对 `confidence` 而不是 RRF 名次（13.2.4）。"沾了点边"不等于"能支持答案"。

**锁四：`answer` 的输出结构由代码决定。** 模型只写建议正文；来源块、核对块、"需你确认"块都是代码拼的。没有检索命中，`answer` 压根不会被执行——条件边会把流程送去 `refuse`。模型没有机会在"无中生有"这件事上发挥，因为**它碰不到引用和结论**。

**锁五：拒答文案本身是设计过的**（`rag.py:326` 起）。三个成分：说清原因、明确表态（"我不能可靠确认"）、**给出下一步**。不是干巴巴一句"我不知道"，用户知道该怎么帮它。

**为什么家居场景对拒答格外苛刻？** 因为这里的错误答案会变成**物理动作**。聊天机器人编错一个历史年份，用户笑一下就过去了。编一句"滤芯 3 个月换一次"，用户会真的照做——然后在第 11 周开始吸霉菌。

顺便看一眼真实语料里那段"安全提醒"（`docs/knowledge/smartcool-ac2024-errors.md`）：

> 涉及拆机、带电测量或制冷剂回路的维修必须由专业人员完成。智能体只能提供说明书中的排查建议，**不能确认硬件已经修复**。

**连边界声明本身都是被检索的语料。** 这比写在系统提示词里更可靠——提示词会被后面几十轮对话稀释，检索出来的原文永远在最新一条消息里。

### 决策五：评测（evaluation）——不看答案像不像，看路径走没走对

先解释为什么 Agent 项目必须有评测。

传统软件的测试是"给定输入，断言输出等于期望值"。Agent 不行，因为**核心组件是非确定性的**：同一句"帮我把家里弄舒服点"，模型这次调 `control_ac`，下次可能调 `activate_scene`，两次都算合理。你没法 `assertEqual` 一段自然语言。

于是很多人退化成"人工看一眼回答像不像人话"。这是错的方向。**Agent 的质量不在最终那段文字里，在它走过的路径里。** 一个把答案编得天花乱坠但从没检索过的 Agent，和一个老老实实检索后拒答的 Agent，前者的"回答质量"评分可能更高——而它才是要出事的那个。

**轨迹评测（trajectory evaluation）就是把评测对象从"输出"换成"过程"**：它有没有检索？改写了几次？引用的来源对不对？该拒答的时候拒答了吗？

`src/evaluation/trajectory.py` 全文只有一个纯函数 `evaluate_rag_trajectory()`，吃一个状态 dict 加期望值，吐七个指标：

| 指标 | 含义 |
|---|---|
| `route_accuracy` | 意图是否被判成 `device_knowledge`（**路由错了后面全白搭**） |
| `status_accuracy` | 该答的答了 / 该拒的拒了 |
| `source_accuracy` | 引用里是否包含期望的源文件 |
| `has_retrieval` | 轨迹里真的有 `retrieve` 这一步 |
| `rewrite_count` | 改写了几次（衡量检索效率） |
| `citation_count` | 引用条数 |
| `refusal_correct` | 拒答时**必须没有引用**（拒答又给来源是自相矛盾） |

`has_retrieval` 特别值得注意：它不问答案对不对，只问**"你到底查过没有"**。这正是"过程指标"的典型样子。012 之后轨迹里多了 `self_check` 一步（带 auto / manual / problems 三个计数），评测函数不用改——它只认 `retrieve` 和 `rewrite` 两个步骤名，其余节点可自由演化。

**013 补上了另一半：一份真的数据集。**

轨迹评测回答"路径走对了吗"，但它回答不了"**召回率是多少**"。012 版这一章在坑四里承认：全仓库 `.jsonl` / `.yaml` / `.csv` 数据集数量为 0，"混合检索比词法检索好"这句话**没有任何数字**。

013 补上了：

- **`evals/knowledge_recall.json`** —— 63 条 golden 用例。每条是 `{query, model, expected: [source#section], kind, note}`，`note` 写清这条为什么值得测（例：`"口语「不凉」对说明书书面语「制冷效果不佳」，词法零重叠"`）。按 kind 分：**colloquial 30 / literal 10 / code 10 / cross-model 6 / refusal 7**。
- **`src/evaluation/recall.py`** —— runner，一次跑四种配置做消融。

两个刻意的取舍：

**只测首轮检索，不跑查询重写。** 因为它要回答的问题就是"**语义通道能不能替掉那张人工维护的症状词表**"。把重写也跑上，等于让词表替检索背书，测不出通道本身的能力。

**`legacy` 配置是 012 算法冻结在本文件里的一份独立副本**，不是从 git 历史里翻。基线必须能和新实现在**同一次运行**里跑同一份数据，否则"提升了多少"这个数字没法复现。

```bash
python -m src.evaluation.recall            # 四种配置全跑
python -m src.evaluation.recall --offline  # 跳过需要 API 的 dense / hybrid
python -m src.evaluation.recall --sweep    # 在权重 × 下限的网格上重新标定
```

|---|---|---|---|---|---|---|

| `bm25`（仅词法通道） | 58.9% | 62.5% | 0.604 | 7/7 | 7/30 | 10/10 |

四行读出四件事：

1. **口语类 3/30 → 23/30。** 这是整个 013 的主要收益，也正是 012 挂在"已知边界"里的那笔债。
2. **Recall@1 +35.7pp**（51.8% → 87.5%）。
3. **"把覆盖率换成 BM25"单独值 +7.1pp**（legacy → bm25），口语类 3 → 7。也就是说**光换打分函数远远不够**，语义鸿沟得靠语义通道跨。
4. **拒答准确率全程 7/7**，四种配置一个不漏——包括最弱的 legacy。这说明拒答纪律是**结构**保证的（硬过滤 + 绝对分数守门），不是靠某一版检索算法碰巧做到的。

局限也要写清：这份数据集**只测首轮检索**，不测端到端、不测真实 LLM 的综合与重写，也不测路由准确率（`ROUTING_KNOWLEDGE_WORDS` 那 7 个词的漏见坑一）。它把"RAG 召回质量"这一格填上了，另外三格（路由准确率、Planner 计划质量、端到端任务成功率）仍然是空的。

## 13.5 踩坑与局限

### 坑一：加一篇文档是三个声明点

**这一点 `CLAUDE.md` 已经覆盖（"说明书 RAG 的三个声明点"），这里讲为什么。** 实际要动 3 处，缺一处都会在构造期或测试里失败：

1. **写 md 文件**放进 `docs/knowledge/` 并在 `catalog.json` 登记。**必须用 `## ` 分节**——`_split_markdown()` 只认二级标题。排查清单条目末尾挂 `<!--check:xxx-->` / `<!--manual-->`；引用未声明的 id，`KnowledgeBase` 构造直接炸。
2. **`capabilities.py` 的默认实例给设备填 `model`**。型号唯一数据源是 `BaseDevice.model`，知识模块里没有第二份映射表（旧的 `DEVICE_PROFILES` 已删）。
3. **新声明自证检查项**才需要动 `selfcheck.py` 的 `SELF_CHECKS`——语料引用了不存在的 id 会在构造期炸；013 起**反向也有校验**了：声明了却没有任何语料引用它，测试会失败（见坑六）。

还有第 4 处不属于声明、属于检查：**提问方式是否能命中路由**。`ROUTING_KNOWLEDGE_WORDS`（`heuristics.py:83`）只有 7 个词。实测 `classify_intent_fallback('空调滤芯多久换一次')` 返回 `general_chat`，压根走不到 RAG。开了 LLM 路由能救回一部分，但兜底路径上这是真实的漏。

### 坑二：知识库在构造期一次性加载

`KnowledgeBase.__init__` 直接调 `self._load()`，而 `build_graph` 在构造期建它。**所以改了 md 文件必须重启进程**，没有热重载。开发时改一句文档跑一次实验，很容易被上一次的缓存骗到——注意每次实验都是新进程就不会中招。

013 起构造期多做了一件事：**建向量索引**（`_build_dense_index()`）。这一步会对全部 124 个 chunk 算向量，所以第一次启动会有一次批量 embedding 调用。之后靠 `data/embeddings/<模型名>.json` 的内容哈希缓存兜住——**改一节说明书只重算那一节**，没改的从缓存读。缓存键是 `sha256(文本)`、文件按模型名分开存，所以换模型不会读到上一版模型算出来的向量（那种串味不会报错，只会让相似度整体失真）；维度对不上就整份丢掉重算，因为拼接不同维度的向量会在矩阵乘法处炸得莫名其妙。

### 坑三：阈值已经进 `RAGConfig` 了 —— 但换语料必须重标

**012 版这里写的是"三档阈值仍是模块常量，不在 `RAGConfig` 里"，013 修了**：前两档变成 `RAG_MIN_SCORE` / `RAG_REWRITTEN_MIN_SCORE`（`src/config.py:121`）。

当初不放进配置的理由是"放进配置文件会暗示这是个可以随手调的旋钮，而它不是"。013 之所以改主意，是因为**这个理由的前半句仍然成立，但结论变了**：这两个数确实不能随手调，可现在有 `--sweep` 了——**"必须实测标定"和"必须硬编码"是两件事**，前者要的是一份标定实验，不是把数字藏进代码。第三档"带错误码时为 0"**仍然不可配置**，因为它压根不是参数，是"精确键命中不该被模糊阈值否决"这条规则本身。

真正剩下的坑换了形状：**这些数依赖语料，换语料必须重标，而漏了重标不会报错。**

需要重标的量有三组，越往下越隐蔽：

1. **两档 confidence 下限**（0.35 / 0.42）——语料一变，分数分布就变。
2. **BM25 噪声基线 3.5**（`retrieval.py:72`）——BM25 分由 IDF 和平均文档长度决定，**两者都是语料级统计量**。踩过一次：拿三个 chunk 的合成语料写测试，所有 BM25 分数都远低于 3.5，什么都进不了名次——测出来的是"基线没标定"而不是被测的机制。
3. **余弦的两个刻度**（0.42 / 0.70，`embeddings.py:66`）——**换 embedding 模型必须重测**，这一组挂在 provider 上就是为了让你换模型时看见它。

三组都没有"忘了改就报错"的机制。目前的缓解只是把它们写在有实测依据的注释里，并让 `--sweep` 成为一条能跑的命令。

### 坑四：有了召回评测集 —— 但它只覆盖四个维度里的一个

**012 版这里写的是"没有评测回归集，这是本项目学习价值最高的缺口"，013 补了一部分**：`evals/knowledge_recall.json`（63 条）+ `src/evaluation/recall.py`（详见决策五）。

补上的那一格：**RAG 召回质量**。现在"混合检索比词法检索好"这句话背后有数字了，而且是四种配置的消融对比，改一个常量就能看到召回怎么动。

**仍然空着的三格**：路由准确率、Planner 计划质量、端到端任务成功率。而且已有的这一格自身也有明确边界：

- **只测首轮检索**，刻意不跑重写（决策五解释了为什么），所以它测的是"检索通道的能力"，不是"这条链路最终答对没有"。
- **不测端到端**：从 `graph.invoke()` 到最终答案的那一段没有覆盖。`src/evaluation/trajectory.py` 的唯一调用点仍然是 `tests/test_phase_twelve.py` 里的**手写字面量 dict**，不是真实图输出（实验四那段脚本才是"应该怎么用"的样子）。
- **不测真实 LLM**：所有测试仍然用 FakeLLM / `llm=None` / `StubEmbeddings`。**真实模型行为一项都没在衡量。** 唯一打真实端点的是 `recall.py` 的 `dense` / `hybrid` 两档，而它调的是 embedding，不是对话模型。
- **没有 CI**，跑不跑靠人记得。

**为什么这仍算"学科级"缺口？** 因为 Agent 工程和传统软件最本质的区别就是被测系统非确定性。现有测试钉住的是**机制正确性**（权限边界、数据库状态、设备副作用、事件顺序），这部分做得相当好。但**一行 prompt 改动让意图分类准确率从 92% 掉到 71%，当前测试全绿，没有任何信号。**

**读者可以自己动手补的方向**：照 `evals/knowledge_recall.json` 的形状再写一份 `evals/routing.json`（`query → 期望意图`），拿 `classify_intent_fallback` 跑一遍——不需要 API Key，而且你大概会得到一个比预期低不少的数字（坑一那 7 个关键词的漏就藏在里面）。

### 坑五：`self_check` 只核对排名第一的小节

第二三名是"也沾点关系"的小节，把它们的清单一起核对会让答案里冒出一堆和当前症状无关的核对结论。这个取舍目前是对的，但意味着**多症状叠加的提问**（"又响又不凉"）只会核对其中一个症状的清单。修法是把"命中多个带清单的小节"识别出来、分别核对或反问——目前没做。

### 坑六：语料↔代码现在是双向校验了

**012 版这里写的是"自证检查项只有 3 条，且语料↔代码只有单向校验"，013 两头都修了。**

检查项 3 → 12，覆盖全部设备类型（13.2.7）。校验方向从一条变成两条：

| 方向 | 机制 | 失败形态 |
|---|---|---|
| 语料引用的 id 必须存在 | `_validate_check_ids()`，构造期 | `ValueError`，进程起不来 |
| 每条已声明的 id 必须被语料引用 | `CorpusConsistencyTests`，测试期 | 测试失败 |

第二条修的是一个具体的静默失败：`SELF_CHECKS` 里声明了 id、语料却从没引用它——**写了、测了、永远不会被触发**，功能上等于不存在，而没有任何信号。同一组生成式断言还顺手把三件事一起钉住了：设备 `model` ↔ catalog `model` 双向一致、catalog `title` 与 Markdown H1 逐字相等、行内标注不泄漏进检索文本。这是 011 对 `CAPABILITIES` 那套做法的直接搬用。

**两个方向为什么用不同的机制？** 因为它们的严重程度不同。语料引用了不存在的 id 是**会让用户少收到一条诊断结论**的实质错误，必须构造期就死；声明了没人用只是死代码，让测试红就够了——为它拒绝启动会让"先写检查函数、再写语料"这个自然顺序走不通。

### 新增局限一：绝对置信度分不开"对的症状"和"同一电器的另一个症状"

这是 013 最重要的一个已知薄弱点，决策三给了完整数据：**正例余弦中位 0.653，困难负例（同型号的其它症状小节）中位 0.568，大幅重叠。** 拒答用例里最高的假阳性是 0.336，离 0.35 的下限只有 4% 余量。

**提高阈值不解决问题**：提到 0.55 只挡掉 35% 困难负例，同时丢掉 15% 正例。现在挡住它的是**词法通道返回 0**这个额外信号，不是阈值本身。

下一步该做的是 **top1-vs-top2 的差距门**：不只看第一名够不够高，还要看它比第二名高多少。"制冷效果不佳 0.65 / 噪音异常 0.64"和"制冷效果不佳 0.65 / 噪音异常 0.30"是完全不同的两种局面——前者说明模型其实没分开，后者才是确凿命中。**绝对分数看不见这个差别，因为它一次只看一个候选。** 013 没做，因为标定一个差距门需要在 golden 集上重新统计"正确答案与第一个错误答案的间隔"分布，而这份统计目前还没有。

### 新增局限二：BM25 噪声基线依赖语料规模

`_BM25_NOISE_FLOOR = 3.5` 是在 124 个 chunk 的语料上标的。IDF 和平均文档长度都是**语料级统计量**，语料一换这个数就失去含义，而且**失效方式很难认**：基线偏高 → 词法通道整体沉默，表现是"混合检索怎么跟纯向量一样"；基线偏低 → 噪声重新获得投票权，表现是"偶尔莫名排第一"。两种都不报错。

换语料后必须 `python -m src.evaluation.recall --sweep` 重标。这条和坑三是同一类问题的两个实例：**实测标定出来的常量，在语料变化时没有任何自动失效机制。**

**这一章的局限**：语义泛化现在有了，但生产依赖一个外部 embedding 服务，换模型必须重测余弦刻度；绝对置信度分不开同一电器的两个症状小节（新增局限一）；BM25 噪声基线随语料失效（新增局限二）；自证检查 12 条覆盖到了每种设备，但每种设备只有一两条，深度检查（"滤网是不是真的堵了"）仍然只能交人工；同房间传感器配对靠 `location` 字面量相等，沿用模拟器约定，接真实后端要换；评测只覆盖首轮检索，端到端与真实 LLM 行为仍然没有测量（坑四）。

上一版这里写着"结构都给好了，照着换成向量检索就行，**换的时候别把拒答纪律弄丢**"。013 照着换了，拒答准确率 7/7 一分没掉——而且实测发现，**守住这条纪律靠的不是阈值调得准，是那条没被丢掉的词法通道**（决策三）。完整的标定数据与被否决的方案记在 `docs/iterations/013-hybrid-retrieval.md`。

**下一章的问题**：到现在为止，所有能力都要用户开口才发生。可是"明天早上 6 点半，起床前先把卧室空调打开"——这件事发生时用户在睡觉，没人能开口。怎么让 Agent 在**没有对话**的时候干活，而且这个约定还得活过进程重启？
