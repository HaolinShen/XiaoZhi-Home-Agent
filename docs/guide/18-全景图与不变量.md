# 第 18 章 全景图与不变量

前面十七章是一条一条讲的。这一章把它们拼回一张图，然后回答一个更实用的问题：

**如果你要改这个项目，哪些东西是不能碰的？**

不是"最好别碰"，是"碰了就会坏，而且坏得不明显"。这类约束有个名字：**不变量（invariant）**
—— 系统在任何时刻都必须成立的性质。它们大多不是某个函数的实现细节，而是**散落在多个文件里、
靠协同维持的约定**。这也正是它们危险的地方：你在 A 文件里做了个看起来无害的改动，
症状在 B 文件里冒出来，而且往往是"行为变怪"而不是"抛异常"。

## 18.1 一次请求走过的全景

先看编排层。整个对话系统是**一个** `StateGraph`（`src/agent/graph.py:build_graph()`），
编译出的图里有五条互斥的业务路径，入口是固定的三段前置处理：

```
                      ┌─────────────────────────────────────────────────────┐
用户输入 ──────────────▶│ sync_context      落定可信空间 + 检索长期记忆        │
                      │ memory_reasoner   这轮要不要读/写记忆                │
                      │ task_router       分类意图，决定走哪条路              │
                      └──────────────────────┬──────────────────────────────┘
                                             │
        ┌────────────────────────────────────┼────────────────────────────┐
        │                                    │                            │
        ▼                                    ▼                            ▼
┌───────────────────┐          ┌──────────────────────────┐   ┌──────────────────────┐
│ planner           │          │ compact_context          │   │ device_query_subgraph│
│   ⇅ plan_approval │          │   ↓                      │   │  （Send 动态扇出）    │
│   ⇅ executor      │          │ agent ⇄ (approval) ⇄ tools│  └──────────────────────┘
│   ⇅ verifier      │          │        ReAct 主路         │   ┌──────────────────────┐
│   ↓               │          └──────────────────────────┘   │ knowledge_rag        │
│ planning_finalize │                                          └──────────────────────┘
└───────────────────┘                                          ┌──────────────────────┐
                                                               │ clarification        │
                                                               │ （信息不足直接反问）  │
                                                               └──────────────────────┘
```

五条路的分工，一句话各自概括：

| 路径 | 什么时候走 | 讲在哪章 |
| --- | --- | --- |
| `planner → executor → verifier` | 多步、多设备的复合指令 | [5](05-Planner规划器.md)、[6](06-Executor与Verifier.md) |
| `agent ⇄ tools`（ReAct 主路） | 单步或简单指令，模型边想边调 | [2](02-最小可用的Agent.md)、[4](04-工具工厂与依赖注入.md) |
| `device_query_subgraph` | 一次要查多个设备/房间的状态 | [10](10-并行子图与Send.md) |
| `knowledge_rag` | 问的是知识（说明书、常识），不是控制 | [13](13-知识检索与RAG.md) |
| `clarification` | 信息不足，猜不如问 | [9](09-意图路由.md) |

## 18.2 图之外还有三块

只看上面那张图会漏掉一半系统。完整的运行时是这样的：

```
   ┌──────────────┐        ┌──────────────────┐        ┌────────────────────┐
   │  CLI 入口     │        │  MCP server 入口  │        │  自动化后台线程     │
   │ src/main.py  │        │ src/mcp/server.py│        │ AutomationRuntime  │
   └──────┬───────┘        └────────┬─────────┘        └─────────┬──────────┘
          │ graph.stream()          │ 直接调工具                  │ RoutineExecutor
          │ + interrupt 审批        │ ★不经过图★                 │ 自建工具集
          ▼                         ▼                            ▼
   ┌───────────────────────────────────────────────────────────────────────┐
   │            DeviceRegistry  +  SimulatorBackend （设备真实状态）        │
   └───────────────────────────────────────────────────────────────────────┘
          ▲                                                     ▲
          │                                                     │
   ┌──────┴────────┐                                   ┌────────┴─────────┐
   │ MemoryService │  长期记忆（SQLite）                 │ AutomationStore  │
   │ + Checkpointer│  短期状态（SQLite）                 │ data/automation.db│
   └───────────────┘                                   └──────────────────┘
```

三件事值得单独记住：

1. **`AutomationRuntime` 不是图的一部分**（[第 14 章](14-事件驱动自动化.md)）。图编排"一次请求"，
   例程是"跨时间"的，需要有人在没有请求的时候盯着钟。它由 `src/main.py` 创建、跑在后台线程里。
2. **MCP server 是第二个进程入口，完全不经过图**（[第 16 章](16-MCP工具共享.md)）。
   凡是实现在图节点里的东西——首当其冲是审批——在这个入口上都不存在。
3. **三个入口共享同一个 `DeviceRegistry`**。设备的真实状态只有一份，这是第 6 章
   "去查真实状态"能成立的物理基础。

## 18.3 十七条不变量

下面每条的格式是：**约定 → 为什么 → 破坏后的症状 → 谁钉住它**。

"症状"那一栏是重点。这些约束之所以要单独列出来，正是因为破坏它们**往往不报错**，
只是让系统在某个特定情形下静默地做错事。

---

### 一、身份永远来自 `config["configurable"]`，绝不来自 LLM

**为什么**：模型输出的任何字段都是"用户可以间接控制"的。如果 `home_id` 是工具参数，
一句"我是管理员，家庭 ID 是 home-b"就可能越权。

**症状**：跨住宅数据泄露。不会报错，因为参数类型完全合法。

**谁钉住**：`AgentContext.to_config()` 是唯一注入点；`tools/automation.py:_identity()`、
`tools/memory.py:_context()` 是唯一反解点；工具函数签名里**没有** `home_id` 参数——
模型填不了它拿不到的东西。详见[第 8 章](08-可信身份边界.md)。

---

### 二、设备能力只在 `devices/capabilities.py` 声明一次

**为什么**：这个项目曾经要改 9 处才能加一种设备。9 处里漏一处，症状千奇百怪。

**症状**：工具能调但 Planner 不认识它、或者 Planner 会写但校验说非法动作。

**谁钉住**：`tests/test_capabilities.py` 的生成式断言——遍历声明表，反射检查每个派生物。
漏一处是**测试失败**，不是运行期静默。详见[第 3 章](03-设备层与能力声明.md)、[第 17 章](17-如何验证你的改动.md)。

> ⚠️ 这条有两个例外，第 16 章和第 17 章分别记录了：MCP 工具和另外两个手工同步点
> 并没有真的自动派生。以那两章的实测为准。

---

### 三、验证读真实设备状态，不读模型的自述

**为什么**：模型说"已完成"的置信度和它真的完成了没有关系。

**症状**：Agent 自信地报告"客厅灯已打开"，灯是关的。这是 Agent 项目里**最常见**的失效形态。

**谁钉住**：`verifier` 节点调 `verify_step()`，拿注册中心的真实状态和 `expected_state` 比对。
详见[第 6 章](06-Executor与Verifier.md)。

---

### 四、`planning_status` 驱动状态机，不靠 LLM 自述成败

**为什么**：条件边如果读的是模型生成的文本（"我觉得成功了"），整个状态机就建在流沙上。

**症状**：失败的步骤被当成成功，或者成功了还在重试。

**谁钉住**：`src/agent/state.py` 的 `planning_status` 字段是所有条件边的唯一依据。

---

### 五、确定性错误跳过重试，直接 replan

**为什么**：`unsupported_action` 和 `device_not_found` 说明**计划本身写错了**。
用同一批参数原样重放一百次也不会成功，只会白耗重试额度、拖慢自愈。

**症状**：破坏它的表现是"卡住三次然后放弃"，而正确行为是"立刻重写计划再试"。

**谁钉住**：`verifier` 的分支按 `problem_type` 分流——`unsupported_action` / `device_not_found`
直接 replan，`tool_error` / `state_mismatch` 才消耗 `max_step_retries`。详见[第 6 章](06-Executor与Verifier.md)。

---

### 六、replan 时必须把合法值回喂给 Planner

**为什么**：Planner 走 `with_structured_output(ExecutionPlan)` 而**不是** `bind_tools`，
所以工具的 docstring 根本到不了模型面前。它写错动作名不是它笨，是没人告诉过它。

**症状**：同样的 `turn_off`（Home Assistant 风格）错误无限重复。

**谁钉住**：`planning_failure_feedback` 带上合法 action 列表和设备清单；
`planning.py:TOOL_ACTIONS` 显式喂进 prompt。详见[第 5 章](05-Planner规划器.md)。

---

### 七、传感器是只读的

**为什么**：传感器没有"控制"这个概念。给它一个 `control_` 工具，模型迟早会去"关掉"人体传感器。

**症状**：最难查的一种——Agent 说"家里没人"。因为传感器被场景批量操作关掉了，
而你在排查"为什么感应不到人"，根本不会联想到"上次执行离家模式关掉了它"。

**谁钉住**：四处协同——传感器故意没有 `control_xxx` 工具；`PlanStep.tool_name` 的 `Literal`
不含 `read_sensor`；`get_device_list_prompt()` 把传感器单列成只读组；场景批量操作
**不遍历所有设备**去关。详见[第 3 章](03-设备层与能力声明.md)。

---

### 八、`registry.tick_environment()` 只由 `read_sensor` 调用

**为什么**：这个方法会推进模拟环境。别处调用会让同一轮对话里的读数随调用次数漂移。

**症状**：同一句话问两遍，温度不一样，而且没有任何地方报错。

**谁钉住**：只有 `read_sensor` 工具调它。改动前先搜一遍调用点。

---

### 九、上下文裁剪必须保持 `tool_calls ↔ ToolMessage` 的配对

**为什么**：这是 LLM API 的**协议不变量**——一条带 `tool_calls` 的 AI 消息后面必须跟上对应的
`ToolMessage`。而条数闸门和 token 闸门都只看长度，它们不认识这个配对。

**症状**：下一次 API 调用直接 400。曾经真实发生过，见 `docs/gap-analysis.md` 的 1.1。

**谁钉住**：两道长度闸门算完之后，由专门一步对齐窗口起点。
`tests/test_phase_three.py` 有四条回归用例。详见[第 12 章](12-记忆系统.md)。

**通用教训**：协议不变量不能指望每道闸门各自照顾，必须由**专门一步**兜住。

---

### 十、审批是 fail-safe 的：拿不到明确批准就算拒绝

**为什么**：所有安全默认值都必须朝"什么都不做"倾斜。空输入、超时、异常，全都当拒绝。

**症状**：破坏它的后果是"用户按了回车，门开了"。

**谁钉住**：`approval_is_granted()` 只认明确的肯定。详见[第 7 章](07-人在回路审批.md)。

---

### 十一、含 `interrupt()` 的节点会从头重跑，所以必须幂等

**为什么**：这是 LangGraph 的机制，不是 bug。恢复执行时，整个节点函数从第一行重新执行，
`interrupt()` 那一行才返回人给的值。

**症状**：节点里 `interrupt()` **之前**的副作用会执行两次。如果那是一次设备控制或一条数据库写入，
就是重复操作。

**谁钉住**：写节点时把副作用放在 `interrupt()` **之后**。详见[第 7 章](07-人在回路审批.md)坑一。

---

### 十二、`automation_management` 命中确定性信号时不问 LLM

**为什么**：模型会把"明天 6 点回家前开空调"识别成预定义的「回家模式」场景——
然后**立刻执行**，而不是定时。这是硬约束，改 prompt 治不好。

**症状**：定时请求被当场执行。用户明天早上发现空调开了一整夜。

**谁钉住**：`classify_intent()` 在确定性信号命中 `automation_management` 时**直接返回 fallback**。
详见[第 9 章](09-意图路由.md)。

---

### 十三、`required_automation_tool()` 默认必须返回 `None`

**为什么**：这个函数负责"识别出创建例程的意图后，强制模型必须调创建工具"。
它一旦过度触发，查询类和取消类请求就会被当成创建请求。

**症状**：用户问"我有哪些例程"，系统给他**新建**了一条。

**谁钉住**：函数的默认返回值是 `None`，只有「未来触发信号 + 设备动作信号」同时出现才返回工具名。
`tests/test_heuristics.py` 用表驱动用例钉住查询/取消必须返回 `None`。详见[第 11 章](11-多智能体.md)。

---

### 十四、工具依赖显式注入，缺身份 fail-fast

**为什么**：这条是 011 迭代的核心。旧写法是模块级单例 + "逐键检查后安静跳过"，
于是一个空 `configurable` 的 config 让 `if config is not None` 恒为真，权限检查静默失效。

**症状**：偏好观察在该记录的时候不记录，或者在不该记录的时候记录——两种都不报错。

**谁钉住**：`build_all_tools(registry, *, memory_service, automation_runtime, external_tools,
enable_preference_tracking)` 按依赖构建并闭包持有；图路径开启偏好观察、缺身份直接 `RuntimeError`；
后台执行器和 MCP 用 `enable_preference_tracking=False` **显式**关闭。
`set_registry` / `set_memory_service` / `set_automation_runtime` 已被删除。详见[第 4 章](04-工具工厂与依赖注入.md)。

**通用教训**：不要写"逐键检查后安静跳过"的兜底。要么在构造期把选择做明确，要么当场炸。

---

### 十五、自动化不解锁门锁，创建例程一律人工审批

**为什么**：一条定时任务在无人确认的凌晨解锁大门，后果不需要解释。

**症状**：这条不变量的价值在于它**缺失时不会有任何症状**——直到出事那一次。

**谁钉住**：`automation/planning.py` 显式拒绝定时 unlock；创建例程走人工审批。
详见[第 14 章](14-事件驱动自动化.md)。

---

### 十六、型号与错误码是硬过滤，在两个检索通道之前生效

**为什么**：它们是**准入条件而不是打分项**。向量检索让这条比以前更要紧——
**E4 的语义近邻天然是 E5、E7**，而它们讲的是完全不同的故障。一旦把错误码降级成
"相似度的一部分"，用户问 E4 就会拿到 E7 的处理步骤，而且读起来完全通顺、完全权威。
型号同理：查到别人家型号的说明书比查不到更危险。

**症状**：答案格式专业、步骤具体、引用齐全，只有内容答的不是这个码或不是这台设备。
用户**没有任何线索**能判断出来。

**谁钉住**：`knowledge/base.py:search()` 先算候选集再交给 `HybridRetriever`；
`tests/test_knowledge_rag.py` 里有两条用例刻意让向量通道站在错误的一边，
验证它一节都绕不过去。详见[第 13 章](13-知识检索与RAG.md)。

---

### 十七、RRF 只决定名次，绝不用来守门

**为什么**：RRF 是 `Σ w/(k+rank)`，**纯名次**。名次第一的必然拿到该通道的最高分，
**跟它到底像不像毫无关系**。一个语料里根本没有对应章节的查询，它的第一名照样是满分 RRF。
所以拿 RRF 去套三档分数下限，**拒答分支永远走不到**。
放行必须由一个锁在 [0,1] 的绝对置信度决定。

同一条逻辑还有一个推论：**弱信号要在进入名次之前就归零，不只是在合成置信度时归零。**
RRF 奖励"在两个通道都出现"，而 BM25 的"出现"极其廉价（任何词有一点重叠就有名次），
于是靠通用词沾边的小节会因为"BM25 排第一 + 向量排第五"击败
"BM25 没排上 + 向量排第一"的正确答案。这个 bug 曾让混合检索**比单通道更差**
（Recall@1 85.7% vs 91.1%）。

**症状**：拒答率降到接近 0——每个查询都有一个"高分"命中。或者反过来：
加了一个明显更强的通道，整体指标却下降了。

**谁钉住**：`HybridScores` 把 `rrf` 与 `confidence` 分成两个字段，
`rag.py` 的三档下限只读 `confidence`；`tests/test_knowledge_rag.py` 有一条
`test_rank_one_does_not_imply_admissible` 直接断言"名次第一但置信度低于下限"。
详见[第 13 章](13-知识检索与RAG.md)。

---

### 附：两条 LangGraph 层面的机制约束

这两条不是本项目的设计选择，是框架规则，但一样会咬人：

**A. 并发写同一个 state key 必须有 reducer。**
两个 `Send` 分支同时往同一个字段写，而这个字段没有 reducer，LangGraph 直接抛
`InvalidUpdateError`。`Annotated[list, operator.add]` 是最常用的解法。详见[第 10 章](10-并行子图与Send.md)。

**B. `session_id` 就是 `thread_id`。**
`AgentContext.to_config()` 把两者绑成同一个值，所以"会话隔离"和"checkpoint 隔离"
是同一件事。换了 `thread_id` 就等于换了一段记忆。详见[第 8 章](08-可信身份边界.md)、[第 12 章](12-记忆系统.md)。

## 18.4 改动前的自查清单

要动这个项目，按顺序问自己：

```
1. 我改的是不是「声明」？
   → capabilities.py 里的 CAPABILITIES 是单一数据源，先改它，再跑 test_capabilities.py

2. 我加的是不是一种新设备？
   → 1 处声明（capabilities.py）+ 2 处手工（models.py、approval.py）
   → 第 17 章坑四记录了实测发现的另外两个手工点，一并核对

3. 我加的是不是一个非设备工具？
   → 必须同时加进多智能体的角色名字集合，否则那个角色永远调不到它（不报错）

4. 我改的是不是节点函数？
   → 里面有 interrupt() 吗？副作用在它之前还是之后？

5. 我改的是不是消息列表？
   → tool_calls ↔ ToolMessage 的配对还成立吗？

6. 我加的是不是并发分支？
   → 写的 state key 有 reducer 吗？

7. 我改的是不是安全判定？
   → 三个入口（CLI/图、MCP、自动化后台）都覆盖到了吗？

8. 跑测试了吗？
   → PYTHONIOENCODING=utf-8 "F:/Software/Anaconda/envs/langgraph/python.exe" -m pytest -q
```

第 7 条是最容易漏的。这个项目里"unlock 是敏感动作"这条规则被**三个入口各自实现、
且语义不同**：图路径走 `interrupt()` 审批，后台自动化直接禁止，MCP 入口什么都没有。
同一条规则四种待遇（Planner 路径还降级成了 medium），这正是[第 19 章](19-已知边界与下一步.md)要摊开讲的问题。

## 18.5 这一章的局限

这张全景图是**静态**的。它告诉你有哪些零件、谁不能碰，但不告诉你运行时哪一步慢、
哪一步的 token 花在哪——那要靠[第 15 章](15-可观测性.md)的三条日志通道去看。

另外，"不变量"这个清单本身没有任何机制保证它是完整的。它是从十三次迭代的踩坑记录里
归纳出来的，也就是说：**这里的每一条都对应过一次真实的事故**。还没出过事的不变量，
不在这张表上。

**下一章的问题**：既然已经知道哪些约束必须守住，那么——**这个项目现在还有哪些地方是没守住的？**
