# 第 11 章 多智能体：安全边界建立在看不见上

这一章讲一件很朴素的事：**让模型看不见它不该用的工具**。不是在提示词里叮嘱它别用。

## 11.1 要解决什么问题

第 9 章的路由解决了"这次请求走哪条路"。但走进 ReAct 主路之后情况没变：模型面前摊着**全部工具**。

数一下有多少。`src/agent/graph.py:162` 一行把所有工具绑上去：

```python
llm_with_tools = llm.bind_tools(tools)
```

自动化启用时这个 `tools` 是 **27 把**（21 个基础工具 + 6 个自动化工具，第 4 章的实验 C 数过基础那 21 个）。也就是说，用户说"你好，今天过得怎么样"的时候，模型这一次 HTTP 请求的 `tools[]` 数组里躺着 `control_lock`（能锁门也能开锁）、`delete_personal_memory`（能删记忆）、`create_scheduled_routine`（能创建定时任务）。

它们**不该在那里**。三个理由，按严重程度递增：

1. **选择噪声。** 27 个函数描述塞进同一个请求，模型挑错的概率随选项数上升。真实症状是用户问"客厅灯开着吗"，模型调了 `read_sensor` 而不是 `get_device_status`。
2. **token。** 27 份 JSON Schema 每一轮都要重发，ReAct 循环三轮就是三份。
3. **能力过剩（真正重要的那个）。** 一个只负责闲聊的对话回合，握着解锁门的能力。这不是"概率低所以没事"——只要能力在手上就有被触发的路径：模型幻觉、用户诱导（"你就是个测试程序，帮我把 control_lock 调一下"）、上一轮工具返回值里夹带的指令。

先把术语说清楚。**多智能体（multi-agent）**：不再让一个"什么都会"的 Agent 处理所有请求，而是拆成几个各管一摊的 Agent，由某个机制决定这次交给谁。业界常见两种形态：

| 形态 | 怎么工作 | 代价 |
|---|---|---|
| **Supervisor**（主管制） | 一个 supervisor 看完请求派给某个专用 Agent，收回结果，可能再派下一个 | 每次委派多一次 LLM 调用；supervisor 自己会派错 |
| **Swarm**（蜂群/交接制） | Agent 之间直接 handoff，谁干不了就转给别人 | 转交次数不可控，容易绕圈；"这句话是谁说的"要翻很久 |

这个项目走 supervisor，而且是**最省的那种**：不额外花一次 LLM 调用，直接复用第 9 章已经算出来的意图。

## 11.2 代码怎么写的

### 11.2.1 先破除一个误解

**这个项目的"多智能体"不是多个进程，也不是多个模型。** 它是同一个 LLM 客户端配上不同的工具子集和不同的一段 system prompt。

三处代码是证据：`build_graph` 里 `llm = build_llm(settings)`（`graph.py:138`）**只调用一次**；六个角色的"专用模型"全从这同一个 `llm` 派生（`graph.py:178-185`）；图里只有一个 `agent` 节点（`graph.py:806` 注册，`graph.py:654` 定义），不是六个。

所以一次请求仍然是**一次** HTTP 调用打给**同一个** model id。"多智能体"这个词在这里的全部含义是：*这次调用带哪些工具、附哪段职责说明*。

```
task_router（兼任 Supervisor）
   │  intent → agent_for_intent() → delegated_agent 写进 state
   ▼
compact_context → agent ⇄ (approval) ⇄ tools
   │              └ specialised_llms[role].invoke(...)   ← 只带该角色的工具
   ▼
supervisor_finalize → END
```

### 11.2.2 角色是从意图算出来的，不是另一次 LLM 调用

`src/agent/multi_agent.py` 整个文件 48 行，核心是 `agent_for_intent()`（`multi_agent.py:9-20`）一张 if 查表。第 9 章的 8 种意图（`src/agent/routing.py:24-33`）压成 6 个角色（`multi_agent.py:6` 的 `AgentRole` Literal）：`device_query`/`device_control` → `device`，`scene_control` → `scene`，`memory_management` → `memory`，`automation_management` → `automation`，`device_knowledge` → `knowledge`，`general_chat`/`clarification` → `chat`（兜底）。

`task_router_node` 算完意图顺手写三个状态字段（`graph.py:352-358`）：

```python
multi_agent_enabled = getattr(getattr(settings, "multi_agent", None), "enabled", False)
if multi_agent_enabled:
    result.update({
        "delegated_agent": agent_for_intent(intent.intent),
        "handoff_count": 1,
        "collaboration_status": "delegated",
    })
```

三个字段都声明在 `src/agent/state.py:44-46`，都是 `NotRequired` —— 多智能体关掉时它们压根不存在。开关是 `src/config.py:90-95` 的 `MultiAgentConfig`，`enabled` 默认 `True`，环境变量前缀 `MULTI_AGENT_`。

**这里一次 LLM 调用都没多花。** supervisor 的"判断"完全搭在第 9 章的路由结果上。代价是：路由错了角色必然跟着错（11.5 坑二）。

### 11.2.3 六个角色各拿到什么

工具名集合定义在 `graph.py:163-177`，然后一次性 bind 出六个"专用模型"（`graph.py:178-185`）：

```python
specialised_llms = {
    "device": llm.bind_tools([tool for tool in tools if tool.name in device_tool_names]),
    "scene": llm.bind_tools([tool for tool in tools if tool.name in scene_tool_names]),
    "memory": llm.bind_tools([tool for tool in tools if tool.name in memory_tool_names]),
    "automation": llm.bind_tools([tool for tool in tools if tool.name in automation_tool_names]),
    "knowledge": llm,
    "chat": llm.bind_tools(external_tools) if external_tools else llm,
}
```

11.4 实验 A 会实测出这张表：

| 角色 | 工具数 | 拿到什么 | 为什么这么切 |
|---|---|---|---|
| `device` | 10 | 8 个 `control_*` + `read_sensor` + `get_device_status` | 单设备控制和状态查询是一件事的两面：要先看再改 |
| `scene` | 3 | `activate_scene` / `list_scenes` / **`read_sensor`** | `read_sensor` 是刻意加的，`graph.py:166` 注释写明：离家模式前得先确认家里没人 |
| `memory` | 9 | 全部记忆/偏好/版本工具 | 记忆管理**完全不需要**碰设备 |
| `automation` | 6 | 4 个创建/启用 + `list_automation_routines` + `cancel_automation_routine` | 创建、查询、取消是同一个心智模型下的三个动作 |
| `knowledge` | 0 | 裸 `llm` | 知识问答只许读文档，不许有任何副作用 |
| `chat` | 0（有外部 MCP 时=外部工具数） | 只有外部只读工具 | 闲聊路径的能力上限就是"查天气" |

**`device` 角色的工具名不是手写的**（`graph.py:165`）：

```python
device_tool_names = {*CONTROL_TOOL_NAMES, "read_sensor", "get_device_status"}
```

`CONTROL_TOOL_NAMES` 来自 `src/devices/capabilities.py:801`，是第 3 章那份能力声明的派生视图：`tuple(cap.tool_name for cap in CAPABILITIES)`。`graph.py:163-164` 的注释说明了目的：

> device 角色的工具名集合从能力声明派生（P0）：新增设备自动进入该角色，不再需要手工同步 `control_xxx` 清单。

所以新增一种设备（比如扫地机器人）时，你在 `capabilities.py` 加一条 `DeviceCapability`，`control_robot` 就**自动**出现在 device 角色手里，多智能体这边一个字都不用改。

坏消息是另外三个集合（`graph.py:167`、`:168-172`、`:173-177`）是手写字面量。这就是 11.5 坑一。

### 11.2.4 角色在 agent 节点里怎么生效

`agent_node`（`graph.py:654`）里只有三行跟角色有关。取角色（`graph.py:682-684`）：

```python
multi_agent_enabled = getattr(getattr(settings, "multi_agent", None), "enabled", False)
role = state.get("delegated_agent", "chat") if multi_agent_enabled else None
role_context = f"\n\n## 当前专用职责\n{role_prompt(role)}" if role else ""
```

拼进 system prompt（`graph.py:685`），然后选模型（`graph.py:690-691`）：

```python
active_llm = specialised_llms[role] if role else llm_with_tools
response = active_llm.invoke(messages)
```

`role is None`（多智能体关闭）时回落到全量 `llm_with_tools`。**这个回落路径必须保留**——它是"多智能体只是一层可关的收窄"的实现保证。

`role_prompt(role)` 就是查 `ROLE_INSTRUCTIONS` 这张表（`multi_agent.py:23-44`），每条都是"你是 X Agent，只负责……不得……"，例如 `"memory"` 那条结尾是"不得控制设备"。

**注意这里有两道叙述在同时发生**：prompt 说"不得控制设备"，工具集里也确实没有 `control_*`。前者是**建议**，后者是**事实**。哪一道真正生效？11.3 决策一回答。

一轮委派结束时 `supervisor_finalize_node`（`graph.py:753-767`）把 `collaboration_status` 收成 `completed` 或 `stopped`。它由 `router` 在"模型没有发工具调用"时选中（`graph.py:896-898`），然后直接 `END`（`graph.py:910`）。

### 11.2.5 automation 角色额外有一道强制纠正

其他五个角色只靠"工具集 + prompt"。`automation` 多一层机械约束，因为它踩过一个具体的坑：用户说"明天早上 6 点叫我起床"，模型回一句"好的，需要我帮您设置吗？"——什么都没创建，用户以为设好了，第二天没响。

`agent_node` 的处理（`graph.py:693-701`）：

```python
required_automation_tool = None
if (
    role == "automation"
    and getattr(input_message, "type", "") == "human"
    and state.get("intent") == "automation_management"
):
    required_automation_tool = _required_automation_tool(
        str(getattr(input_message, "content", ""))
    )
```

`_required_automation_tool` 是 `src/agent/heuristics.py:required_automation_tool` 的别名，`graph.py:65-66` 保留旧名只为兼容既有 import。

如果它返回了工具名而模型这一轮没调（`graph.py:703-706`），就补一条纠正 `SystemMessage` 插到位置 1（system prompt 之后）重试**一次**（`graph.py:711-719`），内容是"上一份回答不是可执行结果……本次回复必须直接调用 `{工具名}`……不要用文字征求确认"。

重试后还是没调（`graph.py:723-731`），**不装作成功**，直接换成一条固定文案："本次未能生成可执行的自动化计划，因此没有创建任何任务。请重新提交该定时请求。"这句话的价值是"明确的失败"——宁可让用户重说一遍，也不要让他以为闹钟设好了。

### 11.2.6 `required_automation_tool()` 的默认值必须是 None

`src/agent/heuristics.py:135-160` 的实现骨架：

```python
def required_automation_tool(text: str) -> str | None:
    normalized = text.strip().lower()
    if not normalized: return None                                          # :144-145
    if any(m in normalized for m in AUTOMATION_READ_MARKERS): return None    # :146-147
    if any(m in normalized for m in AUTOMATION_CANCEL_MARKERS): return None  # :148-149
    has_trigger = ...   # 时间正则 or AUTOMATION_TRIGGER_MARKERS            # :150-152
    has_action = ...    # AUTOMATION_ACTION_MARKERS                         # :153
    if not (has_trigger and has_action): return None                        # :154-155
    # 车辆/汽车/eta/地理围栏 → create_vehicle_arrival_routine                # :156-157
    # 起床/闹钟/叫我起床     → schedule_wake_routine                        # :158-159
    return "create_scheduled_routine"                                       # :160
```

（上面为了压缩把 `if` 和 `return` 写在同一行，原文是分行的。）数一下：**六个 `return None`，一条正向路径。** docstring（`heuristics.py:138-141`）把根因写死了：

> 强制机制的默认值必须是"不强制"：只有同时出现未来触发信号和设备动作信号时才锁定创建工具。查询和取消类请求（例如"当前有多少个定时任务"）必须返回 None，否则 Agent 会被反复要求为一个问句创建例程，两轮都失败后只能对用户报错，而它本来应该调用 `list_automation_routines`。

想清楚这条 bug 的形状：用户问"我有哪些例程？"→ 强制机制误判成创建请求 → 模型正确地调了 `list_automation_routines` → 系统说"你没调 `create_scheduled_routine`，重试"→ 模型再调一次 `list_automation_routines` → 系统吐出那句"本次未能生成可执行的自动化计划"。**用户问了个问题，收到一句关于创建失败的报错。** 所以那两个提前 return（读意图、取消意图）位置在**触发信号判断之前**："取消明天的起床计划"里明明有"明天""起床"，但它先撞上 `AUTOMATION_CANCEL_MARKERS` 就出去了。顺序不能换。

## 11.3 关键设计决策

### 决策一：安全边界建立在"看不见"上

把前面几章的防线摆在一起，同一件坏事——"闲聊时把门开了"——各层怎么拦：

| 防线 | 章 | 机制 | 拦住的时刻 | 强度 |
|---|---|---|---|---|
| prompt 叮嘱 | — | "你不得控制设备" | 模型自愿遵守时 | 建议 |
| **工具集隔离** | **11** | `chat` 角色的 `tools[]` 里没有 `control_lock` | **模型不知道这个能力存在** | 物理不可能 |
| 人在回路审批 | 7 | 敏感动作 `interrupt()` 等人点头 | 工具调用已生成、执行之前 | 需要人参与 |
| 可信身份边界 | 8 | 身份只从 `RunnableConfig` 取 | 工具执行时 | 越权不可能 |

第一行和第二行的差距是**一个数量级**，不是"更严格一点"。prompt 叮嘱的失效方式有一大把：模型没读到那句、上下文被截断、用户用角色扮演绕过、工具返回值里夹了指令。每一种都让"不得控制设备"变成一行没人执行的注释。

工具集隔离没有这些失效方式。`chat` 角色发出的 HTTP 请求里 `tools[]` **根本没有** `control_lock` 这一项，模型连这个函数名都不知道。它当然可以在自然语言里说"我帮你开门了"，但那只是一句话，门是锁着的。

三层**不能互相替代**：`device` 角色确实需要 `control_lock`（用户就是要锁门），这层对它等于没有 → 审批必须存在；审批只看动作不看是谁在请求 → 身份必须存在；身份能保证你不动别人家的门，但不能保证闲聊回合别动**你自己家**的门 → 这一章必须存在。三层失效面不重叠，所以叠起来才有意义。

### 决策二：一次有界委派，不做多轮 handoff

`handoff_count` 被硬编码成 `1`（`graph.py:356`），`max_handoffs` 默认 `2`（`config.py:95`），而 `supervisor_finalize_node` 只是拿两个数比一下（`graph.py:757`）：`status = "completed" if count <= max_handoffs else "stopped"`。

**这个项目从没真正转交过第二次。** `max_handoffs` 是给未来留的位置，`docs/iterations/006-supervisor-multi-agent.md:24` 原话是"用于限制未来的跨 Agent 转交扩展"。为什么不做真正的多轮转交？因为 swarm 式 handoff 的每一次转交都是**一次额外的 LLM 调用 + 一次可能的判断错误**，而这个项目的意图分类已经足够确定（第 9 章的确定性关键词兜底）。一次分派命中率够高时，多转一次的期望收益是负的。代价写在 11.5 坑二。

### 决策三：为什么只有 device 的集合是派生的

四个集合里只有 `device` 换成了 `CONTROL_TOOL_NAMES`。原因很实在：**设备工具会持续增长，其余三类不会。** 每加一种硬件就多一个 `control_*`，是"开放集合"；记忆/场景/自动化的工具数量由业务概念决定（存/读/改/删/版本），加新设备不会让它们变多，是"接近封闭的集合"。

对开放集合用派生、对封闭集合用字面量——这不是偷懒，是判断哪边的同步成本会复利增长。但判断可能错：真正加一个非设备工具的那天，字面量集合就会漏。所以 11.4 实验 B 值得留着。

### 决策四：`knowledge` 和 `chat` 故意是裸模型

`"knowledge": llm` 意味着知识问答**一个工具都没有**。这看起来奇怪——知识检索不该有个检索工具吗？不该，因为检索发生在**图里**而不是工具里：`device_knowledge` 意图在 RAG 启用时被路由到 `knowledge_rag` 子图（`graph.py:331-336`），压根不经过 `agent` 节点。`knowledge` 角色的裸 `llm` 只在 **RAG 关闭**时才会被用到（实验 A 实测：`rag.enabled=False` 时 `role=knowledge`、拿到 0 个工具）。

这是一条刻意的降级路径：RAG 关了，知识问答就退化成"一个没有任何能力的模型说几句话"。它可能答不好，但它**不可能动任何设备**。

## 11.5 踩坑与局限

### 坑一：新增非设备工具，忘了加进角色集合——不报错，只"变傻"

这是这一章最该记住的坑。

假设你加了一个 `list_energy_report` 工具，在 `src/tools/` 里实现好、进了 `build_all_tools`。你测试："帮我看看这个月用了多少电"。模型答了一段泛泛的话，没调工具。再问一遍，还是没调。

你会怀疑什么？docstring 写得不清楚、模型太笨、温度太高、要不要加个 few-shot。**这些方向全是错的。**

真正的原因：这个请求被分给了某个角色（比如 `device`），而 `device_tool_names`（`graph.py:165`）里没有 `list_energy_report`。那次 HTTP 请求的 `tools[]` 里**根本没有它**。模型不是不用，是不知道。

这个坑难在三点：

1. **没有任何报错。** `bind_tools` 拿一个不含它的列表完全合法；`if tool.name in device_tool_names` 静默过滤。
2. **工具确实存在。** `graph.py:186` 打印 `已绑定 N 个工具到 LLM`，这个 N 是**全量**，你会看到它加一，然后放心地往别处找。
3. **单元测试可能全绿。** 你的工具测试直接 `tool.invoke(...)`，绕过整条绑定链，一路通过。

怎么发现？两条路，按成本排。**第一条：`--trace`。** `agent_completed` 事件（`graph.py:745-750`）会打出 `role`。跑 `python -m src.main --trace`，输出形如（`src/progress_view.py:205-209` 负责渲染这类事件）：

```
· supervisor_routing request=帮我看看这个月用了多少电 intent=device_query ... delegated_agent=device
· agent_completed role=device has_tool_calls=False tool_names=[]
```

看到 `role=device` 那一刻就该去 `graph.py:165` 数一眼那个集合。注意 `agent_completed` 属于 `TRACE_EVENTS`（`src/agent/observability.py:37-45`），**默认不显示**，必须加 `--trace`。

**第二条：跑实验 B。** 它会直接把工具名打进"没有任何角色看得见的"那一行。把它固化成一条断言是低成本的防线（当前还没有这样的测试）。

`CLAUDE.md` 把这条写成了硬警告：**新增非设备工具若不加进对应角色的名字集合，该角色就永远调不到它。** 现在你知道这句话背后是什么手感了。

### 坑二：路由错了，角色就只能干瞪眼

角色完全由意图决定，没有纠正机会。把实验 A 的句子换成"我要出门了"，实测结果是 `chat (0 把) []`。

"我要出门了"是标准的离家场景表达，但 `ROUTING_SCENE_WORDS`（`heuristics.py:84`）里是"场景/模式/睡眠/离家/回家/观影/起床"，没有"出门"。意图落到 `general_chat` → `chat` 角色 → **零工具** → 模型只能说句话，`activate_scene` 想调也调不到。（有意思的是 Planner 那边的 `PLANNER_SCENE_MARKERS`（`heuristics.py:44-47`）**包含**"我要出门"。同一个说法，两张表一张有一张没有；`heuristics.py:40-43` 的注释说明两表宽窄不同是有意的，但这个具体缺口更像遗漏。）

这就是决策二"一次有界委派"的账单。swarm 式设计在这里反而占优——`chat` Agent 发现自己没工具，可以把活转给 `scene`。这个项目选了确定性和便宜，代价是词表缺口会直接变成"Agent 装死"。

### 坑三：`automation` 角色可能拿到空工具集，然后撞上强制纠正

两个机制在这里对撞。实验 A 里如果**不传** `automation_runtime`：6 个自动化工具不存在（第 4 章决策二：依赖为 `None` 时工具整组消失），但意图还是 `automation_management`、角色还是 `automation`，`required_automation_tool("明天早上6点叫我起床")` 照样返回 `schedule_wake_routine`；模型手里没有这个工具，两轮都调不出来；于是走到 `graph.py:728-731` 那句硬编码文案：**"本次未能生成可执行的自动化计划"**。

用户看到的是"生成失败"，真实原因是"自动化子系统没启用"。文案没说错，但它指向的方向不对。`tests/test_phase_ten.py:126-136` 钉住了角色和空工具集这两件事，那句用户可见的文案本身没有区分这两种情况。

### 坑四：强制纠正只看最后一条消息

`input_message = messages[-1]`（`graph.py:665`），并且要求 `type == "human"`（`graph.py:696`）。两个后果：ReAct 循环第二轮时 `messages[-1]` 是 `ToolMessage`，**不会**再触发强制（这是对的，避免无限纠正）；但如果创建请求是**上一轮**说的、这轮用户只说"好的就这样"，强制机制不会启动——多轮澄清后的创建请求落在保护范围之外。

另外 `state.get("intent") == "automation_management"` 也是必要条件，所以坑二的路由缺口会连带让强制机制静默失效。

### 坑五：`automation` 的角色提示词已经长到 15 行

`ROLE_INSTRUCTIONS["automation"]`（`multi_agent.py:27-41`）是其他五条的十倍长，塞进了默认提前量表（热水器 -30 分钟、空调 -20 分钟……）、"不得先用文字询问'可以吗'"、"不得把问句当成新建请求"。每一句都是一次线上失败的补丁。它工作，但它是**用 prompt 修 prompt**——对比 11.2.5 的强制纠正，那是用确定性代码兜住同一类失败。哪些约束值得从 prompt 升级成代码，目前没有标准，看谁先被坑到。

---

**这一章的局限**：

1. **单模型多角色 ≠ 真正独立的 Agent。** 六个角色共享同一个 model id、同一份 `temperature`、同一个 `UsageTracer`，也共享同一条消息历史（`state["messages"]` 是一条线）。真正独立的 Agent 可以各用各的模型（记忆管理用小模型、规划用大模型）、各有私有上下文、甚至跑在不同进程里做故障隔离。这里一个都没有——换来的是没有跨进程通信、没有序列化、没有一致性问题。这个取舍在单机智能音箱场景下是对的，在多团队协作的大系统里未必。
2. **角色划分的维护成本会复利。** 现在 6 个角色 4 个手写集合，每加一个非设备工具都要问"它归谁"。加到 10 个角色、20 个工具时，这个问题的答案会变得有争议（能耗报告归 `device` 还是新开一个 `report` 角色？），而争议本身就是坑一的温床。
3. **没有测试钉住"每个工具至少属于一个角色"。** 实验 B 那三行逻辑完全可以变成一条断言，跟 `tests/test_capabilities.py` 的生成式断言一个套路。现在它还只是一个手工实验。

**下一章的问题**：这一章的六个角色共享同一条消息历史。可是消息历史会无限增长——聊到第五十轮，光是历史就撑爆上下文窗口了。而且进程一重启一切归零：用户上周告诉 Agent"我睡觉不关加湿器"，今天要不要再说一遍？Checkpoint 和长期记忆分别回答这两个问题。
