# 第 14 章 事件驱动自动化

这一章让 Agent 学会在**没有人说话的时候**动手，并且让"凌晨三点会发生什么"这件事在毫秒内可测。

## 14.1 要解决什么问题

到目前为止，Agent 只能在你说话的那一刻干活。你说"打开客厅灯"，它开灯、回话、结束。第 13 章的知识检索也一样 —— 你问，它查，它答。

可这句话就不行了：

> 我明天早上 7 点起床，帮我提前把卧室暖起来。

它要求 Agent 在**没有人说话的时候**动手。而且不是一次动手，是一串：7 点响闹钟、6 点 30 把热水器烧到 45 度、6 点 50 把水壶烧到 80 度、7 点整开窗帘开灯 —— 四件事分布在四个时刻，跨越半个小时，全都在你睡着的时候。

第一个直觉方案是让 Agent 在对话里"记住"这件事，下次你说话时检查时间到了没有。问题是**下次你说话可能是三天后**。真正的痛点不是"记不住"，而是**没有人在没有请求的时候盯着钟**。

第二个直觉方案是在图（`StateGraph`，第 2 章）里加一个"等待"节点，`sleep` 到目标时刻。这个失败得更彻底：

- 图的一次运行从"收到消息"开始，到"产出回复"结束。中间 `sleep` 8 小时，用户的终端就挂在那里 8 小时。
- 进程重启（部署、崩溃、笔记本合盖）→ `sleep` 里的状态全没了。Checkpoint（第 7 章、第 12 章）能救活"等审批"的暂停，因为审批的另一端是人、人会回来；但没人能"恢复"一个 `time.sleep`。
- 一次对话只有一个"当前时刻"。四个动作分布在四个时刻，就是四次独立的执行时机。

结论很直接：**图编排的是"一次请求"，自动化是"跨时间"的**。生命周期不一样，不能塞进同一个抽象里。

## 14.2 代码怎么写的

`src/automation/` 是一个**独立的持久化调度子系统，不是图的一部分**。它和图是并列关系，两者通过工具互相触达：

```
        ┌──────────────── 一次请求的生命周期 ────────────────┐
用户 ──▶ │ StateGraph: sync_context → task_router → agent ⇄ tools │ ──▶ 回复
        └────────────────────────┬──────────────────────────┘
                                 │ create_scheduled_routine 等 6 个工具（审批通过才写库）
                                 ▼
                    ┌───────────────────────────┐
                    │   AutomationRuntime       │  ← 进程内长驻，不随请求结束
                    │  store / executor /       │
                    │  scheduler / arrivals     │
                    └───────┬───────────────────┘
                            │ scheduler.start() 起一条后台守护线程
                            ▼
        每 poll_seconds 秒 tick() ──▶ 取出到期任务 ──▶ executor 执行
                            │                            │
                            ▼                            ▼
                    data/automation.db            DeviceRegistry
                  （进程重启后例程还在）      （和图操作的是同一个注册中心）
```

注意最下面那条：**后台执行器和图操作的是同一个 `DeviceRegistry`**。所以定时开的灯，你下一句"灯开着吗"能查到 —— 设备状态是唯一的事实来源（第 6 章）。

### 14.2.1 `AutomationRuntime` 组装了哪些零件

`AutomationRuntime.__init__`（`src/automation/runtime.py:24-39`）就是一份装配清单，五行代码五个零件，各自的职责边界很清楚：

```python
self.store = AutomationStore(db_path)                                    # :35
self.speaker = speaker or SimulatorSpeakerBackend()                      # :36
self.executor = RoutineExecutor(registry, self.speaker)                  # :37
self.scheduler = RoutineScheduler(self.store, self.executor, event_sink=event_sink)  # :38
self.arrivals = ArrivalOrchestrator(self.store, self.scheduler)          # :39
```

| 零件 | 文件 | 只管一件事 |
|---|---|---|
| `AutomationStore` | `store.py` | SQLite 读写：例程、运行批次、任务。三张表，没有业务逻辑 |
| `RoutineExecutor` | `executor.py` | 拿到一个任务 payload，执行 + 验证，返回成败 |
| `RoutineScheduler` | `scheduler.py` | 把例程展开成带时刻的任务；到点取出来交给 executor |
| `ArrivalOrchestrator` | `vehicle.py` | 把车辆 ETA 事件翻译成"锚点时刻"，再交给 scheduler 排期 |
| `SpeakerBackend` | `speaker.py` | 音响闹钟的适配接口（`speaker.py:10-27` 是抽象基类），默认是模拟实现 |

`speaker.py` 那个抽象基类值得多说一句。真实的智能音响需要 OAuth 令牌，而**令牌绝不能进模型上下文**。所以这里划了一道适配边界：模型只知道"有个工具能设闹钟"，令牌活在 `SpeakerBackend` 的实现里。换成真音响只需要换一个子类。

### 14.2.2 谁创建它、谁起线程、谁关连接

全在 `src/main.py`：

```python
if settings.automation.enabled:                                    # main.py:500
    automation_runtime = AutomationRuntime(
        registry, db_path=..., timezone_name=...,                  # 省略两个 settings 取值
        event_sink=lambda event: logger.info("自动化事件 | {}", event),
    )                                                              # main.py:501-506
    automation_runtime.scheduler.poll_seconds = settings.automation.poll_seconds
    automation_runtime.scheduler.start()                           # main.py:508
```

`start()`（`scheduler.py:117-122`）起的是一条 `daemon=True` 的线程，循环体只有一句 `while not self._stop.wait(self.poll_seconds): self.tick()`（`scheduler.py:124-126`）。用 `Event.wait()` 而不是 `time.sleep()` 是有意的：`stop()` 一 `set`，线程立刻醒来退出，不用等满一个轮询周期。

退出路径同样重要。`_release_runtime_resources`（`main.py:307-321`）在 `finally` 里（`main.py:578-579`）关掉后台线程和两个 SQLite 连接。这个函数的 docstring 记着一次真实修复：

> 长期记忆库由 build_graph 内部创建，只作为 graph.memory_repository 暴露出来，所以退出时必须由调用方来关 —— 之前这里只关了 automation_runtime，那个连接一直靠进程退出兜底，一旦 build_graph 被用在长驻服务里就是泄漏。

再往下 `AutomationRuntime.close()`（`runtime.py:100-102`）先 `scheduler.stop()` 再 `store.close()`。**顺序不能反** —— 先关连接，后台线程下一次 `tick()` 就会拿着一个关掉的连接去查库。

### 14.2.3 本章最值得学的一行：时间从参数进来

`RoutineScheduler` 有两个方法，`schedule()` 和 `tick()`，它们的第一行几乎一样：

```python
def schedule(self, routine, *, anchor_at, trigger_key, now=None):
    now = now or datetime.now(timezone.utc)          # scheduler.py:40

def tick(self, now=None):
    now = now or datetime.now(timezone.utc)          # scheduler.py:80
```

看着平淡，但这是整个子系统可测性的全部来源。**调度逻辑本身不读系统时钟**。时钟只在"调用方没给"的时候作为默认值出现一次，之后所有判断都用参数里那个 `now`。

于是排期就是纯算术（`scheduler.py:44-52`，省略了外层的动作遍历和 `enabled` 过滤）：

```python
due_at = anchor_at + timedelta(minutes=action.offset_minutes)     # :48
if action.tool_name == "set_alarm":
    # The alarm must be armed when the routine is created, not at wake time.
    due_at = now                                                  # :51
    arguments["alarm_at"] = anchor_at.isoformat()                 # :52
```

`offset_minutes`（`models.py:16-29`，docstring 在 `:17-21`）是**相对锚点**的分钟偏移，提前执行用负数。所以"起床前 30 分钟烧热水"就是 `offset_minutes=-30`。

`set_alarm` 那三行是个反直觉但必要的特例：闹钟必须在**例程创建时**就写进音响，而不是等到起床那一刻才去设 —— 否则你的手机闹钟界面在睡前是空的，谁也不敢睡。所以它的 `due_at` 是 `now`（立刻执行），响铃时刻通过 `arguments["alarm_at"]` 传下去。

取任务同样是纯查询（`store.py:120-125`），`due_at<=?` 里那个 `?` 就是传进来的 `now` —— 换成 2026 年、1999 年、或者你想要的任何时刻，逻辑完全一样：

```sql
SELECT * FROM scheduled_tasks WHERE status='pending' AND due_at<=? ORDER BY due_at, created_at
```

**这条原则可以抬得更高一层：把不确定性推到边界外。** 系统时钟、随机数、网络、当前用户 —— 这些东西每一次调用都可能给出不同答案，是测试的天敌。做法不是"想办法 mock 掉它们"，而是**在设计时就让核心逻辑不去碰它们**，只在最外层的一个调用点把它们注入进来。第 6 章的 Verifier 用同样的思路对付"设备真实状态"，第 12 章的 Checkpoint 用同样的思路对付"进程会重启"。

代价是 API 上多一个参数。收益是 14.4 的实验里你会看到，模拟完整的 8 小时起床流程只花 37 毫秒，一次 `sleep` 都没有，而且每次跑出来一模一样。

### 14.2.4 `dedupe_key`：重复触发是常态，不是异常

`dedupe_key` 的构造（`scheduler.py:59`）是 `f"{routine.id}:{trigger_key}:{action.id}"`，三段各自回答一个问题：**哪个例程**、**哪一次触发**、**这次触发里的哪个动作**。数据库上加了 `dedupe_key TEXT UNIQUE NOT NULL`（`store.py:41`）兜底。

为什么需要它？因为**同一个例程被重复触发是常态**：

- 车在路上，导航每分钟推一次 ETA。开一趟车能推几十次，每次都会走一遍排期逻辑。
- 用户说了两遍"明天 7 点叫我起床"。
- 后台线程每秒 `tick()` 一次，任务的执行窗口跨多个周期。

`trigger_key` 这一段是关键，它定义了"什么算同一次触发"。定时例程用时刻（`runtime.py:50` 的 `f"wake:{wake_at.isoformat()}"`、`runtime.py:73` 的 `f"scheduled:{anchor_at.isoformat()}"`），车辆例程用**行程 id**（`vehicle.py:67` 的 `f"vehicle:{event.vehicle_id}:{trip_id}"`）。

同一趟行程推 50 次 ETA，`trigger_key` 不变 → `dedupe_key` 不变 → 数据库里始终是那 4 条任务。换一趟行程（`trip_id` 变了），`trigger_key` 就变了，于是是新的一批任务 —— 这正确，因为那确实是另一次回家。运行批次也有一层同样的保护：`routine_runs` 表上有 `UNIQUE(routine_id, trigger_key)`（`store.py:36`），`create_run` 用的是 `INSERT OR IGNORE`（`store.py:77`）。

### 14.2.5 ETA 更新只移动尚未执行的任务

`add_task` 的 SQL 是全项目最值得逐字读的一段（`store.py:104-111`，省略了 `INSERT` 的列名和占位符）：

```sql
ON CONFLICT(dedupe_key) DO UPDATE SET
  due_at=excluded.due_at,
  payload=excluded.payload
WHERE scheduled_tasks.status='pending'
```

最后那个 `WHERE scheduled_tasks.status='pending'` 就是本节的全部内容。**冲突时只更新还在等待的任务，已经跑过的（`completed` / `failed`）原地不动。**

为什么这个不变量必要？想一个具体场景（14.4 的实验 B 会真跑一遍）：

```
17:00  车报 ETA 20 分钟 → 锚点 17:20
       排期：17:05 烧热水  17:10 开空调  17:18 开窗帘  17:20 开灯
17:05  热水器已开 ✅（任务 completed）
17:01  车报 ETA 25 分钟 → 新锚点 17:26
       ？热水器那条任务的新 due_at 应该是 17:11
```

如果不加那个 `WHERE`，热水器任务会被"改期"回 17:11 并且状态被重置。但**热水器已经在烧了**。把一个已经发生的事实改回"待办"，结果是 17:11 再开一次已经开着的热水器 —— 这一次可能只是浪费，可是同样的逻辑套到"拉窗帘""开门"上就是可见的错误行为，套到"发通知"上就是重复打扰。

一般原则：**已经发生的事实不可改期。** 时间线可以往前调整，但只能调整未来那一段。`tests/test_automation_routines.py:190-216` 是钉住这条不变量的用例，它同时断言三件事：任务总数还是 4（没变成 8）、`completed` 恰好 1 条、`pending` 的第一条挪到了新锚点减 10 分钟。

### 14.2.6 执行器：自己的工具集 + 真实状态验证

`RoutineExecutor.__init__`（`executor.py:13-26`）只做一件事 —— 构造**自己的**设备工具集：

```python
from ..tools import build_device_tools
self.tools = {
    tool.name: tool
    for tool in build_device_tools(registry, enable_preference_tracking=False)
}
```

`enable_preference_tracking=False` 是第 4 章那个"构造期显式选择"的兑现。理由写在 `executor.py:17-21` 的注释里，值得原文引用：

> 执行器构造自己的工具集（闭包注入 registry），并且**显式关闭偏好观察** —— 机器触发的动作不计入"重复手动操作"，否则会凭空造出用户从未设过的偏好。

这句话背后有一个真实 bug（第 4 章讲过根因链）：旧实现里后台执行器无身份调用工具，`record_preference` 抛 `KeyError: 'home_id'`，把热水器、烧水壶、灯光全判成失败，**唯独窗帘活了下来**（窗帘那条动作恰好不记偏好）。"只有一个动作成功"就是那个 bug 的指纹。`tests/test_automation_routines.py:90-161` 是它的回归用例，而且它同时钉住反向行为：同一个工具走对话路径（带可信身份）时**必须照常记偏好**，否则这个修复就退化成"把偏好学习关掉了"。

执行完不算完。`execute()` 的后半段复用了第 6 章的两个函数：`expected_state_for_step(step, self.registry)`（`executor.py:53`）算出期望状态，`verify_step(...)`（`executor.py:65-67`）拿真实设备状态去比。**动作仍然按真实设备状态验证，不看工具返回的那句话。** 工具说"已调至 45 度"不算证据，去注册中心读 `target_temp` 才算。这一点在自动化场景下比对话场景更重要：对话里出错你当场就看见了，定时任务出错你在睡觉。

验证失败后 `tick()` 有一层有限重试（`scheduler.py:98-104`）：`attempts < max_attempts`（默认 2）就把状态退回 `pending` 等下一轮，否则标 `failed` 并记下原因。

### 14.2.7 从对话到例程：六个工具和一道审批

图这一侧的入口是 `build_automation_tools(runtime)`（`src/tools/automation.py:232-236`），六个工具：`create_scheduled_routine`、`create_vehicle_arrival_routine`、`schedule_wake_routine`、`enable_vehicle_arrival_routine`、`list_automation_routines`、`cancel_automation_routine`。

`runtime is None`（自动化未启用）→ 返回空列表，Agent 根本看不到这些能力（第 4 章决策二）。多智能体模式下这六个名字还要出现在 `graph.py:173-177` 的 `automation_tool_names` 里，否则 automation 角色调不到它们（第 11 章）。身份照第 8 章的规矩来 —— `_identity()`（`tools/automation.py:37-43`）只从 `config["configurable"]` 取 `home_id` / `user_id`，缺了直接 `RuntimeError`。**模型无法指定为谁创建例程。**

模型生成的动作在入库前要过一道确定性校验，`normalize_and_validate_automation_actions`（`planning.py:113-155`）：

- 工具名必须在 `AutomationToolName` 白名单里（`planning.py:16`，从 `PLANNING_TOOL_NAMES` 派生 + `set_alarm`）
- `turn_on` / `turn_off` → `on` / `off`（`planning.py:31-34` 的别名表 + `:134-136`）
- 模型写了 `device_id` 就翻译成中文 `device_name`（`planning.py:137-143`）
- 每个动作走一遍 `expected_state_for_step`，设备找不到或动作不支持就直接 `ValueError`（`planning.py:151-153`）

后两条是对着真实模型行为改的 —— docstring（`planning.py:116-122`）说得很明白：通用设备工具刻意用中文 `device_name` 和短 action，但有些模型仍然会在嵌套的自动化动作里吐出注册中心 ID 和 Home Assistant 风格的 `turn_on`。**在入库边界上归一化，而不是在执行时容错。**

## 14.3 关键设计决策

### 决策一：创建例程一律走人工审批

`_is_automation_call`（`src/agent/approval.py:35-42`）把四个创建/启用类工具全部列为需要审批，和 `activate_scene`、`control_lock(unlock)` 共用同一个 `interrupt` 通道（第 7 章），风险等级 `medium`。审批文案会把每个动作的偏移量和描述展开（`approval.py:104-109`）：

```
创建定时自动化「打球回家准备」（2026-08-25T22:00:00+08:00）：-30分钟 准备洗澡热水；-20分钟 降低客厅温度
```

**为什么定时任务比即时动作更需要确认？** 因为即时动作错了你当场看见、当场说"不对，关掉"。定时任务错了要等到目标时刻，那时候你可能在睡觉、在开会、在别的城市。它的错误是**延迟暴露**的，所以确认必须提前。

`tests/test_automation_routines.py:618-739` 用完整图路径钉住了这个边界：Fake LLM 生成动作 → 图在 `approval` 中断 → **断言此刻数据库里例程数为 0** → 批准后才有 1 个例程 2 个任务。"批准前数据库必须是空的"是这个用例的核心，它防的是"先写库再问人"这种看着能跑、实际上审批形同虚设的实现。

### 决策二：自动化动作里没有"解锁门锁"

`ScheduledActionInput` 有一个 `model_validator`（`planning.py:62-66`）：

```python
@model_validator(mode="after")
def reject_scheduled_unlock(self):
    if self.tool_name == "control_lock" and self.arguments.get("action") == "unlock":
        raise ValueError("定时自动化禁止解锁门锁")
    return self
```

一个定时任务在无人确认时解锁大门，后果是什么？**你家的门在一个可预测的时刻自己开了。** 攻击者不需要碰你的账号、不需要绕过审批 —— 他只需要知道你设了"每天 18:30 到家开门"这条例程，然后 18:31 走进去。审批只在创建时问一次，之后这条例程每天自动执行，没有第二次确认的机会。

所以这不是"暂时没做"，是**刻意的缺失**。这一条和第 11 章的工具集隔离是同一种思路：**最可靠的禁止是让能力不存在**，而不是加一层运行期检查。

不过有个精确的边界要说清，我实测确认过：`control_lock` **在**白名单里（`planning.py:16`），也**在**执行器的工具集里 —— 定时**上锁**是允许的（"每天 23:00 检查门锁"是合理需求），被拒的只有 `action == "unlock"` 这一种组合。所以约束的粒度是 per-action，不是 per-tool，唯一的执行点就是上面那 4 行 validator（用例在 `tests/test_automation_routines.py:566-573`）。诚实地说这是个**单点防御**：绕过 `ScheduledActionInput` 直接往 `store` 写一条 `control_lock/unlock`，执行器会照做 —— 它的工具集里有 `control_lock`，`expected_state_for_step` 也认这个动作。真要做深，执行器侧应该再挡一次。

### 决策三：SQLite 而不是内存队列

数据落 `data/automation.db`（`config.py:113` 的默认值），`data/` 和 `*.db` 都在 `.gitignore` 里（`.gitignore:34-35`）。用文件而不是内存的理由就一条：**例程的生命周期比进程长**。用户说"明天 7 点叫我起床"，中间可能有一次部署、一次崩溃、一次笔记本合盖。14.4 的实验 A 最后会真的关掉 store 再打开一个新的，验证例程还在。

还有个额外收益：**停机期间错过的任务会在重启后的第一次 `tick()` 里被追平**。因为 `due_tasks` 的条件是 `due_at <= now`，不是 `due_at == now`。停机 3 小时，重启后第一次 `tick()` 一次性取出这 3 小时里所有到期任务。`tests/test_automation_routines.py:133` 那句注释说的就是这个：

> 单次 tick 追平全部到期任务，正是应用停机后重启的补偿执行形态。

这个行为是不是总对？不一定。凌晨 3 点错过的"开窗帘"，早上 9 点补上还有意义吗？当前实现没有"过期就放弃"的窗口概念，一律补。这是已知的粗糙处。

## 14.5 踩坑与局限

### 坑一：测试里绝对不能硬编码未来日期

这是本章最容易中招的坑，而且它有个恶劣的性质 —— **写的时候是绿的，某天自己变红**。`AutomationRuntime.schedule_wake()`（`runtime.py:44-45`）和 `create_scheduled_routine()`（`runtime.py:64-65`）都有这道校验：

```python
if wake_at <= datetime.now(timezone.utc):
    raise ValueError("起床时间必须晚于当前时间")
```

所以你在 2026-08-10 写下 `datetime(2026, 8, 16, 6, 0)`，用例绿的。等到 2026-08-17，同一行代码永久失败。实验 C 的第一行输出就是这个坑被引爆的样子。

正确写法是构造相对时间。`tests/test_automation_routines.py:748-754` 的注释把这个教训记得最细（另一处更简短的提醒在 `:340`）：

> 这里必须用相对时间：schedule_wake 会拒绝早于当前时间的目标，原先硬编码的 2026-08-16 在该日过去后就让本用例永久失败。保留"带时区的 ISO 8601 + 早上 6 点"这个真实入参形态（工具 docstring 要求的格式），只把日期取成次日。

**反过来，`scheduler.schedule(..., now=...)` + `scheduler.tick(虚拟时间)` 这条路径不做该校验。** 实验 C 里 `anchor_at=2020-01-01` 排出 5 个任务、一声不响。所以规则不是"永远别写死日期"，而是看你走的哪条路：

| 路径 | 校验"晚于当前时间"？ | 该用什么时间 |
|---|---|---|
| `runtime.schedule_wake()` / `runtime.create_scheduled_routine()` | **会**（`runtime.py:44`、`:64`） | 必须 `datetime.now(...) + timedelta(...)` |
| `scheduler.schedule(now=...)` + `scheduler.tick(t)` | **不会**（时间全从参数进来） | **固定日期，而且应该固定** |

第二行为什么"应该固定"？因为 `tick()` 的断言是"这一刻该发生什么"，用相对时间会让期望值随执行时刻漂移。`tests/test_automation_routines.py:63` 写死 `wake_at = datetime(2026, 8, 16, 6, 0, tzinfo=UTC)` 是**安全且刻意**的 —— 它走的是 scheduler 路径。一句话记住这个区分：**runtime 是"面向用户的入口"，它有业务规则；scheduler 是"纯逻辑内核"，它只有算术。** 校验属于入口，测试属于内核。

### 坑二：Windows 上不 `close()` 就删不掉临时目录

`TemporaryDirectory.cleanup()` 遇到没关的 SQLite 连接会抛 `PermissionError: [WinError 32]`，**测试断言全过也判失败**。所以 14.4 的每个实验最后都有 `store.close()` / `rt.close()`。测试里还有一层顺序陷阱，`tests/test_automation_routines.py:37-42` 的注释解释得很清楚：

> unittest 先跑完整个 tearDown 才轮到 doCleanups，所以放在 tearDown 里会早于测试方法内 addCleanup 注册的 close；而 doCleanups 是 LIFO，在 setUp 最先注册就能保证它最后执行。

结论：`self.addCleanup(self.temp_dir.cleanup)` 要写在 `setUp` 的**最前面**。

### 坑三：`routine_runs` 的 `anchor_at` 不随 ETA 更新

实验 B 里任务全部挪到了新锚点 17:26，但我顺手查了一下 `routine_runs` 表，那条记录的 `anchor_at` 还是 **17:20**（第一次 ETA 算出来的值）。根因在 `create_run` 用的是 `INSERT OR IGNORE`（`store.py:77`）—— 同一个 `trigger_key` 第二次进来直接忽略，不更新；而 `list_automation_routines`（`tools/automation.py:182`）恰好用最新一条 run 的 `anchor_at` 当 `target_time` 报给用户。

所以：**车在路上堵了 5 分钟，任务时刻是对的，但用户问"几点到家"时看到的是旧值。** 任务执行不受影响，只是那一行展示会有偏差。这个不一致目前没有用例覆盖。

### 坑四：例程的时区字段和运行时配置是两个来源

`AutomationRuntime` 用 `timezone_name` 参数决定怎么解释**不带时区的** `datetime`（`runtime.py:42-43`、`:62-63` 用的是 `replace(tzinfo=...)`）。但 `Routine.timezone` 是模型上的默认值 `"Asia/Shanghai"`（`models.py:38`），而 `build_wake_routine` / `build_scheduled_routine`（`routines.py`）**没有一处把 runtime 的时区传下去**。后果：把 `AUTOMATION_TIMEZONE` 配成别的时区，排期算得对（都在 UTC 里比较），但 `list_automation_routines` 渲染给用户的本地时间还是按 `Routine.timezone` 走（`tools/automation.py:137-140`），也就是上海时间。单时区部署没问题，一旦跨时区就会露出来。

### 这一章的局限

**单机后台线程，没有分布式调度。** `scheduler.start()` 起的是一条进程内线程，`AutomationStore` 是本地 SQLite 文件。跑两个实例连同一个 db，两边都会 `tick()`、都会取到同一批 `pending` 任务 —— `due_tasks` 查询和状态更新之间**没有行级锁也没有租约**，动作会被执行两次。真要横向扩展，得换成"抢占式领取"（`UPDATE ... SET status='running' WHERE id=? AND status='pending'` 靠 rowcount 判断抢到没有）加上带 TTL 的租约。

**进程被 kill 时正在执行的任务会卡在 `running`。** `tick()` 在调 executor 之前先把状态写成 `running`（`scheduler.py:83-85`），执行完再写终态。如果进程在这中间被 `kill -9`，那条任务永远停在 `running`：它不在 `due_tasks` 的 `status='pending'` 条件里，重启后**不会被重试**，也不会被标失败。当前没有"启动时把陈旧 `running` 回收成 `pending`"的清理逻辑。更麻烦的是，即使有，也无法判断那个动作到底执行成功了没有 —— 想做对得靠幂等的动作加上执行前的意图记录（write-ahead）。

**没有周期性例程。** `Routine.trigger_type`（`models.py:37`）只有 `fixed_time` / `vehicle_eta` / `vehicle_geofence` / `manual` 四个取值，没有 cron，"每天早上 7 点"目前只能每天手动说一次。另外两处不足前面已经点过：**补偿执行没有过期窗口**（停机 8 小时后重启，8 小时前该开的窗帘现在会开，见决策三）、**解锁禁令是单点防御**（只有 `ScheduledActionInput` 那个 validator 在挡，见决策二）。

**下一章的问题**：现在系统里有三条并行的执行流 —— 图里的 ReAct 循环、Planner 状态机、和这一章那条谁也看不见的后台线程。定时任务凌晨三点失败了，你怎么知道？失败原因写进了 `scheduled_tasks.error` 字段，但没人会去 `SELECT`。一次对话烧了多少 token、哪个节点慢，同样没人知道。**出了问题怎么看见？**
