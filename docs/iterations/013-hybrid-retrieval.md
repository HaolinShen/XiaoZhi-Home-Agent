# 013 混合检索升级：BM25 与向量双通道、名次与准入分离、召回评测

> 状态：已实现
> 前置：[012-manual-rag-upgrade.md](012-manual-rag-upgrade.md)（本方案偿还它在「已知边界」
> 第一条挂的账，并把它建立的拒答纪律原样保住）

## 1. 起点与问题

012 把说明书问答做成了可执行诊断：实体消解四态、检查项自证分流、引用由代码拼接。
但它在「已知边界」里给自己记了一笔账，原文是：

> **词法检索没有语义泛化。** bigram 重叠撑不起"同义不同字"的召回，症状词表是人工维护的
> 兜底。真要做下去应换成向量检索或 BM25 + rerank，但那会引入模型依赖，
> 和"测试不需要 API Key"冲突，本轮不做。

这一轮就是来还这笔账的。而"引入模型依赖"和"测试不需要 API Key"的冲突不是靠妥协解决的，
是靠把 embedding 变成显式注入的依赖解决的——细节在 2.5。

### 1.1 检索是在数"共享了几个字"

012 的打分只有一行：

```python
score = len(query_terms & document_terms) / max(1, len(query_terms))
```

没有 TF（`_terms` 返回 `set`，词频在建集合那步就丢了）、没有 IDF（"异常"这种每份故障码
文档都有的词和"排水泵"同权）、没有文档长度归一（分母是**查询**词数，长小节天然占优）。
中文靠字符 bigram：把汉字拼成一串再滑窗取两字。

这套东西在 12 个 chunk、全是空调的语料上够用，是因为查询和文档的用词高度重合。
一旦用户说人话就不行了。013 建的 63 条 golden 用例里有 30 条是口语查询，
**旧算法只答对 3 条。**

### 1.2 同义不同字靠一张人工词表兜底

012 的补救是 `_SYMPTOM_LEXICON`——五条正则，把"不凉"改写成"制冷效果不佳 制冷 室温"。
它确实有效，但性质上是个坏东西：**你得先知道用户会怎么说，才能写下那一条。**
五条全是空调的；扩到十种设备就要再写几十条，而且漏掉哪一种说法不会报错，
只表现为"这句话查不到"。

### 1.3 三处静默失败

顺手要修的，都属于"功能变弱但不报错"这一类：

- **错误码在不带空格时识别不出来。** 正则用 `\b`，而 Unicode 模式下汉字也算 `\w`，
  所以 `\bE3\b` 在"显示E3是什么"里**匹配不到**——「示」和「E」之间没有词边界。
  旧实现只在用户恰好打了空格时才走"精确键"那一档，不打空格就静默降级成普通口语查询。
- **catalog 登记了不存在的 `.md`** 只是 `continue`。那份说明书永远检索不到，
  什么都不报，表现是"我明明加了说明书，它却说查不到"。
- **`SELF_CHECKS` 里声明了却没有任何语料引用的检查项**是死代码。
  `base.py` 只校验了一个方向（语料引用的 id 必须已声明），反方向没人管。

## 2. 设计

### 2.1 分词换成 jieba，并且关掉新词发现

`src/knowledge/tokenizer.py`。返回 `list` 而不是 `set`——把词频交给 BM25。
查询侧和文档侧都用 `cut_for_search`（长词再切短词：排水泵 → 排水 / 水泵 / 排水泵），
这个对称是刻意的：文档切成「排水」「泵」而查询切成「排水泵」就完全对不上，而且失败得很安静。

`HMM=False` 是实测逼出来的。默认开着时：

```
jieba.cut_for_search("卧室灯不太亮了")  →  卧室 / 灯不太亮 / 了
```

「灯不太亮」是 HMM 凭概率粘出来的词，**任何说明书里都不存在**。于是 BM25 只剩「卧室」
可用，而「卧室」恰好出现在讲清洁周期的那节（"普通卧室环境建议…"）、不出现在正确的
「亮度明显偏低」里——BM25 因此给错误小节 4.84 分、给正确小节 0 分。

关掉的代价是技术词会被拆散（换能片 → 换/能/片）。这个代价可以接受，因为它是**对称**的：
用户问「换能片」时查询也这样拆，仍然匹配得上，损失的是精度。
而 HMM 粘连损失的是召回，直接归零。**非对称粘连严格劣于对称拆分。**

错误码的正则同时收敛成单一数据源（012 时代它在 `base.py` 和 `rag.py` 各写了一遍，
靠一句注释"保持一致"约束），边界改成 ASCII 前后向断言，汉字与标点都算边界。

### 2.2 两个通道

`src/knowledge/retrieval.py` 的 `HybridRetriever`：

- **词法通道**：`rank_bm25.BM25Okapi`，在**全语料**上建索引。不按型号过滤后重建——
  IDF 必须是语料级常量，否则同一个（查询, 小节）组合会因为这次解析到哪个型号而得到不同分数。
- **语义通道**：`ApiEmbeddings` 调 OpenAI 兼容的 `/embeddings`，文档向量按内容 sha256
  落盘缓存（`data/embeddings/`），改一个字的说明书只重算那一节。

索引在 `KnowledgeBase` 构造期建一次。012 时代加载是一次性的、**索引不是**——
`_terms(document_text)` 在每次检索的每个 chunk 上重跑一遍正则和分词。

### 2.3 名次归 RRF，准入归 confidence

这是本轮最要紧的一处，也是唯一一处"标准做法直接用会出事"的地方。

标准的混合检索用 RRF（Reciprocal Rank Fusion）融合：`Σ w/(k + rank)`，k 取 60。
它的好处很实在：**对量纲免疫**。BM25 无上界、余弦在 [0,1]，直接加权求和得先把两者拉到
同一尺度，而 RRF 只看名次，两个通道谁强谁弱都能稳定融合。

但 012 的拒答纪律依赖一个**绝对**判断：所有候选都不够好时必须说"查不到"。
而 **RRF 是纯名次的——名次第一的必然拿到该通道的最高分，跟它到底像不像毫无关系。**
一个语料里根本没有对应章节的查询，它的第一名照样是满分 RRF。
拿 RRF 去套三档下限，拒答分支**永远走不到**。

所以两套分数，各管一件事，不能混：

| 分数 | 管什么 | 取值 |
|---|---|---|
| `rrf` | 只决定**名次**，对量纲免疫 | 离散，`Σ w/(60+rank)` |
| `confidence` | 只决定**放不放行**，三档下限套在它身上 | 锁死 [0,1] |

先按 confidence 筛掉不够格的，再按 rrf 排名次。`KnowledgeHit.signals` 把两个通道各自的
原始分与名次都写进 RAG 轨迹——排查"为什么这一节排第一"时需要的正是这个。

### 2.4 硬过滤仍然在两个通道之前

型号相等、错误码 issubset 这两道**是准入条件而不是打分项**，所以在候选集阶段就生效，
绝不能变成融合公式里的一个权重。

向量检索让这条纪律比以前更要紧：**E4 的语义近邻天然是 E5、E7**，而它们讲的是完全不同的
故障。一旦把错误码从硬过滤降级成"相似度的一部分"，用户问 E4 就会拿到 E7 的处理步骤，
而且读起来完全通顺、完全权威。`tests/test_knowledge_rag.py` 里专门有一条用例把向量通道
调到站在错误的一边（stub 让讲排水的小节最相似），验证它一节都绕不过去。

### 2.5 语义通道是显式注入的依赖

`EmbeddingProvider` 协议 + 两个实现。`semantic` 标志决定通道开不开：

- `ApiEmbeddings` —— 远程，生产用。
- `NullEmbeddings` —— **明确宣告"这套配置下没有语义通道"**，检索退化为纯 BM25。
  它的 `embed_*` 直接抛，而不是返回零向量：零向量会安静地参与融合、贡献 0 分，
  看起来一切正常，只有召回质量偷偷退化。

这样 012 挂的那个冲突就不存在了：生产上有真语义泛化，测试注入 stub、离线、确定性、不要 Key。
降级也是可见的——`build_embeddings` 打 INFO 日志说明走了哪条路，
RAG 轨迹的 `retrieve` 步骤带 `dense: true/false`。

## 3. 五个实测得来的设计

### 3.1 假的第二通道比没有第二通道更糟

最初的方案里有第三个 provider：`HashingEmbeddings`——把词特征哈希到固定维度当"向量"。
动机是让混合检索**永远是双通道**，不存在"没配 Key 就走另一条代码路径"这种只在生产上
才暴露的分叉。实测把它否决了：

| 实测 | 结果 |
|---|---|
| 查询「客厅空调开着但一点都不凉」（正确答案是「制冷效果不佳」） | 哈希向量给**错误的**「噪音异常」余弦 0.243 并排第一；BM25 给它 0 分 |
| 六组"口语 → 说明书书面语"的相关对 | 哈希向量有**四组余弦恰好是 0.000** |

根因很直接：**它没有 IDF，所以按"共享了几个常见词"排序。** 那个 0.243 就是靠一个「空调」
凑出来的。而用 IDF 压制通用词恰恰是 BM25 已经做好的事——把这条通道放回来，
等于从旁路重新引入 BM25 刚刚干掉的噪声，而且它绕过了 IDF，BM25 那边的修正管不到它。

它还顺手破坏了阈值标定：真命中与噪声命中的 confidence 一度只差 **0.007**（0.129 vs 0.122），
三档下限没有任何可用的落点。去掉之后同一组查询是 0.278 vs 0.000。

**双通道要靠真模型换来，不能靠一个假的第二通道凑出来。** 宁可诚实地退化成单通道并且说出来。

### 3.2 置信度要"只对有证据的通道求平均"

第一版 confidence 是固定权重加权平均（0.5 × 词法 + 0.5 × 语义）。它有个上限问题：
**"只有一个通道确信"的命中，最高只能拿 0.5**——而那恰恰是混合检索存在的理由。

实测最干净的一例：「洗澡水不够热」查 AquaWarm-W80 的说明书，
**BM25 = 0.00（一个词都对不上），余弦 0.62（语义完全对上）**，正确答案是「出水温度偏低」。
固定权重把它压到 0.362，而离线时靠通用词凑出来的错误命中是 0.331——两者只差 9%，
阈值根本没有落点。

改成"只对有确凿证据的通道求加权平均，弱通道不参与"之后，它是 0.725，噪声是 0。

反方向也要防住：**不能用 max 或概率或（soft-OR）。** 那会让单通道的噪声直接成为置信度，
而两个弱信号本该互相否证。所以关键不在"用哪种合成函数"，而在于
**每个通道各自先有噪声基线**：弱信号必须先归零，再谈合成。

- BM25 的基线取 3.5（实测：通用词噪声命中 ≤ 2.96、真实命中 ≥ 4.26），再饱和 `x/(x+6)`。
  **不能用"除以本次查询的最高分"**——那会让第一名恒等于 1.0，绝对性当场消失，又变回名次分。
- 余弦的基线取 0.42、强命中刻度取 0.70，两个刻度挂在 provider 上（换模型必须重测）。

### 3.3 噪声不该有投票权

加权 RRF 上线后出了个反常结果：

| 配置 | Recall@1 |
|---|---|
| 仅向量通道 | 91.1% |
| 混合（等票 RRF） | 85.7% |

**混合比单通道更差。** 而且给 BM25 降权到 0.2 也只能挽回一部分。

根因是 **RRF 会奖励"在两个通道都出现"**，而 BM25 的"出现"极其廉价——任何一个词有一点
重叠就有正分、就有名次。于是一个只靠通用词沾上边的小节，会因为"BM25 排第一 + 向量排第五"
击败"BM25 没排上 + 向量排第一"的正确答案：

```
0.2/(60+1) + 0.8/(60+5) = 0.0156   >   0.8/(60+1) = 0.0131
```

降权解决不了这个问题（上面那组数就是权重 0.2 时算的），因为问题不在票数权重，
而在**噪声本来就不该有投票权**。修法是让名次也过各自通道的噪声基线，
而不是只在合成 confidence 时才过。改完之后混合的 Recall@1 回到 87.5%，与纯向量持平。

### 3.4 引用要再做一次相对截断

这一条修的是 013 **自己引入**的精度回退。语料从 12 个 chunk 扩到 124 个之后，
同一份症状手册里的**兄弟小节**会一起被召回：

```
"客厅空调开着但一点都不凉"
  制冷效果不佳 0.832   ← 正确
  有异味       0.541   ← 同一份手册的另一个症状
  噪音异常     0.512   ← 同上
```

三条都过了 0.35 的绝对下限，于是答案挂上三条引用而只有一条相关。
012 时代同一个查询只返回一条——**这是退步。**

绝对下限管不了这件事：提到 0.55 会把正确答案一起砍掉（正例余弦 p05 是 0.511）。
该用的是**相对**判断——比最佳证据弱这么多的东西不该出现在引用里。

比例取 0.7，在 63 条用例上实测选的：**Recall@1 / Recall@3 / MRR / 拒答准确率
在 0.0~0.8 的任何取值下一个数字都不变**（说明它从不砍掉正确答案），
而平均引用数从 1.81 降到 1.50。

它**不是拒答闸门**：参照点是第一名，所以第一名永远保留，这道截断只会让引用更干净，
不会把"答得出来"变成"拒答"。有一条测试专门钉这一点（`relative_floor=1.0` 时仍然作答）。

### 3.5 强制单选的重写 prompt 会绕过拒答纪律

这一条是**端到端实测**抓到的，单元测试全绿也发现不了。

用真实 LLM 跑「卧室空调有点响是怎么了」时，系统**答了**，还挂上三条引用——
而 FrostLine 的说明书刻意没有噪音章节。更讽刺的是模型自己在答案正文里写着
"说明书片段中未提及空调异响的相关信息"，系统却仍以权威格式把引用递了出去。

根因不在检索，在查询重写。`_llm_rewrite` 的 prompt 是"请判断最可能属于哪一个小节"，
**强制单选**——正确答案根本不在清单里时，模型必然挑一个最像的（它挑了「蒸发器结霜」）。
而校验只检查"标题真实存在"，**存在不等于相关**，重写后的查询轻松过了 0.42 那一档。

这个漏洞 012 就存在，只是当时所有用例都传 `llm=None`（走词表重写），从没暴露过。
评测也看不到它：评测刻意只测首轮检索，而这条路要走到重写才出现。

修法是给模型一个明确的出口：prompt 里加"如果没有任何小节与用户描述相符，
只输出「无」，不要勉强挑一个最接近的"，`_llm_rewrite` 把"无"作为
"模型明确说都不符合"上报，此时**保持原句去查一次然后拒答**，
连词表兜底都不走——词表只看用户措辞，根本不知道这个型号有没有噪音章节。

取舍是清楚的：信"无"会让"其实有相符小节但模型看漏了"变成一次拒答（少答一次）；
不信会让"没有相符小节"变成一次权威的错答。后者是这个项目明确认定更危险的那一类。

## 4. 阈值是扫参扫出来的，不是手调的

三档下限：**带错误码 0 / 首轮 0.35 / 重写后 0.42**。前两档 013 起移进 `RAGConfig`
（`RAG_MIN_SCORE` / `RAG_REWRITTEN_MIN_SCORE`），因为它们是按语料实测标定的，换语料就要重标。
第三档"带错误码时为 0"**不可配置**——那不是一个可调参数，
而是"精确键命中不该被模糊阈值否决"这条规则本身。

`python -m src.evaluation.recall --sweep` 在（向量权重 × 首轮下限）网格上跑全部 63 条用例。
关键的一格是 **0.35**：向量权重取 0.5~1.0 的**任何**值，拒答准确率都在 0.30 → 0.35 这一步
从 85.7% 跳到 100%。所以它不是拟合某一条用例。代价是 Recall@1 从 89.3%（下限 0.20）
降到 87.5%，离线纯 BM25 从 62.5% 降到 58.9%。这个方向的取舍是刻意的：
查到错章节的说明书比查不到更危险。

**一处必须写明的薄弱**：拒答用例里最高的假阳性是 **0.336**——"卧室空调有点响"在
FrostLine 上命中「制冷效果不佳」，离 0.35 只有 4% 余量。为什么这么薄，
在 63 条用例上统计 `text-embedding-v4` 的余弦分布给了答案：

| | n | min | p05 | 中位 | max |
|---|---|---|---|---|---|
| 正例 | 61 | 0.403 | 0.511 | **0.653** | 0.864 |
| 困难负例（同型号的**其它**症状小节） | 74 | 0.302 | 0.425 | **0.568** | 0.734 |
| 容易负例（保修、除垢等无关章节） | 398 | 0.263 | 0.350 | 0.488 | 0.706 |

正例与困难负例**大幅重叠**，中位只差 0.085。基线提到 0.55 也只挡掉 35% 的困难负例，
同时丢掉 15% 的正例。结论是：**向量通道靠绝对余弦无法区分「对的症状小节」和
「同一台电器的另一个症状小节」**——它们语义上真的很近。

真正能说出"这份说明书没讲这件事"的是**词法通道返回 0**（"响/噪音"在 FrostLine 全文不存在）。
所以这道闸门的可靠性来自 BM25，不是来自阈值调得准——这也是不能为了召回率把 BM25 权重
清零的真正理由，比"鲁棒性"有力得多。

## 5. 语料与自证检查

语料从 5 份扩到 **39 份**（**124 个 chunk**），覆盖全部 10 种设备类型、**13 个型号**，
每个型号三份：故障代码 / 常见症状排查 / 保养与清洁。带排查清单的小节 25 个，人工项 56 条。

自证检查从 3 条（全是空调的）扩到 **12 条**，新增 9 条覆盖灯、窗帘、电视、加湿器、
热水器、水壶、门锁与两类传感器。`CheckContext` 一个字段都没加——
`room_humidity` 本来就在那里，012 时代没人用。

**两处刻意保留的语料缺口**，它们是被测行为而不是遗漏：

| 缺口 | 守住的路径 |
|---|---|
| 客厅灯不登记 `model` | `no_model` 拒答：定位到设备了但没有这份资料 |
| FrostLine-AC310 的症状手册没有噪音章节 | "本型号说明书查不到就必须拒答"，而不是拿讲制冷的内容硬答 |

写新说明书时的用词要求是**一律书面语**（写「雾量明显偏小」而不是「不怎么出雾」）：
口语留给查询侧，否则"语义通道能不能跨过同义不同字"就无从验证了。

## 6. 验证

### 6.1 召回评测

新增 `evals/knowledge_recall.json`（63 条 golden 用例：口语 30 / 说明书原词 10 /
错误码 10 / 同码异义 6 / 应当拒答 7）与 `src/evaluation/recall.py`。
测的是**首轮检索，刻意不跑查询重写**——要回答的问题就是"语义通道能不能替掉那张
人工维护的症状词表"，把重写也跑上等于让词表替检索背书。

| 配置 | Recall@1 | Recall@3 | MRR | 拒答准确 | 口语类 | 说明书原词 |
|---|---|---|---|---|---|---|
| legacy（012 词法覆盖率） | 51.8% | 57.1% | 0.539 | 7/7 | **3/30** | 10/10 |
| 仅 BM25 词法通道 | 58.9% | 62.5% | 0.604 | 7/7 | 7/30 | 10/10 |
| 仅向量通道 | 87.5% | **94.6%** | **0.908** | 7/7 | **24/30** | 9/10 |
| **混合（生产配置）** | **87.5%** | 89.3% | 0.881 | 7/7 | 23/30 | **10/10** |

口语查询 **3/30 → 23/30**，Recall@1 **+35.7pp**，拒答准确率全程 100%。
"把覆盖率换成 BM25"单独贡献 +7.1pp，剩下的 +28.6pp 是语义通道给的。
四种配置套的是**同一套**准入规则（三档下限 + 相对截断），否则比的不是同一件事。

**纯向量的 Recall@3 与 MRR 比混合更好**，这个结果照实写在这里。仍然选混合，三条理由：

1. `bm25_weight=0` 会让词法通道完全关闭，**embedding 一挂就全部拒答**；
   混合配置下还有 BM25 兜着（离线 Recall@1 58.9%）。
2. 说明书原词类上 BM25 更强（10/10 vs 9/10）。
3. 最重要的是第 4 节那条：**"这份说明书没讲这件事"只有词法通道说得出来。**

### 6.2 单元测试

`tests/test_knowledge_rag.py` 从 36 项扩到 **66 项**，全量基线
从 `234 passed, 137 subtests` 变为 **`264 passed, 383 subtests`**。新增五组：

- **混合检索机制**：硬过滤不被向量通道绕过（型号与错误码各一条）；**名次第一 ≠ 够格放行**；
  纯语义命中不被缺席通道腰斩；低于噪声基线的弱 BM25 分拿不到名次；
  语义通道缺席在轨迹里可见；embedding 挂了是降级不是崩；单次查询失败只影响这一次；
  排序确定性；catalog 指向不存在的文件构造期报错。
- **分词**：错误码整体保留且只计一次；不带空格也能识别；型号数字段不被误当错误码；
  HMM 幻影词不出现。
- **引用精度**：每条引用都不低于第一名的 0.7 倍；弱兄弟小节不进引用；
  证据相当时都保留；**相对截断永不把作答变成拒答**。
- **语料一致性**（生成式断言）：设备 `model` ↔ catalog `model` 双向一致；
  catalog `title` 与 Markdown H1 逐字相等；**每条已声明的自证检查都被语料引用**
  （补上 012 缺的反方向校验）；至少保留一台无型号设备；标注不泄漏进检索文本。
- **新设备自证检查**：9 条新检查读真实设备状态；**挂错设备类型必须是 unknown，
  绝不能假通过**。

另外补了一条守 3.5 那个漏洞的用例：模型回"无"时必须拒答，且不退回词表。

向量通道用 `StubEmbeddings`（按主题词返回设计好的单位向量）。它不是在模拟语义，
而是用来**构造出想验证的那种局面**。所以测试仍然不需要 API Key、仍然确定性。

### 6.3 单元测试测不到的那一层

3.5 那个漏洞是**端到端跑真实 LLM** 才暴露的：单元测试全部传 `llm=None` 或注入
`EchoLLM`，走的是词表重写；评测刻意只测首轮检索。两道防线都没覆盖"真实模型被迫在
不相关的小节里单选"这条路。

结论不是"要给所有东西加测试"，而是**验证要覆盖到配置的真实组合**。
013 的验证因此分三层：单元测试（确定性、无 Key）、召回评测（真实 embedding、
无 LLM）、端到端手动跑（真实 embedding + 真实 LLM，走完整主图）。
第三层没有自动化，但它是唯一能发现 3.5 那类问题的地方。

## 7. 已知边界

- **绝对置信度分不开"对的症状"和"同一台电器的另一个症状"。** 第 4 节的余弦分布说明了
  为什么，代价是拒答闸门那 4% 的余量。3.4 的相对截断只解决了引用精度那一半
  （比最佳证据弱太多的不进引用），**没有解决拒答那一半**——它刻意保留第一名，
  所以当第一名本身就是个不相关的兄弟小节时，它帮不上忙。
  真要补这一半得让"第一名与第二名的差距"参与拒答判断，那是第四种机制，
  本轮不做：得先有数据证明它比现在这套更稳，而不是又多一个要标定的常量。
- **BM25 的噪声基线依赖语料规模。** 它由 IDF 与平均文档长度决定，都是语料级统计量。
  换语料必须 `--sweep` 重标。踩过一次：拿三个 chunk 的合成语料写测试，
  所有 BM25 分数都远低于 3.5，测出来的是"基线没标定"而不是被测的机制。
- **确定性的代价真实发生了。** `docs/guide/13` 当初把"换个 embedding 版本测试断言可能全变"
  列为上向量检索最贵的一项。测试侧用 stub 躲掉了，**生产侧躲不掉**：
  余弦的两个刻度（0.42 / 0.70）是对 `text-embedding-v4` 测的，换模型必须重测。
- **评测只测首轮检索。** 不测端到端任务成功率，不测真实 LLM 的综合质量，
  也不测查询重写——3.5 那个漏洞正是因此漏掉的，只有 6.3 说的第三层验证抓得到。
  这一层目前没有自动化。
- **`_SYMPTOM_LEXICON` 还在，且仍然只有空调那五条。** 它现在的定位从"语义泛化的唯一手段"
  降级成"没配 embedding 时的确定性兜底"。要不要给另外十二个型号补词表，取决于
  离线配置到底是不是一个需要认真支持的场景——本轮没有下这个判断。
