# 012 说明书 RAG 升级：实体消解、检查项自证分流与强制引用

> 状态：已实现
> 前置：[008-agentic-rag-evaluation.md](008-agentic-rag-evaluation.md)（本方案替换其中的型号定位与作答环节）

## 1. 起点与问题

008 落地的 Agentic RAG 是一条能跑通的最小链路：JSON catalog + Markdown 分节、
子串词法检索、identify → retrieve → rewrite → answer/refuse 的子图骨架。
但把它当作"设备说明书助手"来用，有三处是站不住的。

### 1.1 型号是猜出来的

原 `rag.py` 里有这样一段：

```python
if "空调" in query:
    return None, "SmartCool-AC2024"
```

这在当时看不出问题——因为模拟器里两台空调**恰好是同一个型号**。一旦不是，
"空调显示 E4"就会被安静地按客厅那台的说明书回答。

这类错误比"查不到"危险得多：**查不到只是没帮上忙，查错型号是拿着别人家的答案
指挥用户拆机。**"E4 表示排水异常，请检查排水管是否弯折"读起来完全权威、
格式专业、步骤具体，用户没有任何线索能判断这段话其实属于另一台空调。

### 1.2 型号表是第二份数据源

`DEVICE_PROFILES = {"living_room_ac": {"model": ...}}` 写在知识模块里，
跟设备注册中心是两份数据。换设备、加设备时有两处要改，
而漏改的那一处不报错——只会让检索按旧型号查。这与 011 确立的
"能力声明单一数据源"原则相悖。

### 1.3 检索命中之后就没事做了

命中小节后原文整段念出来。可是"制冷效果不佳"那一节有 5 条排查项，
其中 3 条（是否开机、设定温度是否低于室温、模式是否为制冷）**系统读一下设备状态
就能核对**，只有 2 条（滤网积尘、室外机遮挡）必须人到现场。
把 5 条一起念给用户，等于手里握着答案却让用户自己去做四件事。

## 2. 设计

### 2.1 检索之前先做实体消解，四态而非"型号或 None"

新增 `src/knowledge/resolution.py`，把"用户措辞 → 设备实例 → 型号"这条链显式化：

| 状态 | 含义 | 后续 |
| --- | --- | --- |
| `resolved` | 唯一一台设备且登记了型号 | 进检索 |
| `ambiguous` | 条件对上多台（两台空调型号还不同） | 反问是哪一台 |
| `no_model` | 定位到设备但没登记型号 | 说清"没有这份资料" |
| `unknown` | 连是哪台都没解析出来 | 反问 |

**后三种一律不进检索**。子图的 `after_identify` 只在 `resolved` 时放行，
不存在"兜底成不带型号搜全库"的分支——那正是这个模块最该防住的失败模式。

配套把 `KnowledgeBase.search()` 的 `model` 改成**关键字必填**参数：

```python
def search(self, query: str, *, model: str | None, top_k: int = 3)
```

`model=None` 依然能搜全库，但必须由调用方写出来。全库检索从此不可能是
"漏传参数"的副产品。

消解顺序是 **显式设备名 > 类型关键词 > 可信上下文**。用户明确说了"卧室空调"，
不能被 App 当前所在房间覆盖；用户只说"空调"时，`sync_context` 落定的
`active_room_id` / `active_device_id` 才用来消解多候选。用的是同一套可信身份边界：
房间与设备来自 `RunnableConfig`，不是模型生成的。

类型关键词命中多类时（`TYPE_KEYWORDS` 里"温度"属传感器、"空调"属空调，
"空调设置温度多少合适"同时命中两类）按两条确定性语言习惯择一，不问模型：
**更长的关键词更具体**、**出现更早的通常是句子主语**。两条都平手才认定为真歧义。

### 2.2 型号落在设备身上

`src/models.py` 的 `BaseDevice` 新增 `model: Optional[str]`，
`capabilities.py` 的默认实例里按台声明。知识模块不再持有任何型号映射。

两台空调刻意给了**不同**型号（`SmartCool-AC2024` / `FrostLine-AC310`），
且两份说明书里 **E4 含义完全不同**（室内外机通信异常 / 排水泵异常）。
这不是为了好看：若两台同型号，型号过滤这条约束在演示和测试里都不可见，
等于摆设。灯、窗帘等留空 `model` 也是刻意的——它演示了
"型号未登记 → 必须拒答"这条路径。

### 2.3 检查项按可自证 / 需人工分流

新增 `src/knowledge/selfcheck.py`。说明书排查清单的条目末尾挂 Markdown 注释：

```markdown
1. 确认空调处于开机状态，待机或定时未启动时不会送出冷风。<!--check:device_is_on-->
4. 检查进风口滤网是否积尘，滤网堵塞会显著降低风量。<!--manual-->
```

选择行内注释而不是在 `catalog.json` 里另开一张表，理由有三条：

- **同位。** 标注跟着它描述的那一行走。写在索引里就要靠"第几节第几条"定位，
  说明书改一行顺序，全部标注错位，而且错位是静默的。
- **不可见。** Markdown 注释渲染时不显示，说明书在任何阅读器里仍然是一份说明书。
- **正文不受污染。** 解析时标注被剥离，既不进给用户看的文本，也不进检索词表
  （否则 `ac_target_temp_below_room` 会被切成 latin token 参与打分，
  搜 "target" 能搜出空调说明书）。

判定结果是 `problem` / `ok` / `unknown` **三值而非布尔**：`unknown` 是必需的第三态，
因为"房间里没有温湿度传感器所以读不到室温"跟"室温确实高于设定温度"是两件事，
前者必须回退给人确认，后者才是定位到了根因。

判定读注册中心的真实设备状态，不问模型——跟 verifier 是同一个原则：
模型会把"设定了 26 度"复述成"温度设置正常"，只有实测值能反驳它。

`CheckContext` 刻意做成一个小对象而不是直接传 `registry`：检查函数只该看到
"这台设备"和"这个房间的环境读数"，不该有能力遍历全屋设备或触发
`registry.tick_environment()`（环境推演只允许 `read_sensor` 触发，
别处调用会让同一轮对话里的室温随调用次数漂移，诊断结论再也复现不了）。

**语料引用未声明的 check id 时 `KnowledgeBase` 构造直接抛 `ValueError`。**
若容忍未知 id（比如降级成"需人工确认"），一个拼错的 id 就会让一条本该自动核对的
检查项无声消失：功能变弱但不报错，是最难定位的那类缺陷。宁可启动失败。

### 2.4 模型组织语言，代码陈述事实

`answer` 节点的输出由四块拼成：

```
<模型写的处理建议>            ← LLM，只允许用检索片段里的信息
自动核对结果（已读取设备真实状态）：  ← 代码渲染，不经模型
需你确认（系统读不到，得人到现场）：  ← 代码渲染，说明书原文逐字
来源：                              ← 代码拼接
```

prompt 里明确要求模型**不要复述核对结果、不要写来源**——那两块由系统另行附上。
这样"引用"是结构保证，不是提示词里的一句请求：模型无论怎么发挥，
来源块都在，且指向真实被检索到的小节。

`llm=None` 或调用抛异常时退回片段原文拼接：信息量下降，但引用与核对结论一个不少。
`GraphInterrupt` 显式重抛——人工审批靠抛它实现，无条件 `except Exception`
会让用户还没回答就重跑节点（`middleware/interceptors.py` 早已记下这个坑）。

## 3. 一个实测得来的设计：分数下限分三档

检索分数是"查询词在该小节出现的比例"。原实现一个硬编码的 `0.12` 卡所有情况，
实测下来这个单阈值同时犯了两种错。

| 查询 | 分数 | 单阈值下的结果 |
| --- | --- | --- |
| `客厅空调显示 E3 是什么意思` | 0.18 | 对 |
| `空调显示 E4 是什么意思`（FrostLine） | 0.111 | **错杀**：那一节正是唯一答案 |
| `空调开着但一点都不凉` | 全部 0.11，第一名是 E3 | **错放**：靠通用词凑出的噪声 |
| 重写后 `制冷效果不佳 制冷 室温` | 0.75 | 对 |
| 重写后 `噪音异常 噪音`（FrostLine 无此章节） | 0.25 | **错放**：靠"异常"命中 E4 |

根因是**把三种检索机制混用了一个阈值**：

1. **查询带错误码** → `search` 已经把不含该码的小节全部滤掉，活下来的必然就是讲
   这个码的那一节，词法分数毫无意义（"是什么意思"永远匹配不上说明书，
   只是把分母撑大）。此时下限取 **0**。
2. **原始口语** → 用 `min_score = 0.15`，滤掉靠"空调""是不是"这类通用词凑出的重叠。
3. **重写之后** → 用更严的 `rewritten_min_score = 0.4`。不是"重写更可信"，
   恰恰相反：重写后的查询是纯说明书用词、没有一个虚词，分母很小，
   真命中的分数会很高（实测 0.57~0.80）。0.25 那一档是这么来的——
   FrostLine 说明书**根本没有噪音章节**，却靠"异常"这个在每份故障码文档里都出现的
   词命中了 E4（排水异常）。沿用 0.15 就会把一段讲排水的内容当成噪音问题的答案。

同理，**带错误码的查询永不重写**：错误码是精确键，语料里没有 E9，
换任何说法也变不出 E9 来，重写只会把用户引到某个"看起来相关"的小节。

## 4. 查询重写：两层，且都要接受校验

口语症状匹配不上说明书用词是词法检索的固有短板（"一点都不凉"与"制冷效果不佳"
几乎没有字面重叠），所以重写不是优化项而是必需项。两条路：

- **有 LLM**：把**该型号说明书真实存在的小节标题清单**给模型，让它在里面挑一个，
  而不是让它自由发挥关键词。模型给的标题必须能在清单里对上，否则视为无效重写。
  这层校验是必要的：一个凭空编出来的小节名会让重写后的检索比重写前更差，
  而且失败得很安静。
- **无 LLM**：确定性症状词表（`_SYMPTOM_LEXICON`）。测试因此不需要 API Key，
  也不会因为没配 Key 就整个功能不可用。

重写是**替换式**而不是追加式。分数分母是查询词总数，把原话留在查询里，
"开着""一点""都不"这些永远匹配不上的 bigram 会一直稀释分数——
实测同一句话替换式命中 0.73，追加式只有 0.39。

## 6. 验证

`tests/test_knowledge_rag.py` 36 项，全部验证边界与副作用而非返回文案：

- **实体消解**：显式设备名压过房间上下文；两台不同型号的空调必须反问；
  房间过滤后剩零台时不采纳过滤结果（否则会把正确候选删光）；
  类型关键词排序不会把"空调设置温度"解析到温湿度传感器。
- **型号过滤**：同一个 E4 在两台空调上答出完全不同的内容，且互不含对方的关键词；
  `search()` 漏传 `model` 直接 `TypeError`。
- **自证核对**：读不到室温时判 `unknown` 而非 `ok`；结论随实测状态翻转；
  `CheckContext` 不会被 Pydantic 抹掉子类字段（抹掉的表现是 `mode` 变 `None` →
  结论退化成 `unknown`，整个自证功能静默失效）；连续两次调用不推进环境推演。
- **拒答**：四种拒答都不产生 `retrieve` 步骤，都带"不能可靠确认"，引用为空。
- **重写**：替换式而非追加式；模型编出不存在的小节名时退回词表；
  首轮命中够强时不重写；`max_rewrites` 收敛。
- **综合**：引用块与核对块由代码拼接；LLM 抛异常时降级但引用不少；
  `GraphInterrupt` 不被吞。

全量 234 项 + 137 subtests 通过。

## 7. 已知边界

- **词法检索没有语义泛化。** bigram 重叠撑不起"同义不同字"的召回，
  症状词表是人工维护的兜底。真要做下去应换成向量检索或 BM25 + rerank，
  但那会引入模型依赖，和"测试不需要 API Key"冲突，本轮不做。
- **只核对排名第一的小节。** 第二三名是"也沾点关系"的小节，
  把它们的清单一起核对会让答案里冒出一堆和当前症状无关的核对结论。
- **自证检查项只有 3 条**，且都是空调相关。新增一条要同时改
  `SELF_CHECKS` 和语料标注；漏改哪一边都会在构造期或测试里失败，不会静默。
- **同房间传感器配对靠 `location` 字面量相等**，沿用模拟器自己的约定。
  接入真实后端时这里需要换成后端的房间标识。
