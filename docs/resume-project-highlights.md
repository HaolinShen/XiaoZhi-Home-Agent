# 智能家居 Agent——简历重点挑选说明

> 本文档回答一个问题：**这个项目写到简历上，应该重点挑哪些内容，以及怎么表述。**
> 依据：`README.md`、`CLAUDE.md`、`docs/iterations/001–013`、`docs/resume-memory-system.md` 及代码统计（src ≈ 12,500 行，tests ≈ 5,600 行，264 个测试用例）。

---

## 一、先定调：这个项目在简历上的定位

**一句话定位：**

> 一个生产级工程实践的 LLM Agent 系统：LangGraph 状态图编排、Planner–Executor–Verifier 显式状态机、多级作用域长期记忆、说明书混合检索（BM25 + 向量双通道、RRF 融合）配 63 条 golden 召回评测集、事件驱动自动化，并有 264 项自动化测试钉住权限边界与行为正确性。

写简历时最容易犯两个错：

1. **写成功能清单**（"支持灯光、空调、窗帘……8 种设备控制"）——这是 demo，不是工程能力。设备数量没有区分度，面试官也不会追问。
2. **写成框架简历**（"使用了 LangGraph、MCP、Pydantic"）——技术栈谁都会写，区分度在**你解决了什么框架没解决的问题**。

正确的挑法：每一句都指向一个**设计决策 + 权衡理由 + 验证手段**。下面按「含金量」排序。

## 二、重点一：可信身份边界（安全设计，最值得放第一句）

### 为什么它是第一优先级

所有 Agent 教程项目的共同盲区：身份与权限。而这个项目把「身份永远来自 `RunnableConfig["configurable"]`，绝不接受 LLM 生成的 `home_id` / `user_id`」作为系统级不变量，贯穿工具层、记忆层、空间归属校验三层。

### 简历表述

> 设计并实现可信身份边界：请求身份只来自运行时配置而非模型输出，工具层从 config 反解身份，配合住宅归属校验（room/device 必须属于当前 home）与管理员权限规则，杜绝模型参数越权访问跨家庭数据；相关权限边界（跨家庭隔离、非管理员写共享记忆被拒、模型参数无法覆盖身份）全部有自动化测试钉住。

### 面试可展开的点

- **为什么不能信模型输出**：prompt injection 一句话就能让 Agent「帮我把隔壁家的门锁解开」——身份必须来自可信通道。
- **011 迭代修掉的隐性陷阱**：旧实现里 `if config is not None` 恒为真（空 configurable 的 config 也是真值），导致「逐键检查后安静跳过」的兜底逻辑形同虚设；改成**构造期的显式选择**——图路径开启偏好观察、缺身份直接 `RuntimeError`（fail-fast），后台执行器显式关闭。这是一个很好的「我踩过坑并从根因修掉」的故事。
- 「工具从 config 反解身份」意味着模型连伪造身份的**接口**都不存在，而不是「有校验但能绕过」。

## 三、重点二：Planner–Executor–Verifier 显式状态机（架构能力的最佳证据）

### 为什么含金量高

这是项目里最能体现「把 LLM 当不可靠组件来工程化」的设计：

- 多步任务**先出计划、逐步执行、按真实设备状态验证**——验证读的是**注册中心的真实设备状态**，不靠 LLM 自述「我成功了」。
- 失败分支按 `problem_type` 区分：确定性错误（`unsupported_action` / `device_not_found`）**跳过重试直接 replan**——同样参数重放不可能成功，重试是浪费；可重试错误（`tool_error` / `state_mismatch`）才消耗重试额度。
- 整条链路由 `planning_status` 字段驱动条件边，是**显式状态机**而非「靠模型自己说做完了」。
- replan 时把**合法 action 列表和设备清单**回喂 Planner——因为 Planner 走 `with_structured_output` 而非 `bind_tools`，工具 docstring 到不了模型面前，合法词表必须显式注入。这个细节说明你真的理解两条工具调用链路的差异。

### 简历表述

> 设计 Planner–Executor–Verifier 显式状态机执行多步设备控制任务：Planner 结构化输出计划、Executor 逐步执行、Verifier 比对注册中心真实设备状态与期望状态；失败按错误类型分流——确定性错误跳过重试直接重新规划，可重试错误消耗重试额度，重规划时将合法动作词表与设备清单回喂 Planner，避免模型在无效动作上循环。

### 面试可展开的点

- 「为什么验证不能问 LLM」：LLM 会把工具返回的报错文案复述成『已完成』；真实设备状态是唯一的 ground truth。
- 「为什么确定性错误不重试」：能讲清这一点 = 你理解重试预算是资源，不是仪式。
- 一个具体的失败案例：「明天 6 点回家前开空调」会被模型误判成预定义『回家模式』——解法是意图路由里加**确定性硬约束**（命中未来时间信号直接短路，不问模型）。这是「模型分类 + 确定性兜底」分层决策的好例子。

## 四、重点三：设备能力单一数据源（工程收敛，最能打动有后端经验的面试官）

### 为什么它是被低估的亮点

迭代 011 之前的痛点极具说服力：新增一种设备要**手工同步 9 处**（工具 if/elif、Planner 词表、`Literal` 枚举、MCP 工具……），其中两处是无法反射检查的副本，漏改的表现是「Planner 第一版计划**稳定失败且不报错**」。

改造后：**1 处声明 + 2 处手工**。`src/devices/capabilities.py` 的 `CAPABILITIES` 是唯一数据源，工具 Schema、Planner 词表、`PlanStep` 枚举、`registry.find` 关键词、模拟器实例、场景集合、自动化工具名、MCP 工具**全部自动派生**，一致性由**生成式断言**（`tests/test_capabilities.py` 声明 ↔ 工具实现双向反射）兜底——漏一处 = 测试失败，而非运行期静默。

### 简历表述

> 主导设备能力的工程收敛：将原先散落在工具实现、Planner 词表、Pydantic Literal、MCP 服务等 9 处的手写副本收敛为单一能力声明数据源，工具 Schema、规划词表、枚举约束等全部自动派生；通过生成式一致性断言（声明与工具实现双向反射）使漏改在测试阶段失败而非运行期静默，新增设备成本从改 9 处降至改 1 处。

### 面试可展开的点

- 这个模式在后端面试里通用：本质是 **schema-as-code / 单一事实来源（SSOT）**，可类比数据库 migration、OpenAPI 生成客户端。
- 「一致性靠测试钉住而不是靠 code review 记性」是区分 junior 和 senior 的表达。
- 面试官若问「为什么不用装饰器/注册器」，可以答：显式声明表比隐式注册更可审计、可 diff、可生成文档。

## 五、重点四：多级作用域长期记忆（有专门的量化文档支撑）

项目已有一份 `docs/resume-memory-system.md` 专门写这个模块的简历表述，这里只收拢核心，并强调它的独特点：

> 设计分层长期记忆系统：个人 / 家庭 / 房间 / 设备多级作用域与权限隔离；自然语言偏好候选**必须经用户确认才写入**（误记忆率目标为 0）；结合词项相关性、置信度、重要性、时近性与访问次数的可解释的多信号加权 Top-K 排序；记忆版本追踪与置信度衰减；SQLite 持久化并支持旧库自动迁移。

两个面试细节：

- **候选确认制**是「人在回路」思想用在记忆写入上——不是所有从对话里抽到的东西都该记住。
- 短期（Checkpoint + 滚动摘要 + 工具结果裁剪）与长期（结构化记忆库）**分离治理**，各有各的生命周期（TTL、版本、置信度）。

## 六、重点五：图外事件驱动自动化（系统设计的完整度信号）

这不是「加了个定时任务」，而是一个有真实系统设计问题的子系统：

- **运行在图之外**：LangGraph 图是对话路径，持久化例程由独立的后台调度器执行——你理解 Agent 框架的边界在哪。
- **确定性测试**：`RoutineScheduler.tick(now=...)` 支持注入虚拟时间，调度测试**不睡眠、完全确定**——这是很多人做不到的测试工程。
- **去重与幂等**：任务按 `dedupe_key` 去重；车辆 ETA 更新只移动**尚未执行**的任务，不重复执行。
- **安全下限**：自动化动作**不含门锁解锁**，创建例程一律人工审批——把重点一的安全不变量延伸到了后台路径。

### 简历表述

> 实现图外事件驱动自动化子系统：SQLite 持久化例程（定时 / 起床 / 车辆 ETA 触发）由后台调度器独立于对话图执行，动作同样经真实设备状态验证；任务按 dedupe_key 去重、ETA 更新只调整未执行任务；调度器支持注入虚拟时间，使调度逻辑的测试完全确定、无需睡眠。

## 七、重点六：说明书混合检索 + 召回评测（全项目唯一有实测数字的模块）

### 为什么它现在排得进重点

013 之前这块的短板是「检索是词法 bigram，没有语义泛化」——**那句话现在作废了，别再说**。
013 把说明书检索从「bigram 集合交集 ÷ 查询词数」换成 **BM25 词法通道 + 向量语义通道、
加权 RRF 融合名次**（分词从字符 bigram 换成 jieba），并且配了 **63 条 golden 召回评测集**
和一个离线 runner，做了四组配置的对照。

评测结果（63 条：口语 30 / 说明书原词 10 / 错误码 10 / 同码异义 6 / 应拒答 7）：

| 配置 | Recall@1 | Recall@3 | MRR | 拒答准确 | 口语类 | 说明书原词 |
|---|---|---|---|---|---|---|
| 旧词法（012） | 51.8% | 57.1% | 0.539 | 7/7 | 3/30 | 10/10 |
| 仅 BM25 | 58.9% | 62.5% | 0.604 | 7/7 | 7/30 | 10/10 |
| 仅向量 | 87.5% | 94.6% | 0.908 | 7/7 | 24/30 | 9/10 |
| **混合（生产）** | **87.5%** | 89.3% | 0.881 | 7/7 | 23/30 | 10/10 |

口语查询召回 **3/30 → 23/30**，Recall@1 **51.8% → 87.5%**，**四组配置的拒答准确率全程 100%**。
拆开看：「把覆盖率换成 BM25」单独贡献 +7.1pp，剩下的 +28.6pp 是语义通道给的。

同一轮还把语料从 5 份说明书扩到 **39 份**（**124 个可检索小节、13 个型号，覆盖全部
10 种设备类型**），可自证诊断检查项 **3 条 → 12 条**（从只有空调扩到灯、窗帘、电视、
加湿器、热水器、水壶、门锁、两类传感器）。

### 简历表述

> 升级说明书故障排查检索：BM25 词法通道与向量语义通道加权 RRF 融合，错误码与型号走硬过滤不参与打分；建立 63 条 golden 召回评测集与离线 runner 做配置对照，口语化查询召回 3/30 → 23/30、Recall@1 51.8% → 87.5%，四组配置的拒答准确率均为 100%。

### 面试可展开的三个判断（这一节的真正价值）

- **错误码必须是硬过滤，不能是打分项。** 错误码类所有配置都 10/10，因为它走**硬过滤**
  （查询里的码必须出现在该小节），向量根本碰不到。理由：**E4 的语义近邻天然是 E5、E7**，
  而它们讲的是完全不同的故障。一旦把错误码降级成「相似度的一部分」，用户问 E4 会拿到
  E7 的处理步骤，**而且读起来完全通顺、完全权威**。型号过滤同理。
- **纯向量指标更好，但我仍然选了混合**（这条一定主动说）。纯向量的 Recall@3
  （94.6% vs 89.3%）和 MRR（0.908 vs 0.881）都赢。三条理由，第三条最关键：
  ① 把 BM25 权重清零等于关掉词法通道，**embedding 一挂就全部拒答**，混合下 BM25 还兜着
  （离线 Recall@1 58.9%）；② 说明书原词类上 BM25 更强（10/10 vs 9/10）；
  ③ **「这份说明书没讲这件事」只有词法通道说得出来**——63 条用例的余弦分布实测：正例
  中位 **0.653**，「同一型号的其它症状小节」这类困难负例中位 **0.568**，两个分布大幅重叠，
  所以向量靠绝对余弦**分不开「对的症状」和「同一台电器的另一个症状」**。而「卧室空调
  有点响」查那台空调时，「响/噪音」在它的说明书全文不存在，**BM25 返回 0**——这是唯一
  能触发拒答的信号。**拒答闸门的可靠性来自 BM25，不是来自阈值调得准。**
- **RRF 只能排名次，不能守门。** RRF 是纯名次的（`Σ w/(k+rank)`），名次第一的必然拿到
  该通道最高分，**跟它到底像不像毫无关系**；语料里根本没有对应章节的查询，它的第一名
  照样是满分 RRF。**拿 RRF 去套拒答阈值，拒答分支永远走不到。** 所以做成两套分数：
  `rrf` 只决定名次（好处是对量纲免疫），另一个 [0,1] 的绝对置信度只决定放不放行。

## 十、三个诚实性提醒（与 resume-memory-system.md 的口径一致）

1. **不要写「已达到先进智能体记忆系统水平」**。准确口径是「面向智能家居 Agent 的工程化长期记忆系统」。**记忆**检索的量化指标（token 降幅、命中率）目前**还没有实测数据**，面试前若能按 `docs/resume-memory-system.md` 第三节补一组对照实验，说服力会显著提升。注意跟重点六区分开：有实测数字的是**说明书检索**，不是记忆检索，讲的时候别混成一个。
2. **车辆 / 音响是模拟器闭环，未接真实厂商 API**。面试被问到就直说「本地模拟后端闭环，接口按 Backend 抽象隔离，替换真实 API 不动上层」——这本身反而是面向接口编程的正面例子。
3. **013 有两件事要主动交出来，别等被问**：① 纯向量的 Recall@3 与 MRR 都比生产用的混合配置更好（94.6% / 0.908 vs 89.3% / 0.881），选混合是为了通道冗余和拒答可靠性，不是因为指标更高；② 三档分数下限（带错误码 0 / 首轮 0.35 / 重写后 0.42）不是手调的，是在 63 条用例的（权重 × 下限）网格上扫出来的——关键那一格是 0.35，向量权重取 0.5~1.0 的**任何**值，拒答准确率都在 0.30 → 0.35 这一步从 85.7% 跳到 100%，所以不是拟合某一条用例；代价是 Recall@1 从 89.3% 降到 87.5%，这个方向是刻意的（查到错章节比查不到更危险）。但**拒答用例里最高的假阳性是 0.336，离 0.35 只有 4% 余量**，根因就是重点六里那个余弦分布重叠——这句薄弱点主动说，比被面试官问出来强得多。
